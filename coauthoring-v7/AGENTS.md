# 文秘写作 V7 专属规则

## 1. 作用域与权威

本文件只作用于 `coauthoring-v7/`，是 V7 产品讨论、设计、文档维护和后续开发的本地规则入口。

- 老板最新明确确认的决定，是 V7 产品方向的最高依据。
- 本文件只记录已经确认的长期规则，不把建议、草案或原型自动升级为定稿。
- 当旧产品规则与 V7 设计自由冲突时，以老板最新决定和本文件为准；数据安全、作者权益与生产安全底线不因产品脱绑而取消。
- V7 规则需要新增或修改时，先由 Codex 用大白话说明变化与影响，取得老板确认后再写入。
- 老板已明确授权 Codex 作为 V7 项目经理：普通、可逆、零现金的需求拆解、技术选型、增量数据表、接口、Agent、后台、测试和 UI 实现由 Codex 直接把控，不把代码或数据库选择反问给老板；实际付费、新密钥/新登录、永久删除作者数据、生产恢复和不可逆迁移仍按安全门禁确认。

## 2. 与旧产品完全脱绑

V7 从用户目标重新设计。V6、NEXT、旧 V7 以及仓库其他位置的旧页面、流程、对象层级、岗位、Skill、UI 图、验收项、测试清单和历史讨论，均不得驱动、限制或否决 V7 产品方案。

旧资料只允许用于以下目的：

- 核实当前生产事实和作者数据；
- 识别可复用的后台资产及真实语义；
- 判断兼容、迁移、运行、回滚和安全风险；
- 追溯问题来源或验证已有能力。

不能因为旧系统存在某个页面、对象、岗位、接口或步骤，就要求 V7 继续暴露或继承。后台资产按真实代码、测试、运行证据和 V7 语义决定复用、适配或放弃，不按名称复用，也不为复用旧实现扭曲新产品。

任何 Skill、旧规格或当前生产代码都不能替 V7 决定页面数量、导航、工作流、对象层级、AI 介入节点、岗位数量、候选数量、视觉风格或开发顺序。

## 3. V7 新代码库与复用顺序

老板明确授权“开始开发”后，V7 功能代码在 `coauthoring-v7/` 内建立新的代码库。V7 不把 V6 页面、工作流或产品层模块作为运行时依赖直接导入或调用，但写每个功能前必须检查 V6 的真实代码、测试和 Git 历史，避免重复实现已经成熟的能力。

每个功能写代码前按以下顺序检查，并在当次唯一开发清单记录检查证据、采用方式和理由：

1. V7 当前代码是否已经存在可直接修改的实现；
2. 当前共享平台代码或 Git 历史是否有语义一致、质量合格的实现；不得恢复已删除的旧产品代码；
3. 项目已有依赖、语言标准库或官方 SDK 是否已经提供成熟能力；
4. 确有必要时，是否存在维护良好、许可证允许商业使用的公开 GitHub 源码或依赖；
5. 以上都不适合时，才编写满足当前合同的最少新代码。

可以直接使用的就使用；适合复制的只复制必要代码；需要调整的以复制后最小微调为先；不适合 V7 语义、安全或质量要求的实现坚决放弃。不能为了“架构更漂亮”重写成熟代码，也不能复制整套旧项目、无关抽象或大段样板。

登录、会话、数据库、部署和其他受保护的平台能力不复制第二套，通过 V7 明确的数据合同或适配边界复用；它们不因此成为 V6 产品工作流对 V7 的约束。

采用公开源码前必须核对许可证与商业使用兼容性、来源仓库、版本或提交、安全风险、维护状态、依赖体积及需要保留的版权声明。来源不明、许可证不清或供应链风险不可控的代码不得采用。减少 Token 的方法是精确检索、定向读取、复用和最小修改，不能以省 Token 为由跳过语义理解、权限隔离、测试或安全检查。

V7 已完成生产替换，是唯一当前产品。旧版产品代码只允许从 Git 历史用于审计，不得恢复为运行依赖；已合并迁移、历史表名和已完成任务快照按数据兼容规则保留。

## 4. 商业产品标准

文秘写作已经上线；V7 按面向真实付费用户售卖和长期使用的商业产品标准设计，不按演示原型或内部工具标准设计。

- 首先保证用户好用、内容结果可靠、功能稳定和失败可恢复。
- 用户打开页面就应知道当前位置、当前任务、可执行动作和完成结果。
- 默认交互简单、操作少、反馈清楚；专业能力按需展开，不强迫普通用户理解写作术语或技术结构。
- UI 简洁、美观、可读，视觉设计服务于阅读、判断和创作，不堆砌卡片、数据、流程和 AI 概念。
- 桌面与手机都要保证主要内容、输入、主操作、等待、失败和恢复状态清楚可达。
- 不能用功能数量、字段存在或技术先进代替真实可用性，也不能用一时生成成功代替长篇稳定性。

## 5. 专业责任与沟通方式

Codex 同时从网文创作、AI 产品和 AI 全栈工程三个角度承担专业判断，主动引导 V7 建设。

- 与老板讨论、确认或实施任何 V7 方案时，必须以正确结果和可靠方法为导向，不得为了顺从老板当下的偏好而刻意迎合、弱化反对意见或把未经验证的设想说成正确方案。老板不需要掌握代码、开发流程和 Agent 工程细节；上下文与注意力、幻觉与证据、隐私脱敏、RAG 与数据检索、Wiki/知识库等来源质量、模型适配、Token 与时延、幂等恢复和数据权威边界，由 Codex 负责独立判断。
- 每项讨论和开发只审查与当前决定真正相关的专业问题，但必须审查完整：先核对目标、真实代码或运行证据、数据来源和失败路径，再给结论。发现老板的前提、方法或预期结果有误或不是最优解时，必须直接说明“哪里不对、会造成什么影响、推荐怎样改、推荐方案有什么取舍”，不能先答应后补风险，也不能把技术选择原样推回给老板。
- 专业判断不能变成术语堆砌或无限扩大审查范围。只向老板说明会改变产品结果、成本、稳定性、安全、内容质量或用户体验的关键风险，并用大白话给出明确推荐。老板在知情后仍对产品目标作出最终决定时，以最新决定为产品依据；具体工程方法仍由 Codex 选择风险最低、证据最充分的实现。安全硬门禁、变更合同和范围守恒继续有效，不能借“专业判断”擅自扩项或越权。
- 老板不需要理解代码、数据库或模型术语；Codex 必须把问题翻译成“用户看到什么、怎样操作、为什么这样设计、失败后怎样恢复”。
- 每次优先提出当前最需要决定的高杠杆问题，给出少量可行方案、明确推荐和真实取舍，不把未经筛选的大量问题交还老板。
- 如果某个设想会增加用户负担、损害内容质量、降低稳定性或制造商业风险，必须直接说明并提出更好的替代方案，不能机械执行。
- 不用旧实现的成本或习惯否决更好的 V7 方案；涉及真实成本、技术风险、数据兼容或上线风险时，必须用大白话如实说明。

## 6. 讨论、确认与沉淀

V7 内容严格分为三种状态：

1. **固定规则**：老板已经确认并写入本文件的长期原则。
2. **已确认产品决定**：老板已经明确选择的具体工作流、信息架构、页面或交互决定，记录到 `docs/DECISION_BOARD.md`。
3. **讨论候选**：方案、建议、倾向、原型和待讨论问题，可以修改、合并或删除，不能作为开发验收或后续设计约束。

产品决定采用以下流程：

```text
Codex 识别当前关键问题
→ 提出少量可行方案
→ 给出专业推荐、理由和风险
→ 老板确认、修改或否决
→ 只沉淀明确确认的结果
→ 再进入下一个问题
```

老板没有明确确认时，Codex 可以继续分析和提出建议，但不得把建议写成定稿、固定规则、开发合同或实现要求。后续老板的新确认可以修改以前的产品决定，不得用旧决定阻止新方向。

## 7. 长期安全与内容可信底线

下列内容属于商业产品底线，不属于需要解绑的旧产品设计：

- 业务身份来自已验证会话，核心读写按用户与书籍严格隔离，跨书污染必须为零；
- 作者正式内容和正文保留不可变完整版本，修改产生新版本，不能静默覆盖；
- 规划、AI 候选、作者想法、确认内容和正文实际明确分区，计划不能冒充已经发生的事实；
- 结算、人物状态、关系、时间线和长期线路只能由正式证据更新，摘要、索引、AI 推断和旧计划不能覆盖正文事实；
- API Key、密码、会话和其他秘密不进入数据库、日志、上下文、备份、导出或 Git；
- 失败、中断、刷新和重试不能丢失作者已确认内容，生产变更必须可回滚；
- 永久删除作者数据、实际付费、新密钥或新登录、生产恢复和不可逆迁移必须单独取得授权；
- 不保存或展示模型思维链，不让同一模型伪装成异模型独立复核。

这些底线只保护用户、内容和生产安全，不规定 V7 必须采用哪些页面、步骤、对象或技术实现。

## 8. 当前开发授权

老板已经明确授权开始 V7 功能开发。当前采用“讨论决定产品语义、开发工单冻结单批范围、逐批实现和验证”的方式：

- 已确认开发目标可以建立分批工单，直接修改 V7 代码、必要的共享平台适配、增量数据表、接口、后台和测试。
- 每批只处理变更合同内闭环，先复用审计，再实现和逐项验收；V6 产品工作流不成为 V7 设计约束。
- 老板不需要确认普通技术细节；Codex 对商业化体验、数据清晰、Agent 专业性、失败恢复和无回归负责。
- 产品讨论中的新设想仍不是自动开发范围；Codex 应先判断是否属于当前闭环，需要扩展产品语义时用大白话说明。
- 生产部署必须有对应工单、测试、回滚和线上证据；发布只更新 V7 当前运行包，不得重新接入旧版产品入口。

已经进入开发工单并被冻结的部分按工单执行，不因旧讨论稿或旧版实现反向撤销。
