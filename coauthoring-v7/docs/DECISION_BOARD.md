# V7 决策看板

> 用途：区分已经确认的边界、当前倾向和仍待讨论的问题，防止讨论稿被误当成开发规格。

## 已确认

- V7重新设计前端UI和创作工作流。
- V7视觉以白色和浅绿色为主；作者端直接以V6原版页面外壳为改造基础，保留其左边栏、顶部栏、整体排版与现有样式，不重新开发同一套外壳。
- V7保留V6作者端“左侧书籍栏＋上方功能导航”的排版外壳；顶部入口按当前讨论使用“信息、时光机、卷、链、章、库、任务、团队”，设置放入个人中心。
- 沿用历史版本只限视觉风格、排版布局和上述入口位置，不确认或继承旧页面职责、功能逻辑、数据读取、创作工作流与旧测试；各入口具体功能继续逐项讨论。
- V7 已完成生产替换；当前只维护 V7 作者端、独立后台和共享平台底座。旧版外壳与工作流不得恢复，历史实现只从 Git 用于审计。
- 旧文档、旧Skill、旧UI图和V6流程不驱动V7产品设计。
- 现有代码、接口和数据在新闭环完成前保留。
- V7功能代码后续在`coauthoring-v7/`建立新代码库，不把V6产品层模块作为运行时依赖直接导入或调用。
- 每个功能编码前依次检查V7当前实现、V6真实代码与测试、现有依赖/官方实现和合适的公开源码；优先直接使用、复制或最小微调，最后才写最少新代码。
- 后台资产逐项审计后复用，不整体复制旧项目；V6中语义一致且质量合格的必要片段可以复制或抽取到V7。
- 公开源码必须满足商业许可证、来源版本、安全、维护性和必要声明要求，不能为了节省Token跳过核查。
- V7继续位于当前仓库，不建立第二套登录、数据库和部署系统。
- V7完整验收并通过兼容、迁移和回滚验证后上线替换当前版本；安全切换前继续保留V6和回滚能力。
- RAG、ContextPack、正史/结算和Agent执行底座属于优先复用资产。
- Wiki尚未形成完整投影闭环。
- V7按老板明确确认的独立工单增量开发；没有“开始开发”授权的页面和工作流仍只讨论，不部署未经验收的能力。
- 创建书籍提供“AI团队设计”和“自己设计”两种方式：前者承担全量设计，后者保留作者逐项填写、逐项调整和按需调用AI的控制权。
- 开书信息需要包含“时代背景”和“角色背景”：时代背景说明故事所处时期、社会环境或世界层级；角色背景说明主角来自哪里、进入哪里、当前身份及其与时代的关系。
- AI团队全量设计先生成完整开书信息，作者确认后，再依据确认稿生成本书实际需要的全部设定；“全部设定”不等于生成设定库中所有无关条目。
- 开书信息主界面不显示与开书方向无关的信息；具体字段排布、折叠方式和视觉表现仍由本轮原型继续确认。
- 全书规划采用“嵌套阅读体验树”：全书顶层骨架负责整本书的长期起伏；跨卷分配把顶层阶段、剧情责任和读者体验分配到各卷；每一卷再选择适合本卷任务的卷内节奏；卷内由多条单元链完成阶段目标；章节负责兑现单元链的局部阅读节奏。
- “跨卷分配”和“单卷节奏”不是两个重复的故事层级：前者是全书到各卷的分配与衔接关系，后者是某一卷内部的独立推进方式。V7当前不因此增加“大小卷”双重对象；如果以后需要大小卷，必须另行确认。
- 每个规划节点都允许组合一个主要方法和少量辅助方法，并允许Agent加入创意。方法是软性设计工具，不是冻结剧情的模板合同；下层必须承接上层责任，但可以用不同方法实现。
- 每个层级除记录采用的方法外，还要记录读者体验目标，至少能回答：希望读者主要感受到什么、压力怎样积累和释放、多久获得一次回报、信息怎样揭示、与上一阶段相比发生了什么变化以及为什么这样安排。跨卷层同时维护全书体验曲线。
- 不为追求变化强迫相邻卷使用不同方法。节奏差异必须服务于故事责任、因果连续和长期方向；是否重复、突兀或失去变化感属于语义判断，由规划Agent审查，不能用关键词或固定规则代替。
- 未来卷先保留可调整的粗方向与体验目标，进入当前卷时再展开卷内方法、单元链和章节执行，避免一次性锁死全书；已确认规划与正文实际继续严格分离。
- 作者端只用大白话展示每卷和每条链“接下来大概写什么、读起来是什么感觉、为什么这样安排”；专业方法编号、组合依据、审查意见和完整参数保留在独立后台，作者需要时再展开。
- 全书路线先由三名“全案规划主编”彼此隔离地提出精简规划简报。三人都必须同时兼顾作者原意、人物选择、因果、长篇容量、商业追读、阶段回报和作品辨识度，不按“结构/商业/创意”拆成单项偏科岗位；独立终审只比较、挑刺和提示风险，作者仍负责最终确认。
- 作者端规划只保留三棵竖向综合树：时光机显示全书树，卷页显示单卷树，链页显示单元链树。故事、事件、情绪、阅读体验、因果、伏笔和开放问题合并进对应树节点，不再拆成多棵平行树；全书卷节点引用单卷树，单卷链节点引用单元链树。
- 作者端层级职责已经确认：时光机显示全书骨架与各卷粗骨架；卷页显示当前分卷详细骨架和单元链目录；链页显示当前卷全部单元链并把当前链展开成章纲；章页只负责正文，把当前章章纲、审校和换成员操作作为原位折叠参考。四层共用同一份正式规划和创作状态，但页面主体按入口隔离，不在页面内重复卷、链、章导航。
- 三棵树必须完整可读、可局部修改、可重排、可确认且保留历史；未来规划与正文实际分开保存，正式结算只把有证据的实际进度投影到原节点，不覆盖作者确认规划。
- 时光机首次生成正式全书树前，编辑部先完成“三套全书路线”选择闭环：每名全案规划主编只收到与本书、本层任务有关的8—12张精简候选卡，自主选择少量可用方法并至少提出一项只属于本书的原创策略；三名编剧分别依据三份小资料包设计三套真实路线，独立终审比较点评，作者可以选定、补充意见后重做或融合；作者未作正式决定前不得生成全书树。
- 开书阶段只把“预计总字数”交给作者决定；发布平台在当前阶段由系统内部默认番茄，不在普通作者流程增加选择负担。建议卷数、商业受众和追读定位不是开书既定事实，而由三名全案规划主编分别随各自全书路线独立提出，终审主编比较其合理性，只有作者选定、调整或明确融合后的完整路线才能进入正式资料和全书树。
- 方法库只负责候选召回和审计，不把完整方法目录发送给成员。系统负责版本、权限、幂等、候选存取和硬校验；方法取舍、组合适配、路线差异、作品相关性和文学判断由具有明确任务合同的Agent完成。
- 方法资产是可选工具，不是必须照抄的剧情答案。时光机只生成全书卷级骨架，进入当前卷时才把该卷展开为事件链，进入当前链时才生成具体剧情推进与章纲责任；卷级和链级也只接收本层少量候选，并必须保留当前作品原创策略。原创策略只随当前候选、决定或树版本保存，不自动写回全局资产库。
- 作者端只展示三套路线各自“这本书会怎么走、读起来是什么感觉、为什么这样安排”和主编的大白话建议，不展示方法编号、模型、提示词、内部字段或检索过程；管理员端保留方法检索、配方、成员输出、模型调用、主编审查、作者决定和树版本的只读审计证据。
- 作者确认路线决定后，正式全书树必须绑定精确的路线决定和来源版本；未选方案不能进入正式资料，重新生成或融合必须产生可追溯的新候选/新决定，不能静默覆盖旧结果。
- 卷与链的三套候选统一由固定“策划编剧”岗位完成，不再建立“结构编剧、追读编剧、人物编剧”等临时岗位或永久人设。每轮只创建方案一、方案二、方案三三个任务席位，优先派给不同模型的三名不同策划编剧；三席分别收到“局势递进、追读兑现、人物抉择”等本轮差异要求，但每名成员都必须独立交付一套兼顾结构、商业、人物与创意的完整方案。席位不进入团队成员页，主编继续独立比较三案，旧任务里的历史席位值只作只读兼容。
- V7 Agent 治理只有一份全局权威成员表：主编3、副编3、策划编剧5、主笔6、独立审查4、连续性编辑3、视觉执行1，共25名唯一成员。成员底座不保存永久题材倾向；开书、设定、时光机、卷、链、章和正文只是固定工位，不再复制成员或创造临时岗位。
- 每次模型任务按“已发布岗位提示＋已发布工位提示＋当前书题材工作档案＋少量已发布Skill＋任务合同＋最小ContextPack”编译，并冻结为不可变PromptManifest。后台编辑源资产只影响后续任务；历史任务继续读取自己的成员、模型、合同、资料包和提示快照。
- 主体题材与融合题材不能机械拼接多份人设提示。系统只召回候选并校验范围，副编Agent负责语义融合为一份短工作档案；任务成员只读取该档案和本次需要的少量资料。
- 新任务只能从全局25人成员表派单。旧两岗位开书成员表只为没有冻结新名册的历史任务恢复使用，不能成为新任务默认来源。

## 当前倾向，可重开

- AI做专业重活，作者主要选择、补充、编辑和确认。
- 只选择题材也能开书。
- 一次只处理当前任务，未来计划保持轻量骨架。
- 详细章纲先于正文，正文后结算实际发生。
- 故事线、伏笔和关系从正文实际中逐步长成故事雷达。
- 每个AI节点都有可留空的作者想法输入。
- 普通节点优先使用完成任务所需的最少成员；全书路线选择节点固定采用“三名全案规划主编独立出精简简报＋三名编剧独立出路线＋独立终审比较”的三方案闭环，作者最终决定。

- 历史“95%还原”UI图；
- 开书前必须完成故事线、角色卡、完整事件链；
