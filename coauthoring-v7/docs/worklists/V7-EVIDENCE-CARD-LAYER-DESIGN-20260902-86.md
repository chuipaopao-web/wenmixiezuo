## 二、三个关键决策的论证（含诚实边界）

### 决策1：单库多层标注，不分库

层轴召回是精确交集判断（当前层 ∈ 资产标注层），不存在"分库更准"的空间。分库有害：①自相似框架同一资产天然属多层（标签重叠：book 93/volume 119/event 99/chapter 51），分库=同一资产存多份、改一处忘多处、必然漂移；②新增一层只需补标签，不用整库复制。

### 决策2：菜单制（系统按层供给，成员单次调用内自选），不上工具检索

**为什么不用成员自己工具检索（边设计边查）**——三个硬理由：

1. **库的性质不需要检索**。146条、静态、成员内建知识全懂。成员需要的不是"搜索"，是"一张本层可用清单"提醒自己有什么、确切 key 怎么写。确定性按层过滤本身就是检索，不需要模型再做一次。
2. **失败面与成本**。V7 成员是单次调用出 JSON 合同模式。工具检索=1次调用变3~5次；两次调用（先查后设计）=翻倍且剧情上下文断开。GLM-5.3 思考失控刚修复（第85批），每一次多余调用都是白送的风险。
3. **注意力**。菜单（主框架提名卡+名册）约2k字，比现在下发的资产详情（6~10k字）还少；选择发生在设计当下，成员脑子里正装着剧情，此刻选框架最准。

**诚实边界——什么条件下我会改口建议上工具检索**：①资产库长到数千条、名册本身超过上下文预算；②成员需要检索的是动态生长的大语料（例如让成员自己查本书全部历史正文，而不是由资料策划选事实卡）；③底座换成工具循环经过验证的供应商端点。三条都不满足时，工具检索是纯亏。目前三条都不满足。

### 决策3：底座能力评估（老板问"现在成员底座是否合格"）

用生产近48h真实数据回答，不凭感觉：

| 成员 | 底座 | 近48h表现 | 判定 |
|---|---|---|---|
| 妙玉（资料策划） | deepseek-v4-pro | 141次仅1败 | 合格，最稳 |
| 谢临川 | Kimi K3 | 75成2败 | 合格 |
| 西施/规划师/主编 | GLM-5.3 | 08-31起成功率 75%→37%→9% | **底座合格，工程缺陷**：失败全部是同构的"思考烧穿"（自产4.4万~5.1万字符思考烧光额度、正文为空），不是看不懂方法论；第85批已修复上线，成功率待观察期验证 |

结论：五幕式、故事圈这类叙事方法论是三个底座训练数据里的常识，"提名卡+名册"模式对它们远低于能力上限。**瓶颈从来是工程（资料包过大、思考余量不足），不是模型智商**。本方案不更换任何底座。

### 联网能力说明（老板："不限制AI的联网能力"）

如实说明：V7 成员**现在就没有联网**，走火山方舟端点单次调用，无浏览器无工具。本方案不新增联网，理由：方法论是稳定知识，不需要联网；联网会引入不确定性、成本和注入风险进一个 JSON 合同校验管道。如果未来写历史/现实题材需要成员查真实资料，那是**独立批次**单独立项评估，与本方案不冲突——本方案没有任何一处"锁死"模型能力，名册只是提醒，不是白名单围墙（成员可完全不用任何资产、可自创方法、可上报缺卡）。

## 三、资产库改造

### 3.1 新增"提名卡"字段（≤100字，方法25条 + 配方36条）

只为**会以完整卡片形态进入任务输入的资产**凝缩提名卡（新文件 `coauthoring-v7/backend/narrative-methods/method-nomination-cards.ts`）：①宏观节奏框架组（exclusiveGroup='macro-framework'，13条）+ 全书形态组（story_form 的 book-topology 组，约12条）；②**全部36条剧情配方**（卡=名字+五段节奏线+一句注意，节奏线从配方引用的模式名自动生成初稿）。方法的 modifier/technique/foundation 资产与全部剧情模式在菜单里**永远只以名字出现**（名册），成员凭内建知识理解，不做提名卡、不进审核流程。

```ts
// methodKey → 提名卡；总量 ≤100字，结构固定：分段节奏 + 一句防误读
{ 'five-act': { stageRhythm: '①建置 ②发酵 ③转折 ④高潮 ⑤收束', guard: '转折点位置按本层预算放，不是死板等分。' } }
```

- 产出方式：模型辅助从现有详版字段一次性凝缩 → 管理员逐条审核后生效；此后新资产入库时，仅当属于上述两组才必须带提名卡。
- 详版字段（publicExplanation/cautionSignals/responsibilities 等）**不删**，留后台供管理员参考，**不再进任何任务输入**。
- 确定性校验：每张提名卡 ≤100字，超出构建期报错；两组资产必须全覆盖。

### 3.1补 节奏线段数不定死（老板第十二轮确认）

提名卡的"分段节奏线"**有几段画几段**（三幕式3段、五幕式5段、配方按自身阶段数），不存在"必须五段"。现状36条配方恰好都是5段，是 GPT 建库时在校验器里写死的（`validatePlotRecipeRegistry` 要求 `stages.length === 5`）——本批将该硬编码放宽为 **2~7段**，新入库配方按内容需要定段数；现有36条内容本身合格，不返工。

### 3.2 补 chapter 层标注（修自相似断链）

宏观节奏框架按"能在章层自相似成立"补 `chapter` 标注：三幕式、四幕式/起承转合、五幕式、起承转结、完形原则、承诺-进展-兑现等。`layersForScopes` 已有 chapter→chapter_execution 映射，补标即生效。`validateMethodExecutionProfiles` 增加检查：framework 类资产至少覆盖一个层（现有）+ 宏观框架组（exclusiveGroup='macro-framework'）应覆盖 chapter 层（新，防再次断链）。

### 3.3 名册生成器（替代检索召回，三库合一视图）

新确定性函数 `buildLayerAssetMenu(layer, genreFamilies)`，**每一层（含章/事件层）都供给完整菜单**——老板第九轮定稿：链是若干事件的组合，事件自身同样有起因/过程/转折/结果的内部节奏，章纲成员设计事件时与上层成员一样需要框架候选，不得因层级靠下削减供给。三库统一视图（老板第十一轮定稿：方法=骨、模式=肉、配方=预制菜）：

| 供给物 | 内容 | 供给层 | 体积估算 |
|---|---|---|---|
| 主节奏框架提名卡组 | `exclusiveGroup='macro-framework'` 且本层可用的资产（全书层另加 story_form 形态组），每条=名字+提名卡 | 每层 | 8~13条 ≈ 1k字 |
| 配方提名卡组 | 36条剧情配方按本书题材（`commonGenreFamilies`，开书已确定）确定性过滤，每条=名字+**五段节奏线**（从其引用的模式名自动生成初稿，管理员审核）+一句注意，≤100字 | 卷/链层 | 15~20条 ≈ 1.5k字 |
| 模式名册 | ~156条剧情模式**只列名字，按6类节奏角色分组**（容器/策略/压力/转折/兑现/过桥）——分组即提示：成员给事件定拍子时按类别找积木，也可完全自创 | 链/章层 | ~156名 ≈ 1.2k字 |
| 方法名册 | 其余本层可用方法**只列专业名**，按16维度分组（"冲突压力：X、Y、Z"）。名字即索引——成员看到"扮猪吃虎"就知道是什么 | 每层 | 50~120名 ≈ 0.5~1k字 |

成员用法闭环：节奏卡告诉成员"这个事件扛链内转折拍" → 去 turn 组扫积木名册（或完全自创）→ 写进方案并注明引用；卷成员从题材过滤后的配方卡里采用/改写/无视。配方与模式引用走同一套 libraryRefs 校验（key 存在、本层可用、限量、有说明），参考包的两个死槽（plotRecipes/plotPatterns）随之通电。

**移除**：资料策划的"方法检索请求"调用（planningLayers/dimensions/searchQueries 字段从检索合同删除，`retrievePlanningMethodCandidates` 及其语义打分退役）。资料策划保留它真正需要判断的工作：本书事实/设定筛选（relevantSettingSourceIds、missingCriticalInputs、taskPersona 等字段保留）——**这是协调变更，妙玉提示词与解析器同步改，老合同测试同步更新**。

## 四、节奏继承结构化（本批核心新增）

### 4.1 规划树节点新增 rhythm 字段

```ts
interface PlanningNodeRhythm {
  // 本节点在上层节奏中承担的阶段（非根节点必填，即使上层未命名框架，
  // 也要写清"本单元承担什么"；根节点为 null）
  inheritedStage: { framework: string | null; stage: string; duty: string } | null;
  // 本层自选主框架（可选；'custom:名字' 允许自创，null=未命名框架。
  // 填了才触发阶段覆盖检查——合同逼的是"有节奏"，不是"报菜名"）
  ownFramework: { key: string; note: string } | null;
}
// PlanningTreeNode 增加 rhythm 字段
```

**节奏组成金字塔（2026-09-03 老板第十轮定稿，实现不得跑偏）**：下层单元串联组成上层节奏，每层只管自己的下一层，不隔层伸手——

| 层 | 由什么串联组成 | 设计该层时思考什么 |
|---|---|---|
| 全书节奏 | 各**卷**承担的阶段 | 本卷在全书框架里扛哪一段 |
| 卷节奏 | 卷内各**链**的故事基本方向 | 链是大故事：这条链讲什么方向，若干链的方向拼出卷的起伏；**卷成员不碰事件** |
| 链节奏 | 链内各**事件**承担的节奏 | 每个事件扛链内节奏的哪一拍，事件串联成完整的链 |
| 事件 | 章纲成员拆成**章** | 每章扛事件节奏的起因/过程/转折/结果 |

写入时机（严格对应老板的流程描述）：

- **全书树设计**：成员选全书主框架（如五幕式），并给**每个卷节点**写 `inheritedStage`（"卷1-2承担建置、卷3承担转折…"——几卷承担什么由成员按剧情定，卷数不定死）。
- **卷设计**：确认本卷 `ownFramework`（可继续用五幕式，也可换三幕式、起承转合、组合或不命名），并给**每条链节点**写 `inheritedStage`——内容是该链的**故事基本方向**及其承担的卷内节奏（"链1-2承担本卷五幕的建置…"），若干链的方向串联拼出本卷完整起伏。链数由成员定；卷成员不设计事件。
- **链设计**：链的子节点是**事件**（一条链由几个到十几个事件组成，数目成员定），给每个事件节点写 `inheritedStage`（该事件扛链内节奏的哪一拍），事件串联组成链内完整节奏。
- **章纲生成**：事件自身同样有起因/过程/转折/结果；章纲成员在事件的 inheritedStage 基础上，为每章写节奏承担（各章变化可不同，合起来组成事件与全链节奏）。
- 每条 `inheritedStage.duty` 必须写清"这个阶段要求本单元完成什么"（如"转折：旧办法失效、损失不可逆"），不允许只写阶段名。

### 4.2 节奏卡：继承信息确定性注入下层

编译下层任务时，系统从已确认上层树中**确定性投影**出本单元的节奏卡（不调用模型）：

```
节奏卡〔hard〕全书主框架：五幕式｜本卷承担：第三幕·转折——旧办法必须失效，损失不可逆。
防误读：这是节奏位置要求，不是情节模板；用什么事件完成转折由你设计。
```

下层召回的主框架提名卡默认与上层框架兼容项排前，但**成员可自判替换**（candidateOnly 原则不变）。

### 4.3 双向责任合同（独立必填字段，不塞 decisionNote）

树输出合同新增两个独立必填字符串字段（自由文本大字段里"要求回答"只能查写没写，独立字段才是真校验）：

- `internalRhythm`：本层内部节奏怎么排——选了什么框架（或不命名框架时的自排阶段）、为什么、各单元分别承担什么；
- `upstreamDuty`：这么排如何完成上层节奏卡交给本层的阶段责任（根层填"无上层，本书自定"）。

回校（第86c）检查：两字段非空、`upstreamDuty` 与节奏卡责任的对照一致性、rhythm 字段链是否断裂（子节点 inheritedStage 与父层 ownFramework 对不上时记录）；**不评价节奏好坏**——节奏判断是成员的创意权。

### 4.4 数量不定死（合同条款化）

写入提示词与校验器：节奏阶段映射的是**位置与比例**，不是固定数目；链数、章数、每段长度由成员按剧情设计；`budget.chapterRange` 维持建议区间性质；校验器不得因"五幕式但只有4条链"这类数目不匹配报错。

## 五、选择与校验流程（菜单制闭环）

1. **系统装配**（确定性）：事实卡/责任卡/节奏卡 + 主框架提名卡组 + 本层名册，一次交给成员。
2. **成员单次调用**：设计剧情 + 自选框架（或自创/不用）+ `libraryRefs` 写明引用 key 和本书应用说明。
3. **确定性校验**（第82批归一逻辑扩展）：引用 key 必须在本层名册内（存在且本层已标注）、去重、超 `libraryUseLimit`（book 3/volume 4/chain 5 维持）截断、缺 applicationNote 丢弃；**不合格丢弃，不硬失败、不重试**。
4. **缺卡上报**：成员可输出 `neededCards: [{title, why}]`（名册里没有、本层又需要的方法/资料）。不丢弃不失败，落档为结构化缺卡请求，86b 出后台聚合视图——高频缺卡=补库信号。

## 六、资料包卡片化（fact/rhythm/responsibility 卡）

沿用前五轮定稿的卡模型与分层预算：

- 四类卡：fact（本书硬事实）/ rhythm（4.2节奏卡）/ method（提名卡+名册）/ responsibility（本层责任，从上层确认树节点确定性提取）。统一带来源 sourceKey，可回溯审计。
- 分层装配：**继承卡（压成一行"[来源] 结论"）+ 本层精选卡（全文）**；预算：全书≤8卡/4k，卷≤6卡/3k，链≤6卡/2.5k，章≤6卡/2k。
- 裁剪顺序：软卡尾部→次要软卡→软卡压半行；**hard 卡永不裁**，只降级为一行结论+来源。
- 快照 sources 机制保留，降级为追溯与审计来源（sourceFingerprint、sourceTraces 不动）。

## 七、不限制创意的保险（全部保留+新增）

1. `originalStrategyRequired`（1~6条本书原创策略）原样保留，允许完全不引用任何资产——现有测试锁定，继续有效。
2. 资产只是参考：提名卡、名册、上层节奏卡全部是"候选与位置要求"，剧情方案永远成员原创。
3. 名册全量开放本层资产（不是资料策划猜的3~8条），成员选择权反而扩大。
4. 可自创框架（`custom:` 前缀）、可上报缺卡、可提议调整上层（deviationPolicy 保留："改变父层方向必须产生调整建议"）。
5. 回校只查事实矛盾与责任回答缺失，不评价创意质量、不强制贴合任何资产。

## 七补、防偏机制（2026-09-03 老板第七轮问题："资产只是参考，担心创作太偏"）

**认知前提：偏分两种——偏手法（鼓励，是创意）与偏责任（不允许，有闸）。资产从来不是防偏工具，责任锚才是。**成员可以不用任何资产，但不能不完成上层责任。四道防线：

1. **责任锚定**：rhythm 卡/责任卡（hard）写死"必须完成什么"（如"转折：旧办法失效、损失不可逆"），不规定怎么完成；完成度可检查。
2. **偏离申报制**：创意要改变上层方向，必须产出调整建议退回作者/主编确认（沿用现有 deviationPolicy），**不允许静默改写**——这是偏的唯一合法通道，且走人工闸口。
3. **回校兜底**：确定性检查 hard 事实矛盾、rhythm 继承链断裂、decisionNote 未回答双向责任；命中即定向 revise（注入证据卡），不整树报废。
4. **人工闸口**：三席独立提案→主编比较→作者确认后冻结的现有流程不变，成员方案不直接进正史。
5. **观测信号（86c）**：采纳率、返工率、偏离申报频次纳入观测报告；系统性跑偏先于读者暴露。

**"怕平不怕乱"专项（老板第八轮：担心自由设计导致卷没有宏观节奏）**：

- "没有宏观节奏"在合同里属于**没完成作业**而非作业差：节点 schema 强制每单元填 turningPoint/pressureMovement/releaseEmotion/pressureRhythm/payoffCadence（空=校验失败）；`internalRhythm`/`upstreamDuty` 两个必填字段强制陈述本层节奏安排与上层责任兑现（不答=校验失败）；完全原创也绕不开这些字段。
- 上层节奏卡把全书曲线拆成各卷硬责任（"本卷承担转折：损失不可逆"），宏观起伏通过继承链**压下来**，不靠成员自觉。
- **平直度检测（86c，确定性软信号）**：全卷 intensity 无变化、相邻单元 turningPoint 雷同、子单元 inheritedStage 对父层自选框架的阶段覆盖不全——不判失败，标注给主编重点审。
- 边界说死：机器只查"有没有节奏"，"节奏好不好"由主编比较+作者确认判断。

验收补充：第86c观测期内，因"偏责任"导致的整树返工率不得高于当前基线。

## 七补之二、数据决策：全量清空老书数据（2026-09-03 老板第九轮定稿）

老板决策：**切换新方案前，清空生产库中所有作者的书籍数据（全部删除）**——旧方案产生的数据在新合同下只会引发 bug，不保留、不迁移、不做兼容。由此：

1. **取消一切老书兼容要求**：rhythm 等新字段按"所有规划树都是新树"设计，合同不容忍缺省兼容分支，代码更干净。
2. **清空作业是 86a 部署的前置步骤，单独安全流程**：①先全量备份（数据库+文件）并拉回异地副本；②执行清空（书籍及其级联数据，用户账号/会员/平台数据保留）；③验证：用户账号数不变、书籍数为零、服务健康；④清空后原"本地9本管理员测试书迁线上"计划**作废**（如仍需测试书，清空后再重新创建）。
3. 用户沟通与执行时点由老板定，清空操作由部署方按上述流程执行，开发侧提供清空脚本与验证 SQL。

## 十、验收指标

1. 任务输入体积：规划层编译后提示词 estimatedTokens 下降 ≥50%（卡预算2.5k~4k vs 现状10k~18k字自由文本）。
2. GLM-5.3 规划调用思考字符从 4.4万~5.1万 降到 ≤2万。
3. "引用未提供/过多后台资产"类校验失败保持 0；缺卡请求有落档、有聚合视图。
4. rhythm 字段覆盖率：新开规划树卷/链节点 100% 带 inheritedStage；继承链断裂有记录、可回查。
5. 质量不回退：原创策略仍1~6条；作者采纳率与基线持平或更好。

## 十二、明确不做

- 不给成员配工具检索/联网（条件见决策2诚实边界，触发条件满足时单独立项）。

- 不做全量语义回校（v1 只确定性检查+事实矛盾）。
- 不做老书数据兼容与迁移（老板决策全量清空，见七补之二）。
