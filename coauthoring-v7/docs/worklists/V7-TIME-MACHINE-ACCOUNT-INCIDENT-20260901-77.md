## 用户端三句话

1. 作者此刻要看清自己的书已经完成到哪里，并从正确位置继续。
2. 当前最大障碍是时光机读取或投影失败，让真实成果被错误状态遮住。
3. 页面必须显示正式成果、准确进度和一个可执行动作；任务码、模型名、堆栈和内部键只留在后台。

## 最小交互合同

- 页面唯一主任务是展示真实创作进度并允许从正确节点继续。
- 有正式成果时先展示成果；后台局部读取失败不能清空上次有效页面或降级为整书未完成。
- 真实未完成时只突出一个“继续未完成步骤”；暂时性服务失败只突出“重新读取”。
- 不新增弹窗，不移动无关导航；桌面和手机都保证错误、成果和主操作可达。

## 阶段证据

- 生产应用与静态资源确为第76批：应用 `wm-v7-20260901-153007-bb16a6ec`、静态 `6fba50a787f23722fcaf`；API、Worker、Caddy active，数据库106项迁移、完整性和外键检查正常。故障不是部署遗漏。
- 指定账号 active，包含一本当前 V7 活动书和一本未进入 V7 规划表的历史书；本批只处理当前 V7 活动书，不恢复旧书工作流。
- 当前 V7 活动书的全书路线任务已 `completed / route_confirmed`，但没有正式规划树头；15次全书树生成均失败，最近失败仍无候选树。
- 生产模型输出证明两个资料策划成员都选择了本书真实设定的稳定条目键，例如 `world-layer`、`history`；当前数据库合法引用却是对应不可变设定版本 UUID。第三席多次因输出预算耗尽未形成有效 JSON。
- 代码根因：`planningMethodSearchPrompt` 明确要求返回逐项事实源的 `sourceId`，但全书树路径使用 `publicSnapshot()` 删除了 `sourceKind/sourceId/sourceVersion`，Agent不可能返回系统要求的精确引用；路线任务传入完整快照，因此路线成功而树连续失败。
- 复用决定：保留现有资料策划 Agent、严格来源验证、任务冻结与重试；只为资料策划输入增加任务所需的精确来源引用，主设计成员仍使用去内部字段的公开快照。不新增状态机、数据库迁移或第三方依赖。
- 兼容决定：旧任务已经成功返回的 `itemKey` 只在当前冻结快照的正式逐项设定事实内做唯一一对一 `itemKey → sourceId` 归一；重复键、未知值和跨书值仍由原严格校验拒绝，不做语义猜测。
- 生产形状回归主动删除已冻结任务中的 `contextPlan`，保留成功的资料策划模型调用，再续跑同一任务；服务复用旧输出、恢复规范化资料计划，资料策划模型调用数没有增加，证明不会因本次兼容重复扣量。
