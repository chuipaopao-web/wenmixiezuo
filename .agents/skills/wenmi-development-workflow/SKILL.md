# 文秘写作开发闭环

把老板最新任务变成一批可核对、可测试、可报备的改动，不用旧规格否决新功能。

## 开始开发前

1. 新任务只读一次项目 `HANDOFF.md`；同一任务后续不重复读取。
2. 读取 `docs/DEVELOPMENT_WORKFLOW.md`，按受影响范围再选择 UI、长篇质量、数据、API 或部署资料，不全量通读。
3. 可以先做只读定位；修改产品代码前，必须新建本次开发与验收清单。清单至少覆盖：用户目标、各页面/任务状态、AI介入、数据与接口、失败恢复、手机端、旧实现清理、逐项验收证据。
4. 把老板每一条要求映射到清单项。含糊但可从当前代码、真实页面和运行证据判断的内容直接查证；会改变任务范围或产生新外部权限时才停下询问。

## 逐项开发

- 一项只有同时具备“实现完成、直接核查通过、相应测试通过”才能标为通过；相关代码可以同批编辑，验收仍逐条对应。
- 状态、任务进度、模型结果和失败恢复必须来自真实后端事实，不用前端猜测伪造成功。
- 新流程替代旧流程后，检查并清理旧入口、旧分支、旧文案、旧测试和当前文档中的冲突说法；历史作者数据和已合并迁移不删除、不改写。
- 测试按风险执行：先受影响测试，再类型检查和构建；核心工作流、数据、权限、任务恢复或模型调用语义变化时，执行项目规定的更高门禁。
- 浏览器或外部环境不可用时如实标为“未验证”，继续完成可确定的代码和自动测试，不用截图或字段存在冒充真实交互。

## 完工报备

结束时逐项回看最初清单，只能使用“通过、未通过、未验证、不适用”。报备至少说明：

- 每条老板要求改了什么；
- 对应测试、类型检查、构建或运行证据；
- 未验证项与真实原因；
- 是否清理了被替代实现；
- 是否部署，以及部署需不需要老板另行授权。

清单未全部结算、关键测试失败、旧入口仍可用或作者数据安全无法证明时，不宣布完成。
