# 文秘写作长篇质量审查

## 目标

在不压缩AI合理创作空间的前提下，降低长篇创作的事实漂移、层级越权、错误检索、版本错配、结算失真和不可恢复失败。

本Skill是开发设计与验收工具，不是小说创作岗位的上级提示词。不要把本Skill全文、检查表、证据等级或评分维度注入AI成员上下文。
本Skill不能覆盖老板最新明确决定、`docs/DECISIONS.md` 的当前条目或 `docs/LAYERED_CREATION_IMPLEMENTATION_AND_ACCEPTANCE.md` 的现行总表。三者更新后先修正Skill，再继续开发；不要为了迁就Skill保留已经废弃的产品逻辑。

每次触发本Skill时完整阅读本文件。参考文件按末尾“参考路由”选择：只读当前任务真正需要的参考；工作流、ContextCompiler、生成审校或验收类大改按对应路由读取多份，普通局部问题不机械通读全部参考。

## 当前工作流基线

按以下正式生产对象链审查，不使用聊天推进、对话记忆或抽象创作模式分流：

`开书信息 → 非剧情设定骨架 → 当前卷故事方向 → 当前卷事件链 → 当前事件完整设计 → 当前事件完整章链 → 最近1—3章详细章纲 → 单章正文 → 章节结算 → 事件结算 → 卷结算 → 下一卷`

越近越具体，越远越开放。计划只通过活动版本向下传递；事实只通过已确认正文和结算向上、向后回传。开书只提供基础方向；设定通用必备项只有世界舞台、主角底板、世界运行规则与代价、边界与留白，且不承担剧情；核心对立、卷内目标和高潮属于卷设计。

每个规划节点允许作者输入原话，AI成员直接提交可比较方案，作者选择、融合、编辑或退回；只有作者确认的版本才能成为下游活动版本。

独立灵感可以作为生产流程之外的辅助域存在，但它不能生成、确认或修改正式对象，也不能成为生产记忆或检索源。只有作者主动摘录、选择强度并绑定具体业务对象的片段，才能以作者原话进入上述对象链。

## 不得做的事

- 不建立面向创作成员的“质量层级”或分层报告门禁。
- 不固定团队人数、岗位名称、模型供应商或永久上下文字段；这些由当前产品规格和任务类型决定。
- 不定义开放讨论、创意推演、试写、正式生产等创作模式，也不要求模式路由。
- 不把聊天记录或对话摘要当作长期事实源；灵感默认隔离，作者主动摘录的原话必须附着到明确的书、设定、卷、事件、章纲或正文任务对象。
- 不把卷级或事件级叙事方法变成硬公式，不固定爽点、反转、打脸、节拍或章数。
- 不让普通作者选择“救猫咪、三幕式、五幕式、英雄之旅”等抽象理论。版本化内部方法库只为AI生成两条实质不同的具体故事路线服务；一次任务只注入当前路线需要的短脚手架，不注入方法百科，也不把多套节拍表首尾串接。
- 不以向量库、多Agent、长上下文、更强模型或更高审校分数代替根因分析。
- 不以一致性提升抵消原创性、合理惊喜、人物可辨识度、情绪力度或整体阅读质量下降。
- 不在顶栏已经说明功能后，于中心页重复同名功能标题、宣传副标题和固定教学横幅；同一含义只保留一个最接近操作的位置。
- 不把任务ID、内部状态/阶段键、检查点、ContextPack、哈希、JSON、SQL、Worker、SSE、原始供应商路径或模型内部ID暴露在普通创作页面；后台审计证据必须保留。
- 不把隐藏技术细节等同于隐藏真实进度、错误、影响或恢复入口；作者看到的状态必须来自真实任务并转换为自然语言。
- 不允许页面组件直接回退原始动态值；界面说明、进度和错误必须经过统一作者展示门禁，过滤内部编号、机器键、技术路径和协议词后才能显示。
- 不用大白话门禁机械改写小说梗概、章纲叙述、正文或作者原话；人物用词、世界观术语和剧情语义必须保持。故事文本若混入资料回查、正史、结算、质量理由、测试解释或系统工作方式，必须停止裸露并要求重新生成或修改，不能翻译后继续冒充小说。
- 不用透明绝对定位控件承载作者意见强度等关键决定；切换选择不得触发提交、导航、重载或滚动跳转。

## 审查顺序

### 1. 确认任务边界

记录当前任务对应的工作流节点、目标对象、活动版本、作者原话、硬事实、软偏好、未知项和下游影响。

若是重大设计，建立唯一 `design_review_id`，按 `docs/DESIGN_GOVERNANCE_AUDIT.md` 记录Skill快照、替代方案、两轮审查、证据等级、停止条件和回滚方法。

### 2. 建立故障链

对每个重要问题建立：

`痛点 → 可观察症状 → 根因假设 → 机制 → 反例 → 指标 → 证据 → 停止条件`

先从真实代码、数据、ContextPack、检索轨迹、模型调用和版本依赖建立基线；证据不足时标注未知，不补造结论。

### 3. 检查规划对象链

确认：

- 开书只提供题材、定位、角色起点、开局/结局方向、标签、必须项和作者补充，不代替后续剧情设计；
- 设定只维护四项通用非剧情骨架和作者按需增加的题材/自定义项；故事内核是可选软方向，核心对立移入分卷；缺一项局部事实时就地请求补充，不强迫一次填满；
- 卷纲只约束当前卷的目标、核心对立、主要因果、人物变化、高潮与卷末接口；
- 事件链说明事件职责、次序，并明确“上一实际结果—主角与局面新状态—触发—选择代价—结果—下一接口”的因果衔接；
- 当前事件完整设计细化起因、升级、选择、代价、高潮和结果，不跨越活动卷方向；
- 章链覆盖当前事件全部章节，只把当前及随后一至三章提升为正文可用的详细章纲；每章结算后按实际正文复核后两章；
- 章链或单章可有作者主动触发的轻量挑战者，但挑战必须绑定精确主方案版本、最多给3条关键替代建议、说明收益/代价/后续影响，不自动融合、不写正式对象、不进入后续资料包；
- 正文任务冻结卷纲、事件和章纲版本，同时保留对白、动作、意象、局部调度和自然因果实现的自由区；
- 章节、事件与卷结算只从作者确认的正文和正史生成，规划只能用于差异对照；
- 第一卷额外保存全书故事总线与强启动计划：前500有效中文字兴趣锚点、黄金三章整体承诺、累计10万有效字或卷末取更早的大高潮、代价与不可逆变化、防疲劳安排。代码只核对位置和覆盖，吸引力由体验审查引用正文证据判断；
- 故事线程台账区分承诺、伏笔、问题、关系、冲突、身份/资源/情绪等类型；规划只能登记“计划”，已埋、推进、到期、回收或放弃只能由正文结算或作者决定更新。

上游版本变化时，必须显示影响并使相关下游候选失效或等待重核，禁止静默改写。

### 4. 编译任务型上下文

不要审核“某岗位永远收到哪些字段”，而要审核“当前任务需要哪一组完整上游约束和补充证据”。最小充分只用于排除其他书籍、未摘录灵感和当前任务无关材料，不能用来裁掉作者已经填写的开书字段、作者原话、活动设定或上层规划因果。

ContextCompiler至少按任务区分：设定候选、卷方向候选、事件链、事件完整设计、章链、详细章纲主方案、章纲挑战、正文、事实审查、文学审查、体验审查、章节结算、事件结算、卷结算和下一卷规划。挑战包必须额外冻结目标候选版本并排除其他候选、聊天和审查报告。

上下文选择遵守：

1. 开书和设定直接接收完整开书活动版本；卷纲及后续使用覆盖全部开书字段、可回查原文的结构化 `BookCorePack`；
2. 卷、事件链、事件大纲、章纲、正文、三类审查、三级结算和下一卷逐层接收压缩但完整覆盖的上游约束，并接收当前目标对象的完整信息；
3. 事实、文学和体验审查绑定同一不可变正文与完整当前章纲，但按职责分离附加资料，且不读取彼此报告；占位符、格式和字数等硬检查由确定性代码执行，不得伪装成AI成员工作；
4. 章节、事件和卷结算只把作者确认正文及既有正史作为事实源，规划只用于“计划—实际”对照；下一卷必须以真实卷结算为起点；
5. 直接活动版本优先于检索结果；
6. 作者原话原样保留并标注强度；
7. 摘要只导航，事实回查正式源；
8. 只检索与当前任务、实体、时间和因果相关的内容；
9. 记录纳入、排除、裁剪和来源理由；
10. 软偏好与模板不得伪装成事实或硬规则；
11. 完全相同来源只保留一次；完整权威对象已进入硬来源时排除其同版本摘要、尾段和检索切片，只有切片包含未覆盖的独立证据或完整源未纳入时才保留，并记录每项排除理由；
12. 留出明确创作预算，避免上下文把正文压成资料复述。
每条上下文项同时携带约束强度（硬事实/当前任务/软参考/开放区）和真实性（计划/已发生），并记录适用范围、来源版本和依赖。超预算固定按“精确去重 → 删除重复摘要 → 缩短或丢弃软参考 → 丢弃无关证据”处理；不得对硬事实或当前任务做原始字符串截断，仍超预算就阻断并重新编译。

详细任务矩阵见 `references/context-and-rag.md`。

### 5. 审查AI协作与作者裁决

AI成员的数量、名称和分工可以随产品规格变化。Skill只检查这些结果性条件：

- 配置为独立提案的成员必须拥有独立ContextPack和真实调用记录；
- 同一模型不得冒充异模型独立意见；
- 融合者只能读取已保存候选，并明确说明采用、调整或舍弃了什么；
- 作者能够比较、局部融合、直接编辑、退回和最终确认；
- 未被作者确认的候选不得进入活动规划或正史；
- 一个正式正文版本只由一个活动写手负责，除非作者明确选择接管或定点重写；
- 审查意见不得自动重写正文或把软建议升级为硬错误。正文中的内部治理说明、机器载荷和最近5章大段直接复用属于确定性硬错误；只换标题、地点、人物名、数值或段落顺序不能绕过。
- 正文有效字数、占位符、格式和内部泄漏由确定性硬检查独占裁决；三席不得使用ContextPack或供应商Token重新判字数。冻结章纲的必须实现、禁止违反、当前章结束状态和下一章接口不能被文学/体验偏好要求删除。
当前分层流程还要检查：设定由三名编剧独立出方案，卷方向由两名编剧使用不同隐藏路线独立设计；普通作者只看到代入本书的具体方案、收益和风险。主编必须等作者以稳定proposalId选中整案或碎片后才能融合，未选择时不得自动平均化。

### 6. 审查混合检索

检索必须以工作流节点、对象身份和版本依赖为路由条件，按需组合：

- 结构化精确查询；
- 全文检索；
- 向量语义召回；
- 关系扩展；
- 时间与因果邻域；
- 正史原文和不可变正文回查。

禁止用单一相似度阈值决定全部召回。检索结果必须经过书籍隔离、版本有效性、来源权威、时间一致性、冲突检测、去重和预算裁剪。

### 7. 保护创造性和人物生命力

把约束按四种强度处理：

- 硬底线：作者确认事实、活动版本、数据隔离、安全、版权来源、费用和不可逆操作；
- 任务约束：当前卷、事件、章纲明确要求；
- 软参考：模板、节拍建议、作者灵感、风格倾向和审查建议。
- 开放区：对白、动作、意象、场景调度和不改变关键因果的自然发现。

只有前两类能够阻止正式提交。软参考可以被AI有理由地偏离；开放区不得被规划穷举。重大且有价值的偏离应形成影响预览交由作者选择。

质量指标用于离线验收和故障诊断，不应作为正文逐项打分提示，更不能被主笔写进小说解释“为什么符合规范”。本地确定性生成只允许显式E1/E2测试；设定、分卷、事件、章纲、正文、审查、灵感和续写分析都不能在正常作者流程缺少真实模型时使用夹具。真实长篇按20、50、100、200章分段放行，发布级运行每章在作者确认前停下并由项目经理或作者通读；自动确认只属于E1/E2夹具。发布级验收器若支持自动放行，还必须确认当前正文的最新完整三席报告无`major`/`blocker`且没有`rewrite`/`blocked`，否则停止；待通读文件只收录这一组报告，不混入旧稿或旧轮次。上一阶段出现模板复用、人物工具化、无场景正文、因果漂移或内部说明泄漏时立即停止扩大。详见 `references/creativity-and-output-quality.md` 与 `references/evaluation-contract.md`。

事实席只有在两端证据属于同一对象、同一指标、同一范围且明确互斥时才能判重大冲突；不得臆造独立数量的一一对应关系，也不得用主观耗时估计、公开来源、行动意图或章末状态推导不存在的硬矛盾。文学席和体验席的严重级别按实际修复范围判断：只需删改、压缩、移动一两句或增减一个局部动作、反应、过渡，且主场景、人物动机、核心因果和章末接口仍成立时，最高只能是轻微建议并保持通过。Skill审计必须检查提示合同、服务端规范化和回归样本三处是否一致。

### 8. 审查结算与恢复

每章、每事件、每卷都要区分“计划发生什么”和“实际发生了什么”。结算只聚合已确认正文、正史变更、角色状态、开放线索、因果结果和来源。

检查幂等键、租约、取消栅栏、检查点、晚到结果隔离、原子事务、不可变版本和恢复入口。Worker不得直接修改正式正文或核心正史。

### 9. 做两轮审查

第一轮检查可靠性：事实、版本、隔离、来源、检索锚定、任务状态、失败恢复和可观测性。

第二轮检查非劣效：上下文是否膨胀、模板是否公式化、人物是否变平、方案是否同质、AI是否迎合、作者决策成本是否增加、整体阅读质量是否下降。

## 输出要求

输出应直接服务当前决定，不固定“质量分层报告”。至少给出：

1. 已确认事实、作者决定、推断和未知项；
2. 与当前工作流节点对应的问题和根因；
3. 推荐机制及被否决替代方案；
4. 对创造性、人物、检索、版本和恢复的影响；
5. 可执行验收、证据等级、停止条件和回滚方法。

无问题时可以给出简短结论，不为凑格式制造风险。

## 题材无关资料沉淀门禁

当测试或修改事实审查、章节结算、资料库、图谱、时间线与检索投影时，必须用至少两种差异明显的题材验证，不能让提取器只认识旧样稿的人名、道具或关系。

正式事实必须携带当前书、来源章节、不可变正文版本和可在正文逐字找到的短证据。无事实时允许空结果；不得为填满资料库而猜测。补建历史资料不得覆盖正文或伪造旧审查，必须创建可追溯纠错修订，并验证幂等、跨书隔离和投影可重建。
