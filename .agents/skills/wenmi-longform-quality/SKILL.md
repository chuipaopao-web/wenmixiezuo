# 文秘写作长篇质量

这是开发与验收 Skill，不是小说创作提示词。不要把本文件、工程检查表或证据等级注入AI成员上下文。

它也是质量护栏，不是工作流蓝图。V7 讨论中只有涉及事实来源、上下文、连续性、生成或文学质量的具体问题才使用；不能因为“长篇小说”四个字就用本 Skill 规定产品必须采用卷、事件链、章链、三席、主编或其他旧对象。

## 先判断是否触发

触发：正式/候选/实际来源边界、版本失效、作者原话、ContextCompiler、RAG、生成/审校、事实连续性、人物漂移、重复模板、事实沉淀、长篇质量和真实模型验收。

不触发：普通产品讨论、信息架构选择、事实问答、低风险UI/样式、纯文案、明确局部BUG、部署或账号运维本身。UI交互使用 `wenmi-ui-ux`。

## 六条硬底线

1. 作者确认的正式内容、作者原话、不可变正文和从正文证据沉淀的实际状态是权威源；候选、摘要、索引和AI推断不是。具体正式对象由当前产品合同定义，Skill不预设名称或层级。
2. 规划描述可能的未来，实际状态只记录作者接受的正文证据。计划不得写成已经发生，正文实际不得被旧计划覆盖。
3. 每次任务只使用当前 `owner_id`、`book_id` 和活动版本；其他书、过期候选、未摘录灵感和无关全文必须排除。
4. 每个任务只接收完成当前目标所需的最小充分资料，并保留来源与版本；是否存在上层、下层以及如何命名由当前产品设计决定。
5. 作者硬要求必须遵守；软偏好可调整；开放区要足够大，允许人物选择、合理惊喜、题材差异和AI发挥。
6. 一致性提升不能以模板化、人物工具化、情绪变弱、重复冲突或整体可读性下降为代价。

## 工作步骤

### 1. 定位当前任务与来源

说明用户当前要完成什么、哪些内容是候选、哪些已经确认、哪些来自正文实际，以及活动版本和作者原话。不要先假设任务属于旧版开书、设定、卷、事件链、章链或结算层级。

修改创作链路前，登记本次必须保留的正式源、活动与历史版本，以及下游读取、失效和恢复行为；局部修复不得覆盖作者确认内容、不可变正文、结算或历史版本。

### 2. 读取最少证据

优先读正式对象和实际运行证据，不先读全部规范。按问题选择一份参考：

- 上下文、检索、切片、资料包：`references/context-and-rag.md`。
- 生成质量、原创性、人物和重复：`references/creativity-and-output-quality.md`。
- 任务、审校、确认、结算、恢复：`references/runtime-quality-loops.md`。

只有跨三个方向的大改才读取多份。产品字段和页面语义以老板当前决定与已批准合同为准。Skill不冻结对象层级、团队人数、模型、UI布局、候选数量、事件数量、审查岗位或测试规模。

### 3. 查真实根因

从版本、来源、ContextPack、检索轨迹、提示合同、模型调用、正文和结算找证据。常见根因只有在证据支持时才采用：

- 用摘要/猜测替代正式源；
- 未确认候选或旧版本进入下游；
- 当前任务不清、资料过多或硬事实被截断；
- 审查意见互相污染或严重级别过度；
- 计划没有根据正文结算回校；
- 为了通过检查而重复同一情节、句式或数据面板。

不要把“换更强模型”“加更多Agent”“塞更大上下文”当作默认答案。

### 4. 设计最小修复

先修数据/版本/上下文/任务合同，再考虑提示词。保留作者已确认内容和失败证据；上游变化让下游候选失效，不覆盖正文。软倾向用自然语言目标表达，不转成固定爽点间隔或强制节拍。

### 5. 按证据声明

- E0：规格；E1：机制；E2：确定性工程；E3：真实模型/独立阅读；E4：真实长篇。
- 字段存在、页面可见和夹具通过只能证明E1/E2。
- 真实文学质量需要阅读正文、相邻章节、人物弧线、承诺兑现和长期衔接。
- 日常开发不自动启动20/50/100/200章；只有用户明确要求专项长篇验收时才执行。

## 与产品结构无关的检查重点

- 规划深度、候选数量和确认次数服务于当前作者任务，不能为了旧流程完整而增加负担。
- 需要比较多个方案时，差异应体现在人物选择、因果、代价、关系、冲突方向或结果等真实维度；是否比较、比较几份由当前产品决定。
- 任何“前若干字、前若干章、固定节拍、固定高潮位置”都只能是本书或本任务明确选择的目标，不能作为通用长篇门禁。
- 生成从最新可信实际状态出发，结束后只把作者接受且有正文证据的变化写入正式状态。
- 未来规划应允许根据实际写作校准；正文上下文不塞整套治理规则或无关全文。
- 故事线、人物关系、伏笔、阶段计划等可以显式管理、后台推导或暂不建立；质量检查只验证当前设计宣称的能力，不强迫创建某类对象。

## 验证

使用 `docs/ACCEPTANCE.md` 的风险矩阵。Skill或文档修改运行Skill结构校验与项目文档同步；核心工作流、数据或隔离变化才运行完整工程门禁。若检查规则本身迫使作品模板化、要求无关材料或阻止合理产品调整，先修订规则再继续。

创作质量或连续性实现必须同时验证新逻辑，以及变更合同明确保留的正式源、活动版本与历史版本仍可读取；被新设计明确废弃的旧工作流不构成质量回归门禁。
