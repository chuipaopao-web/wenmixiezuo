# 文秘写作 UI/UX

目标不是美化旧卡片，而是让作者更快理解当前任务、完成决定并继续写作。产品尚未定型，现有布局、卡片、导航和视觉都可调整。

## 先看真实界面

开始前只读取：当前页面代码、直接共享组件、相关状态/API合同，以及可用的当前截图或浏览器状态。不要先通读产品全部文档。需要整体视觉重设计时可按需使用 OpenAI 官方 `frontend-app-builder`；普通逐页调整不触发它。

先写三句话：

1. 用户此刻要完成什么；
2. 当前最妨碍完成的是什么；
3. 改完后首屏唯一主操作是什么。

## 写作工作台结构

优先采用三层，而不是卡片矩阵：

- 导航层：当前书、当前创作阶段、可切换对象；
- 工作层：作者此刻阅读、选择、编辑或写作的主要内容；
- 上下文层：AI状态、设定/资料、差异、帮助和检查结果，按需展开或抽屉显示。

一个页面可以有多个信息区，但同一状态只保留一个显著主操作。导航不与页面动作竞争；解释不应比正文或决定更醒目。如果一个面板去掉边框仍能理解，就不要套卡片。

## 状态驱动

每页先设计状态，再设计组件：

- 初始/空：说明本步产出和最小开始条件；
- 可编辑：作者输入简短、可留空、可保存；
- AI工作中：显示正在做什么、已完成什么、可否离开；
- 待决定：直接比较差异，支持整选、片选、融合、编辑、重做；
- 已完成：收起过程，突出确认结果和下一步；
- 失败：说明影响、保留内容、提供就地重试/继续/返回修复；
- 只读/过期：说明为何不可继续和怎样恢复到活动版本。

没有死胡同。每个阻断都给动作，不让作者靠猜去其他页面找前置条件。

## 逐层显露

作者只处理当前层，不提前填写卷、事件和章节的未来细节。可选项默认少量推荐，更多内容搜索或展开；高级/专业字段隐藏在“需要时补充”。AI在作者需要方案、比较或生成下一层时介入，不在建书后擅自启动长任务。

长说明改成一句范围说明 + 就近帮助；专业结构术语转换为本书的具体故事路线。作者原话、AI方案、活动定稿和历史版本视觉上必须可区分。

## 手机优先

以 360、390、430px 为基本宽度：

- 主操作位于自然阅读流末端或稳定底部操作区，不能被浏览器栏/键盘遮挡；
- 触控目标约44px，输入字号至少16px，尊重安全区和动态 `visualViewport`；
- 桌面侧栏在手机变成抽屉、分段页或按需面板，不把三栏硬压成一栏小字；
- 比较方案时一次聚焦一个方案/一个维度，可横向切换但页面本身不产生横向溢出；
- 长内容优先折叠导航和辅助说明，不折叠当前正文、作者输入和主操作；
- 键盘弹起、旋转、长书名、长错误和高倍字体都要可达。

## 视觉语言

写作产品应安静、耐读、有层级：中心内容优先，少颜色、少装饰、少厚边框，密度适中。使用现有设计 token 作为起点，可随整体重设计统一调整。

避免：通用AI仪表盘式卡片海、每段都有标题/说明/边框、多个同色主按钮、装饰性渐变、重复状态横幅、空洞营销文案、无意义图标、专业术语和内部ID。

保留：清楚的字号层级、充足行高、稳定对齐、状态与操作的单一强调色、明显焦点、可读对比、简洁过渡。动效只解释状态变化或空间关系，并尊重减少动画设置。

## 实施节奏

整体重设计先做信息架构和交互原型，再定视觉；按页面小批落地，但共享壳、token和状态组件统一。每批必须能独立回滚，不用半套新旧交互强迫作者跨页面猜规则。

优先顺序：应用壳/手机导航 → 开书 → 设定 → 分卷 → 事件/章纲 → 正文 → 资料库/辅助页。先修阻断、状态和主操作，再修视觉细节。

## 验收

读取 `references/interface-review.md`，按本次页面做短检查。至少验证相关组件测试（若有）、Web类型检查、Web构建，并在可用环境检查手机和桌面关键状态。普通UI改动不触发长篇Skill、全量迁移或200章验收。

写作产品参考模式按需读取 `references/writing-workspace-patterns.md`；不要照抄任何项目外观，只提取可验证的交互结构。
