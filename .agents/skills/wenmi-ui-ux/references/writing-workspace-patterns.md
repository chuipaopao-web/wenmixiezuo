# 写作工作台参考模式

这些是历史交互研究，不是外观模板、V7产品输入或默认信息架构。只有老板明确要求比较外部写作产品时才读取；其中“对文秘写作”的旧推论均视为当时假设，可以全部推翻。每次只取能解决当前问题且经本轮讨论确认的模式，不复制品牌、颜色、对象层级或整套信息架构。

## novelWriter

来源：https://github.com/vkbo/novelWriter

它把小说拆成许多小文档，以项目树组织正文和笔记，并强调纯文本、可读存储和专注写作。可借鉴：

- 长篇必须始终看得见层级和当前位置；
- 正文与参考资料属于同一项目，但编辑面保持安静；
- 元数据、梗概和交叉引用辅助导航，不抢正文；
- 功能边界要克制，写作页不是全能办公套件。

当时推论（V7不自动采用）：可用一级导航、面包屑或对象树表达位置，也可以设计完全不同的导航；是否存在卷/事件/章由当前产品决定。

## Manuskript

来源：https://github.com/olivierkes/manuskript

它提供大纲、索引卡、人物/世界、故事线与无干扰写作模式。可借鉴：

- 同一故事对象可以有大纲、卡片和正文等不同视图；
- 组织阶段适合卡片/结构视图，写作阶段适合专注编辑；
- 拖拽/重排服务于结构理解，不应成为所有页面的默认形态。

风险：功能视图多时很容易形成复杂“写作IDE”。文秘写作应按当前阶段只展示一个主视图，其他视图按需打开。

## Kindling

来源：https://github.com/smith-and-web/kindling

它的核心主张是写正文时大纲仍可见，场景节拍作为可展开提示，也可切换全页正文。可借鉴：

- 上层约束应靠近正文，但默认折叠，避免来回切页面；
- “完整结构 + 当前详细提示”比一次把所有细节展开更适合长篇；
- 作者可在支架写作和纯正文之间切换。

当时推论（V7不自动采用）：需要在写作时提供任务或事实时，可比较抽屉、内联提示、独立视图或其他方式，不默认采用“本章”对象或固定审查卡。

## Zettlr

来源：https://github.com/Zettlr/Zettlr

它把文件管理、标签/目录、编辑器窗格和发布能力放在一个工作台，可折叠工作区并支持多编辑窗格。可借鉴：

- 主编辑区稳定，导航和辅助面板可折叠；
- 多窗格只在比较、引用或研究时出现，不应永久占据空间；
- 键盘、标签、固定页签和可恢复工作区对长时间写作有价值。

当时推论（V7不自动采用）：需要比较方案时，可测试双栏、逐个查看、差异摘要或其他布局，由目标设备和内容长度决定。

## Manuscript（SwiftUI）

来源：https://github.com/manuscriptapp/manuscript

它同时面向 iOS/macOS，提供项目树、corkboard、分屏和离线写作。可借鉴：

- 手机不是桌面缩小版；相同对象在手机用分层导航和全页编辑；
- corkboard适合重排场景，分屏适合桌面比较；
- 同一数据在不同屏幕采用不同呈现，不强求组件像素一致。

## 综合到文秘写作

建议形成三种主要工作模式：

1. 设计模式：大纲/方案/事件以可比较、可重排的结构视图呈现；
2. 写作模式：正文占中心，上层任务与资料按需展开；
3. 复核模式：差异、审查和实际结算围绕精确版本展示。

三种模式共享当前书和对象位置，但不把全部工具同时摆出来。AI状态属于当前对象，不应只藏在全局任务中心；全局任务中心保留跨书汇总和异常恢复。

## 明确不照搬

- 不照搬桌面三栏到手机；
- 不把所有规划都变成可拖拽卡片；
- 不给小白作者暴露专业模板库；
- 不用项目树替代逐层向导；
- 不用更多功能页解决当前状态不清的问题。
