## 设计缺陷检查与修正

实施前从真实代码建立基线，确认旧流水线存在两个阻断级冲突：只调用一个审稿模型；审稿通过后在老板确认前自动选稿、抽取事实并结算正史。继续沿用会制造同模型自审和未经确认的“正史”。Schema 16将旧表留作历史兼容，新正式路径改为：

`老板确认方案 → 表达/视角确认 → 工单与最小资料 → 单活动写手 → 完整不可变稿 → 三异模型同稿点评 → 最多两轮定点重写 → 正文确认单 → 老板接受后事实候选与正史结算`

反例复核还修正了四项边界：相同哈希不能冒充新稿；点评坏Schema保持阻断并保留模型调用证据；老板拒稿不污染正史且可沿同一任务重写；AI腔只报可解释风险，政治/情色风险必须分开带位置、证据、动作和策略版本。

## 实现范围

- 新增向前迁移 `0016_production_workflow.sql`：工单、工单来源、正文确认门禁和点评冻结字段。
- 写作准备增加确认表达/视角；老板确认创作方案时生成版本化表达基线。
- 工单冻结决定、章纲、契约、正史/定位版本、硬约束、自由创作区和审校阈值，只记录资料指针/哈希，不一次塞入全部资料。
- 每稿冻结事实、文学、体验三席；默认GLM/Kimi/豆包，GLM写手时事实席DeepSeek；三席彼此且与写手异模型。
- 每席读取同一完整不可变正文并保存真实快照、严格报告、哈希和Token。主编合并结构化修订单，不向写手倾倒三份原始长报告。
- 三评通过只进入 `waiting_confirmation`。老板接受后才选稿、形成带正文证据的B级候选、结算正史和质量记录；拒绝则不改正史并在安全轮次内重写。
- 自然“开始写/继续写”只启动唯一下一章；历史批次API只作为内部串行兼容，不再作为前端产品入口。
