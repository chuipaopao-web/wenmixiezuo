## 3. P0 阻塞问题

### P0-1：真实规划输出存在，却被过窄正则判为无效

**症状**

- 锁定规划任务：`8ddd78b0-e1c5-4047-b235-e27081a36529`
- 讨论：`35eb8dbf-25f1-4fd8-b063-9a58a7fa8f29`
- 任务结果：`failed / DISCUSSION_FAILED`
- 讨论停留在 `collecting`，有2份独立意见、0份主编决定。

**事实证据**

- GLM 返回了可解析的：
  `章节跨度估算 {"minimum":5,"recommended":8,"maximum":12,...}`
- DeepSeek 返回了语义和 JSON 均有效的：
  `**章节跨度估算**`，下一行紧跟合法 JSON。
- `parseSpanEstimate()` 只接受“章节跨度估算”后直接空白和 JSON；Markdown 标题结尾的 `**` 使整份 DeepSeek 结果被拒绝。
- 代码位置：`apps/api/src/application/discussions/discussion-pipeline-service.ts` 的 `parseSpanEstimate()`。

**影响**

- 主编综合阶段未执行；
- 总纲、卷纲、未来1—3章章纲均未落库；
- 整条正式正文生产链被阻断；
- 自动化测试未覆盖真实模型常见的 Markdown 包裹格式。

**建议**

1. 不应只靠单条正则从自然语言尾部抽取关键协议；
2. 给跨度估算使用独立结构化输出合同或工具调用；
3. 解析器至少容忍 Markdown 标题、代码围栏和合法换行；
4. 解析失败时只做一次“结构修复调用”，不得重新生成创意内容；
5. 增加 DeepSeek/GLM 真实形态回放测试。

### P0-3：模型失败触发主编来回接管，并违背本次禁用 Codex 的测试意图

**接管轨迹**

1. epoch 1：貂蝉；
2. 人工授权接管到西施，epoch 2；
3. DeepSeek 一次调用异常后，系统自动从西施切回貂蝉，epoch 3；
4. 约0.5秒后又从貂蝉切回西施，epoch 4。

相关接管包：

- `ae44c3df-709b-43a7-b7ea-cbe64dcb6f2a`
- `fd817c7c-aee8-4901-b624-62ae1cb6b4ea`

期间产生一次 `openai-codex-subscription / gpt-5.6-sol` 调用，状态 `interrupted`。这说明一次可恢复的格式/技术异常会触发“双向自动接管抖动”，且不能稳定遵循“本轮不要使用 Codex”的运行意图。

**建议**

- 区分模型不可用、格式不合格和业务内容不合格；
- 格式失败不得触发主编接管；
- 自动接管增加冷却时间、单向熔断和最大切换次数；
- 为一次运行提供明确的模型禁用列表，路由层和接管层共同遵守。

### P0-4：失败任务留下46,000 Token预留

测试结束预算状态：

- 上限：240,000
- 已消耗：73,784
- 仍预留：46,000
- 现金消耗：0

当前没有运行中的任务，但预留 Token 未释放。失败/中断调用的预算对账存在缺口，会导致后续任务被错误判定为额度不足。

**建议**

- 失败任务终态必须原子释放尚未消费的预留；
- 对 `interrupted/provider_result_unknown` 做异步核对后完成预留结算；
- 增加“无活动任务时 reserved_tokens 必须为0”的一致性检查与恢复命令。

## 4. P1 用户可见问题

### P1-1：有效 DeepSeek 回复被展示层误杀为统一错误话术

作者界面连续3次出现完全相同的：

> 这次回复的格式不适合直接展示，我已经把内部杂乱内容拦下了。请继续追问，我会重新整理成清楚的结论。

但底层模型调用并非都失败：

- 一次返回完整 JSON，但 `risks` 被模型写成字符串而非数组；
- 一次因为输出长度上限在 JSON 中部截断；
- 一次已生成总纲/卷纲/章纲说明，但 JSON 同样被截断。

`prepareEffectiveOutput()` 发现合同不完全匹配后直接使用统一拦截文案，没有执行一次确定性的结构修复，也没有把可安全提取的 `answer` 展示出来。任务却被标记为 `succeeded`，造成“后台成功、前端无有效结果”。

代码位置：

- `apps/api/src/application/chat/effective-output-service.ts`
- `apps/api/src/application/chat/conversation-reply-pipeline-service.ts`

### P1-2：活动主编已是西施，系统提示仍写死貂蝉

当前书活动主编为西施，但本次产生3条错误提示，例如：

- “貂蝉会先主持两位异模型编剧……”
- “貂蝉会沿着现有分歧……”
- “貂蝉只细化未来1至3章……”

根因是 `conversation-service.ts` 的作者提示文案写死“貂蝉”，没有读取活动主编显示名。

### P1-3：固定口令匹配过严

只有整条消息完全等于“锁定当前方向”等固定文本才会进入锁定规划。作者写：

> 锁定当前方向，采用方案C……（后附补充设定）

会被当作普通会话继续处理，不进入规划。作者自然表达与系统命令契约不一致，容易重复调用模型、浪费 Token。

代码位置：`apps/api/src/application/chat/conversation-service.ts` 的锁定方向正则。

### P1-4：轻量设定补充被当作“重大改向”，重复启动完整团队

为了补充旧法、木秤和代价归属三个设定，系统重新执行：

- 双编剧独立推演；
- 双向交叉质疑；
- 主编综合。

该轮调用6次模型，其中1次技术失败；只是补充已锁定方向的事实，却没有轻量合并路径。对真实用户表现为延迟高、Token消耗高、意见重复。

### P1-5：作者可见消息存在精确重复

当前书消息中：

- “已把原话交给西施”重复3次；
- “格式不适合直接展示”重复3次。

系统可以保留底层事件，但作者界面应合并连续同类通知，或以任务状态更新代替重复气泡。

### P1-6：任务成功但阶段仍显示 working

任务 `ab200d08-d90b-45c8-aab4-f63aa566a42d` 的任务状态为 `succeeded`，但任务详情中的阶段记录仍显示 `working` 且 `completed_at=null`。任务中心可能出现状态互相矛盾。
