# 混合RAG与长篇知识库最终设计

## 1. 明确结论与置信度

结论：文秘写作采用“SQLite权威库＋不可变正文文件＋SQLite FTS5＋LanceDB本地嵌入式向量索引＋SQLite时间关系投影＋派生Wiki＋不可变上下文包”。这是当前产品约束下的推荐最终架构：本机独立运行、零现金、无需额外服务端口、可重建、可恢复，并能同时处理精确事实、关键词、语义改写、多跳关系和故事时间。

置信度：高。SQLite、FTS5、正文文件和现有Repository已经在项目中运行；LanceDB OSS提供TypeScript本地嵌入模式和Windows原生包。具体嵌入模型、维度、切片目标值和重排参数仍必须通过本机独立金标评测锁定，不能在文档阶段用排行榜替代实测。

该结论只表示架构选型已确定，证据等级为E0；在代码、迁移、Windows运行、重建、消融和真实创作盲评完成前，不得声称运行时混合RAG已经完成或已经提升文学质量。

## 2. 当前事实基线

- 权威业务数据位于 `data/database/wenmi.sqlite`，正文使用不可变文件和哈希指针。
- 当前检索只有SQLite FTS5/BM25和固定同义词扩展，没有真实向量、查询理解、关系扩展、融合重排或原文证据回查闭环。
- 项目运行时是Node.js 24、TypeScript、Fastify、React和独立Worker；不得增加需要用户单独维护的数据库服务。
- 正史、临时、候选、Wiki和检索索引已经在规格中分权，但尚未形成完整运行时实现。
- 老板要求本地零现金运行、API Key不落盘、数据保存在 `D:\wenmixiezuo\data`，并要求系统优先保证长篇准确性而不压低创造性。

## 4. 最强替代方案与取舍

| 方案 | 优点 | 关键问题 | 结论 |
|---|---|---|---|
| 只用SQLite FTS | 最简单、当前已有 | 无法稳定处理无关键词语义、多跳和主题改写 | 保留为精确通道，不单独承担RAG |
| SQLite＋`sqlite-vec` | 单文件、事务简单 | 当前仍为pre-v1；稳定ANN能力尚在演进；扩展故障进入权威数据库进程 | 作为回退实验，不作为默认最终引擎 |
| SQLite＋LanceDB OSS嵌入式 | 向量数据与正史隔离；TypeScript/Windows本地运行；支持精确和ANN向量检索 | 增加一个可重建数据目录和双存储版本同步 | 推荐 |
| Qdrant/Milvus/Chroma独立服务 | 专业向量能力丰富 | 额外进程、端口、部署、升级、备份和故障面 | 不采用 |
| Neo4j/Graphiti/Cognee独立图系统 | 多跳与时间图能力强 | Python/图服务/模型写入链复杂，容易形成第二权威源 | 不采用；吸收思想，不作为依赖 |
| GBrain/LLMWiki整套接入 | Wiki、综合检索和知识整理成熟 | 面向通用个人/组织知识，不具备小说正史、稿件版本、人物认知和章节结算门禁 | 不整套接入；只借鉴分层切片和可重建索引 |

最强替代方案是“SQLite＋`sqlite-vec`”。它的组件更少，但当前版本成熟度和ANN扩展路线不足以抵消把向量扩展加载进权威SQLite进程的风险。LanceDB只保存可重建投影，因此即使整个目录损坏也不会伤害正史。

## 5. 预先验尸与反例

假设推荐方案已经失败，最可能原因是：旧正史向量未失效、Wiki把人物认知写成客观事实、双存储中断导致投影落后、关系扩展或相似场景过多淹没真正证据、本地模型过大拖慢电脑，以及无答案查询被相似文本强行填空。因此最终设计加入正史水位、观点主体、幂等outbox、有限深度、软资料限量、硬件基准和无答案门禁。

最强反例是：即使混合RAG召回完全正确，基础模型仍然可能写出平庸正文。检索架构只能降低正史、检索和注意力方面的系统性失败，不能单独保证文学质量；真实价值必须由创造性和整体质量盲评证明。

## 6. 修正后的最终设计

最终设计保留主笔自由创作区：数据库只提供事实、任务目标和少量可选灵感，不预写对白、动作、意象和局部调度。权威与投影、正式与临时、硬事实与软资料在存储和检索阶段就分开。

### 6.1 最终存储结构

```text
data/
├─ database/wenmi.sqlite                # 唯一权威结构化数据库
├─ books/<book_id>/                     # 不可变正文与正式资料文件
├─ staging/<task_id>/                   # 初稿、重写稿和任务中间结果
├─ indexes/
│  ├─ lance/<book_id>/canon/            # 每书正式向量投影
│  ├─ lance/<book_id>/tasks/<task_id>/  # 仅当前任务可用的临时向量投影
│  └─ manifests/                        # 索引版本、模型、维度、哈希和水位
├─ cache/models/                        # 本地嵌入/重排/工具模型缓存及许可哈希
└─ backups/                             # 权威库、正文和必要任务资料备份
```

### 6.2 为什么不是两个权威数据库

“正史知识库”和“临时知识库”是两个权限域，不是两套互相竞争的真相。正式记录、聊天、任务和稿件元数据保存在同一SQLite中不同表和Repository；提升时创建新的不可变正式版本，不把临时行直接改名为正史。这样章节、事实、确认和任务可以在一次权威事务中结算。

逻辑生命周期按DEC-016细分为四层：临时层保存工作过程，候选层保存有来源但尚未确认的可选结论，正史层保存确认或分级结算后的不可变正式版本，派生投影层保存可重建的FTS、向量、Wiki、关系、摘要和缓存。四层不是四套数据库；每条资料必须能说明来源、权威状态、生命周期状态和保留类别。

临时正文文件和临时向量索引物理分开，正式检索默认没有访问路径。聊天为界面、审计和任务恢复而保存，但不进入正式向量库；只有当前任务明确需要时才建立任务级临时索引。

### 6.3 各技术职责

- SQLite：书籍、Agent、任务、确认、规划、实体、事实、故事时间、关系、Wiki元数据、索引任务和水位。
- 不可变文件：完整正式正文和历史稿件内容，SQLite保存路径与SHA-256。
- SQLite FTS5：姓名、专名、原句、口头禅、明确关键词和原文定位。
- LanceDB OSS：语义改写、主题、行为、情绪、人物声音和相关场景候选；只保存块ID、向量和必要过滤元数据。
- SQLite关系投影：人物—地点—组织—事件—规则—伏笔的有向边、有效故事时间和来源事实；使用索引和有限深度递归查询，不增加图数据库。
- 派生Wiki：从正式源编译的人物、地点、组织、事件、规则和伏笔页；每句话保留来源，不作为事实源。
- 上下文包：冻结某次岗位真实采用的最小资料，记录采用与排除原因。

### 6.4 分类型切片

固定字数切片不能覆盖小说全部资料。系统先按结构和语义边界分，再使用目标长度控制；所有块保留父级、邻接、顺序、原始UTF-8字节范围、来源版本、故事时间、视角/说话人/叙事模式、实体、策略版本和哈希。不可变原文、结构节点、父子检索块和原子事实各司其职；索引规范化/嵌入文本与引用证据原文分开。

| 资料类型 | 切片单位 | 初始目标 | 规则 |
|---|---|---|---|
| 正式正文 | 场景根＋场景节拍父块＋段落组合子块 | 子块软目标350—700、默认硬上限1000；父块目标1200—3000、软上限4500个中文字符 | 不跨场景/章节；默认不复制重叠，使用父级、邻接和有界扩展；跨章场景用关系连接 |
| 设定/故事圣经 | 一个设定主题或原子规则 | 约100—600字符 | 世界规则、人物设定、势力和物品分开；冲突版本不合并 |
| 总纲阶段/故事弧/章纲 | 一个层级节点或场景目标 | 约100—500字符 | 章纲引用相关总纲阶段和确认故事弧，保留目标、状态和适用章节；计划不得伪装已发生事实 |
| 正史事实 | 一个断言 | 不做文本重叠 | 主体、关系、值、故事时间、证据和等级结构化保存 |
| Wiki | 一个实体页中的一个主题段 | 约150—500字符 | 仅派生；每条结论回链事实或正文 |
| 人物声音/风格证据 | 已确认正文中的短片段 | 约150—400字符 | 单独索引；主笔默认最多取2—4条；标注可不用、不可仿写原句 |
| 聊天/讨论/草稿 | 当前任务的问题组或暂存场景 | 按任务边界 | 不进入正式索引；任务结束后归档、失效或按保留策略清理 |

上述数字是可测试起点，不是文学硬规则。不得把完整对白轮次、动作—反应、句子、诗节和结构块为了凑长度切断，也不得把多个无关场景、视角或叙事模式拼在一起。梦境、回忆、预言、计划、反事实、文中作品和不可靠叙述必须保留叙事模式；不同位置的相同文字不得被物理去重。完整合同见 `docs/CHUNKING_DESIGN.md`。

### 6.5 本地嵌入与重排

#### 6.5.1 嵌入

- 使用本地Node推理适配器，不调用按量Embedding API，不需要API Key。
- 首次安装或显式模型升级时下载模型到 `data/cache/models`，之后可离线运行。
- 安装/升级保存模型来源、许可、文件清单、SHA-256、量化、Tokenizer和验证结果；正常Web/API/Worker运行只读锁定的本地快照并禁用远程模型加载，不得首次查询时下载或把长期缓存落入 `node_modules`/公共缓存。
- 候选模型以中文小说独立查询集实测选择，首轮比较Qwen3-Embedding-0.6B与BGE-M3的量化本地版本；比较质量、CPU延迟、内存、模型体积和Windows兼容性。
- 每个向量索引固定 `embedding_model_id`、版本、维度、归一化和查询指令。模型或维度变化必须全量重建，禁止混用向量空间。
- 本地推理由Worker执行，API不加载大模型；硬件较弱时索引允许后台慢建，但正式任务不得使用半完成索引。
- 模型缺失、哈希不符或平台不兼容时明确降级为结构化＋FTS或阻断依赖语义证据的正式任务，不用随机向量、假嵌入或在线按量API冒充向量通道。

#### 6.5.2 融合与重排

```text
任务/岗位识别
→ 实体、别名、关系、故事时间与意图解析
→ owner/book/正史版本/权限硬过滤
→ 结构化事实、FTS5、LanceDB向量、关系/Wiki并行召回
→ 去重、冲突和无答案检测
→ RRF融合＋权威/时间/岗位加权
→ 对软语义候选执行本地重排
→ 正式事实或正文原文回查
→ 约束胶囊＋灵感调色板
→ 不可变上下文包
```

结构化硬事实不能被语义重排降掉；向量相似度不能推翻版本、故事时间或正史权威。重排只在候选层工作。首次查询不足时允许一轮定向回查，仍无答案则明确“不足以判断”。

小文秘书使用的通用本地工具模型不是向量数据库组件，也不能与嵌入模型混为一个能力。它只可在确定性代码之后生成意图、实体/别名、标签/切片、重排和压缩候选；所有候选仍进入相同查询计划、三轴时间、H/E/I和证据闭环。E0不固定型号，阶段1/3/4根据硬件、许可、哈希、中文否定/实体/路由金标、峰值内存和延迟选择；不可用时不影响结构化/FTS/关系的允许降级路径，也不触发在线按量服务。

四路并不是四个可直接相加的分数。DEC-019将结果分为H硬约束、E证据和I灵感三条车道：H不参加RRF，也不能被重排删除；E/I分别按查询意图和岗位融合。正文子块、父块、摘要和Wiki派生副本按来源血缘聚成一个证据簇，冲突不平均，重要结论必须闭环到当前正式事实或最小原文。关系扩展只接受已消歧种子，并受类型、深度、扇出和节点预算约束。完整可实施合同、DEC-021十一人团队配方和E0起始预算见 `docs/HYBRID_RETRIEVAL_ORCHESTRATION.md`。

实体解析必须先在当前书、故事时间和正史版本内产生候选ID、别名命中与依据。同名、旧名、伪装或多候选未消歧时，低风险查询可以并列返回，高风险事实和正式生产只问一个必要问题；不得把最高向量分静默当成实体身份。模型只能提交受Schema、操作白名单和深度限制的查询计划，不能生成任意SQL、文件路径或工具命令。

查询按意图区分 `leaf/parent/summary` 粒度：叶子承担精确FTS/向量，场景节拍父块只作为宽主题向量候选，摘要承担旧阶段导航；父块/摘要命中必须折叠或下钻到最小证据。所有召回文本作为引用数据隔离，文本内命令不具有系统或工具权限。详细规则见 `docs/CHUNKING_DESIGN.md`。

### 6.6 索引一致性与生命周期

1. 正式正文或事实结算时，SQLite权威事务同时写入 `projection_outbox`；Worker幂等领取后才创建/更新 `projection_jobs` 执行记录。
2. FTS可在同一数据库事务更新；Wiki、关系和LanceDB由Worker按任务构建。
3. 每个投影保存 `source_canon_revision`、构建版本、嵌入模型、切片策略和完成水位。
4. 正式生产使用投影前检查水位。落后时等待、定向补建或明确降级；不得静默使用旧向量。
5. 旧正史仍可追溯，但不能驱动当前任务；旧索引版本进入失效状态后再清理。
6. LanceDB、Wiki或关系投影损坏时，删除对应投影并从SQLite和正式文件按书重建。
7. 备份以SQLite、正式文件和必要暂存为权威；向量索引可选随备份复制，但恢复后必须校验水位，不一致则重建。
8. 重切片在旁路新快照完成来源覆盖、字节范围、父子/邻接、哈希和探针校验后，才在SQLite事务中原子切换当前清单/水位；失败不污染上一有效快照。

### 6.7 正史、候选与临时提升

- 讨论结果先进入候选，不因模型一致同意而进入正史。
- 老板确认的设定、规划和正文创建新的正式版本；原候选和稿件保留来源关系。
- 正文结算提取的内容先成为带精确来源、否定/叙事模式、观点主体和三轴时间的派生候选。普通明确事实通过B级来源/冲突规则后可以受控绑定，但不得高于确认原文，作为正式生产硬约束前必须回查最小来源证据；歧义和冲突进入C级主编复核；人物命运、世界规则、主线和核心关系进入D级老板确认。
- 推断、人物误解、谎言、计划和客观事实分别建模，不合并成一句Wiki结论。
- 临时聊天和稿件不能通过向量相似度进入正式上下文；正式生产若需引用候选，必须由任务显式列入重大候选区。

### 6.8 作者可见资料库与标签治理

向量是机器检索坐标，不是作者资料页。资料库前端展示角色、势力、地点/地图、道具/资源/技能、事件/时间线、规则、伏笔/钩子、关系图谱、情绪图谱、标签和资料缺口，并为每项显示故事时间、观点主体、正史/候选/派生状态、证据和来源版本。原始向量数组只存在可重建索引，不通过普通API暴露。

标签定义和标签赋值分别版本化。标签定义保存命名空间、别名、说明和适用对象；赋值保存目标对象、故事时间、观点主体、证据、状态和确认来源。老板可以通过活动主编的受限工具直接新增明确、可撤销的标签或赋值，其他Agent与自动抽取只能提出候选。任何标签写入都经过应用服务、Repository、审计和投影任务，不能由Agent直接改表。

标签默认作为结构化过滤、RRF后的岗位重排信号和资料库导航，不拼接到原始正文后重新嵌入；普通新增或改名只更新相关结构化/投影元数据。只有嵌入模型、维度或实际嵌入文本策略改变时才建立新向量空间并重建。标签命中仍需最小充分裁剪，不能因为作者可见就默认注入所有Agent上下文。

资料缺口按当前任务分为硬缺口、建议补充和可选灵感。可解释空白、刻意悬念和主笔自由创作区允许标记为有意未知；系统不得用统一知识完成率把创作空间转化为待办清单。关系、情绪和视觉地图都是带来源版本的时间投影，不能反向裁决正史。

### 6.9 保留、归档与清理

- 原始聊天默认本机归档、可回看和导出，但不进入正式向量索引；模型只读取任务所需的有界近期消息。
- 完整初稿与重写稿保留。每章最近20个版本保持热访问，更早版本转为压缩归档；归档不能破坏独立恢复与版本追溯。
- 候选区分 `active/dormant/promoted/rejected/superseded`。只有当前任务显式激活的候选可进入重大候选区；任务/阶段关闭后未确认项转休眠并退出其他正式任务默认检索。被拒绝或替代的候选保留状态和来源，默认不召回，不因否决就抹去。
- 任务级临时向量索引在任务结束后保留7天恢复宽限期再清理；索引、缓存和可重建投影不作为作者原始资产。
- 老板可见的原始内容只默认归档，不自动永久删除；永久删除仍需影响预览、严格确认词和墓碑。
- 投影清理或损坏后从SQLite、不可变文件和来源关系重建；重建失败时标记陈旧并降级或阻断，不能使用无水位保证的结果。

### 6.10 三轴时间与上下文预算

事实、关系和状态必须分开世界有效时间、人物/群体知情时间与系统记录/正史修订时间。查询路由在召回前确定故事时点、观点主体和正史版本；任一关键轴不明确时返回分支或未知，不允许“最新记录”或向量相似度替代时间裁决。

上下文组装使用目标模型实际Tokenizer或经过误差上界验证的估算器，先预留最大输出、工具结果、结构化格式和安全余量，再分配输入。硬资料超预算时回到检索层缩小证据或暂停，不能静默截断；上下文包保存预算版本、估算/实际Token、资料位置和排除原因。完整修正及Skill前置治理见 `docs/DESIGN_GOVERNANCE_AUDIT.md`。

## 7. 创造性与输出质量保护

主笔的自由创作区必须真实存在。新检索方案与旧流程、FTS、单向量、整书上下文和只有硬事实基线进行多样本非劣效盲评；一致性或召回率提高不能抵消原创性、人物声音、情绪力度和整体输出质量下降。

- 主笔检索目标是最小充分，不是最大召回；默认禁止整书、全部Wiki、全部聊天和全部相似场景进入上下文。
- 硬事实组成短约束胶囊；少量人物声音、主题、意象、开放伏笔和技法卡组成可选灵感调色板。
- 先形成场景方案，再针对缺口二次回查，避免历史正文先入为主。
- 每条软资料必须记录“为什么采用”；召回但未采用不要求正文消费。
- 混合RAG相对FTS、单向量、整书上下文和只有硬事实做多样本盲评。若文本更像旧文、更套路或整体质量下降，只回滚检索权重、块策略、重排或软资料模板。

### 7.1 失败处理细化

最可能的失败路径：

1. 向量命中语义相似但故事时间错误的旧章节；解决方式是向量前硬过滤、结果后原文回查。
2. Wiki把人物谎言写成客观事实；解决方式是观点主体、知情范围和证据类型分开。
3. 双存储更新中断造成向量落后；解决方式是SQLite outbox、投影水位和幂等重建。
4. 相似场景大量进入主笔上下文导致仿写和套路化；解决方式是独立风格索引、严格条数上限和创造性盲评。
5. 本地嵌入模型过大导致低配机器难用；解决方式是安装时基准、量化模型、后台构建和全量可重建模型切换。
6. 关系图无边界扩展淹没真正证据；解决方式是岗位化边类型白名单、有限深度和结果预算。
7. 查询确实没有答案却被最相似文本填空；解决方式是无答案阈值、冲突检测和显式资料缺口。

再次验证最强反例：即使检索完全正确，模型仍可能写出平庸正文。因此本架构只能降低检索、正史和注意力方面的系统性失败，不能单独保证文学质量。

## 8. 测试与证据等级

- E0：本设计、引擎选型、切片合同、生命周期和验收标准。
- E1：LanceDB、嵌入适配器、块表、投影任务、水位、融合和上下文代码存在。
- E2：空库/升级迁移、Windows运行、跨书隔离、中断、损坏重建、模型切换和构造查询测试通过。
- E3：在500万字符、1500章语料上分层抽样建立独立金标，完成通道消融、无答案、时间冲突、多跳、位置敏感和故障注入；金标与实现代码和内置同义词分离。
- E4：真实模型20/50/100—200章分层创作、创造性非劣效、跨章盲评和老板验收。若对外声称“1000章以上一路陪伴”或“500万字文学质量”，E4必须实际覆盖相应范围，不能由200章外推。

完成实现必须分别报告结构化、FTS5、向量、关系、融合和重排的Recall@K、Precision@K、MRR、nDCG、无答案准确率、P50/P95延迟、索引时间、磁盘、内存和上下文Token。不得只报告一个综合分。

## 9. 剩余风险与未知项

- 当前无法读取目标电脑硬件信息，最终本地模型量化和并发必须由安装时基准决定。
- LanceDB、Transformers.js和ONNX Runtime属于新增原生依赖，必须验证锁定版本在Node 24与Windows上的安装、升级和离线启动。
- 中文小说的最佳块长度、重叠、向量维度、融合权重和重排阈值未知，必须用与实现独立的查询集选择。
- Wiki与实体抽取仍可能误判含蓄、讽刺、谎言和不可靠叙述，原文回查和观点主体不能省略。
- 本地索引会增加磁盘、内存和首次构建时间；具体上限只能在真实书籍规模下测得。
- E0架构选型不能证明真实创作收益，E3检索改善也不能替代E4文学质量评测。

## 10. 停止、回滚和升级条件

- 本地向量组件不能在当前Windows/Node运行或恢复时，停止默认启用，先保留FTS和结构化通道，不用假向量冒充完成。
- 投影水位落后、模型版本混用、来源丢失或证据冲突无法裁决时，正式生产暂停相关检索。
- 创造性或整体质量低于基线时，回滚块策略、向量权重、重排和软资料，不回滚正史、安全和隔离门禁。
- 只有独立评测证明本地嵌入式方案无法满足规模/延迟时，才提交引入独立数据库服务的重大架构决定。

## 12. 500万字分层检索

单书500万字符预计形成数万级正文、规划、Wiki和人物声音块，仍在本地嵌入式架构的设计范围内。检索不建立一个“整书向量摘要”，而是同时使用场景/章节原文块与场景、章节、故事弧、卷、全书主脊五级派生节点；查询先选择需要的层级，再在相关范围下钻原文。

故事弧和卷节点使用增量编译：每章结算产生事实与承诺差量，更新当前章节和故事弧；故事弧结束后更新卷；卷结束后更新全书主脊。每个节点保留正史版本、来源范围、内容哈希和原文指针。普通新增章节不触发全书重新摘要或重嵌入，正史修订只重建受影响范围。

11名成员的岗位连续性日志作为带来源的结构化候选和过滤信号存在，不默认与正文混合召回。Agent唤醒时先加载身份和当前关注，再针对当前问题查询权威知识；岗位历史只有与当前任务相关且未失效时才进入上下文。三点评席共同读取当前完整稿，但各自附加资料仍最小化。详细设计见 `docs/ULTRA_LONGFORM_CONTINUITY.md`。

### 12.1 活动工作集与检索活跃度

故事弧/卷完成结算后，旧正文不再进入默认活动工作集，但仍在正式FTS、向量、关系和原文索引中可回查。派生的检索活跃度至少区分：`always_active`（全局硬事实）、`open_loop`（开放承诺/伏笔）、`stage_active`（当前阶段）、`dormant_triggered`（休眠待触发）、`closed_local`（已闭合局部）和 `superseded`（仅历史用途）。这是可重建的排序/过滤投影，不改变任何来源的正史状态。

章节距离只能衰减普通局部材料的软相关性，不能衰减世界硬规则、不可逆结果、当前有效状态和开放线程。正式查询不得使用“早于当前N章就不检索”的硬截断。

### 12.2 触发器和逐级下钻

查询理解除了实体、别名、关系和故事时间，还要输出 `trigger_reasons`。实体重现、旧事件/地点/道具/规则被引用、开放线程临近窗口、人物声音或知情需要证据、当前结论与摘要冲突、摘要缺项/低置信以及老板明确回顾都会触发下钻。

标准路径为：

```text
活动工作集
→ 相关卷阶段结算
→ 相关故事弧结算
→ 章节/场景节点＋结构化事实/承诺
→ 最小正式原文
```

低风险且摘要证据完整时可提前停止；硬事实、重大呼应、冲突裁决和摘要缺项必须回到权威事实或原文。一次初始检索后只允许一次有界补充周期，周期内最多下钻三级：活动工作集为0级、相关卷为1级、故事弧为2级、章节/场景及结构化事实为3级；从已选来源指针取得最小正式原文属于证据解引用，不增加语义深度，但仍计候选量、延迟和Token。精确ID可以跳级。`retrieval_record` 必须记录触发原因、路径、语义深度、证据解引用、本地扫描/候选数量、实际注入块和Token、采用与排除理由。

### 12.3 反例与创造性约束

- 只读摘要、不允许原文回查：被摘要遗漏的旧承诺、规则例外或知情边界会在后期失真。
- 任何实体出现都全量回查：高频角色会让每章退化为整书检索，延迟和上下文随书增长。
- 过多旧正文进入主笔包：事实更全却更容易模仿旧场景、重复表达和丢失新鲜感。

因此触发器必须按风险、岗位和作用限量。主笔只接收必要的短证据；编剧可多取因果与开放线程；设定师和审校在硬冲突时优先原文。默认策略必须与“摘要永不回查”“任何命中都回查”和“整书长上下文”做消融，并通过连续性正确、Token有界和创造性非劣效三类门槛。

## 13. DEC-020实现与切换冻结

混合RAG不随迁移立即全库启用。Schema、权威outbox、切片/FTS/Wiki/关系/向量非活动快照完成后，按书执行冻结查询探针和影子检索；只有跨书、来源、三轴时间、H/E/I和无答案门槛通过，才原子切换该书活动策略。失败切回旧策略指针，SQLite权威和新诊断证据均保留。

本地向量资产缺失、LanceDB不可加载或投影陈旧时，向量通道进入明确降级；结构化、FTS和允许的关系通道继续服务。依赖向量语义且不能用证据替代的任务报告能力不足，不使用随机/假向量。具体迁移顺序、性能门槛与回滚见 `docs/PRE_DEVELOPMENT_DESIGN_FREEZE.md` 和 `docs/EVALUATION_PROTOCOL.md`。
