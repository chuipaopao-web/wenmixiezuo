# 验收标准

## 1. 完成的基本含义

完成 = 用户目标已实现、受影响路径可用、没有已知阻断缺陷、验证与风险相称。工程机制通过、真实模型质量通过、长期阅读效果通过必须分别声明，不能互相冒充。

## 2. 所有改动的共同检查

- 改动范围与用户要求一致，没有顺手扩大权限或覆盖无关修改。
- 无明文密钥、密码、会话、模型思维链、路径/堆栈或内部协议泄漏。
- 涉及书籍数据时，`owner_id`、`book_id` 隔离和不可变正文成立。
- 新失败状态有用户能理解的原因和恢复动作；旧数据与旧缓存至少可读或有明确兼容路径。
- 产品文案和页面不把软参考伪装成必须，不把计划冒充正文实际。

## 3. 按风险选择门禁（统一测试矩阵）

根AGENTS、开发流程和Skill均引用本节，不另设更宽的默认门禁。任务清单记录适用行及具体风险；不适用的检查不补做。

| 变更类型 | 必须验证 | 不默认要求 |
|---|---|---|
| 纯文档、规则、Skill | 相关结构、链接、引用和规则场景核对；改动可执行工具时运行直接受影响工具测试 | 全量应用测试、产品构建、真实模型、生产部署 |
| 单页 UI/样式 | 相关组件测试（若有）；Web类型检查；Web构建；关键宽度走查 | 全量迁移、API/Worker构建、长期章节验收 |
| 局部前端逻辑 | 受影响测试；Web类型检查/构建；成功/空/加载/失败/恢复状态 | 无关包全量测试 |
| 局部API/Worker | 受影响测试；对应包类型检查/构建；权限与错误合同 | 无关UI真机、长期文学验证 |
| 独立新功能的加法表/索引，未改变既有数据语义 | 迁移清单、空库安装、重复执行安全性、受影响仓储/接口测试及对应类型检查/构建 | 全量验证、历史数据回填 |
| 改变既有受保护数据语义/形状、回填历史数据、权限/账号隔离、跨服务恢复、不可逆迁移或核心工作流结构变化 | `npm run verify:full`，再做适用的迁移/恢复/隔离/真实服务检查 | 无关市场或文学效果承诺 |
| 生产发布 | 按发布类型执行 `docs/DEPLOY.md`；保留回滚；公网冒烟 | Web-only发布等待后端任务清零 |

同一次提交中若包含多类改动，采用最高相关风险，不叠加无关门禁。老板明确要求全量时执行；其余情况只有上表高风险事实触发全量，运行前在清单记录理由。“有数据库迁移”或“更保险”本身不是理由。模型调用局部变化优先验证适配器、受影响业务测试及必要的相称真实探针，不自动运行全量。

产品代码中的文案按实际受影响包检查；纯规则维护不构建应用。浏览器、真实模型或运行环境不可用时，完成其他可执行检查并将缺失证据标为未验证，不伪造通过。

## 4. UI/UX 验收

只验收当前合同真实存在的状态，不要求为了清单增加初始、候选、融合、审查或其他步骤。用户能理解当前位置、当前状态和主要操作；多个并列操作有清楚优先级与真实业务理由。

按当前合同确认的目标设备和视口检查：

- 无非预期横向滚动；正文和输入区可读；固定区域不遮住主内容。
- 主要触控目标约44px；输入字号不小于16px；键盘弹起后焦点和提交按钮仍可达。
- 长文本、长书名、任务进度、错误提示不会把页面撑坏。
- 页面标题、当前对象、当前状态和下一步操作可以在首屏快速理解。

检查层级、密度、键盘焦点、空白和长内容；视觉风格以老板批准的设计基准为准，不由本验收文件规定卡片、边框、配色或布局。

## 5. 管理后台验收（仅在任务影响后台时）

- 管理权限由服务端验证，普通用户不能读取或执行管理功能；入口、域名、导航和模块数量由当前产品合同决定。
- 实际受影响页面的加载、空、成功、失败与恢复状态清楚；桌面和手机主要操作可达，不规定布局或容器形式。
- 账号状态与会话撤销策略一致；算力、收入和API成本来自真实记录，模型配置与权限按当前合同校验。
- 失败与作者反馈可追溯，反馈不能跨用户绑定书籍或任务；采用问题中心、日志或其他载体由架构决定。
- 影响模型行为的资产、提示和配置可追踪到任务使用的版本；不强制采用配方、固定检索方式或某种内部字段。
- 会员、订单等变动保持可审计、可核对的历史，不伪造收入或历史流水。
- 后台接口不返回密钥、密码、明文会话、思维链或未授权作者数据。

## 6. AI共创与长篇工作流验收

本节不规定开书、设定、卷、事件、章纲、正文、故事线或结算必须成为哪些页面或层级。具体业务按当前任务合同验收，质量与可信原则如下：

- 作者输入、AI候选、正式内容、正文实际和历史版本边界清楚，不因界面简化而混写。
- 其他书和无关资料不进入任务；候选、历史版本或推断可以用于明确的比较、修订或审查任务，但必须标明身份，不能冒充当前正式事实。
- 当前任务读取必要的最新可信状态，不用旧计划覆盖正文实际，也不把无关全文塞入上下文。
- 作者可以执行当前产品承诺的选择、编辑、跳过、重做或继续动作；刷新、失败和离开返回后不漂移、不重复付费。
- 普通作者不被迫理解模型ID、任务ID、ContextPack、内部结构方法或机器合同；是否展示专业创作工具由当前产品设计决定。
- 工作流采用多少层、多少岗位、多少候选、是否使用故事线/章纲/审查席，都只能由当前批准的产品合同决定，不能从本文件反推。

## 7. AI与长篇质量证据

- E0：规格存在。
- E1：机制/字段存在。
- E2：确定性工程链路与自动测试通过。
- E3：真实模型、多样本或独立阅读证据通过。
- E4：真实长篇分阶段阅读与连续性验证通过。

只做到E1/E2时可以声明“工程实现完成”，不能声明“文学质量、爆款效果或长期稳定性完成”。这些等级用于说明已有证据，不要求每次报告同时填写全部等级或固定章节。长篇专项按明确授权的目标、样本和用量范围分阶段执行，不把固定章数或长期文学试验加入普通小修门禁。

## 8. 重大缺陷

出现下列任一项不得宣布完成：跨用户/跨书泄漏、作者原文被覆盖、未授权永久删除、明文密钥/会话泄漏、旧数据无法进入且无迁移/恢复、主流程阻断、生产服务不可用、用户被困在无恢复动作的失败状态。

视觉偏好、次要文案和可继续优化项应如实记录，但不与安全或数据阻断混为同一级别。

## 9. 文档与Skill

当前规则只描述生效状态；历史证据在 Git。Skill 主文件保持短，参考按任务路由。文档直接维护源文件，不再生成合订版、HTML中心或指纹索引。旧的阶段表、事故证据与发布日志只在 Git 历史中追溯，不再阻塞普通功能和UI迭代。
