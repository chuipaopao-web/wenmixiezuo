# 老板决定登记册

本文件记录专题讨论结束后的老板最新决定。这里的生效决定优先于旧共识中的冲突部分。

## DEC-001：每本书采用9个岗位

- 状态：生效
- 决定时间：2026-07-16
- 决定人：老板
- 影响共识：第5条“岗位、Agent实例与模型配置”，以及涉及岗位数量的产品、架构、数据、成本和验收规则。

### 原规则

每本书原子创建5个常驻岗位：总编与编排、剧情架构、设定与一致性统筹、主笔、审校。

### 新规则

每本书原子创建9个岗位，分为：

5个核心岗位：

1. 总编与编排；
2. 剧情架构师；
3. 设定与连续性统筹；
4. 主笔；
5. 审校。

4个按需专家岗位：

6. 读者体验与情绪专家；
7. 文风编辑与去AI味专家；
8. 资料研究与考据专家；
9. 版权与原创安全专家。

### 执行约束

- 9个岗位都建立稳定Agent实例和书籍级配置，但按需专家默认待命，不在每轮讨论中全部激活。
- 调度器根据任务类型激活2至5个相关岗位；正式会审可以扩大，但受预算和独立性门禁约束。
- 同一模型可以承担多个岗位，但界面必须显示真实模型来源。
- 同模型分身不算异模型独立意见，不能成为唯一独立复核。
- 新书创建时，9个岗位及配置快照必须原子创建；部分创建失败则整次建书回滚。

### 修改原因

5个岗位足以跑通基础流水线，但不足以长期覆盖读者情绪、语言去AI味、联网考据和版权安全。采用“5个核心＋4个按需专家”可以提升专业覆盖，同时避免9个成员在每轮对话中同时发言造成Token浪费。

## DEC-004：工作台采用内容优先的智囊团式界面

- 状态：生效
- 决定时间：2026-07-17
- 决定人：老板
- 生效版本：首版 `release_id` `wm-v1-20260716-220959-d5dd704d` 的界面增量
- 影响文件：`docs/PRODUCT.md`、`docs/ACCEPTANCE.md`、Web工作台、任务工作区接口、界面测试和使用说明。

### 原规则

桌面采用可折叠三栏，但左右栏分别为272像素和320像素；当前任务位于右侧检查器，成员只有状态点，没有人物头像；底色和字号仅跟随固定CSS与系统偏好，用户不能自行调整。

### 新规则

- 默认采用低饱和浅绿色工作台，并提供米白、雾蓝和夜间底色。
- 用户可在设置中调整小、标准、大、特大四档字体；底色和字体只保存在本机并即时生效。
- 桌面左右侧栏压窄至内容够用的宽度，中间创作、对话和正文区域占据主要横向空间。
- 当前任务放在左栏，必须显示章节、任务类型、真实阶段和状态；点击后可查看任务书、检查点、执行岗位和任务ID，并可通过真实任务接口取消。
- 右栏以紧凑成员列表为主，每个小说岗位显示原型人物头像、真实模型来源和事件驱动状态。
- 手机不压缩三栏，书籍/任务与成员分别进入左右抽屉；设置入口在窄屏仍可使用。

### 执行约束

- 头像资产允许从 `D:\AI智囊团` 只读复制，但文秘写作必须保存自己的副本，不能形成运行时依赖，也不得修改、停止或重启智囊团。
- 九个岗位的头像是视觉身份，不得用头像或文案伪造Agent在线、工作或独立模型状态。
- 任务章节信息必须来自数据库任务记录和章节记录，取消必须调用持久任务状态机。
- 主题必须保持键盘焦点、对比度和减少动画支持。

### 修改原因

老板认为原界面左右栏过宽、创作区受挤压、成员缺少原型头像、任务位置和信息不直观，要求界面更接近AI智囊团的浅绿、紧凑、内容优先风格。

## DEC-008：开放对话与写作准备门禁必须先于主笔生成

- 状态：生效
- 决定时间：2026-07-17
- 决定人：老板
- 生效版本：首版 `release_id` `wm-v1-20260716-220959-d5dd704d` 的流程纠错增量
- 影响文件：`docs/PRODUCT.md`、`docs/API.md`、`docs/ACCEPTANCE.md`、`KNOWLEDGE.md`、聊天/讨论/规划/章节应用服务、Worker、Web工作台、测试、任务账本和验收证据。

### 原规则

普通消息只保存并显示“确定性离线适配器”能力提示，即使真实订阅模型已启用也不回复；只有带 `讨论` 前缀的消息才触发岗位讨论。“写一章”会绕过创作方案、故事圣经和章纲门禁，流水线自动创建与题材无关的通用章纲，并在事实与结算阶段写入固定测试故事数据。

### 新规则

- 普通消息由活动主编通过持久Worker任务真实回复，保存上下文包、模型调用、预算和真实模型来源。
- 自然创作意图自动进入主编加相关岗位的讨论；`讨论 <问题>` 继续作为显式快捷方式，但不再是唯一入口。
- 最近聊天只作为有界任务上下文，不自动进入长期记忆或正史。
- 创作讨论先由相关岗位给出真实意见，主编必须读取这些意见后再真实汇总；禁止用固定文案冒充汇总。
- `写N章` 和直接批次API共用写作准备门禁：必须存在老板确认的创作方案、活动故事圣经、总纲和每个请求章节的可追溯活动章纲。
- 资料不足时不创建章节、不启动主笔，自动发起或复用规划讨论；老板输入完整 `确认方案 <decisionId>` 后才把决定版本化为规划成果。
- 章节预检只能消费已确认章纲，不再生成通用剧情；事实与章末结算只能保存选中正文的真实来源和原文摘录，不写固定人物、地点或钩子。
- 已取消且没有任何正文版本的章节壳可以安全复用；旧任务、旧章纲和旧调用记录保留追溯，不静默删除。
- 章节任务取消后，无正文、无活动任务的章节壳必须回到“未开始”；API启动时确定性修复历史遗留的孤儿“创作中”状态。
- Codex模型保持GPT-5.6 Sol不变；开放回复和讨论使用中等推理，独立审校使用高推理，正式正文使用最高推理，避免普通问候按整章强度运行。

### 执行约束

- 明确暂停、继续、取消、接管和确认命令保持零模型调用。
- 模型调用继续禁止现金回退，凭证仍只读环境变量。
- 所有聊天、讨论、规划和章纲严格携带 `owner_id`、`book_id` 与来源ID。
