# 多Agent协同创作小说平台最终方案 v1.0（待确认）

## 一、产品目标与边界

建设一个本地优先、面向老板个人使用的多Agent小说创作平台，支持从建书、设定、大纲、正文创作到审校、正史结算、长期记忆和恢复的完整闭环。

小说平台与“AI智囊团”完全独立：

- 独立仓库、Web/PWA、API、Worker、端口、数据库、配置、日志、正文、索引和备份。
- 不共享生产数据库、消息、任务、私有记忆、运行状态或密钥。
- 两个产品停止、升级、回滚和恢复互不影响。
- 只允许通过版本化、可审计的导入导出契约交换通用模板。
- 当前不做登录、多用户、收费、云部署和商用后台，但核心记录预留`owner_id`与Schema版本，避免未来推翻小说核心领域。

## 二、系统形态与总体架构

首版采用“本地模块化单体＋独立Worker”：

```text
React响应式网页 / PWA
          │ REST指令与查询、SSE状态事件
       Fastify API
          │
书籍｜Agent｜讨论｜流水线｜正史｜记忆｜检索｜预算｜备份
          │
 Repository统一数据边界
   ├─ SQLite + WAL
   ├─ 不可变正文文件
   ├─ SQLite FTS
   └─ 持久任务、调用与恢复账本
          ↑
独立Worker：模型、检索、写作、审校、工具
只写暂存区，不能直接修改正式正文和核心业务表
```

关键技术约束：

- React＋TypeScript＋Vite、Node.js稳定LTS＋Fastify、SQLite、REST＋SSE。
- 首版不用微服务、WebSocket、独立向量库和图数据库。
- Worker默认全局并发为1，同一本书严格串行。
- SSE支持`eventSeq`断线回放，重要事件至少保留最近7天或10000条，取范围更大者。
- 服务只监听`127.0.0.1`；Worker通过数据库健康记录上报状态，不额外开放端口。
- 模型不可用时，查看、编辑、导出、备份和恢复仍然可用。

## 三、主要功能清单

### 创作工作台

- 桌面端可折叠三栏：书籍与章节、对话与确认、成员状态与引用资料。
- 正文、故事圣经、章纲和图谱具有独立成果页及全屏阅读模式。
- 手机端使用抽屉和全屏页面，不机械压缩桌面三栏。
- 支持PWA安装、已加载内容离线阅读和IndexedDB草稿恢复。
- 自然语言是主要入口，按钮与菜单负责快捷操作和故障兜底。
- Agent状态必须由真实任务、心跳和工具事件驱动，不展示虚构百分比或内部思维链。

### 每本书的创作团队

默认原子创建五个常驻岗位：

1. 总编与编排；
2. 剧情架构；
3. 设定与一致性统筹；
4. 主笔；
5. 审校。

岗位、Agent实例和模型配置三层解耦。默认分工为：

- Codex：总编、结构化验收、主笔候选及GLM正文审校。
- DeepSeek：剧情架构、因果推演、逻辑复核。
- GLM：主笔候选、场景化写作和Codex正文审校。
- Kimi：设定统筹、长文整理、跨章一致性。
- 豆包：情绪、爽虐节奏、读者体验和章节钩子点评。

同一模型可以兼任多个岗位，但必须建立独立实例并如实显示共同模型来源，不得冒充异模型独立复核。

### 主笔选择

- 不永久预设Codex或GLM为胜者。
- 默认按书执行同资料、同章纲、同修改机会的A/B匿名样章盲测。
- 支持标准、快速和老板指定三种模式。
- 完整盲评至少需要两个非参赛的独立评审模型。
- 通过硬门禁后按百分制评估剧情、人物、画面、语言、情绪、钩子、正史符合度和修改能力。
- 总分差达到5分时形成系统推荐；不足5分或存在高分歧时由老板盲读决定。
- 临时代笔与正式换笔分开；连续代笔3章进入正式换笔评估。
- 新主笔接管后的第一章是加强审校的试笔章，不直接进入正史。

### 双主编与接管

- 貂蝉、婉儿具备同级管理能力，但每本书同时只有一个活动主编。
- 通过活动主编租约与`editor_epoch`防止双重指挥。
- 接管优先级为：老板明确指定、双方正式交接、满足故障条件后的自动接管。
- 接管包必须包含任务、章节、正史版本、待决事项、预算、调用状态和下一步。
- 接管后旧`editor_epoch`指令全部拒绝，不能重复生成、重复计费或丢失决定。

## 四、核心创作流程

### 建书

自然语言输入经过确定性解析和必要的模型补全，生成可编辑定位卡，老板确认后原子初始化书籍、五个岗位、配置快照和基础资料。

定位包含：

- 主分类与有限副分类；
- 主题、情节、感情线、爽虐倾向、文笔风格和热门标签；
- 明确内容、系统推断、未指定与冲突状态。

### 规划

依次形成：

```text
创作方案
→ 故事圣经
→ 总纲
→ 卷纲
→ 章纲
→ 写作契约
```

固定骨架负责完整性，题材模块和书籍扩展负责适配；越远章节越粗，近期章节逐步细化。计划、候选设定和正史始终分开。

### 单章与连续多章

一次可以安排3—5章，但必须逐章串行闭环：

```text
预检
→ 组装上下文与写作契约
→ 完整初稿进入暂存区
→ 硬规则检查
→ 异模型审校
→ 最多两次定点重写
→ 最终复核
→ 事实提取
→ 正史结算
→ 保存章节结束状态
→ 更新后续章纲
→ 下一章
```

前章没有完成结算，后章不得启动。中断后从下一未完成章继续；半章不能拼接或进入正式正文。

### 写作质量

- 采用积极写作标准：具体场景、动作、人物声音、心理、张力、信息差和读者期待。
- 不建立永久禁词表；确定性程序只标记重复、套话和句式风险。
- 模型审校必须指出具体段落、问题类型、严重度、依据和修改要求。
- 问题分为`blocker/major/minor/observation`。
- 每次修改生成新的不可变完整版本，不做无痕覆盖或机械同义词替换。
- 同类重大文风问题连续两章且重写无效时，停止机械润色并建议换模或调整上游章纲。

## 五、数据、记忆与正史

### 正文存储

正文采用三层结构：

1. 以内容哈希命名的不可变正文文件；
2. 数据库中的版本、来源、作者、哈希和当前指针；
3. 可随时重建的FTS索引。

Worker只能写`data/staging/<task_id>/`。校验通过后由应用服务原子提升到正式目录。单章历史版本超过20个时，将较早版本归档，但不删除版本清单和来源。

### 分层记忆

每本书包含：

- 会话记忆；
- 书籍工作记忆；
- 故事圣经；
- 章节事实；
- 正文索引；
- 临时任务记忆；
- 岗位私人记忆；
- 老板与系统规则锚点。

每次模型调用生成不可变`context_pack`，记录资料来源、版本、顺序和Token预算。硬规则、当前正文、前章结算和老板决定不得静默截断。

首版使用结构化查询＋SQLite FTS，并保留手动记忆包作为故障兜底。百万字测试要求硬锚点召回100%，语义建议`Recall@10`不低于95%。

### 知识与正史

人物、关系、地点、道具资源、属性、事件、伏笔钩子和世界规则采用类型化事实断言保存。

事实分级处理：

- A：候选；
- B：低风险、可追溯事实，允许受控自动生效；
- C：需要主编复核；
- D：人物生死、世界规则、主线变化等重大正史，必须老板确认。

正史不可静默覆盖。每次调用和最终写入前重新检查`canon_revision`，防止使用过期事实。

### 一致性与叙事图谱

系统检查：

- 人物生死、位置和知情状态；
- 时间线顺序；
- 道具、资源、属性和技能变化；
- 人设漂移与行为证据；
- 主线、支线、人物线和谜题线；
- 情绪变化、信息差、钩子建立与兑现。

图谱是从正式成果重建的分析视图，不是第二套正史。计划轨与正文实际轨分开，章纲生成前形成零额外模型调用的“章节节奏卡”。

## 六、研究、拆书与版权

拆书分为研究分析、快速参考、干净室借鉴和已授权改编四条路径。

硬边界包括：

- 原文、详细逐章摘要、人物映射和拆书FTS不得进入主笔上下文。
- 抽象结构卡必须清除专有名词、独特场景、角色映射和原事件顺序。
- 新方案必须重新设计人物、关系、因果、世界规则、转折、高潮、结局、主题和表达。
- 生成前检查结构，生成后检查文本和结构。
- 文本、设定、人物关系、事件链、章节结构、标志性场景和表达分别评估，不能用单一总分放行。
- 换名仿写、近似改写、翻译规避和多来源拼接属于阻断风险。
- 高风险不能用一句“继续”绕过，只能提供适用权利依据或重新设计。

联网研究只在确实需要当前资料、市场趋势、历史核验或版权核实时触发。网络资料进入独立研究区，保存来源、时间、哈希、可信度和主张—证据关系，只形成候选参考，不能自动进入正史。

## 七、成本与自动运行控制

标准模式为默认档位；省钱模式约为标准预算60%，精细模式最高180%且必须老板明确选择。

标准模式v1主要上限：

| 场景 | 模型调用 | Token | 耗时 |
|---|---:|---:|---:|
| 快速讨论 | 2次 | 4万 | 8分钟 |
| 协同讨论 | 7次 | 16万 | 25分钟 |
| 正式会审 | 12次 | 32万 | 45分钟 |
| 单章创作 | 6次 | 24万 | 45分钟 |
| 联网研究 | 3轮搜索、8页、2次整理 | 10万 | 20分钟 |
| 人物/深度一致性 | 3次 | 10万 | 20分钟 |

另设单书和全局滚动24小时、30天保护线。每次调用前在SQLite持久冻结预算，结束后按实际Token、费用和耗时结算。

- 使用70%时重新预测并优先缩减非必要专家和扩展检索。
- 达到100%后禁止启动新模型或付费工具。
- 结果不明的调用保持`interrupted`，不自动重试。
- 临时技术故障最多自动重试一次；备用模型最多接管一次。
- 超限后由活动主编处理，候任主编接管，二者均不可用时才提交老板决定。
- 明确的暂停、缩减、取消和查看预算命令零Token处理。

## 八、安全、备份与恢复

- SQLite使用WAL、`synchronous=FULL`、外键和短事务。
- 正文提升、正史结算、备份和恢复使用稳定`operation_id`及独立持久恢复日志。
- 模型调用、文件复制和长任务不放在数据库事务中。
- 备份包含数据库、正文、历史版本、正史、任务、预算、调用记录、墓碑、必要暂存成果和完整哈希清单。
- 备份完成后必须在临时目录执行数据库完整性、外键、文件哈希、正文指针、跨书关系和兼容性验证。
- 有数据变化时，每个滚动24小时至少完成一次真实恢复演练。
- 章节、书籍和全系统恢复必须先展示影响，由老板明确确认。
- FTS、缓存和图谱损坏可以重建，不影响正文和正史。
- API Key只从环境变量读取，不进入数据库、聊天、日志、上下文、备份、导出和Git。
- 普通删除为归档；永久删除必须输入包含`YES`、书名和短ID的完整确认词，并通过删除墓碑防止旧备份复活数据。
- 第二物理位置未配置时，只能声称能防软件故障，不能声称能防硬盘损坏。

## 九、持续开发顺序

正式开发使用一个`release_id`连续推进，分八个串行主阶段：

1. 独立项目、契约、迁移、文档和测试底座；
2. Repository、跨书隔离、不可变正文、操作日志和备份恢复；
3. Worker、任务状态机、预算、模型适配、双主编接管；
4. 建书、五岗位、标签、题材适配、故事圣经和大纲；
5. 分层记忆、知识实体、正史门禁和一致性；
6. 先跑通单章，再扩展3—5章串行创作；
7. 情绪钩子图谱、拆书版权、联网研究和完整PWA界面；
8. 全量验收、恢复演练、文档同步和本地发布。

阶段内只有文件范围完全互斥时才允许并行。数据库迁移、公共API、共享类型、核心编排和安全机制始终串行。

前一阶段通过门禁即可进入下一阶段，不重复向老板询问普通继续；但扩大范围、改变架构、增加现金预算、修改安全门禁、执行生产恢复或遇到外部阻塞时必须暂停请示。

## 十、最终验收标准

最终版本只有同时满足以下条件才能宣布完成：

- 第1—23条全部映射到实现、测试和文档，没有未说明的跳过项。
- 类型检查、全量测试、构建和本地运行验证全部通过。
- 全部迁移可在空库执行，也能安全升级已有数据。
- Web、API和Worker统一启动，仅监听本机。
- Agent状态、任务、预算、模型和工具调用全部来自真实事件。
- 完成两本原创测试书的隔离验证。
- 主测试书连续生成5章，每章2500—3500字，逐章完成审校和结算。
- 验证第2章后中断恢复、第3章前双主编接管、旧指令拒绝、预算冻结和正史变化。
- 前章未结算时后章不能启动；已完成章节不会重复生成。
- 两本书的消息、正文、知识、任务、记忆、FTS、缓存、预算和主编租约零串线。
- 版权、联网、费用封顶、永久删除墓碑、索引重建和备份恢复门禁通过。
- 在干净临时目录真实恢复数据库、正文和正史，哈希完全一致。
- 使用确定性适配器完成24小时Worker稳定性测试，无僵尸任务、异常暂存残留或失控资源增长。
- 桌面、平板、手机、PWA离线阅读和草稿恢复通过。
- 项目总纲、产品、架构、API、记忆、路线图和老板说明全部同步。
- 主分支、任务账本、文档指针、迁移和运行版本一致。
- 没有未解决的`blocker`或`major`问题。
- 最终由项目经理依据完整证据签署通过，执行成员不能自行宣布完成。
