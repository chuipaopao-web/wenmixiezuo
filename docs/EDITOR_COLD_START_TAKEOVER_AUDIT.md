# 新书编辑冷启动接管审查

- `design_review_id`：`DR-20260801-editor-cold-start-recovery-v1`
- 适用Skill：`wenmi-longform-quality`；本轮读取当前Skill及其路由要求，未把Skill注入产品成员提示词。
- 范围：新书主编开场、候任副编接管、失败任务恢复、成员状态、有效输出展示。

## 故障基线

痛点是新书开场失败后副编也无法工作。实机证据显示，活动主编的订阅模型调用在返回前进入 `provider_result_unknown`；接管门禁随后要求副编模型在过去24小时必须已有成功调用。新书副编没有历史调用，因此无法获得第一次调用机会，形成冷启动死锁。原 `conversation_reply` 留在失败状态，界面只能显示“主编这次没有成功接入”。

这不是提示词或创作质量问题，而是候任可用性验证把“没有证据”误当成“不可用”。同时，历史失败任务仍冻结故障主编的Agent、模型快照和epoch，即使租约完成接管，普通重试也可能再次路由到旧成员。GLM真实回复还暴露了展示解析缺口：JSON字符串中未转义的中文引号式短语会让整份有效内容被误判为机器载荷。

## 已确认事实、推断与未知项

- 已确认：书籍、原开场触发消息、原任务、主编失败调用、副编接管包、任务第2次尝试、副编GLM成功调用和回复消息都有独立记录。
- 已确认：接管后编辑epoch为2；貂蝉为待命，西施为空闲；没有伪造工作中状态。
- 已确认：原始GLM输出包含完整有效答案，只是字符串内部引号未转义；修复展示不需要再次调用模型。
- 推断：允许“无历史且无近期反证”的单次冷启动，比要求先有成功记录更符合新书和新模型的可达性。
- 未知：不同方舟模型长期返回近似JSON的比例，后续只能通过真实调用样本积累，不能从单次成功外推。

## 方案与替代方案

采用方案：近期成功直接通过；完全无历史允许一次冷启动；同模型正在调用或十分钟内有失败/结果未知则拒绝。接管事务更新租约、书籍活动编辑和Agent激活状态；非点名失败回复重试时重绑当前活动编辑；展示层只对可确定恢复的引号做解析修复。

拒绝方案一是永久要求历史成功，因为它无法解释第一次成功从何而来。拒绝方案二是启动时额外探测所有候任模型，因为会增加无任务调用和Token。拒绝方案三是创建新的开场任务，因为会重复老板原话、预算和回复。拒绝方案四是把副编显示为工作中，因为任务完成后真实状态应为空闲。

## 两轮审查

第一轮检查安全与恢复：冷启动只在无历史且无反证时发生；任务租约、预算、epoch和提交栅栏不取消；点名消息不改派；同一原任务恢复；迟到主编结果因旧epoch不能提交。

第二轮检查创造性与输出质量：不修改开书资料、上下文包、岗位提示词、模型绑定或创作要求；解析器只恢复原模型已经输出的字段，不删除风险、未知、候选或作者问题，也不生成新内容。因此相对旧流程不会收窄创意空间，且避免用机械故障话术遮蔽真实回复。

## 指标、证据与停止条件

指标包括：原任务ID保持不变、attempt递增一次、成功调用恰好一条、Agent/模型/epoch与活动租约一致、回复哈希可追溯、刷新不新增调用、专项与全量门禁通过。证据等级上限为E2。

若出现重复调用或回复、点名任务改派、鉴权/额度错误被接管绕过、近期失败模型被立即再次调用、关键信息被解析器删除、跨书或Agent状态与真实任务不一致，立即停止并回滚代码；历史任务、消息、调用和epoch保持不可变。
