## 1. 总则

所有业务状态转换由应用服务在SQLite事务内执行，Worker只领取被允许的工作、提交有版本和幂等键的结果。自然语言意图只能请求状态转换，不能绕过权限、确认、费用、隔离或正史门禁。

状态显示必须来自持久状态、租约、心跳、模型调用或工具事件。UI上的“工作中、取消、恢复、完成、降级”必须对应真实状态，不用文案或动画模拟。

## 2. 统一任务状态机

### 2.1 状态

`draft → queued → leased → running → awaiting_input|awaiting_confirmation|succeeded|failed|cancelling|cancelled`

附加恢复状态：`retry_scheduled`、`orphaned`、`resuming`、`degraded`、`blocked`。

### 2.2 合法转换

| 当前 | 事件 | 下一个 | 条件 |
|---|---|---|---|
| draft | enqueue | queued | 输入Schema、预算和依赖通过 |
| queued | lease | leased | Worker能力匹配、租约原子取得 |
| leased | start | running | epoch、模型/工具能力再次验证 |
| running | checkpoint | running | 幂等序号递增 |
| running | need_input | awaiting_input | 缺老板信息且不能安全推断 |
| running | need_confirm | awaiting_confirmation | 产生候选方案/高影响操作 |
| running | succeed | succeeded | 输出Schema、取消栅栏、版本和业务不变量通过 |
| running | transient_error | retry_scheduled | 重试预算未尽且不会重复正式副作用 |
| running | permanent_error | failed/blocked | 保存错误分类和恢复入口 |
| 任意未终态 | cancel | cancelling | 持久化新epoch并传播Abort |
| cancelling | cancel_ack/timeout | cancelled | 晚到提交被epoch拒绝 |
| orphaned/failed | resume | resuming | 依赖可用、检查点完整、老板无需重确认 |
| resuming | enqueue | queued | 使用同一operation与新attempt |

`succeeded` 不等于“已进入正史”。任务结果先进入临时或候选；只有对应确认/结算事务能产生正式版本。

### 2.3 幂等和竞态

- `operation_id` 表示用户意图，`task_id` 表示任务，`attempt_id` 表示一次执行，`epoch` 阻止旧执行提交。
- 外部模型和工具调用记录请求哈希；超时未知不能盲目重复有副作用工具。
- 提交事务同时检查任务状态、epoch、输入版本、活动主编租约、预算冻结和依赖水位。
- 取消后生成的文本可以作为诊断附件保留，但永不自动提升。

## 3. 开放聊天模式

### 3.1 消息生命周期

`accepted → persisted_with_hash → deterministic_intake → local_analysis? → routed → response_tasks_created? → partial_responses → settled`

面向老板的普通回复在同一次岗位模型调用中生成结构化有效输出；服务端只做白名单字段解析、确定性套话清理和完全相同段落去重，不再调用第二个模型做摘要。默认消息保存直接结论、必要依据、风险/未知项和动作，允许公开的完整回复以带哈希的 `effective_output` 引用保存并可展开。结构输出无效或无法确认安全压缩时，完整原样显示；正式正文、试写正文和完整点评报告不经过此层。

进入书籍即处于自由聊天，不先要求选择写1章或连续写多章。每条老板消息先原样持久化并计算内容哈希，再按以下优先级路由：

1. 明确暂停、继续、取消、回到版本等控制命令由确定性应用服务处理；
2. 明确 `@成员` 直达该成员，除非触发安全、费用或不可逆硬门禁；
3. 存在活动剧情/专项会话时先判断是否续接，避免每条消息重新启动全团队；
4. 低风险状态、导航、精确资料查询和可撤销候选由小文秘书本地处理；
5. 明确专项问题激活对应岗位；
6. 明确剧情或重大创作方向建立主编主持的双编剧会话；
7. 低置信、高影响、歧义或越权候选升级活动主编或只问一个必要问题。

“小任务”按权限、风险、可逆性、权威和创作影响判定，不按消息长度判定。点名成员必须创建真实回复任务；小文秘书可以返回有证据的本地结果或简短受理状态，但不能用自己的摘要替代原始消息、口头模拟任务或垄断成员回复。

### 3.2 小文秘书路由状态

`received → deterministic_route|local_candidate → direct_local_result|specialist_task|plot_session|editor_escalation|need_clarification|blocked`

每个状态转换保存路由政策版本、风险/置信带、点名、活动会话、实体候选、来源、选择/排除理由、本地模型快照、资源/延迟和最终云Token。确定性结果仍经权限、版本和幂等检查；本地模型只生成严格Schema候选。模型离线、哈希错误、内存不足或低置信时显示 `degraded`，回退确定性/结构化/FTS/关系允许路径或升级现有套餐岗位，不远程下载、不按量付费fallback。

作者实际进入对话时执行一次 `conversation-entry` 观察，不属于轮询，也不创建新的创作轮次。观察顺序为：当前设定候选→相同设定项的真实任务→活动设定→后续规划。已存在任务或回复时只返回 `guidance_in_progress|guidance_available|awaiting_confirmation|guidance_paused|guidance_failed|guidance_cancelled`；只有从未建立当前项任务时才创建一个隐藏触发和一个活动主编回复任务。隐藏触发不进入作者消息、正史、规划或检索索引；失败、暂停和取消不自动重试。

### 3.3 回复结构

岗位回复面向老板展示结论、依据、风险、未知和建议；检索引用可展开。内部查询计划、候选和排除理由进入诊断页，不显示思维链。

聊天文本停留临时层。若讨论形成决定，主编生成结构化候选；老板确认后产生对应正式对象。不能把整段聊天或多数投票直接当正史。

### 3.4 会话收口

主编在形成可执行方向时给出：方案摘要、分歧、被否决项、两名编剧独立估算后的推荐章节跨度、估算前提、不确定性、待确认高影响项和来源。作者确认方向与必要决定，不负责凭空填写章节数。只有老板执行明确确认动作，讨论才进入规划确认状态。

## 4. 探索与规划模式

### 4.1 讨论任务

`collecting_scope → retrieving → dual_writer_independent_opinions → bounded_cross_review → editorial_synthesis → awaiting_confirmation → confirmed|rejected|reopened`

- 范围必须包含问题、涉及章节/故事时间、期望产物和不做什么。
- 剧情任务默认由婉儿/DeepSeek和红玉/GLM两个异模型编剧先独立判断，Kimi可按活动绑定替换其中一席，豆包不得进入剧情任务。两席互相看不到未提交的方案和章节跨度数字；提交后才允许一轮有界交叉质疑。非剧情任务按相关岗位独立判断。
- 主编不得抹去少数异议，要说明采用/不采用依据。
- 老板修改方案时生成新候选版本，不改旧版本文本。
- 当剧情方向足以规划时，两席分别输出最小/推荐/最大章节数、剧情单元、前提和不确定性；主编合并成滚动预测，不把估算转换为多章并行或一次性生成命令。

剧情讨论由原始老板消息触发时，先经历 `secretary_preparing → editor_opened`：小文秘书只做实体/时间识别、受限检索和两个互不锚定的最小资料包，随后退到后台。主编、两名编剧和被点名成员直接向老板显示回复。普通追问续接当前 `discussion_epoch`；只有主线、人物命运、核心规则或讨论目标发生重大改变，主编才开启新的双编剧独立轮次。

讨论首屏由主编有效收口，并明确保留了多少份独立岗位意见；展开后显示每个参与岗位的完整允许公开回复和主编完整收口。独立编剧意见不得先互相锚定，也不得因首屏精简而丢失；正式讨论决定、候选方案和后续规划使用完整主编结果，不使用被折叠后的展示文本作为唯一输入。

### 4.2 设定大纲逐项引导

新书建书事务按活动类型画像初始化设定工作区，并把“策划理念”置为唯一正在讨论项；作者是否打开规划页不得影响初始化。每个本书必谈项首次进入时创建一次三席独立提案任务：活动主编与两名编剧读取同一份当前项最小资料，各自独立调用模型并提交一个候选，调用前和输出时都不得读取另外两席答案；该任务不进入交叉质疑、投票、主编自动综合或候选自动落库。三份真实候选逐席展示并等待作者选择、明确组合、自拟或否定。作者反馈后，只由活动主编按明确选择形成一个候选→作者确认或直接修改→保存来源并推进下一项。相同项的刷新、普通追问和修订不重复启动三席；次要未知项用明确、可逆的假设推进，只有会改变重大方向或使候选无法成立的阻塞信息才允许问一个问题。

作者反馈候选时先由确定性路由识别处理方式。具体修改直接合并；只说“不满意/不喜欢/不对”时，第一轮由主编主动修正并给出更具体候选，第二轮改给结构不同的新候选，前两轮不得追问原因；只有连续两轮仍未认可，主编才可在先给当前最佳候选后问一个关键问题。作者明确“完全换方向”时直接换核心方向，不要求作者先填写原因或从多方案中选择。

每轮模型输入只包含当前项、最多三条直接依赖、精简开书定位和与当前项相关的故事方向。故事方向是软参考，不能切换讨论主题。设定完成前的剧情总纲、章纲和正文请求全部回到当前设定项，不启动双编剧剧情会话。旧书补齐活动项时不得覆盖已有内容、候选、确认状态或自定义项。

### 4.3 规划层级

全书终局、主题和重大承诺保持为远期软锚点。第一次剧情总纲只规划当前一个具有起承转合和明确结算点的阶段，单阶段最多50章；当前阶段正文全部完成并结算后才追加下一阶段。阶段内部只为未来5—10章保留轮廓，1—3章进入精确场景契约；每章结算后滚动更新，不一次写死全书细节。

每份章纲必须精确引用所属总纲阶段。阶段结束章额外携带闭环合同，承接总纲确认的解决方式、阶段结果和允许保留的未决线索；保存前由确定性门禁拒绝错误阶段、错误范围、额外未决线索及“阶段主事件仍未完成”等反闭环要求。闭环合同进入主笔资料包，但只约束必须发生的结果，不规定对白、动作、意象和局部调度。

### 4.4 确认结果

确认事务原子创建：规划正式版本、决策记录、来源绑定、被否决候选状态、受影响投影outbox和下一步任务入口。部分确认必须明确范围；未确认部分仍是候选。

## 5. 写作准备门禁

### 5.1 必要条件

- 书籍存在有效表达基线，或存在可在本次试写/讨论后确认的临时基线；首个正式工单前必须确认叙事视角与距离版本。
- 存在被确认的上位规划，或本次场景被老板明确批准为例外探索稿。
- 当前章/场景边界、视角、时间、地点、目标、不可发生事项和结尾意图明确。
- H硬约束无未解决冲突；关键实体已消歧。
- 当前书的最低检索/权威投影水位可用；降级不会损害该任务硬事实。
- 活动写手只能是主笔或副笔之一；其模型能力、输出预算、费用、取消能力和 `writer_epoch` 通过。
- 事实、文学和体验三点评模型快照均可用、彼此不同且均与活动写手模型不同；GLM写手时事实席必须改用DeepSeek；三份全文输入和最多两轮预算已冻结。

### 5.2 写作工单

工单是版本化正式任务输入，包含：

1. 目标与读者体验。
2. 章/场景范围和不做什么。
3. 视角、世界时间、地点和出场角色。
4. H硬约束与来源。
5. 必须推进/暂不兑现的承诺和伏笔。
6. 角色声音与表达基线的最小证据。
7. 可自由发挥区和I灵感上限。
8. 结尾状态和后续接口。
9. 三职责/三异模型点评门槛、实际选择原因、AI腔与政治/情色风险字段、预算和停止条件。

资料包按岗位编译，不把所有检索结果原样附在工单中。工单过大时必须先结构化压缩和去重，不能挤占输出预算。

## 6. 正文创作模式

### 6.1 状态机

`preflight → focused_retrieval → context_compiled → drafting → draft_saved → review_panel_frozen → three_reviews_running → reviews_complete → editorial_merge → revision_needed|ready_for_owner → owner_confirmed|owner_rejected`

`drafting` 过程中可以按段落流式展示，但正式草稿只在完整生成、持久化和哈希完成后登记。流式残片不是正文版本。

### 6.2 主笔检索

活动写手仍执行检索，但维度受限为：当前角色状态/声音、已承诺伏笔、当前场景因果、表达基线和必要空间/规则。默认不获取整卷旧正文或大量相似战斗/感情场景，避免仿写和注意力锚定。同一正式版本只允许主笔或副笔一人持有写手租约。

### 6.3 审校与修订

完整草稿生成并哈希后，冻结事实/连续性、文学/AI腔、体验/政治情色三个点评职责席。默认成员/模型为文姬（GLM）、妲己（Kimi）和昭君（豆包）；若活动写手为湘君（GLM），事实席改由婉儿（DeepSeek）承担。三席实际模型必须彼此不同且均不同于活动写手。三席并行读取同一不可变正文版本、写作工单、前章结尾和各自最小附加资料，互相看不到报告：

1. 事实席（默认GLM，GLM写手时DeepSeek）检查正史、时间、人物状态、知情边界、规则与伏笔闭环；

事实席先执行相邻定稿对照，再做因果与认知检查。明确的编号种类、日期时间、颜色材质、数量尺寸、位置、身份或状态冲突必须引用两端并返回 `major/rewrite`；不得因为只需修改一两句而降为 `minor/pass`。只有当前稿无法安全定点修复并确需老板裁决时才使用 `blocker`。
2. Kimi席检查文学、人物、语言、节奏、重复和可解释AI腔风险；
3. 豆包席检查读者体验、情绪、钩子，以及政治/情色内容风险。

共同报告必须带 `manuscript_version_id`、`model_snapshot_id`、结论、评分、位置、严重度、正文证据和修改目标。Kimi额外返回 `ai_style_risk_score`、段落总数/标记数和 `flagged_paragraph_ratio`；该分数不是AI作者概率。豆包额外返回政治与情色风险级别、位置、依据、建议动作和策略版本；该筛查不是法律意见或目标平台审核保证。

三席不是多数投票。证据闭环的正史、安全或合规阻断项必须进入修改单；互相冲突的文学软意见由活动主编保留差异并综合。主编只读取报告和引用片段，不默认再次读取全文。任一席在有限重试后失败，当前稿保持暂存/受阻，不以空报告、确定性假模型或现金回退冒充通过。

每轮三席完成后只生成一张定点修改单。最多触发两次定点修订；每个新完整草稿版本都重新运行三席，旧稿和旧报告保留。第二轮后仍有阻断项则返回章纲/设定/老板决策；非阻断建议交老板决定。禁止任何点评模型以“优化”为名无痕重写整章，也禁止为降低AI腔风险机械加入错别字、碎句或随机口语。

### 6.4 老板确认

老板可以确认、退回、基于任一旧稿创建新稿或直接编辑。确认后原子登记正式不可变正文版本；确认前任何稿件只在临时层。

## 7. 章节结算与正史提升

### 7.1 结算状态

`formal_chapter_registered → extraction_candidates → source_validation → conflict_review → owner_gate_if_needed → settlement_committed → projections_queued → projections_ready`

### 7.2 自动与人工边界

- 普通、明确、无冲突的A/B/C级事实可继承已确认正文来源，按规则自动结算，但仍保留抽取器版本和原文指针。
- 歧义、观点、反事实、梦境、假情报、冲突和D级事项进入人工门禁。
- 自动抽取的事实权威不能高于来源正文；摘要、Wiki和向量不能提升权威。
- 结算失败不回滚已确认正文，只阻断下游正史投影并显示待处理。

### 7.3 结算内容

事实、人物状态、知情边界、资源、关系、规则例外、事件、承诺/伏笔、秘密、债务、目标、故事弧状态、叙事活动度、下一章接口和受影响投影。每项都有三轴时间、来源和权威等级。

## 8. 阶段结算与下钻

### 8.1 阶段边界

由故事弧或卷的叙事闭合触发，不按固定章节机械切分。超长未闭合阶段可以有技术检查点摘要，但不能标为正式阶段结算。

### 8.2 锚定式增量合并

新阶段结算从上个有效版本和新增正式结算合并，只更新受影响项。固定探针检查人物生死/身份、全局规则、开放承诺、核心关系、资源和不可逆结果。探针失败保留上个有效版本，当前结算进入修复，不向全书主脊合并。

### 8.3 检索下钻

初始读取活动集和相关阶段结算。关键触发后只允许一个补充周期，最多按卷、故事弧、章/场景及事实三级下钻；最小原文解引用另计证据预算。仍无证据则报告未知。

## 9. 知识治理工作流

### 9.1 标签/实体Schema

`proposed → validated → applied|awaiting_confirmation → active → deprecated|merged`

清晰、单书、可逆且不改变事实的新增标签可由活动主编直接应用；合并、重命名冲突、删除、改变实体类型或大量重标注需要老板确认。废弃不删除历史赋值；投影按版本重建。

### 9.2 候选知识

`active → sleeping|rejected|promoted|superseded`

休眠只退出默认检索，不删除。拒绝保留原因和来源，防止重复建议。提升产生新正史版本；不修改候选原文。

### 9.3 知识缺口

系统可以发现“实体无类型、地点无空间、关系无时间、规则无来源、承诺无窗口”等缺口，但缺口是诊断，不等于自动补全。主编可根据老板自然语言创建治理任务。

## 10. 投影与重建工作流

`outbox_pending → claimed → building_snapshot → validating → ready_to_switch → active|failed`

- 构建使用非活动快照；每个源版本只产生一次幂等投影项。
- 验证包括行数/来源覆盖、哈希、跨书零命中、冻结查询探针和活动指针一致性。
- 同一书同一投影类型只能有一个切换事务；切换只是更新指针。
- 失败保留旧活动快照；重试创建新attempt，不覆盖失败证据。
- 全量重建可暂停/恢复；交互任务有资源优先级。

## 11. 导入、导出和恢复状态机

### 11.1 导出

`requested → snapshotting → manifesting → hashing → validating → ready|failed`

导出从一致性快照读取；失败包不得显示为完成。下载/复制后可选再次校验哈希。

### 11.2 复制导入

`quarantined → structural_scan → hash_scan → schema_preview → impact_preview → confirmed → importing_new_ids → rebuilding → ready|failed`

任何失败只影响隔离副本和未提交的新ID。禁止通过复制导入覆盖当前书。

### 11.3 生产恢复

`snapshot_selected → dry_run → impact_confirmed → pre_restore_backup → restoring → validating → reopened|rolled_back`

生产恢复必须暂停对应书写入、创建恢复前备份并由老板确认；自动化测试只运行临时恢复，不能触发本状态机。

## 12. 预算与能力状态机

调用前：`estimated → frozen → admitted|denied`；调用后：`actual_recorded → settled`。预估必须包含模型输入、输出、工具和重试上限。多个并发任务通过事务冻结预算，不能各自看到同一余额。

套餐/登录态模型以额度而非现金计价时仍记录Token和套餐来源；不能把套餐称为无限或零资源。任何可能产生现金费用的fallback默认关闭，只有老板单次明确授权才能启用。

### 12.1 书籍模型绑定变更

`draft_revision → previewed → capability_validated → independence_validated → active|rejected|superseded`

- 预览必须展示未来剧情席、写手、三点评席、共享模型来源、自动事实席替补、套餐状态和现金风险。
- 新修订激活前，两个剧情席必须异模型，豆包不能进入剧情池；三个点评席必须能针对Codex或GLM活动写手形成三个不同且均不等于写手的快照。
- 激活事务只更新书籍活动绑定指针。已创建的讨论、工单、稿件、点评和模型调用继续引用旧修订，不在中途换模型。
- 回滚是把经过重新验证的旧修订激活为新当前指针，不修改历史任务；无兼容组合时保持旧配置或受阻，不启用按量付费回退。

## 13. 恢复优先级

1. 保护权威正文、正史和老板确认。
2. 阻止重复副作用和晚到提交。
3. 保留任务检查点、调用与错误证据。
4. 恢复结构化/FTS硬事实能力。
5. 重建关系/Wiki/阶段摘要。
6. 最后重建向量、缓存和活跃度。

恢复不得为了“让页面先变绿”伪造Agent状态、投影水位或任务完成。

## 14. 工作流验收场景

- 只有书名后说“写一章”或“开始写”：系统必须在同一自由聊天中自然进入范围/规划，不得启动主笔，也不得要求作者先选择1/3/5章批次。
- 普通长消息未点名：主编必须真实回复；剧情讨论创建两个异模型编剧独立任务，点名其他成员时也有真实独立任务和结果。
- 明确点名消息由目标成员直接回复；小文秘书只附加资料。明确剧情请求不得由小文秘书直接给剧情结论，老板原文哈希与岗位输入中的原文必须一致。
- 两千字低风险资料导入不能因长度自动升级重大创作；一句人物生死/核心规则改变不能因短而本地直答。
- 活动剧情会话中的普通追问不重复创建双编剧首轮；重大改向才生成新轮次并保留旧意见。
- 普通聊天默认不显示寒暄、重复解释和内部流程播报，但事实、风险、未知项、少数异议与确认动作可见；展开可看到同次调用的完整允许公开回复，且不会新增一次远程模型调用。
- 超长单段回复、结构解析失败或内容安全性不明时不得截断；正文、试写稿和三席完整点评不得被有效输出层压缩。
- 本地工具模型缺失、哈希错、低置信或资源不足时显示降级；点名直达、确定性控制和数据查看仍可用，且没有远程下载或现金fallback。
- 规划未确认、H冲突、实体未消歧、预算不足、投影阻断时，所有写作入口一致阻止。
- 主笔生成中取消：适配器收到Abort，晚到全文不能登记正式草稿。
- Worker在模型返回后、提交前崩溃：接管任务只产生一个可用草稿版本。
- 正文确认后抽取失败：正文正式版保留，结算显示阻断，不产生半套正史。
- 摘要与原文冲突：保留冲突并回查原文，摘要不能覆盖。
- 向量不可用：任务按策略降级，界面如实显示，不影响可由硬事实完成的工作。
- 两名编剧实际模型相同、豆包被配置进剧情席或两席提前共享章节跨度：来源如实显示并阻断“异模型双方案”状态。
- 三点评席任一模型重复、与活动写手相同、事实席未在GLM写手时切换DeepSeek、报告版本不同或缺席：正文保持暂存/受阻，不能计为完成。
- Kimi输出“AI生成概率”但无段落证据，或豆包输出政治/情色风险但无位置/策略版本：Schema拒绝该报告并按有限重试处理。
- 复制导入同一本书：生成新book_id，原书和原索引零变化。

## 15. DEC-049持续创作会话状态机

会话状态：

`exploring → awaiting_direction → planning → awaiting_plan → ready → closed`

任一活动状态可进入 `paused`；明确继续或新的老板创作消息根据最新黑板成熟度恢复到 `exploring/awaiting_direction/planning/ready`。同书只允许一个活动或暂停会话。

事件路由：

- 首条剧情消息：创建会话、黑板修订和 `initial_exploration` 双编剧轮；
- 普通追问：追加老板事件/黑板修订，只创建主编回复任务；
- 明确重大改向：追加黑板并创建 `major_redirect` 双编剧轮；
- 锁定当前方向：绑定真实决定，进入 `planning`，再创建独立跨度估算；
- 规划完成：只形成故事弧和未来1—3章，进入 `ready`；
- 剧情总纲规划：双编剧先各自提交完整连续阶段结构，服务端分别校验后才允许一次交叉质疑；主编据两份真实产物综合为 `stage_master_v2`。远期停留在阶段主线与结算边界，不能提前展开成逐章清单。
- 试写：切换 `trial_draft` 模式，稿件完成后不等待三席或老板确认；
- 正式写作：切换 `formal_production`，逐章经过三席、修订、确认和结算；
- 阶段结束：从连续已结算章节生成故事弧结算，不读取或提升未定稿试写。

黑板与预演均使用修订/来源指纹。正史或黑板变化使未采用预演陈旧；重试读取同一持久任务和修订，不能重新生成一个无关联会话。质量回退时章节正文指针恢复上一最佳稿，退化稿和修订单保留审计但不得继续成为活动输入。

## 16. 已有正文接续状态机（DEC-077）

`draft → parsed → importing → ready`，解析或确认失败进入 `failed`，作者未确认前可以 `cancelled`。`failed` 保留源哈希、逐章元数据和最后完成检查点；重试回到 `importing` 并从检查点继续。

1. 预览：规范化换行并校验字符上限，以确定性标题规则解析；保存源哈希和逐章范围。不得创建章节、正文、正史、事实、索引请求、讨论或模型调用。
2. 作者校正：作者修改标题和纳入开关。服务端不接受客户端正文片段或字符范围，避免篡改解析边界。
3. 确认：再次校验书内无章节、无活动生产任务、源文件哈希匹配和至少一章纳入。创建导入任务并按顺序执行“创建章节→提升不可变正文→登记`creator_kind=import`版本→作者确认结算→记录检查点”。
4. 恢复：任一步失败只标记当前导入和任务失败；已完成章节保持有效。重复确认复用已登记目标ID并补完缺失步骤，不能产生第二份章节或第二次正史结算。
5. 接续：导入完成后由作者点击“请主编接手续写”或发送同义自然语言。主编先做缺口诊断，不直接写正文；重大未来方向按持续创作会话启动双编剧，锁定后只滚动生成未来1—3章章纲。
6. 新章：从导入最后一章之后编号。试写与正式生产边界、三席点评、定稿和结算规则均不因导入来源而降低。
### 16.1 已有正文分析与续写优先

`ready_import -> continuation_analysis_queued -> analyzing_chapters -> baseline_ready|analysis_failed`

导入结算和分析任务相互独立：原文一旦确认导入就保持有效，分析失败只影响派生续写基线。每章分析按源哈希幂等，任务检查点记录已完成章节；恢复时跳过哈希一致的成功记录。对话接待在调用通用设定引导前先检查已有正文状态：分析中返回进度，分析成功加载有界续写基线，失败提供重试；三种状态均不得落入空白新书的设定门禁。

### 16.2 反向章纲、设定确认与首阶段总纲衔接

`baseline_ready -> reverse_outlines_ready -> continuation_settings_confirming -> continuation_settings_confirmed -> first_stage_planning_queued -> first_stage_candidate`

1. 每章分析成功后生成或复用同源哈希的反向章纲；反向章纲绑定正文版本、分析记录和模型快照，只是可重建派生资料。
2. 续写设定引导始终以正文与反向章纲为事实依据。开书档案中的频道、分类、标签、主角草案和剧情简介只提供定位与软方向，不得覆盖原文事实。
3. 设定逐项确认期间只加载当前项的直接证据和少量相邻章纲；不得把整本正文、全部章纲或完整聊天一次性发送给成员。
4. 最后一项设定确认后自动排队首阶段剧情总纲讨论。该任务从反向章纲归纳已导入正文覆盖的第一个连续事件阶段，不重写正文，不规划超过50章的远期故事。
5. 首阶段候选必须包含阶段章节范围、出场人物、起承转合、章节内容区块、预估字数、情绪、爽点、虐点、转折及伏笔释放周期；作者确认前保持规划候选状态，不进入正史。
