# 一、目标与事实

## 1. 文档用途与证据等级

### 1.1 本文解决的问题

产品已有较多功能，但用户反馈故障多、部分能力不到位、交互不顺。重构应使作者更容易开始、连续写作和修改长篇，同时使故障可定位、结果可恢复、费用可解释。衡量结果不是重写了多少代码，也不是用了多少Agent。

本文细化每项能力的入口、输入、输出、状态、边界、失败恢复、依赖和验收。具体函数、SQL迁移与组件实现由相应开发批次编写；不能直接把本文中的概念表当作已验证迁移脚本执行。

| 新旧切换 | 第107批先隔离内测；生产单一写入权威，不默认启用跨库新旧混合运行 | 数据完整性与切换范围按第58章核定，不能直接发布覆盖 |

### 2.3 不成立的承诺

没有“不会写错、绝无BUG”的架构。数据库、队列、强类型和多模型只能降低特定风险。长篇质量也不能靠固定流程保证“不散架”“必成爆款”。合理承诺应是有明确失败边界、数据保护、恢复能力、量化运行指标和实际质量证据。

## 4. 缺口、故障与重构优先级

### 4.1 已有证据支持的关注点

| 问题 | 证据边界 | 推荐处理 |
| --- | --- | --- |
| 资料编号合同曾不对称，模型交回有效内容仍可能失败 | 第90批修复与发布记录；本批未重跑两项作者历史任务 | 单一Schema来源、当前任务资料句柄、边界合同测试、保留返回结果 |
| 模型空返回/截断和多成员长时间失败 | 交接中的实际故障与热修记录 | 总任务预算、单次预算、明确未知状态、小任务和检查点 |
| 各业务自带任务恢复逻辑 | 本批核对的服务启动代码 | 统一运行状态与恢复语义；逐模块迁入，不能一次大替换 |
| 全站真实作者回归与容量证据不足 | 操作总览与交接明确标为未验证 | 在隔离环境建立代表性长篇路径和故障注入 |
| 资料入口与后台配置分散 | 页面和导航证据，使用效果仍需原型验证 | 作者围绕写作组织；后台围绕问题处理组织 |

### 4.2 不能直接断言的事

- 没有证据认定每个功能都有BUG，或现有基础设施全部不可靠。
- 链是否“过重”不能只看名称；要看它是否重复全书/卷设计、每次实际输入多大、需要几次调用、作者要确认几次。
- 代码行数、测试数量、成员数量不能代替稳定性和文学效果。
- 当前未核验到某入口时标“未核实/待补齐”，不等于证明整个仓库绝无相关能力。

### 4.3 优先顺序

先保护数据和费用、统一任务执行与错误状态；再做“开书到连续创作”的新闭环；同时验证文学质量、编辑和恢复；随后补齐资料管理、运营与迁移。支付、推广、复杂图谱不应抢占正文可靠性工作。

## 5. 对V9的核心修订

| V9表述或设计 | 本文处理 | 理由 |
| --- | --- | --- |
| 默认全自动，作者只有否决权 | 调整：授权明确的自动准备和有界托管 | 沉默不能证明作者接受，托管也需要预算、范围和退出条件 |
| 账本是唯一事实源 | 纠正：正文是叙事证据，账本是可纠错派生层 | 提取会错；事件流不能消除漏提、误提和投影滞后 |
| 机器校验提取证据发生在提取前 | 纠正顺序 | 提取前只能验证正文/版本/资格；提取后才能检查提取证据 |
| 四个提取员、22名成员固定编制 | 调整为职责与能力合同 | 固定席位增加调用与跨分片一致性成本，不能保证准确 |
| 高影响事实争议仍永不阻断 | 纠正为只暂停依赖它的任务 | 死亡/持有/时间等关键事实不明继续写会放大错误 |
| 超时立刻换模型 | 纠正为先区分明确失败和远端结果未知 | 超时不等于没有生成或没有收费 |
| 修改≤10%且轻量事实检查通过后免重结算 | 保留等价修订快路径，取消比例门槛并补证据映射 | V9已含语义检查；仍需核验其准确性，以及旧证据对新文本是否有效。比例本身不证明事实不变 |
| 双键取最近状态就解决倒叙 | 扩展到场景时间、叙述可知范围、人物认知与版本 | 一个章节内可同时有现在/回忆，时间点也未必可全序排列 |
| 修缮后沿用原结算无新关联 | 改为证据映射验证和新派生版本 | 原段落位置可能改变；旧引用不得装成新正文证据 |
| 未登记角色自动判过场、事件后退场 | 不采用 | 新角色可以合法产生，角色重要性与离场必须由内容支持 |
| 每章3000字、每场景1—2段、前三章固定职责 | 改为书级偏好与可选模板 | 不能用固定篇幅和节拍限制所有题材 |
| 主笔上下文预算必须≥审查者 | 不采用大小比较 | 审查可能需要完整正文；任务资料完整性比相对大小重要 |
| 函数调用不支持时透明模拟 | 改为显式能力降级或换适配方案 | 不能把模型输出文本当已经执行的工具调用 |
| 换模型不动提示或代码 | 改为兼容测试、灰度和版本冻结 | Schema、参数、拒绝和工具行为都可能不同 |
| 强制全系统事件溯源、八账本、MinIO合规锁 | 不照搬 | 增加不必要组件和删除/恢复困难；不可变正文可先在同一数据库事务实现 |
| 所有迁移有down即可回退 | 不采用 | 新数据写入后逆向迁移可能丢失数据；使用扩展—切换—收缩 |
| 邮箱必然不合规、手机号验证码作为实名基础 | 不直接采纳其合规结论 | 需按业务、适用法规与实际核验核定，第51章列核查工作 |
| 真实模型成本可用mock书压测证明 | 拆为确定性故障样本与真实模型测量 | 模拟返回测不出真实模型消耗、准确率和文学表现 |
| 每批三核心模块强制全测、用户亲自逐项验收 | 不恢复 | 按风险测试，开发者承担验证责任，用户体验反馈补充证据 |

# 二、产品与创作设计

## 6. 产品定位与日常体验

### 6.1 服务对象

重点服务希望持续写长篇小说的独立作者：有构思但难以铺成长篇、已经写作但管理连续性困难、希望AI承担规划与初稿的人。支持网文、幻想、现实、悬疑、历史、言情等差异，不把“升级打怪”设为通用世界模型。

核心日常：打开正在写的书，读当前章，补充想法或修改，保存/采用后继续。作者不需要操作记忆账本、选择检索算法、分配结算员。

### 6.2 首期商业目标

- 能稳定完成从开书到多章连续写作、编辑、保存、回看和导出。
- 作者知道哪些是草稿、哪些已接受、哪些状态仍在更新。
- 出错后保留输入和成果，能从明确位置继续。
- 关键人物、资源、时间、承诺与故事方向有来源可查。
- 在公开支持的负载和模型范围内，有成功率、时延、成本和质量证据。

首期不承诺无限自动连载、全自动出版、万人并发、所有体裁、多人实时协同或自动生成爆款。剧本能力在正式规划前不作为可用入口宣传。

## 7. 共创方式与授权

### 7.1 展示深度和执行权限分开

“简洁/展开专业细节”只控制显示内容，切换不启动任务、不收费、不改变正式数据。“手动/协作/托管”控制执行授权，不能混为一个模式开关。

| 执行方式 | AI做什么 | 正式采用方式 |
| --- | --- | --- |
| 手动 | 按作者主动请求答疑、提供候选 | 作者明确保存或采用 |
| 协作（推荐默认） | 自动补齐完成下一步必需的内部工作，生成候选 | 关键方向与正文由作者采用；可以与“继续”合并一次操作 |
| 有界托管 | 在约定章节/时间/预算范围内生成、审查并按授权采用 | 保存自动采用回执，关联明确托管授权；不能标成作者亲自逐章确认 |

### 7.2 托管授权内容

授权必须包含书籍、分支、起始版本、任务范围、最多章节、用量上限、允许自动采用哪些类型、停止条件、到期时间。书级习惯偏好不等于永久无限授权。作者取消后禁止开始新调用，已经发出的远端调用按第39章处理。

托管默认在关键事实冲突、结果未知、预算不足、权限失效、必需能力不可用时暂停相关流水线。普通语言润色建议不阻断。开始前用大白话显示“本次最多继续X章、用量不超过Y”，不是让作者配置任务引擎。

### 7.3 作者意见

保存原话、对象范围、版本、强度与生效时间。推荐交互为“请按这个改”“尽量照顾”“仅作灵感”“先讨论”，明确讨论不落正式数据。输入默认不能悄悄降为“可忽略灵感”；明确要求按要求处理，语义含糊时Agent给出理解供就地纠正。

与已接受正文冲突时提供“这是要改历史，还是只改未来”的具体差异说明。不得一边声称遵守一边继续采用冲突事实，也不得宣布作者永远不能改变自己作品。

## 8. 创作对象与职责总图

```text
作品意图、题材与世界资料
        ↓
全书蓝图：长期承诺、人物弧线、阶段方向、结局开放度
        ↓
卷设计：完整阶段故事、跨单元因果、关系与资源布局、伏笔安排
        ↓
故事单元（链）：近期局部冲突与人物选择，承接并展开卷设计
        ↓
章计划 → 正文候选 → 审查/作者编辑 → 接受版本
                                            ↓
                                 事实提取、复核、投影
                                            ↓
                           校准未来计划与下一章所需资料

时光机：读取上述计划和实际的总览，不另存一套剧情事实
```

### 8.1 基本对象

| 对象 | 核心责任 | 不应承担 |
| --- | --- | --- |
| 作品资料 | 作者意图、题材、目标读者、偏好与硬约束 | 预写每章内容 |
| 世界设定 | 规则、社会与空间边界、未发生人物档案 | 把预计变化写成已发生 |
| 全书蓝图 | 跨卷故事意义、长期变化、主要线索与承诺 | 开书时详写数百章 |
| 卷设计 | 当前阶段完整设计与单元安排 | 只列链名和一句方向 |
| 链/故事单元 | 当前局部故事的进入、展开、变化和退出 | 重建全书规则、重新决定所有主角 |
| 章计划 | 下一段阅读的场景、视角、行动与承接 | 规定每句话、每段长度和强制爽点 |
| 正文 | 作者可读、可编辑的文学文本 | 携带工程协议或流水线说明 |
| 派生记忆 | 以正文证据说明发生与未知 | 自行修改正文或代替作者决定 |

事件/场景是链与章之间的可关联设计素材，默认不增加必经页面和全套确认流程。一个事件可跨多章，一章可覆盖多个事件；允许过渡、氛围与关系章节。

## 9. 书架、开书与第一轮准备

**当前已确认的迁移范围（第120—126批）**：团队设计、自己设计、资料、设定、取名沿用现有功能和UI，只做已授权的成员头像选择与状态文案精简。以下扩展体验仍是候选规格，不能以此重写已经跑通的功能。按用户最新要求，当前由主代理直接实施，不再默认委派GPT-5.5。

原开书引擎和提示编译器以独立副本接入新后端；数据库适配保存作者原话、冻结成员/提示/参数、模型可见结果、候选来源和阶段检查点。模型解析成功不等于候选已提交：候选与下一阶段必须同事务落库；提交前中断恢复已有回执，不能再次调用。结果未知时保留预留并等待可信回执，不盲重发。作者确认/修订/建书继续遵守原候选版本、独立审查和作者决定约束，未完成前不切换生产入口。

**确认建书（第127批）**：确认复用原严格校验和作者可见字段比较，不能通过规范化丢弃作者改稿来绕过复审。采用最新已审候选后，AI来源单独保存原话、候选/审查引用、规范资料及确认指纹，书籍/资料第一版/空目录/审计一起提交；失败全部回滚，同一任务只建立一本书。资料后续编辑形成新版本，不覆盖原话和采用来源。确认不产生新的模型调用或扣量；待作者决定及已修改未复审内容仍不能直接正式建书。

### 9.1 书架

支持新建、继续、搜索、排序、归档与恢复，展示最新正文位置和真实任务状态。选择书后恢复该作者最近阅读位置，跨设备读取服务器已保存位置。书籍不存在或无权访问只给安全提示，不泄漏存在性或他人标题。

封面、书名、状态、字数都是投影；缺封面不阻断。归档书不能新建创作任务，但仍能阅读和导出。已有在途任务归档前说明处置，默认先请求停止后归档，不静默丢结果。

### 9.2 开书输入

R208已实现并发布：不增加作者初始必填问题。候选复用positioning.coreAppeal作为核心卖点，新增positioning.readingTone作为阅读味道；正式blueprint保存两项，信息→资料可看可改。原styleIntent、创意偏向与历史版本保留，缺失不伪造，清空不回填。旧资料任务使用原版提示，新卡使用card-6。105项相关工程测试及手机编辑保存刷新通过；三国/悬疑合成样例完整解析通过，日常样例目录外标签问题仍待修。长期期待留时光机，题材库另批；详见[本批合同](../coauthoring-v7/docs/worklists/OPENING-APPEAL-208.md)。

提供两个清楚入口：“带着想法开书”“让AI提议一个故事”。后者允许零创作输入，但必须明确它会产生推荐方向，不能把系统猜想标为作者原始意图。书名、简介、题材、目标篇幅和参考材料可选填；不强迫新手先填世界百科。

保留“自己填写并建立作品”的辅助入口，不调用模型也能建书、编辑正文；后续作者可按需让AI补充设计。模型不可用或会员额度不足不应挡住合法的手工保存。

草稿自动保存，分账号隔离。服务端保存成功前标明本机草稿，清除浏览器数据可能丢失未同步内容；恢复会话后合并需比较版本，不直接覆盖。

### 9.3 自动准备流程

1. 保存想法或明确的自由提议请求，建立任务及用量授权。
2. 生成一个可读故事提案：主角、困境、核心吸引力、发展方向、风格和重要限制。
3. 作者可直接采用、口头调整或主动再看一种方案；默认不强迫多方案比较。
4. 采用方向后，自动准备必要设定、全书蓝图、第一卷设计、首个故事单元与近期章计划。
5. 在总览展示准备结果与关键未定事项，主操作是“写第一章”；内部步骤不逐项等待点击。

“一键”是一次授权驱动多个持久化任务，不是一个模型输出整棵巨树。需要读取上一步已完成输出才能生成下一步；彼此独立的设定项可并行。目录、证据、方案每步保存，失败只补失败步骤。

### 9.4 开书验收

零想法和长想法两条路径均能到可写第一章；刷新/离开后恢复同一任务；采用方向后不出现另一套未选方向；中途改目标只失效相关未采用候选；费用不足保留输入并停止新调用；不为生成封面等待全部开书完成。

## 10. 设定、世界与作品意图

### 10.1 按书需要建立设定

Agent从题材和作者目标推荐最小必要设定。现实题材不必有境界和金手指；无战斗内容不要求技能树；社会关系和生活规则同样可成为核心设定。

设定项包含名称、正文描述、适用范围、硬限制、允许例外、来源、作者批注、版本、是否已用于正文。数值规则和资源上限仅在作品确实需要时结构化。

### 10.2 设定状态

候选、已采用、被新版本替代、归档分开。自动准备的设定在开书采用或明确托管授权下转为活动规划依据；它们仍不是“故事中已经发生的事件”。作者原话单独保存，不能只留AI摘要。

### 10.3 修改设定

未被使用的设定可直接形成新活动版本。被正文使用后，系统展示影响：仅改变未来计划、故事内规则从某时发生变化、修订既有叙事版本。不能简单把“从当前章开始”解释成历史章节永远豁免；第27章处理时间与叙述范围。

### 10.4 验收

同一设定修订后旧任务仍可追溯旧版本；未来新任务读取适用新版本；已经接受正文不被自动替换。自定义设定与默认目录同等支持；目录服务失败时可读旧设定并继续不依赖该服务的任务。

### 10.5 第139批设定交付与交互

本批已获开发授权：作者从常显头像中选一位成员，或由系统自动安排。该成员统筹本轮设定，按小组顺序完成；已完成草案和作者当前修改供后续条目参考，明确标为待确认，不能冒充正式事实。遇到已知可恢复失败自动转交，成功接手者负责后续小组；每组最多尝试三位成员，每位至多一次针对格式/篇幅的修订。结果未知先核对原调用，权限、额度或版本冲突不盲重发。

新增AI设定通常150～300字，复杂内容可至600字；保留条件、例外、限制、代价、数值，减少重复解释和剧情例子。检索摘要不超过100字，事实最多12条且合计不超过500字。交付前程序检查；超限交回成员精简，不直接截断保存。已有作者原文和已确认长设定不自动缩写。上下文超过现行安全预算时，成员选择完整相关事实，重新检查预算后再生成；原文与版本可追溯。

设计完成自动交给未参与本轮设计模型的主编统一核对；审查只返回明确冲突及必要修订，不重复抄写全部事实账本。系统复用未修改条目的已保存事实，修改条目使用本次有效修订事实，不能借审查扩写新条目。作者仍负责正式采用。设计、审查、已保存、未完成应来自真实任务状态；参与成员常显，内容采用紧凑阅读与直接操作，正在执行时避免让作者发起冲突修改。换成员和重发保留已完成条目，仅接续未完成部分。

此批复用既有任务、版本与账本适配器，并扩展独立设定运行包；不是整站数据库切换。开发与上线证据见[第139批合同](../coauthoring-v7/docs/worklists/SETTING-EXPERIENCE-20260907-139.md)；一次真实样例不代表所有模型或所有题材长期质量均已验证。

## 11. 全书蓝图

### 11.1 必须提供的设计能力

全书蓝图不能只是一句锚点，但也不应成为完整剧透脚本。它应描述：作品核心问题、主角长期欲望与变化、主要对立力量、重要关系的长期张力、世界扩展方式、主要故事线、读者承诺、阶段目标、结局开放程度、不可触犯约束。

卷级方向按当前已知程度记录。远期可以是开放假设，下一卷较清楚、当前卷最详细。结局可明确、多个可能或暂不决定；空值不强行补一个终局。

### 11.2 蓝图字段

| 内容 | 表达 | 更新时机 |
| --- | --- | --- |
| 核心吸引力 | 一段可读描述，加可选简短摘要 | 作者改方向或实际发展显著变化 |
| 主角长期弧线 | 初始状态、欲望/盲点、可能转变、开放项 | 卷结束或关键选择后 |
| 主要线索 | 目标、读者承诺、阶段参与、优先级 | 新线显现、暂停、兑现 |
| 卷方向 | 该阶段解决与打开的问题、变化、衔接 | 当前卷完成或作者调整 |
| 结局范围 | 明确/开放/备选及作者限制 | 作者决定或故事发展支持 |
| 创意开放区 | AI可自主创造的范围 | 作者更新偏好 |

### 11.3 动态校准

正文偏离原计划时，先判断新发展是否成立、是否符合作者意图，不能默认把故事拉回旧路线。AI提出“保留新发展并调整后续”或“修订相关章节”的可读方案，只有活动版本被采用后影响后续。

全书蓝图修订不应把已完成章节标记成“未完成”；时光机继续显示真实成果。验收以跨卷承接和长期承诺的明确去向为主，不能仅测试蓝图JSON字段齐全。

### 11.4 卷结束与全书完结

完成一卷前，按接受正文核对本卷关键问题、人物变化、留下的承诺与下一卷入口；未兑现不一律算错误，可以是作者选择保留的悬念，但不能默默遗忘。卷实际总结与下一卷计划分开保存。

全书完结由作者明确选择，AI给出未解线索、主要人物与结局承诺的复盘建议；不要求所有开放结局变成全部解答。完结停止自动续写排程，保留修改、回看、导出和重新开启创作入口。完结、归档、会员到期是三个不同状态。

## 12. 卷：承担完整的阶段设计

### 12.1 卷必须比链更全局

本卷设计回答：为什么需要这一卷；主角从什么处境到什么处境；主要冲突如何产生、发展和改变；对手与配角各自想做什么；多条线怎样交织；读者期待怎样形成和兑现；本卷结束后为何需要下一卷。

卷不只是若干链的排序列表。卷设计先成立，链才展开局部情节。人物核心设计可以在开书/全书/卷层形成，不能都等进入链时才第一次决定。

### 12.2 卷方案结构

| 字段组 | 具体内容 | 边界 |
| --- | --- | --- |
| 起点与终点 | 真实起始状态、计划终点、变化意义 | 起点有已接受正文或明确初始设定来源 |
| 核心故事 | 主问题、矛盾、行动、重大选择、代价、阶段结果 | 允许开放结尾，不要求全部矛盾解决 |
| 人物布局 | 主角弧线、对手目标、关键配角动机、关系转折 | 角色不是只有“阻力/工具”的功能标签 |
| 故事线配置 | 哪条线主导、交织、暂缓，何处发生交叉 | 暂缓有理由，不按固定章数推进所有线 |
| 资源与空间 | 关键资源变化、地点转移、约束与代价 | 不提前作为实际物品归属入账 |
| 信息布局 | 谁知道什么、读者何时知道、伏笔与答案 | 避免为设计方便提前泄谜 |
| 单元安排 | 每个单元的作用、入口、预期出口、相互影响 | 远期保持粗粒度，近期才细化 |
| 阅读节奏 | 紧张与休息、情绪变化、重复风险 | 自然描述，不固定“每三章爽一次” |
| 篇幅预算 | 目标区间、可伸缩部分、超出后的处理 | 字数是约束或偏好，不能改写已写正文凑数 |
| 接续关系 | 承接上卷结果、向下卷交出的新处境 | 不等同“上一链结果文本必须等于下一链起因” |

### 12.3 设计与修订流程

读取全书蓝图和最新实际→形成卷草案→进行一次针对全局完整性的审查→在需要时局部修订→作者采用。一个方案通常足够；需要比较时才增加独立方案。审查关注因果、人物主动性、长线承诺和可展开性，不要求每个字段都有固定数量项目。

卷内写作过程中，维护建议进入卷的未来部分；已采用且已写出的部分作为历史保留。改变后续单元顺序需要检查依赖，例如某角色尚未获得的知识不能提前使用。

### 12.4 验收实例

例如“边军覆灭到主角进入新组织”的一卷，必须解释覆灭后人物目标、逃亡/调查/结盟如何互相影响、加入组织的选择与代价。不能仅给出“逃亡链、调查链、入宗链”三个名字即算完成。

## 13. 链：近期故事单元

### 13.1 定义与推荐命名

新内部对象建议用`arc`表示，作者端显示“故事单元”，与当前`chain`建立兼容映射，旧名称“链”保留说明与导航兼容。最终名称可经原型评审调整，不改变数据语义。

链是一段能被理解为局部故事的组织单元，长短取决于题材和节奏。它承接卷给定的责任，设计当前局部矛盾、行动、选择和后果；不要求固定5—15章，不强制每链不可逆升级或至少一项资源收获。

### 13.2 精简合同

必需：所属卷版本、承接的真实状态、这一单元想完成什么、核心局部问题、相关人物及动机、预期变化或保留的问题、结束条件与下一步。可选：主要事件顺序、节奏提示、资源限制、伏笔安排、预计篇幅。

沿用上层人物/世界/长期目标的引用，不复制完整字段。若需要新增重要角色或改变卷目标，形成相应上层候选变更并说明影响，不在链内悄悄改全书。

### 13.3 事件与章的关系

事件记录“发生什么变化与为什么”，章记录“读者如何经历”。使用多对多关联和顺序，场景可承接同一事件的不同阶段。计划事件尚未发生不写实际记录；没有推进点的章节仍可承担休息、氛围、人物关系或必要过渡。

### 13.4 验收

链输入应比卷完整方案更聚焦，不能机械附加上层全文。链内人物与设定有引用，新内容有设计身份；章节安排可自然增减；局部修改不会迫使重做全卷；跨链承接由最新正文和卷计划共同约束。

## 14. 章计划、场景与正文创作

### 14.1 近期详细、远期粗略

默认只细化下一章，必要时准备后续少量章计划；数量由用户选择和实际任务需要决定。远期保留目标与依赖，避免第一章变化导致数十份详细章纲报废。

章计划包含本章阅读目标、视角、场景与时间范围、起始实际状态、人物行动和选择、阻力、信息/情绪变化、预期结尾、与下章衔接、作者特别要求。文学描述按适用性留空或简化；目标、对象身份、来源版本与必要承接必须明确，不能为了通过格式检查虚填内容。

### 14.2 写作任务

主笔读取章计划、相关人物和世界事实、近邻正文、重要长期承诺、当前声音/风格示例与作者意见。不能只给上一章摘要而省掉必要的对白和叙事衔接。首次出场允许创造未规划的合理细节；禁止伪造已有经历、关系、能力和规则。

文字目标优先遵守本书设置；默认值仅是起点，超短/超长由完成度与预算判断。正文以独立文本产物保存，状态信息和审查报告与正文分开。流式文字标为未完成草稿，断流不自动定稿。

### 14.3 每章主循环

准备可信资料→生成正文草稿→连续性与文学/体验检查→必要局部修订→作者编辑或采用→保存精确接受版本→自动更新事实→准备下一章。正文阅读与后续投影更新可并行；依赖尚未核实关键事实的下一章要等待。

### 14.4 特殊章节

开篇按题材和本书吸引力设计，不固定前三章公式。回忆、番外、间章、书信、不同视角章节须明确叙述位置和与主线的关系。允许一章多个场景时间；只读未来章节不得让角色在过去提前知情。

### 14.5 验收

实际阅读检查开头承接、人物声音、场景行动和结尾效果；换成员仍得到同一事实基线；手动修改被保留；正文不混入JSON、提示词或后台状态；正常失败可继续审查已保存草稿，不能总从生成第一字重新收费。

### 第185批：信息短卡与分层方法（历史实现；方法范围由186批覆盖）

先完成两项基础功能，不重构时光机结果页或增加作者节拍选择。全书方向准备时，资料编辑按照共享六栏模板整理已确认开书资料与设定：创作要求、主角与起点、核心卖点、世界背景、影响全书的规则、作者指定内容。原文不改；每批最多9000字符，分批提取、两两合并，再按原页核对姓名/能力条件/关键规则/作者要求，输出完整短卡。目标约1800字符、正文最多3200字符，每次请求最多18000字符且输出预留4000Token；这只是本批工作预算，不是注意力或准确性保证。结构失败最多补交一次，成功阶段缓存；作者继续时只补未完成部分。全书短卡按owner/book/来源ID、版本、哈希及模板版本复用；新来源产生新卡，原版本仍保留。短卡只做派生阅读视图，规划原始快照和正文实际仍是权威。当前接全书方向路线准备，卷/链/章不复制此卡，分层重构后再明确各层短卡。

已完成短卡直接供给设计，不再额外调用成员重新筛选同一份资料。系统生成任务说明并绑定方法版本，资料成员负责语义整理，设计成员负责新故事。资料正文与方法指令分开；完整短卡、来源映射存储于可重建投影表，前端只显示设计所需状态。模板规则在后台只读展示，随代码发布；本批不宣称模板在线编辑、整书长期质量或新时光机页面已经完成。

### 第140批已确认：节奏资产与分层调用

后台新增“节奏资产”（RB-51.1），四类为全书组织、阶段推进、节奏模式、事件配方。完整方法理论保留查阅，运行时按当前层只供给少量候选短卡；成员可组合、忽略或原创，不能以每层强制宏观结构或固定章数替代文学设计。允许跨层复用方法，但具体行动、因果、代价和兑现需服务本书。

### 15.1 故事线

每条线保存作品内独立ID、名称、核心问题、涉及人物、读者承诺、当前进展证据、未来计划和状态。支持构思、活动、暂缓、完成、放弃；“规划为完成”与“正文实际完成”分开。V9列出的25类线可作参考标签，允许自定义，不作为所有作品固定清单。

Agent发现潜在新线先给候选和证据；不能因为矛盾连续出现三次就程序自动宣布成立。角色争执也不必成为一条长期故事线。

### 15.2 人物

稳定身份ID与姓名分离，支持同名、别名、化名、称谓、身份揭示。核心角色可以有欲望、恐惧、矛盾、价值观、声音、关系和弧线；配角按实际需要展开，不强迫完整问卷。

“人设/预计发展”“正文实际状态”“某人的看法”“AI推断”分区保存。物品、技能、势力归属、宠物是否独立角色按作品内容建模，不强制同一事物重复写两套权威状态。

### 15.3 方法资产

保留已有有效方法库、题材资料与编辑部形象资产。每项记录定义、适用条件、局限、任务用法、来源和版本。可选可不用；方法选择由Agent按任务语义完成，系统只负责索引、权限、版本和预算。

不把整套教材塞进每个任务；适用的简短任务用法可以预先编写，也可以由资料Agent在任务中转换，保留来源。若只是已确认精确片段的读取，不必多调用一个Agent“整理”一遍。复用资料包必须通过版本与适用范围校验。

### 15.4 验收

选择不同方法应产生实质不同的行动或人物选择，而非换标题。角色不因未列入章纲而自动退场；改名不改变身份ID；故事线和方法不会强迫正文重复同一种节奏。

# 三、作者工作台

## 16. 信息架构与视觉保留

### 16.1 推荐入口

书外：书架、任务、个人中心。书内主入口：写作、时光机、资料；团队、作品信息、导出和设置按使用频率放到就近入口。卷、链、章保留为创作对象和直接定位，不必继续占用八个同级导航。

这只是推荐信息架构，实施前用现有视觉做关键页面原型验证。不能把“减少导航”变成隐藏必要能力，所有旧有效功能都应在第61章有去向。

### 16.2 视觉保留合同

保留当前品牌、主色体系、圆角与字体气质、编辑部人物形象和舒适阅读方向。实施时从现有CSS和授权资产提取设计变量，不凭描述重画一套新风格。先保存同视口基线截图，再比较重构前后；本批未做截图，因此不声称视觉已通过。

组件优先统一：页面标题、正文阅读区、编辑区、主要动作区、成员状态、候选比较、就地错误、空状态和历史版本。减少多重边框、同义标题与重复说明，但不删作者判断必须的信息。

## 17. 写作页完整状态与操作

### 17.1 页面结构

顶部显示当前书、卷/故事单元/章节位置与保存状态。中部以正文为主，作者意见、章计划、审查意见按需展开。底部提供当前状态对应的主要动作；侧边或二级区提供版本、资料、成员与导出。

手机不把桌面侧栏压成狭窄文本；采用切换内容区或页面内展开。进入资料再返回必须保留光标、滚动位置和未提交输入。

### 17.2 状态表

| 状态 | 显示 | 主要动作 | 必须保留 |
| --- | --- | --- | --- |
| 无章计划 | 当前目标与准备说明 | 准备并写这一章 | 作者补充与上游位置 |
| 已排队 | 已安排，尚未开始；有依据才显示预计等待 | 停止等待 | 相同任务入口 |
| 生成中 | 真实成员与阶段；流式稿清楚标未完成 | 停止后续处理 | 已落盘草稿 |
| 审查中 | 正文可读，检查尚未完成 | 查看正文 | 草稿和作者编辑分支 |
| 草稿就绪 | 检查摘要、重要问题、保存状态 | 采用本章并继续 | 全文与报告 |
| 作者正在编辑 | 已同步/本机待同步，撤销可用 | 保存修改 | 编辑基线与变更 |
| 正文已接受，事实更新中 | 正文已保存，故事资料正在更新 | 阅读/修改；依赖就绪后继续 | 接受回执 |
| 关键事实待处理 | 说明哪一项影响下一章 | 按推荐修复/调整 | 正文和未冲突事实 |
| 明确失败 | 对不起，这次没有完成；保留什么、能怎么继续 | 恢复原任务 | 成功步骤和作者原话 |
| 结果未知 | 已暂缓后续调用，正在核对结果 | 查看状态/停止等待 | 调用标识与预算占用状态 |
| 已完成 | 当前正式正文和下一步 | 写下一章 | 历史和阅读位置 |

“写下一章”若兼有采用本章含义，按钮首次及相关状态必须明确为“采用本章并写下一章”。不能让作者误以为只是生成下一份候选。

### 17.3 保存与并发编辑

服务端草稿是跨设备恢复来源，本地草稿只是未同步保护。保存携带基线版本；另一设备已保存时展示差异和合并选项，不能最后一次写入覆盖前一设备。

AI生成期间作者可以另开编辑分支或修改独立意见，不可同时覆写AI正在追加的正文缓冲区。中文输入法组合输入完成后再触发保存/快捷键；撤销栈不被后台刷新清空。

### 17.4 验收

切后台、断网、登录过期、刷新、键盘弹起、双设备冲突、生成与编辑并发均不丢已确认保存内容。未同步状态清楚，不能把本地保存显示成云端保存。所有错误状态至少有一个真实可执行恢复动作。

## 18. 时光机：计划与实际的全书总览

### 18.1 页面责任

时光机回答三件事：写到了哪里、故事发生了什么、后面准备怎样写。显示实际完成章数与字数、当前卷/单元、计划与实际差异、未来调整建议和可继续位置。

不新建独立“时光机剧情”，不让时光机与卷页面分别维护同一套卷设计。图形只是投影，任一节点的编辑跳到同一对象版本；列表模式提供同等信息，手机不必拖拽大图才能使用。

### 18.2 计划/实际比较

计划显示预期，实际显示接受正文证据。未写节点明确为未来；候选节点明确待采用；旧方案可以回看但默认不参与当前进度。差异由Agent解释对作品的影响，不靠百分比自动认定偏离越多越差。

关键操作：继续当前章节、打开卷设计、查看实际来源、调整后续、比较旧蓝图。没有正文时仍可以看规划；没有新规划时仍可以看实际。某个投影加载失败不会清空其余数据。

### 18.3 验收

未来规划删除不会减少已写章数；旧任务失败不盖住新正式成果；重新规划只作用于选定未来范围；从时光机进入写作后定位到同一书、分支、卷、单元和章。

## 19. 资料库、人物库与关系图

### 19.1 资料类型

包含作品资料、设定、人物、关系、地点/势力、物品、时间线、故事线、伏笔/开放问题、正文目录、作者参考材料。首期优先可查的列表与详情，复杂关系图可后置，但人物和事实详情不能一起后置。

资料页区分“作者设定”“正文已发生”“计划中”“尚不确定”。允许作者增加笔记与请求修正，笔记不自动改叙事实际。每条关键事实可跳转原文和对应版本。

### 19.2 搜索

按名称/别名直达对象，按问题搜索相关正文与事实。回答说明来源和未知，不把另一书的近似名称召回给当前书。筛选范围可选当前活动版本或指定历史版本；历史结果醒目标明用途。

资料页刷新时保留正在查看对象；关联片段按需加载，不默认下载整本书。索引未完成显示覆盖范围，不能把“未检索到”解释为“从未发生”。

### 19.3 关系图

节点与边来自同一资料对象，支持按当前阶段/选中人物展开。关系具有时间、证据与视角，例如“甲认为乙是盟友”不等于客观同盟。计划关系使用不同显示形式。

大量节点采用分页/局部展开，并提供列表替代。拖动仅改变布局，不改变故事关系；点击“修改关系”进入候选修订，不直接改实际状态。

### 19.4 验收

同名人物不串联，别名可找到同一身份；关系断裂能定位正文依据；人物死亡后历史页仍可查其生前状态；记忆更新失败时显示旧数据时点与恢复状态，不能展示假“最新”。

### 19.5 已有作品与参考材料导入

新增导入能力建议在R4的基础资料功能完成后交付，首期先支持UTF-8 TXT/Markdown，再按需要适配其他格式。导入先解析与预览：章节边界、标题、正文、编码问题、重复内容、目标书与来源用途；作者确认后才创建对应版本，不自动覆盖已有章节。

“这是我的已写正文”“作为设定”“仅供参考”三种用途分开。只有作者确认作为本书正文的内容进入接受/事实更新路径；参考材料不能直接变成当前书实际。导入未完成时书籍状态明确，分批校验与后台更新有检查点、进度、取消和用量预估。图片/OCR或无法可靠解析的内容标待处理，不把乱码交给模型当正式源。

导入校验包含旧书重复导入、同名章节、长文件、章节识别错误与中途失败，保留原文件及解析版本直到确认完成。该能力是本稿新增建议，不代表当前已实现。

## 20. 任务、通知与问题处理

### 20.1 统一任务中心

覆盖开书、设定、规划、正文、审查、事实更新、命名、封面、导入导出。按进行中、需要处理、已完成、历史筛选；内部子任务默认合并展示为一次用户操作，可展开成员和步骤。

每项显示书、目标、真实状态、已耗时、保存成果、下一步。历史任务不能与当前有效任务重复计入待办。归档任务只是隐藏，不删除审计或撤销正文。

### 20.2 通知策略

完成/失败/需要决定按用户通知偏好呈现；一项父任务不因十个子步骤完成发十条通知。后台自动修复成功无需打扰。结果未知、额度待核对等不能伪装成功，也不频繁重复推送。

作者可在问题卡上表达自己的决定，不限选择按钮；推荐方案需有影响说明。批量采用只能包含互不冲突且仍基于当前版本的建议；过期建议不能被“全部采用”误提交。

### 20.3 验收

页面与任务中心同状态；离开后能回到原结果；失败不显示一直工作；通知点击定位准确；问题已解决后待办消失但审计仍在。

## 21. 命名、书名、封面与导出

### 21.1 命名和封面

保留当前书名、封面生成与采用能力。人物/地点/势力/物品命名读取本书语言风格、已有名称、禁用项；输出候选与解释，候选不改实体ID。

改已出现姓名先预览：别名变更、未来称呼、历史文字替换三种不同动作。禁止整书字符串替换造成同名人物或普通词误改；语义识别由Agent处理，实际文本编辑绑定版本。

封面生成独立任务，失败不挡正文；采用只改作品封面指针，保留历史。素材来源、授权、模型生成标识和导出授权单独记录，不能因平台生成就承诺适合所有商业出版用途。

### 21.2 导出

首期支持TXT、Markdown，HTML阅读版与DOCX作为后续扩展，不假设已经实现。支持单章、单元、卷和全书；默认导出活动接受正文，草稿导出须明确标记，规划资料单独选择，不混入小说正文。

创建导出任务时冻结章节清单、顺序和各正文版本；生成过程中发生编辑不改变这一导出。内容包含可选卷标题、章节标题、正文、适用标识；不包含任务ID、提示词、审查报告和私密管理信息。

权限校验在任务创建、生成和下载均执行。下载地址短期有效，归档仍可导出；无效会话不能凭旧链接下载。文件名与HTML内容安全转义，超大导出异步处理。

### 21.3 验收

中文、罕见字、换行、空章节、重名卷、长标题顺序正确；逐章正文与冻结版本内容一致，完整导出另记文件哈希；中途改稿后旧导出不变，新导出使用新版本；账号间无法下载彼此文件。标识实现按第51章，不假设TXT自带标准文件元数据容器。

## 22. 移动端、可访问性与完整交互验收

手机优先，桌面自然扩展。关键验证包括约390px手机视口、窄屏、平板与桌面；这些是测试起点而非宣称覆盖所有设备。

- 输入字号、触控目标、焦点与对比满足可读可操作要求；关键按钮不被键盘、安全区和浏览器工具栏遮挡。
- 长正文按章节/片段加载；导航和操作不依赖悬停。正文可选中、复制，编辑撤销和快捷键可用。
- 屏幕阅读器能理解阶段变化；加载和错误使用适当语义，焦点不会被轮询抢走。
- 必须展示的信息不只靠红绿颜色区分。减少动画模式下保留状态解释。
- 弹层仅用于确有必要的选择/确认；普通修改和错误优先在当前页面完成。
- 断网时仍可编辑已加载草稿，明确离线；AI任务状态不能被本地计时器推成成功。

验收记录设备、视口、浏览器、任务版本和截图/操作证据。组件测试不能代替真浏览器检查；美观与信息清楚也需要阅读判断。

# 四、正文与长期记忆

## 23. 权威来源与版本体系

### 23.1 不用一条简单排序覆盖所有问题

| 问题 | 应使用的权威依据 |
| --- | --- |
| 作者希望以后如何发展 | 当前适用的作者指令、已采用规划 |
| 故事实际上写出了什么 | 该叙事版本内作者接受的正文 |
| 某角色当前状态 | 适用正文证据支持的事实投影，必要时回查全文 |
| 这次任务当时看了什么 | 冻结ContextPack、来源版本与模型配置 |
| 作者是否采用 | 接受回执或有效托管授权下的自动采用回执 |
| 系统是否收费 | 使用与权益流水，不看UI显示或模型自报 |

作者意图与正文冲突时是“需要修订”的业务状态，不能通过把账本排在最高位禁止作者改书。派生事实与正文矛盾则先纠正派生层。

### 23.2 正文版本

正文对象ID稳定，文本版本只追加。正文内容、文本哈希、创建者/任务、父版本、创建时间不可原地覆盖。接受动作引用精确版本；当前接受指针通过并发比较更新。一个章节在一个活动分支上最多一个当前接受版本。

草稿每次服务端保存形成可恢复修订；可合并短间隔编辑为草稿检查点，但不得覆盖已接受版本。采用、撤销采用、归档属于独立动作/指针变化，不修改旧全文。旧审查报告只对旧版本有效。

### 23.3 托管的证据边界

有界托管自动采用需要记录授权ID、实际执行范围、审查结果和采用版本，显示“按你的托管设置采用”。没有授权的自动生成只保存候选；不能用“默认无异议”追认。

## 24. 事实记录、派生事件与查询视图

### 24.1 推荐数据模型

业务对象保存版本化正文、设定、规划与指令；派生事实使用追加记录及更正；投影保存可重建查询状态。只对确有追溯需要的数据采用事件记录，不把所有账号和配置操作改成全事件溯源。

事实记录至少含：范围、稳定实体、谓词/内容、值、事实类型、正文版本、证据定位、叙述位置、故事时间/场景、视角与确定性、提取/复核版本、替代记录引用。数字资源还要单位与变化语义；“持有”“拥有”“借用”不是同一谓词。

### 24.2 事实身份

区分客观叙事事件、角色认知/陈述、假设/梦境、推断和未来计划。小说中的一句“他死了”可能是传闻或误认，不能只做句子匹配就写入死亡事实。

关键状态可用结构化字段，但情绪、信任、欲望不能都压成分数。Agent提出自然语言判断和证据，系统验证来源、身份与结构，不用关键词替代文学语义。

### 24.3 单一事实，多种显示

一条关系变化有唯一事件ID，可同时投影到两个人物页、关系图、时间线。多个视图不是多份可独立编辑的权威账本。不强制“人物、关系、资源……”分别做八套写入系统。

### 24.4 重建边界

已验证事实事件+其来源版本集合+投影代码版本，可以重放查询视图。需要重新理解正文时是新的提取任务，不是保证每次AI都生成一样的记录。重建时不覆盖旧事实批次，比较后切活动投影。

系统必须能区分“投影落后”“源已变更”“事实有争议”，不能以架构上可重算宣称状态永远不会不一致。

## 25. 结算与事实更新流水线

“结算”在这里表示从接受正文提取实际变化，与用户算力结算不是一件事。作者端可称“更新故事资料”。

### 25.1 顺序与责任

| 步骤 | 系统/Agent职责 | 输出与失败处理 |
| --- | --- | --- |
| 0. 保存 | 系统事务保存接受回执、活动指针与outbox | 已保存正文不因后续失败回滚 |
| 1. 前置校验 | 系统核对范围、正文可读、哈希、上次投影水位、重复事件 | 无效事件拒绝，缺资源等待；此时不检查尚未提取的证据 |
| 2. 提取 | Agent读完整本章及必要上下文，提出变化和未知 | 输出候选事实与证据；默认一个有界任务，过大才按实体/场景分片 |
| 3. 结构与证据定位 | 系统校验Schema、正文版本、引用区间、实体引用与格式 | 不通过仅补交对应输出，不擅自改语义 |
| 4. 语义复核 | Agent核对证据支持、否定/推测/转让语义、时间与视角 | 通过、驳回或不确定；高影响类目必须核实 |
| 5. 覆盖复核 | 检查本章关键变化是否漏提，不只检查已提列表 | 有原文场景覆盖记录；漏项进入增补 |
| 6. 提交批次 | 系统保存已验证事件、未决事项和批次完成条件 | 同一来源/管线版本幂等提交 |
| 7. 更新投影 | 系统构建人物/资源/时间等视图，记录消费水位 | 失败可重放，正文不变 |
| 8. 更新规划 | Agent按实际结果提出未来变化建议 | 仍是规划候选，不能冒充过去已经发生 |
| 9. 呈现 | 显示完成、部分待核实、受影响的下一步 | 不以“记了12条”代替质量结论 |

### 25.2 分片与复核策略

默认不固定四个提取员；先测一个任务的完整性和耗时。超过预算时可按场景或实体分片，分片有共享实体目录、重叠证据和统一去重键；跨片关系必须复核，不能分别给同一物品写两个当前主人。

高影响包括死亡/生还、身份揭示、关键能力、物品权属、关系性质、关键线索兑现和时间因果。判定依据是本章和下游影响，不是只看类目名称；普通时间变化也可能是关键冲突。

低风险内容可在已验证策略下抽检，但AI自评分不等于校准过的概率。抽检比例、升级条件通过样本确定，不能直接沿用V9的10%/20%/50章当科学门槛。

### 25.3 不确定与漏提

证据不足保持未知；不能默认采信复核员，因为复核员也会错。高影响争议可做一次独立仲裁或请求作者解释；范围和预算有限。必须有覆盖检查，否则“每条提取都正确”仍可能漏掉最重要变化。

部分无关资料未完成时，不影响已保存正文与独立任务。下一章使用关键资源/人物状态未就绪时，暂停该依赖，提示“正文已保存，正在核实某项变化”。

### 25.4 事务和版本

事实批次引用精确正文版本与父状态水位；新版本提取完成前不能覆盖当前可靠投影。部分批次可以保存但不标整体完成；发布水位必须表示已核验覆盖范围。任务重试不重复创建同一事实事件或扣记同一内部业务用量。

## 26. 持续维护与下一章就绪

### 26.1 三种水位

正文接受水位：哪些章节已有接受版本。关键事实水位：哪些接受版本的下一章依赖已核实。辅助投影水位：Wiki、图谱、统计等处理到哪里。三者分别可见，不能一个`completed`掩盖后续未完成。

水位不仅存最大章节号，还须保存活动章节版本集合摘要；回改第5章不能因“已处理到第20章”被忽略。

### 26.2 继续规则

正常顺序创作默认等待上一章关键事实就绪再启动下一章生成；读取、手动写作、编辑其他独立内容不受影响。首期不默认采用轻量结算放行、完整结算无限追赶的双系统。

以后引入快速连写时，必须明确最大领先窗口、事实差异的停止和修订责任、候选状态及费用；没有验证就关闭。作者可手动写，但系统不能声称未核实状态已可靠。

### 26.3 维护调度

定稿事件立即入持久化队列，按书/分支依赖顺序处理；相关人物、伏笔、关系、资源及时增量更新，不累积到几十章才提取。卷末进行全局复盘，用于长期承诺和重复风险，不代替日常更新。

辅助维护失败触发后台告警和恢复；超出SLO显示落后范围。避免每次刷新重复触发模型；以来源版本、管线版本和步骤键防重。

## 27. 时间、视角与知识边界

### 27.1 至少四个不同维度

1. 叙述顺序：读者在第几章、第几个场景知道。
2. 故事时间：事件在故事世界何时发生，可是区间、相对先后或未知。
3. 知识归属：谁亲历、谁听说、谁误信、读者是否已知。
4. 版本分支：当前正文修订与设定适用的叙事版本。

系统记录数据库写入时间仅用于审计，不把它当故事时间。默认不把模糊时间强行换算成精确日期。

### 27.2 场景时间

一个章节允许多个场景时间。相对时间保存锚点与关系，例如“离城后第三天”；未能比较的两个时间不能武断排序。时间冲突或锚点被修订后，通过依赖关系重检，而不是对字符串做大小比较。

### 27.3 查询示例

第80章写主角童年回忆：查询童年适用身体/关系状态，同时保留第80章读者已经知道的事实范围与当前叙述者视角。第90章揭露的真相不能自动写进第80章读者认知；可有意伏笔但不得直接剧透。

第12章角色A收到传闻“B死亡”：可记录A相信此事，但不能把B客观生死自动改死。之后证实假死应更新相关认识，保留旧章传闻成立的上下文。

### 27.4 验收

顺叙、倒叙、插叙、同章多时间、平行视角、梦境、传闻和身份揭示都要有样本。失败必须指出无法判定的维度，不默认“承接上一章”掩盖输入缺失。

## 28. 修正事实与回改正文

### 28.1 四类修改分开

| 类型 | 实际动作 | 对旧版本和下游的处理 |
| --- | --- | --- |
| 记忆提错、正文正确 | 更正派生事实 | 原文不变，重建受影响投影，检查依赖候选 |
| 文本表达修缮 | 创建新正文版本，验证语义等价与证据映射 | 旧正文和结算保留，新版有新的映射/复用回执 |
| 改变已发生情节 | 创建修订候选与影响分析 | 作者接受前活动线不变；接受后相关后续候选失效，已接受正文不自动重写 |
| 试另一条故事路线 | 新建分支/书副本 | 来源共享只读或复制，写入隔离，主线不变 |

### 28.2 事实更正入口

资料卡“这里不对”、正文旁“纠正故事资料”都可进入。作者用大白话说明，例如“这把剑只是借给他”。Agent定位记录、解释建议更正和影响，系统在核对范围/版本后追加更正事件。无原文支持的新增说法保持作者修订意图，不能当原文证实。

旧事实记录不更新内容；“已被更正”由更正关系计算，避免一边说只追加一边UPDATE原事实。事实投影的缓存行可以更新，但它不是不可变证据。

### 28.3 修缮快路径

比较文本变化→判断是否影响事实/时间/身份/承诺→验证相关证据定位→创建新正文版本与派生关系。确定无语义变化且证据映射有效时可复用已核实事实内容，但仍创建绑定新文本版本的结算/映射记录，不能把旧版本引用冒称新版。

无法确认等价就走完整重提与审查；不以修改比例决定。全局改名需识别实体别名与引用关系，不能保证一律免重结算。

### 28.4 情节回改

先提供影响预览：被改章节、受影响人物/资源/时间、下游候选、已接受章节和估算用量。默认在修订分支处理；可以只保留到指定章节重新展开，但旧线仍可回看，不能把“截断重写”实现成永久删除。

已接受下游正文标记需要检查，不直接丢弃。范围由依赖分析与语义审查确定，不能声称字段依赖图自动发现所有文学影响。新活动线切换前必须验证引用闭合和可读性。

## 29. 分支、索引失效与历史兼容

分支具有父分支与冻结点、独立活动正文清单、规划版本和任务所有权。首期可只做简单副本分支，不承诺任意合并；复制耗时大时是有检查点的任务，未完成副本不能呈现为完整作品。

每个下游产物保存`depends_on`来源集合与版本。上游改变后，系统标记受影响候选过期；不自动使所有无关对象失效。运行中任务可结束并保存旧快照结果，但提交时必须再次比较当前版本，过期结果只能留候选历史。

索引与资料投影可重建；旧正文、旧结算和原始来源不能因重构清理。恢复历史版本是创建新的选择/修订动作，不回写历史日志。迁移时能保留的稳定ID应保留，不能保留时记录明确一对一映射。

验收必须含：两分支同名不同事实不串；旧版本查询可读；投影重建期间读旧完整视图；半成品新视图不外露；删索引后正文与接受记录仍完好。

# 五、AI与资料供给

## 30. Agent职责与执行合同

第130批实施：成员编号与岗位固定，姓名头像统一管理，模型为可替换绑定；候选目录、当前执行兼容、真实评测证据分别展示，不能用通道兼容冒充质量通过。任务保留创建时模型与提示快照。链与章节的节奏按作者目标决定；2—30章为现有章纲接口执行容量，不能解释为回报周期。Skill按任务加载且允许明确为空，基础来源/版本/作者硬要求边界不随Skill移除。后续按实际工位与任务、模型参数、提示版本建立评测准入；本批未完成全模型全工位评测。

### 30.1 岗位是职责，不是固定人数

第131批按本次产品容量建立7岗56个固定身份：主编、资料编辑、策划编剧、主笔、审查编辑、记录编辑各9位，封面画师2位。容量是本次配置，不是永久业务规则。`@wenmi/agent-catalog`为新旧后端和页面共用的纯公开目录；成员编号、岗位、姓名、头像与模型绑定分离，不按模型复制执行器、记忆或账本。当前真实候选为7种文字模型（含GLM5.2）与1种图片模型；每个文字岗位保留2个未绑定位置、图片保留1个，不虚构第8/9种模型已接通。

旧23名执行身份及其运行快照保留，33名新增候选绑定使用加法表`v7_agent_member_slots`，修改/解绑审计入`v7_agent_slot_events`，全局配置版本防止覆盖，重启不回填已解绑选项。新增候选在后台可配但默认不接作者任务；绑定、已有通道兼容、具体业务节点通过是不同状态。岗位职责显示不等于所有工具能力已实现，当前仍沿用已有执行器与任务恢复；没有宣称新通用Agent循环、全模型评测或PG全站切换完成。

下一阶段按节点依次验证：先开书设计与审查，再全书、卷、链、章及正文。每个“节点+模型+参数+提示版本”记录完成率、总耗时/首个有效输出、结构合法性、人工可读质量和用量；模型或关键提示改变后相关证据不能直接复用。先少量代表样本，失败成员在该节点不上岗，不能把一次快请求等同所有场景合格；正式任务默认只调用需要的成员，不自动让每岗9人轮流执行。共享长期记忆继续按书籍、来源和版本治理，不让成员自由记忆覆盖作者确认内容。

| 职责 | 输入 | 输出 | 禁止越界 |
| --- | --- | --- | --- |
| 创作策划 | 作者意图、相关规划与实际 | 开书/全书/卷/单元/章计划候选 | 直接接受候选、改正文实际 |
| 资料策划 | 任务、来源目录、相关候选片段 | 入选资料、缺口、适用说明 | 编造来源、按相似度宣布事实 |
| 人物设计 | 作品方向、人物已有证据、当前需求 | 新人物或发展候选 | 覆盖旧实际状态 |
| 主笔 | 冻结章任务包与工具权限 | 正文草稿、必要问题 | 改接受指针、记费用和改历史 |
| 连续性审查 | 精确草稿、实际与适用设定 | 证据化冲突与问题 | 把偏离旧计划自动当事实错误 |
| 文学与体验审查 | 正文、近邻、目标读者与风格 | 具体阅读问题和局部建议 | 把主观偏好伪装成客观错误 |
| 事实提取 | 接受正文与必要前态 | 有来源的事实候选、覆盖信息 | 写已验证事实或直接改投影 |
| 事实复核 | 候选事实、原文、必要前态 | 支持/不支持/未知 | 只看提取员自信分数批准 |
| 未来维护 | 已验证实际与活动规划 | 未来调整建议 | 擅自重写已接受正文 |
| 主编/综合判断 | 明确指定的方案或争议 | 比较、推荐、取舍说明 | 默认插入每一步增加等待 |

同一角色可有多个可用成员，一个成员可适配多种任务，但运行合同独立。头像和姓名不应制造实际不存在的独立模型审查。

### 30.2 每类任务合同

必须声明范围、目标、输入来源与版本、工具白名单、输出Schema/正文格式、停止条件、允许创造的内容、禁止覆盖的数据、模型能力要求、预算与时限、失败处理和审计。

职责说明保持短而针对任务；工程Skill和全站治理文档不塞进创作上下文。任何语义判断需要模型时保留其输入与输出证据；程序负责精确ID、事务、排序、金额、权限与合法结构。

## 31. 模型能力、配置与版本

### 31.1 配置对象

模型注册包含供应商、准确模型标识、接口路由、上下文上限、输出/推理预算语义、结构化输出、工具与流式支持、已测试参数、限流信息、计价版本、可用状态和数据处理政策引用。密钥只引用环境变量名，不进入注册表。

能力分组可称创作、快速整理、连续性审查等；价格档不代表质量排名。同一模型更换供应商路由也须重新核验超时、截断和用量语义。

### 31.2 参数策略

温度不使用统一固定数值；不支持温度的模型不发送无效参数。每类任务保存已测配置，尤其区分可见输出额度与推理消耗，避免过去“有大量计算但没有可提交结果”的故障。

每个任务冻结实际模型、提示版本、Schema、配置与预算。后台新配置只作用于新尝试；恢复旧任务若换配置，生成明确新attempt并记录变化，不伪装原调用复用。

### 31.3 升级与降级

模型升级先做协议与代表性质量回归，再小范围灰度。不能仅修改注册表便宣称所有任务兼容。故障替换必须满足任务能力和既定价格/授权范围；不为省费悄悄把关键审查降到不具备能力的模型。

没有合适模型时真实排队或暂停；不无限等“独立成员”也不静默破坏比较条件。用户看到能力暂不可用及可选下一步，后台记录具体原因。

## 32. ContextPack与资料编译

### 32.1 两层结构

内部清单保存精确来源ID、版本、哈希、适用范围、入选原因、预算和工具权限；模型可见包保存任务所需原文/结构事实与短句柄。作者界面隐藏技术字段，不意味着从模型返回合同所需的编号也删除。

第90批同类错误的预防：若输出要求返回某个来源句柄，则输入目录必须实际提供该句柄；Schema测试用真实目录构造，测试未知/重复/过期/跨书引用。只能归一当前任务中可确定的一对一别名，不能模糊匹配到其他版本。

### 32.2 编译顺序

1. 从会话和任务取得范围，不能相信模型/客户端提交的owner。
2. 固定目标和活动来源版本，读取任务必需材料。
3. 系统精确读取已知实体与近邻正文；语义相关性不明确时由资料Agent选择候选。
4. 有必要再混合检索，返回带版本片段；语义判断与原文校验分开。
5. 检查关键事实、作者要求、近期正文与必要上层信息完整。
6. 计算完整请求预算，包含系统提示、Schema、目录、工具返回与输出预留。
7. 冻结并持久化资料包，供重试、审查和诊断复用。

### 32.3 不同任务的重点

| 任务 | 必须关注 | 通常不需要 |
| --- | --- | --- |
| 全书设计 | 作者意图、长期承诺、总体实际 | 所有小物品和所有逐章对话 |
| 卷设计 | 全书蓝图、前卷实际、人物与线索长期变化 | 整本方法论和每章全部原文 |
| 链设计 | 当前卷责任、近期实际、局部人物 | 重复完整世界设定 |
| 正文 | 完整本章计划、相关事实、近邻正文、声音与视角 | 所有历史审查报告 |
| 连续性审查 | 当前完整草稿、相关原始证据、适用状态 | 与本章无关的远期计划 |
| 文学审查 | 正文和必要相邻文本、读者与风格目标 | 数据库字段和任务控制协议 |
| 事实提取 | 接受正文完整覆盖、相关前态、实体目录 | 未采用结局、落选正文 |

### 32.4 超预算

优先去除重复和无关参考；若关键资料仍放不下，缩小任务、分段处理或按需查证。不能静默裁掉作者硬要求和原文证据。工具返回同样消耗上下文，不是绕过预算的无限通道。

模型有可靠分词器时按其估算，无可靠分词器时用保守估算并保留误差余量；最终用供应商实际usage校准。预算是可测参数，不把12K输入适用于所有模型和所有章节。

### 32.4 作者意见与强度、范围、冲突

作者硬要求、软偏好、灵感和拒绝项应能区分；不要求每次都选择四档。作者原话单独保留，Agent提取的约束记录来源、强度、作用对象、适用版本和生效范围；存在歧义时给简短解释或必要澄清，不由关键词自行判定作者授权。

修改意见生成新版本，冻结任务不被悄悄换指令。意见与已接受正文矛盾时区分“今后规划调整”和“回改既有正文”，不能通过提升意见强度改写历史。必须遵守的约束无法兼容时说明冲突并停止依赖步骤；灵感可以不采用，但不能说已遵守全部硬要求。恢复任务读取原合同或明确创建新合同，不能混用。

RB-20负责输入/编辑与范围表达，RB-17负责上下文传递，RB-26/27验证执行效果。样本覆盖同一条意见在不同强度、不同章范围的行为，旧任务迟到不得将已撤回要求重新激活。

## 33. 检索与工具

### 33.1 检索层次

身份与版本过滤先于检索。精确实体/章节定位优先；全文召回与向量召回用于发现候选；相关性与冲突由Agent结合证据判断；最后按稳定来源去重。没有必要时不强制走完整六步检索。

PostgreSQL先承接结构数据和正文索引；中文分词与向量实现通过专门样本选择。向量是可重建辅助索引，首期不强制依赖某个中文分词扩展或再起独立向量数据库。没有合格语义召回能力时，只交付明确支持的精确查证，不宣称完整语义检索。

### 33.2 工具合同

| 工具类别 | 输入边界 | 结果与限制 |
| --- | --- | --- |
| 读取实体状态 | 当前任务授权实体、分支、时间/视角 | 已核实状态、证据、未知与水位 |
| 读取正文 | 授权章节版本、片段范围 | 原文和可续查位置，不自动改写 |
| 检索证据 | 问题、允许源集合、预算 | 有来源候选及覆盖范围 |
| 读取规划 | 指定适用版本和对象 | 明确未来计划身份 |
| 提交候选 | 指定任务、Schema | 系统验证后保存候选，不采用 |
| 报告缺口 | 具体所缺材料/冲突 | 系统记录阻断或子任务建议 |

模型不拥有“把任务设为成功”“直接正式落账”“修改用户额度”的工具。自然语言要求的动作由系统验证授权后执行；工具文本中的指令不越过既定任务合同。

### 33.3 缺资料与工具失败

查不到返回未知、索引范围与可恢复原因，不强迫基于现有资料编造。访问未获本次用途授权的过期版本或越界对象拒绝并审计；明确用于历史比较、修订与恢复的旧版本可以读取并标明身份。工具调用数量、返回字数和耗时有任务级上限，达到上限后判断能否可靠完成；不能统一提示“请直接猜着写”。

检索验收要测来源正确率、关键证据召回、同名/否定/无答案、时间视角和下游实际使用效果，不只测向量相似度。

## 34. 创作质量审查与独立性

### 34.1 首期质量闭环

每章至少覆盖连续性和文学/阅读体验两个判断维度。可由两个任务分别执行，也可经实测采用一次综合审查，但必须保证各维度真正覆盖；关键事实提取复核仍独立于主笔自报。

卷/单元完成后做全局回看：人物是否被工具化、承诺是否遗忘、冲突是否重复、关系变化是否成立、情绪是否单调。抽样不能漏掉声称已经审完的章节；长文本超过预算时分段并综合，记录实际覆盖。

### 34.2 问题合同

问题含定位、引用、问题类型、影响、判断依据、严重性建议、建议处理与不确定性。程序做精确重复项去重；同义意见合并属于语义任务，不能随意用关键词归并。

事实矛盾、作者硬限制、合理悬念、人物有限认知、风格偏好分开。文学建议默认不强制重写，硬问题也优先局部修复。修订后报告绑定新稿，不能用旧稿审查放行新稿。

### 34.3 独立性

需要独立比较时冻结相同信息范围，生成者互不看对方结果；独立审查初审不看其他审查意见。不同模型是一个可记录条件，不等于观点无偏或结论正确。不可把同一底层模型换名字称为异模型交叉验证。

事实复核尽量与提取采用不同模型，并记录实际身份；如当时只有同模型可用，按当前评测和风险策略决定等待或披露降级，不能自动宣称同等独立。没有证据要求所有提取分片必须四家厂商。

### 34.4 修改上限

任务冻结有限修订次数与总预算。达到上限后保留最好可用草稿与未解问题，允许作者手动编辑或另立目标，不再无限自审自改。每次修订说明解决了什么及保留什么，防止越改越模板化。

### 34.5 多方案与多主笔

默认一份主稿，作者可主动增加独立方案，开始前显示新增用量。多主笔读取同一事实与任务目标，分别保存完整候选；成员参数可因适配不同而不同，不能声称仅模型名称不同、其余实验条件完全相同。

候选以标签切换并支持查看关键差异，手机不强制并排两篇长文。选中底稿后做完整审查与修订，未选稿保留在历史且不结算实际事实。一位失败不删除其他稿；重新生成只有失败部分计新调用，已保存结果读取不重复计费。

融合请求生成一份新候选并保留来源，不能把不同稿的资源和人物状态直接合并成事实。基线意见有变时，旧候选标明来源过期；不能与新基线候选无提示混合比较。

### 34.6 新出现人物和审查覆盖

章纲未登记的具名人物先由语义任务结合正文判断实体身份、是否新人物、叙述是否可信和作用，不能按“名字首次出现”自动定为过场角色。候选稿产生的人物保持候选；只有被接受正文中的有效证据才能进入实际人物状态，传闻、梦境、别名和同名人物分别处理。

人物重要性可随故事变化。需要补充动机、关系或后续责任时，给相关设计任务明确问题；不凭固定核心/配角字段数量判角色质量。审查和事实提取分别记录文本版本及覆盖区间，分片漏掉的段落不能因为各片任务都成功而标为全章完成。

RB-27负责提出问题与候选判断，RB-28/29负责接受后的证据更新，RB-32提供详情与更正。验收至少包含未入纲的重要人物、现有人物化名、同名两人、只在传闻出现的人物，核对候选未采用时不污染正式人物库。

## 35. 调用预算与成本评估

### 35.1 三种预算

单次模型调用预算、一个业务任务总预算、用户本次托管授权预算分别管理。所有补交、工具、换模型、子任务共享业务总上限，禁止适配层重试两次、岗位再试三人、工作流再重试造成乘法膨胀。

费用估算：输入、输出、供应商计费的推理/缓存/图片等项目按计价快照计算，未知项目记待核对。不能用模型自报token记账，也不能只用章节字数推算精确费用。

### 35.2 不固定“每章10次调用”

每章成本应包含规划摊销、资料选择、生成、审查、修订、事实提取/复核、维护、失败/未知、基础设施与客服运维。报告均值及P50/P95，单看均值会隐藏连续失败的重尾成本。

真实模型样本和确定性测试分开计量。成本样本绑定题材、字数、上下文、模型/提示版本、接受率与质量，不能用低质量便宜稿证明商业毛利健康。

### 35.3 可优化项

复用未变的冻结资料、精确取数减少额外语义调用、批量核验、无关投影异步、小范围修订、模型路由按证据选择。不能靠漏掉关键事实或审查、隐瞒失败、把新费用当免费重试来降成本。

# 六、可靠任务执行

## 36. 统一任务模型与状态

### 36.1 四层对象

- Workflow：一次作者目标，例如准备第一卷、继续五章。
- Task：一个可独立恢复的步骤，如生成正文或提取事实。
- Attempt：某任务的一次具体执行，绑定模型、输入和租约。
- ProviderCall：实际远端请求，记录发送边界、请求标识、返回、用量和未知状态。

父任务聚合子任务状态，不要求每个业务再维护一套同义状态。候选、正文和审查结果是产物，有自己的版本生命周期，不能仅因任务取消就删除产物。

### 36.2 规范状态

| 状态 | 含义 | 允许转移 |
| --- | --- | --- |
| queued | 已持久化，等待执行 | running、cancelled、blocked |
| running | 有有效租约/活动尝试 | succeeded、failed、retry_wait、awaiting_author、blocked、reconciling、cancelling |
| retry_wait | 明确可重试，等待退避 | queued、cancelled、blocked |
| awaiting_author | 有具体待采用/决定产物 | succeeded、cancelled；决定可创建新任务 |
| blocked | 前置条件不满足且没有远端未知调用 | queued、cancelled；需重新验证条件 |
| reconciling | 远端可能已执行，结果/费用待核对 | succeeded、failed、queued或保持；转queued必须满足安全重发条件 |
| cancelling | 停止请求已收，当前尝试尚未完成收尾 | cancelled、reconciling |
| succeeded | 当前任务合同的产物与提交已完成 | 终态，不被迟到失败覆盖 |
| failed | 明确失败且本次自动恢复已结束 | 终态；用户恢复创建关联恢复任务并复用合格产物，不改旧终态 |
| cancelled | 不再启动后续，已经完成的产物保留 | 终态；未决远端调用仍单独核对 |

`partially_succeeded`用于父Workflow聚合：部分独立产物成功，另一些失败。不让一个小任务同时具有多个矛盾终态。结果未知不能直接按failed处理。

## 37. 入队、领取、租约与事务

### 37.1 入队

用户请求先验证会话、对象、版本、授权和用量，在同一数据库事务写命令回执、任务与必要预算预留。HTTP快速返回已接受任务；远端模型调用不得在持有数据库事务锁时等待。

定稿与下一步维护事件同事务写入outbox。outbox事件处理成功和消费记录在可验证事务中提交，重复投递通过消费者幂等键去重。持久化队列可以与业务表同库，不必先引入Redis双写。

### 37.2 领取

目标数据库使用短事务选择可执行任务，设置租约和递增fencing token后提交，再执行外部调用。PostgreSQL的`FOR UPDATE SKIP LOCKED`可用于队列表多消费者领取，但不适用于需要完整一致视图的普通业务查询；这是官方提供的能力，完整恢复逻辑仍由应用实现。[PostgreSQL SELECT](https://www.postgresql.org/docs/current/sql-select.html)

### 37.3 租约失效

Worker定期续约，续约失败停止新的外部动作。旧Worker迟到结果只允许登记远端调用证据；业务提交需要当前token匹配，避免租约转移后的双提交。

租约到期不等于调用未发送：无发出证据且明确未发送可安全排回；已发送/发送边界不明转核对。不能“Worker重启→所有working自动重跑”。

### 37.4 幂等层次

命令键防重复点击；任务步骤键防重复调度；尝试/供应商请求键用于核对；产物唯一约束防重复正式化；用量流水键防内部重复计账。不同层不能共用一个万能ID掩盖不同语义。

同键同内容返回原回执，同键不同内容返回冲突。新语义请求创建新键；保留键和请求摘要的周期至少覆盖对应任务恢复周期。

## 38. 失败分类、自动恢复与异常呈现

### 38.1 双维度策略

采用V9减少打扰的目标，但把“后台如何恢复”和“作者是否需要处理”分开。L0—L3只是展示/处置分组，不是所有错误固定硬编码一个级别。未知异常先安全暂停受影响操作并记录，不默认降为无关紧要的L1。

| 错误类 | 系统处理 | 作者体验 |
| --- | --- | --- |
| 暂时限流/明确未执行 | 在总预算和deadline内退避，遵守供应商提示 | 排队与预计状态，不反复弹窗 |
| 空输出/结构不完整且明确结束 | 原尝试结果留档，有限补交或调整粒度 | 成功则无额外操作；失败给恢复 |
| 输入合同/权限/版本错误 | 不机械换模型；修输入或重新编译 | 说明可处理的业务原因 |
| 网络断开/远端执行未知 | 核对，禁止盲目重发 | 清楚显示未确认结果与保留成果 |
| 用量或授权不足 | 停止新调用，保留成果 | 返回个人中心/调整范围后继续 |
| 关键事实冲突 | 自动查证/有限修订，仍未解暂停依赖 | 就地给证据与建议 |
| 文学建议/非关键漂移 | 进入后续设计建议，绑定版本 | 可查阅，不硬挡正文保存 |
| 跨书或数据完整性错误 | 拒绝提交、隔离结果、告警 | 安全提示，其他书不受影响 |
| 内容服务拒绝 | 按策略记录原因与允许修改路径 | 不伪装成成员忙，也不靠换厂商规避限制 |

### 38.2 预算示例而非未测承诺

初始试点可设“结构补交最多1次、最多一个合格备选、总尝试上限3次”，但所有路径共用同一上限。不同任务的deadline和输出预留依据实测配置；本批不将某个分钟数宣传成已达标服务时限。

达到上限就结束自动处理，保留成功检查点。后台按错误族看趋势，反复同错误时应修合同或模型适配，不能只提高重试次数。

### 38.3 异常登记、软建议与批量处理

异常类型记录适用操作、触发证据、影响、恢复办法、责任模块、通知策略和策略版本。程序处理明确技术错误；语义冲突的判断由Agent给证据。未登记异常先保护受影响数据并进入诊断，不能默认按低风险处理。后台修改展示级别不能解除权限、版本、内容安全或费用门禁。

软建议和待处理问题记录未处理、已提供给后续设计、已处理、已失效或有理由搁置；“已注入上下文”不等于“已解决”。规划漂移、伏笔延迟按本书意图和实际正文判断，不用固定分数自动纠偏。新规划保留实际事实，受影响方案绑定新版本。

批量采用建议前显示具体对象和变更范围，服务端对每项核对权限、版本与依赖，分别返回成功/冲突/未执行。部分失败保留已成功结果；依赖互相冲突的修改不能无提示全部执行。作者已接受正文、付款、永久删除等不因“全部按推荐”取得额外授权。

RB-18负责作者任务/问题呈现，RB-27负责审查问题归并与建议，RB-33负责长期线索责任，RB-47/48负责后台记录与策略治理。验收覆盖未知类型、重复意见、过期建议、批量部分成功、软建议不打扰但关键阻断不隐藏。

## 39. 远端未知结果、取消与重复费用

### 39.1 不承诺远端恰好执行一次

本地事务无法与第三方模型调用组成原子事务。若请求已发出但响应未收到，系统不能确定是否生成或收费。目标是本地业务最多一次提交、完整记录远端尝试、可核对费用，不声称能无条件保证供应商只计一次。

### 39.2 恢复顺序

先检查本地已保存返回与产物→用供应商请求ID查询（能力存在时）→接受回调/账单证据→按超时和人工策略处理。没有查询或幂等能力时明确保留未知，不凭等待时间推定未执行。

需要另发请求时记录这是有潜在额外成本的新attempt，使用已授权剩余预算或请求新的费用范围；旧请求迟到结果只能附入历史或按明确规则选择，不能覆盖较新接受版本。

### 39.3 取消

取消立即停止排队和新子任务；能取消供应商调用则请求取消，但“已请求”不等于远端已停止或免费。已经安全保存的草稿、审查与正文保留。取消和成功同时发生时以数据库原子提交次序及授权截止规则裁定，不让界面来回跳。

### 39.4 作者恢复按钮

每个按钮由服务端返回可执行动作与前置条件：继续审查已有草稿、补齐资料、重新核对结果、按新资料重做、停止后续。不能所有失败都指向“重新开书”，也不能让前端自行推断重试安全性。

## 40. 公平调度、容量与背压

按用户、书籍、任务类别和供应商分别限制并发；同一章活动写入串行，不同书可并行。长托管不得占满所有槽位，交互小任务与后台维护分别设置权重，等待过久任务逐步提升优先级。

队列达到容量时明确暂缓新模型任务，保存作者输入并返回重试时间或等待状态。不能用无限接单换表面可用，再让用户等几十分钟失败。预计等待依据当前队列与历史同类分布，不用固定进度条假装准确。

分别记录：在线会话数、HTTP并发、排队任务、正在调用模型数、每分钟token、供应商限流、数据库写事务、文件和网络吞吐。“一万人在线”不等于“一万路模型同时生成”。

性能不达标优先定位慢查询、锁、上下文与模型速率，再决定增加Worker、连接池、缓存或外置组件。增加Worker不能突破供应商额度，也可能加重数据库竞争。

## 41. 用量预留、扣记、释放与核对

### 41.1 双账分离

供应商实际成本流水与作者权益/算力流水分开，优惠、故障补偿和测试赠送都有明确记录。供应商花了钱不意味着应重复向作者扣同一业务费用；是否平台承担失败成本要在商业政策中公开说明。

### 41.2 事务流程

验证授权与余额→原子预留业务预算→分配各尝试额度→调用结束记录实际usage→幂等结算作者用量→释放未用额度。重试也在同一总预留中，不每层重新扣一次最大值。

核对未知调用时预留有明确状态和最长运营处理时限，但超时释放只表示平台暂不占用作者权益，不代表供应商调用不存在。迟到成本登记为调整流水，不能覆盖原账或未经政策再次扣用户。

### 41.3 并发与金额

金额采用整数最小货币单位，算力采用定义清楚的整数单位，费率版本化。余额检查与预留同事务并锁定同一权益范围；两个并行任务不能各自看到相同余额后超支。

唯一键确保一个远端调用usage一次、一个内部结算动作一次。退款/撤销用反向流水，不能删除原扣记。实际用量缺失标待核对；允许保守预估展示但必须标为估算。

### 41.4 验收

双击、断线重发、Worker崩溃、返回后提交失败、取消后迟到、并发余额不足、供应商补账都需测试。账务不平触发核对，不允许管理员直接改余额数字“修好”。

## 42. 总体架构与技术取舍

### 42.1 已定目标结构（第107批，尚未实现）

```text
作者Web / 独立运营Web
          ↓ HTTPS，同源API，鉴权
API进程：命令校验、快速事务、查询与任务事件订阅
          ↓
共享领域模块：作品/规划/正文/事实/任务/权益
          ↓
PostgreSQL：业务版本、正文、任务、outbox、事实、用量
          ↑
Worker进程：领取持久化任务→模型适配/受控工具→结果验证
          ↓
模型服务 / 图片服务 / 受控文件存储

监控、备份、发布与审计贯穿各层
```

现有工程已有模块目录和API/Worker分进程基础，但不能据此认定责任边界或恢复机制正确。新实现采用模块化单体：API只鉴权、校验、事务、查询及任务事件订阅；模型与耗时工具调用统一由Worker处理。选择相同架构形态不等于复用旧业务实现；不拆十几个微服务和独立业务数据库。

### 42.2 组件决定

| 项目 | 推荐 | 原因、限制与实施条件 |
| --- | --- | --- |
| 语言/运行时 | TypeScript严格模式、Node.js 24 LTS | 新独立工程和锁文件；跨前后端合同仍需运行时校验 |
| 前端 | React/Vite；作者端和后台独立入口 | 第110批起兼容组件、路由和CSS可复制到新工程，受保护页面UI保持；复制后独立依赖构建与浏览器回归，不运行时导入旧目录 |
| API | Fastify 5承载新路由 | 薄路由调用模块应用服务；兼容纯逻辑可复制并验证，旧会话信任、SQLite仓储与不符合事务/任务边界的实现必须适配或重写 |
| 主数据库 | PostgreSQL 18，首轮验证基线18.6 | 事务与恢复方案先在隔离库验证；生产SQLite在切换前继续为权威，不就地改造 |
| 数据访问 | node-postgres（pg）+参数化SQL、新仓储和显式事务 | 同一业务事务使用同一client；不引入重型ORM或隐藏跨模块写入，迁移SQL与校验和版本化 |
| 任务队列 | 同库持久化任务表+outbox，新写任务实现 | 首期不另加Redis；任务领取租约/过期隔离、幂等、退避与未知结果政策必须实测 |
| 正文存储 | 首期正文完整版本存同一数据库 | 降低数据库元数据与正文文件提交不一致；后续超大附件走对象存储 |
| 图片/附件/导出 | 独立存储适配器，当前本地受控目录可过渡 | 目标多实例需要共享存储；新服务费用另行确定 |
| 搜索 | 结构化与全文优先，向量辅助按实测加入 | 不在首期强制安装全部检索组件 |
| 通知 | 持久化事件+SSE，轮询降级 | SSE只是通知通道，数据库才是任务状态来源 |
| 发布 | 新工程独立构建与发布清单；保留原子切换、资源保留和回滚要求 | 不直接套旧脚本发布新业务；当前生产脚本继续服务旧系统，不强制换Caddy或引入Kubernetes |

PostgreSQL不是“零BUG选择”。版本核对日2026-09-06：18.6为18分支当前维护版本，官方支持到2030-11-14；安装时再次核对补丁与校验和，不采用Beta。[PostgreSQL版本政策](https://www.postgresql.org/support/versioning/)。Node.js 24处于LTS，具体补丁在新工程独立锁定，不顺带更新生产运行时。[Node.js发布状态](https://nodejs.org/en/about/previous-releases)。pg事务必须绑定同一client，仓储不得在事务内混用pool.query。[pg事务说明](https://node-postgres.com/features/transactions)。这些依据只支持相应技术行为，不证明整个产品可靠；新服务采购仍单独授权。

### 42.4 新旧实现与验收边界

- 第121批手动路径采用保留前端＋兼容API＋独立PG事务：公开手动创建、分类目录和资料GET/PUT；初始书籍/不可变来源/空目录/资料v1/审计一起提交，资料更新完整追加版本并同步书架标题。资料版本与归档版本独立，旧手动来源无投影时只读计算v1，首次变更补存原始v1再生成v2。团队任务来源不得通过手动入口冒充。这个局部实现不代表AI、会员、邮件或生产数据迁移完成；实际状态见执行文档和121批合同。
- 第110及120批允许兼容旧代码复制到独立rebuild工程，保留来源与适配差异；新工程运行时不import旧工作区，不将目录或类名变化冒充功能重写。账号权限、数据库事务和任务所有权不兼容的部分必须适配；不能为满足新目录结构重做成熟功能。
- 旧源码和测试可作复用输入；需求仍由最新确认范围决定。复用测试核对新环境依赖，并补已知故障与迁移边界的验收；旧代码跑通不等于新架构接入通过，不把旧函数输出全部视作正确答案。
- 页面、样式、图片、标志、字体、确认文案及兼容业务实现均可保留复用，按批准范围验证。R105/106首页继续在旧站服务，是过渡交付，不表示新工程真实接口已完成；后台96—98同理。
- API命令、运行时校验和TypeScript类型采用单一合同来源；持久化结构通过明确映射连接，前端不得导入仓储。Fastify封装用于隔离插件上下文，仍需导入边界检查，不能把插件隔离当数据权限。[Fastify封装说明](https://fastify.dev/docs/latest/Reference/Encapsulation/)
- Worker领取任务后先保存调用意图，成功结果先持久化再推进；超时未知不盲重发，旧租约不能提交，取消不抹掉已经产生的结果/费用。`SKIP LOCKED`仅用于队列领取，不用于需要完整视图的业务查询；它本身不保证恰好调用一次。[PostgreSQL锁定查询](https://www.postgresql.org/docs/18/sql-select.html)
- 基础验证先用合成用户、合成书籍和确定性任务，不触发真实模型费用；模型、语义与文学质量的真实验收留在相应功能批次。账户隔离、旧数据迁移及生产切换各自具备证据后才允许承载真实用户。

### 42.3 暂不引入

首期不引入微服务拆分、Kafka、Kubernetes、通用低代码工作流编辑器、独立图数据库、整站事件溯源、默认WORM合规锁。这些方案有适用场景，但当前没有证明其额外运维与一致性成本必要。后续用容量或产品需求证据触发评估。

### 45.2 返回与错误

成功读返回200；创建资源201；持久化长任务202；认证失效401；授权拒绝403或不暴露对象的404；版本冲突409；输入不合法422；限流429；依赖不可用503。状态码辅助客户端分支，不直接当中文提示。

错误体包含稳定业务码、安全消息、可重试属性、允许恢复动作与追踪关联。作者界面不展示内部码；后台可凭授权追踪ID关联。失败不能返回HTTP200加空对象导致页面判断为无数据。

### 45.3 事件与缓存

状态事件只通知“发生变化”，前端用服务器版本防乱序；断线后续读持久化事件或拉最新快照，不依赖SSE消息一定送到。状态轮询是降级，不触发新任务。写入后根据返回版本失效相关查询缓存，不盲目刷新所有页面。

前端状态区分服务端事实、本地未保存编辑、加载与乐观展示。只对可逆且能回滚的显示采用乐观更新，定稿、扣费、任务成功均等待服务端回执。

## 48. 支付、订单、退款与核对

当前操作总览记载作者主要联系客服、后台办理，本批未核实自助支付闭环。推荐在核心创作稳定后接入正式商户通道；接入账户、密钥、费用和业务资质是独立条件。

### 48.1 状态与提交

订单：待支付、已确认、已关闭（过期/取消等原因）。支付：待确认、成功、失败、结果未知。履约：待发放、已发放、发放失败/待修复。退款：申请、审核、处理中、成功、失败/待核对。分开记录，避免一个`paid/refunded`字符串无法解释多次部分退款和履约；过期订单迟到成功支付进入核对，不能丢弃到账或直接重复收款。

### 48.2 失败恢复

支付成功而发放失败：优先幂等补发并告知处理状态，超过服务期限按政策退款；不因一次数据库暂时失败立刻退款又迟到补发。退款成功后权益调整按已公开政策执行，保留余额与在途任务核对，不能做出负数异常权益。

用户退款资格、数字服务已使用部分的处理、退款期限与费用需要按实际销售协议和适用法律确认，不直接采用V9“用过就不能退”的绝对条款。

### 49.3 用户反馈

### 50.2 配置发布合同

每项配置含类型、默认、有效范围、校验规则、作用域、风险、版本、何时生效和回退条件。关联任务类型与受影响能力，运营者能看懂改它会怎样。需要运营维护的项必须有受保护的管理接口及可理解的表单，不能长期只能改代码或直接改数据库。程序实现、安全底线和数据库结构仍由研发发布，不开放任意执行代码或无限提高重试和预算。

Prompt/模型/任务参数走草稿→校验→代表性测试→灰度→发布。正在运行任务使用冻结快照；高风险开关变更同样记录审计。安全底线如跨书校验、幂等和正文保护不能通过普通运营开关关闭。

### 50.3 恢复动作

后台可重建索引、重新消费安全事件、核对未知调用、补发权益等，但必须预览对象范围并由服务验证。对作者内容的更改要走同样版本/授权路径；后台不得直接“修一下正文/余额”。

提供功能矩阵：设计、代码、测试、真实模型、浏览器、部署证据分栏显示。不能把人工勾选“上线”当生产已切换。

管理接口复用模块化单体和已有认证基础，采用各业务模块的读查询及明确命令。共享表单、版本比较和审计元信息可以复用，数据语义与执行权限仍由所属模块校验；不建一个接收任意表名/字段名的万能写接口。具体路径/Schema在单元开工时确定，本文不把尚未实现的接口列成已可调用。

| 合同部分 | 每个适用管理功能必须明确 |
| --- | --- |
| 用途和责任 | 功能名称、解决的问题、所属模块、维护者、使用它的页面/Agent/任务 |
| 当前状态 | 当前环境、有效值/版本、草稿值、配置来源、检查时间；无运行证据显示未验证 |
| 可编辑范围 | 字段名称、人话说明、类型/单位、默认值、允许范围、依赖、示例与禁止项 |
| 来源与作用域 | 平台默认、试用范围、账号/书籍覆盖；明确优先级和继承，覆盖只适用于允许的业务项 |
| 权限 | 谁可看摘要/全文、谁可编辑、测试、发布、回退、导出；服务端按对象和动作校验 |
| 并发与持久化 | 草稿保存回执、预期版本、重复提交幂等、冲突差异；断线不清空未提交内容 |
| 预览与测试 | 影响页面/任务、关键字段变化、权限/结构检查、相关样本和实际用量上限；模拟与真实调用分开 |
| 生效 | 立即、下次任务、下次读取、重编译、重启或代码发布；界面显示实际生效结果，不能只说已保存 |
| 历史 | 修改人、时间、原因、前后版本、受影响范围、验证结果和成功/失败事件；敏感值不留明文 |
| 回退与失效 | 哪些内容可回退、哪些需新版本纠正、相关候选怎样失效、索引/投影怎样刷新、旧任务怎样追溯 |
| 删除与停用 | 停用未来引用、可恢复归档、永久删除分别命名；显示影响，不提供默认级联删除 |
| 空白与异常 | 未配置、无权限、无数据、过期、部分失败、只读旧版本、并发冲突各有下一步；按钮禁用说明原因 |

生效机制必须逐类定义：普通展示文案可以短缓存后读取；Prompt/模型/工具/上下文策略从新任务起使用；资料纠正生成新来源/事实版本并触发受影响投影维护；运行参数按支持能力热更新或安全重启。界面与服务端必须一致，不能套用一个“保存即全站生效”。

多项互相依赖的配置使用组合版本或兼容性检查，先校验完整候选集合再原子切换有效指针；失败保持旧有效配置。正在执行任务冻结自己的输入与策略，发布后不会无声改变。回退配置是新的发布记录；不会自动撤销已经生成的正文、计费或对外副作用。

### 50.7 上下文、资料包与知识修改的责任链

责任链为：来源及作者要求→检索/切片→Agent选择资料→编译并冻结资料包→Prompt与工具合同→模型调用→候选/作者采用→事实提取与复核→Wiki/图谱/检索投影。管理页面必须能沿这条链查看引用，某层失败应定位该层而非一律“重试全部”。

四类修改使用不同操作：

1. **改策略或提示**：保存新配置草稿，预览/验证后发布；新任务使用新版本。旧任务若需要新输入，建立合法的派生任务/资料包并保留原调用。
2. **改作者资料或正式内容**：按作者权限及确认流程产生新版本，预览并标记受影响候选，触发必要的增量维护；后台管理员身份不等于可以代替作者改变创作事实。
3. **纠正提取错误**：绑定原文证据和旧事实记录，追加更正；需要语义重判时交Agent。更新活动投影并核对Wiki、关系、时间线、检索一致，不覆盖历史记录。
4. **调整显示或重建投影**：布局、筛选、显示标签不改变事实。用相同已核实事实构建新索引/视图，完成后切换；若需重新调用AI理解正文，应明确是新提取任务并显示用量，而不是假称无成本重建。

新增管理功能必须保留原错误证据，说明是哪个版本修正了什么。查询可打开有授权的来源全文和技术资料，默认列表使用最少必要信息；任何页面都不展示模型思维链，密码/密钥不进入资料包、日志、导出或Git。

### 50.8 管理能力开发顺序与验收

按执行文档顺序逐页讨论，业务与管理能力配对交付：第一次用到Prompt/模型就有最小受控配置和版本；第一次编译就有来源与资料包诊断；第一次接受正文就有维护状态和失败恢复；首次公开商业能力就有其必要的运营处理路径。RB-48至RB-56的子单元完善独立页面，不能用其排期靠后为由延后前述基础要求。当前79项只表示工作拆分；新增12项前后端均未实施，进度不因本章写完而变绿。

每个单元分别验“可读”“可保存草稿”“可校验/试运行”“可发布/执行”“确实生效”“可恢复”，不以一个保存按钮通过全部验收。当前不适用的动作说明原因，不制造假按钮。至少采用与变更相称的失败场景：

| 场景 | 结果要求 |
| --- | --- |
| 非管理员、跨账号/书籍、旧会话或越权动作 | 服务端拒绝且不泄漏内容，不靠前端隐藏按钮保护 |
| 两人同时编辑、网络断开、重复点击 | 不丢草稿、不后写覆盖新版本、不重复发布/收费；可查看冲突和重试 |

| 修改资料/Prompt时任务正在执行 | 旧任务原快照可追溯，新任务使用正确活动版本；不能混拼新旧输入 |
| Wiki/图谱纠错或索引重建中断 | 旧完整投影仍可查，新结果未完成不切换；源证据和正文不受损 |

| 试运行和真实模型调用 | 标明真实/模拟、预算和样本；结构合法不等于文学质量通过，失败样本仍保留 |

## 51. 内容安全、隐私与合规实施边界

### 51.1 核查范围与来源

本章是工程准备与待核事项，不是对产品已合规的判断。2026-09-05核查了正式发布的[《生成式人工智能服务管理暂行办法》](https://www.cac.gov.cn/2023-07/13/c_1690898327029107.htm)和[《人工智能生成合成内容标识办法》](https://www.cac.gov.cn/2025-03/14/c_1743654684782215.htm)。前者涉及用户数据保护、服务稳定、投诉和特定条件下安全评估/算法备案；后者涉及生成内容标识及相关责任。上线前仍需按当时有效规定、具体服务方式与属地办理要求核实。

V9关于“纯邮箱必然不满足实名”的依据不足，不能把征求意见稿当正式条文，也不能把短信验证等同全部身份核验。应核定本服务适用要求及可用方式，再设计补充核验流程。

### 51.3 内容处理

关键词只能做风险召回；上下文安全判断交由合格审核能力和必要人工处理。创作规划阶段做相称预检，正文按适用要求检查，减少生成后才发现不能交付。审核结果绑定文本版本，修改后按影响重新检查。

服务拒绝时保留允许保存的用户输入和可恢复状态，说明能改的范围；不显示敏感内部风控细节，不通过自动换模型绕开适用限制。文学中的冲突/暴力不能仅因关键词全部判违规。

### 51.4 标识与保留

默认提供满足适用要求的标识；TXT、Markdown、HTML、图片等逐格式确认，不能笼统写“文件元数据已标识”却没有实现。本文不开放去标识功能；法规中的例外如需使用，另行核查条件、日志和用户责任。

日志保留期限按类别和适用义务制定，不一律永久或一律一年。审计、交易、正文、模型快照和备份分别设置策略，删除请求与备份到期关联。合规验收需要实际材料和行为证据，页面勾选框存在不算完成。

### 51.5 内容审核的可执行合同

本节补充工程闭环，不新增法律结论或指定第三方厂商。具体规则适用范围、数据传输授权、服务商和人工责任在实施前核实。作品私有草稿、AI输出交付、正式采用、复制/下载和对外发布是不同动作；按已核定政策明确各动作是否检测及阻断，不能把文学审查当安全审查，也不能用安全审查替作者评价文学。

审核对象绑定owner、book、文本完整版本/摘要校验、触发动作和策略版本；结果记录待检查、检查中、通过、不通过、待人工、失败/未知，并保留提供方回执与可向作者展示的理由。内部规则细节和不必要全文不写普通日志。文本改变后旧结果只能用于历史，不能放行新稿；复用须满足同文本、同策略及约定有效期。

| 环节 | 功能及责任 | 可观察验收 |
| --- | --- | --- |
| 生成前预检 | RB-16.1在开书/规划/正文任务发送前检查适用约束；后端统一策略接口 | 明确不能执行的请求不产生无效模型花费；普通文学冲突不因关键词被一概拒绝 |
| 正文/图像结果检测 | RB-27.1提供版本化审核服务；封面接入RB-34相应媒体策略 | 旧版本通过不能放行新结果；按需检测的动作不会因审核超时而默认通过 |
| 失败和恢复 | 走RB-14/18持久化任务、预算和有限重试；有独立恢复键 | 供应商超时、回执丢失、重复回调、服务限流可追踪；不盲目换厂商规避拒绝 |
| 处置与申诉 | RB-47.1提供受权限保护的审核案件、复查和通知 | 申诉只能关联自己的内容；改判留理由、操作身份、策略和原结果，历史不被擦除 |
| 来源与标识 | RB-10.1维护来源记录和逐格式方案，RB-35完善格式 | 页面、复制、TXT/MD/HTML/图片的实际输出逐项验，不以一处标签代替全部渠道 |

必需审核不可用时阻断对应受限动作，允许的草稿保存/阅读和其他独立任务保持可用；不得无依据删除作者原文。人工改判只在授权政策范围内改变审核结论，不绕过账号隔离、不可变版本和费用规则。若没有合格审核通道或复查责任人，该闭环标未验证，相关商用动作不得宣称可用。

### 51.6 生成来源、标识与格式边界

每个版本保留来源类别（作者输入、AI候选、混合修订、导入及未知）和可追溯生成记录；来源是证据，不是凭模型猜测作者是否用过AI。导入来源未核实则保留未知，手工改一个字也不能自动清除原AI生成记录。如何向用户解释混合来源在相应页面讨论。

复制和导出固定同一版本快照，保存标识策略版本和结果清单。纯文本没有可任意依赖的通用文件元数据，不能声称TXT已通过不存在的字段完成隐式标识；开发前按适用格式规范选择实际可验证方法。格式暂不支持时明确限制，不宣传已满足所有格式要求。来源信息和必要标识随任务重试、版本导出、文件下载保持一致。

文案、标识位置与可读性按手机/桌面查看和实际输出验证，不能把内部任务ID或哈希显示给作者来充当标识。未授权不新增去标识入口。

| T20 | 灾难恢复并重建投影 | 正文/回执/费用/文件/权限一致 |

### 53.3 语义与文学样本

借用不等于拥有、假死不等于死亡、传闻不等于事实、回忆不读取未来能力、化名与同名不混、梦境不改变实际、否定词小改改变事实、线索尚未回收不标完成。无来源答案必须未知。

文学样本同时看人物主动性、语言声音、场景可感性、情绪层次、重复、承诺与兑现。不要为了减少误报放过明显错误，也不要为了高召回把所有合理悬念判错。

### 53.4 回归样本、执行时机与结果留证

RB-00建立测试数据分类与运行入口，RB-16开始积累模型适配合同样本，RB-27/29分别维护审查和事实连续性样本；不把全部样本与故障验证拖到最后RB-58。测试清单与实际功能同时增长，按受影响范围运行；模型/Prompt/流程变化选对应样本和必要真实探针，不触发无关全量或默认100章调用。

每个语义样本记录版本、来源许可、预期证据/结论、严重程度、允许的合理答案、标注分歧和实际输出。成功识别比例之外报告误报、漏报、漏提和未覆盖区间。固定回归集与未用于调参的保留集分开，文学判断保留真实阅读意见，不用模型自评分独自签发质量通过。

成本试验记录真实供应商用量、排队/准备/生成/审查/整理分段时延、失败尝试和内部记账；压力测试记录负载模型、并发、持续时间、错误/尾延迟和资源瓶颈。这两种试验分开：生成100章的费用不能证明多用户并发能力，mock跑得快也不能证明真实模型便宜。

## 54. 商用试点指标与发布判定

### 54.1 指标口径

以一次用户目标为单位统计首次成功、自动恢复成功、部分成功、失败、主动取消和等待用户/权益阻断；失败的子任务不能从分母删除。请求成功率、模型成功率、用户目标成功率分开。

时延包含排队、资料准备、生成、审查和必要事实更新，并单列各段。质量测量要报告样本数、类别、标注方法、错误严重程度与统计不确定性；模型自评分不能当真实准确率。

### 54.2 推荐初始试点目标（尚未实测）

| 项目 | 建议目标/判定 | 注意 |
| --- | --- | --- |
| 数据安全 | 验收集中跨书泄漏、接受正文丢失、重复正式提交为0 | 测试中为0不证明未来绝对0；任一实案阻止扩大试点 |

### 54.3 放量条件

功能、数据、真实模型质量、手机、恢复、成本和适用商业条件同时满足试点范围。任何未解决的数据串书/正文丢失/费用重复问题阻止发布受影响能力。未达性能指标可缩小支持容量并明确说明，不能修改测试口径伪装达标。

试点先少量隔离书，再获授权用户，小范围新书，最后迁移旧书。只对有证据范围对外承诺；没有容量和长篇阅读证据时不宣传“万人并发”“任意长度稳定”。

## 55. 监控、备份与灾难恢复

### 55.1 监控

观察API成功/延时、队列年龄、租约续约、未知调用、供应商限流、重试次数、事实滞后、正文与投影一致性、预算未释放、支付差异、数据库容量和备份年龄。告警要有责任人/处置入口，不只堆日志。

健康检查区分进程活着、数据库可用、Worker在工作、模型任务可接受；普通首页能打开不等于创作服务健康。故障面板对作者显示可用能力和下一步，后台显示细节。

### 55.2 备份

目标PostgreSQL采用完整基础备份与持续WAL归档以支持时间点恢复；必须同时验证归档链、保留和可还原性。仅有每日逻辑导出不能证明PITR能力。[PostgreSQL连续归档与PITR](https://www.postgresql.org/docs/current/continuous-archiving.html)

建议每日校验备份、保留30天恢复窗口、异地独立副本；实际周期、成本与地域在实施时核定。正文存数据库简化一致性，图片和附件仍需文件清单、哈希与备份对应。当前SQLite迁移前继续使用已有一致性备份，不提前改生产备份方法。

### 55.3 演练与恢复

在隔离环境恢复指定时点，核对用户/书归属、接受正文哈希、活动版本、任务未知状态、费用流水、附件和删除墓碑，再重建索引。恢复期间禁止自动重发历史未知模型请求。

代码回滚不等于数据库恢复。生产恢复必须预览恢复点之后的新作者数据并有明确授权；不能为回滚一个BUG抹掉新章节。保留事故时当前副本用于追赶和核对。

恢复演练至少在首次商用放量、迁移前后和备份机制变化时执行，稳定后按运营周期进行。备份文件存在不等于演练通过。

## 56. 发布、配置切换与回滚

### 56.1 发布包

冻结源码提交、依赖锁、构建产物、迁移列表、模型/Prompt兼容范围、配置与回滚目标。发布号、静态资源哈希、API/Worker引擎版本必须可核对，不能用Git远程HEAD代表线上版本。

Web静态资源单独发布可保留旧哈希并原子切入口；API/Worker/迁移按[现行部署规则](DEPLOY.md)及获准范围执行。在旧运行形态下仍遵守在途任务安全窗口，不取消作者任务制造窗口。

### 56.2 新执行器发布

新任务引擎可逐步支持停止领取、完成/检查点交接、租约安全转移和版本兼容。只有这些机制实际验证后才能改变现有发布等待要求；本文不自动取消现有门禁。

同一任务有唯一engine_version，不被新旧Worker同时领取。变更配置只作用于后续尝试，已冻结任务不改模型和Prompt以“顺便更新”。

### 56.3 回滚

优先回到兼容当前数据的上个已验证应用版本或关闭新入口。数据库使用扩展—回填—验证—切换—延后收缩，尽量保持旧应用读兼容。并非所有迁移都有安全down；不可逆变化需要独立计划和授权。

切换后验证登录、读旧正文、新任务、失败恢复、用量、后台与静态资源。生产探针不得复用真实作者任务或把确定性模型开放给普通作者；隔离账号/书和明确路由，费用受控。

发生重大数据/权限/收费错误先停止受影响写入、保留现场并执行可用回滚，不边猜边修改作者数据。恢复后记录影响范围、根因、修复和复验，不以道歉结案。

## 57. 重构能力阶段与逐页执行入口

### 57.1 分期原则

第110批用户已明确允许经核实兼容的旧代码复制到新工程，不兼容才重写，覆盖第107批全量重写要求。复制保留来源与差异并在新依赖/数据合同下重新测试，不能将旧工作区作为运行依赖。旧代码在迁移验收前继续服务，不能提前删除；逐功能交付，不以文档、空目录或首页代替真实架构与业务验收。

以下R0—R7是原稿的能力阶段背景，**不是当前逐页开发顺序，也不是已启动的开发任务**。当前以 [全产品逐页执行文档](REBUILD_EXECUTION_PLAN.md) 的RB编号、依赖与唯一状态表安排工作，先RB-00再注册登录；本表仅解释不同能力的完成层次。产品页逐项细化，已定工程工作由开发者安排，不重复询问技术选择。

### 57.2 首个纵向闭环的最小完整性

一册隔离书至少能保存作者意图、得到可用卷方向和下一章计划、生成草稿、真实审查、手动编辑/采用、可靠更新关键事实、写下一章、查看原文来源、导出，且各步失败可恢复。只做一个漂亮首页或只能返回固定文本的Demo不算完成。

### 57.4 排期方式

## 58. 旧数据迁移、兼容与退出

### 58.1 迁移对象清单

账号与owner、书籍与归档、会员/余额/预留/流水、作者原话、正式开书与设定、规划树、章纲、正文所有受保护版本、接受回执、章节/卷链对应、结算与证据、人物/故事状态、任务与模型调用、Prompt快照、封面/文件、审计、删除墓碑。

数据量、异常记录与存储形态必须实测；不能只复制正文和最新摘要就认为全书迁移完整。旧表名不等于旧数据无用。当前已合并迁移永久保留供升级追溯，不重写历史SQL。

### 58.2 单一权威与切换单位

第107批默认先内部隔离验证，不向真实作者开放两套同时可注册/扣费的系统。生产切换要求身份、权益及作品依赖有明确的单一写入权威；切换清单记录所有依赖，不能只迁一本书就假定账号和余额已兼容。按书或按账号灰度只有在专用路由、会话撤销、账务与失败补偿通过专项验证后才启用，未完成时不得强行灰度。

数据库目标迁移先离线副本演练。正式迁移前短暂冻结该范围新写入，等待安全任务状态，导出一致快照/增量，导入并逐项校验后原子切书籍路由。不能无补偿双写SQLite/PostgreSQL。

### 58.3 过渡期账号与计费的事务边界

目标新系统的身份、预留/用量和任务均在同一PostgreSQL权威中，按第37、41章处理事务。新系统首期不通过调用旧账务服务拼装业务，不实现SQLite/PostgreSQL无补偿双写；旧系统继续自行服务现有用户，新工程仅用独立测试身份和测试权益。真实账号开放前，专项迁移合同必须确定身份/权益整体切换或经过验证的灰度边界。

迁移保留有效期、余额、历史流水、未释放预留和未知模型调用证据；必须按总额与逐笔两层核对。新实现的预留释放、消费授权和usage提交都按持久化键幂等；未知调用先核对，不因迁移或换引擎再次付费执行。测试环境的演练凭证不得用于真实作者调用。

账号ID与归属保持稳定或一对一映射；密码哈希通过成熟库按原算法和参数验证兼容，不迁移明文或统一重置密码。旧会话采用显式撤销/重新登录策略，不能自动等同新会话。整体平台切换必须包含备份副本演练、安全在途窗口、写入冻结、校验与失败处置；新系统开始接受写入后，不得简单切回已过期旧数据库。没有验证增量回放时进入维护状态保留新数据，生产数据恢复另行授权。

第107批只读代码核对的迁移基线：旧账户使用独立user_id/owner_id和归一化唯一邮箱，password_salt/password_hash由Node scrypt生成（N=16384、r=8、p=1、64字节），会话存token的SHA-256摘要；新实现按合成测试向量验证兼容，不复制旧账号服务。会员当前权益与不可变办理流水、用量/预留、正文全部受保护版本与活动指针、模型working/unknown记录、正式化事件及文件清单分别迁移核对，不能只取最新摘要或余额。源证据为account-auth-service.ts及迁移0043/0045/0076/0084/0101/0103/0105，实际数据量和异常分布仍未审计；迁移时必须复核当前生产版本。

### 58.5 切换与失败

回滚优先停新写并读完整已接受数据；不可逆迁移和生产恢复仍需具体影响预览与授权。迁移脚本重复执行安全，不能让同一章导入两次或用户额度翻倍。

## 60. 三个贯通示例

### 60.1 从开书到第三章

作者输入“边军斥候寻找同袍失踪真相”→AI提出方向→作者采用→系统准备必要边境/军制设定、全书主要承诺、第一卷“从逃亡到获得调查入口”的完整故事→首单元设计救援与调查的局部选择→写第一章。

第一章主角从军医处借到一把刀。正文被采用后，提取记录“借用/持有”，不记“永久获得”。复核和投影就绪，第二章资料含这项限制及近邻原文；作者点“采用本章并继续”，不需要另点“更新资源”。第三章归还刀后更新持有状态，但历史借用证据仍可读。

全书蓝图只承诺寻找真相，不要求首章就揭秘；卷设计安排调查机会和人物动机；链负责这段救援的选择/后果；章负责读者具体经历；时光机显示实际完成与后续计划。

### 60.2 生成成功但网络断开

任务已保存且预算预留→Worker发请求→远端可能生成→连接断开→attempt进入reconciling。页面说明尚未确认结果，保留章计划和输入，禁止连续点击产生多次新调用。

若找到完整返回，校验并复用，继续审查；若供应商明确未执行，允许预算内重发；若无法确定，保留未知与费用核对记录，作者可停止等待或在明确预算内启动新尝试。旧响应迟到也不能覆盖后来采用的新正文。

### 60.3 回改已写出的第五章

作者将“刀是借来的”改为“刀是赠予的”。改动很小仍是资源事实变化。系统显示第6章归还刀的场景、第9章相关对白和受影响记忆，提供修订分支。

新第五章重审/重提，后续章节先保留并标需检查。作者采用一组自洽修订后切活动分支；旧第五章和旧结算仍可查看。不能只更正账本为“赠予”而让现有正文仍写“借”，也不能自动删除第6—20章。
