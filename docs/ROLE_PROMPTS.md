# AI成员完整工作手册（当前实际运行版）

> 本文把文秘写作11名创作成员的职责、介入节点、资料包、工作方法、输出规则、独立设计、融合、压缩、审查、重试和作者控制权整理在同一处。它描述当前代码实际采用的运行方式，不是理想化岗位介绍。

## 1. 基本概念

### 1.1 “思考规则”不等于隐藏思维链

系统不会保存、展示或要求模型输出内部思维链。本文所说的“思考规则”，是作者可以检查和调整的外部工作方法：

1. 核对正式事实与作者偏好；
2. 确认本次任务允许改变哪一层；
3. 按规定顺序完成设计或审查；
4. 按输出合同提交结果；
5. 无依据内容标成不确定；
6. 结论能回到当前书、对象和版本。

系统只保存任务输入快照、资料包清单、提示词版本、模型结果、结构化报告和作者选择，不保存模型隐藏推理。

### 1.2 资料包大小和输出字数不同

- **输入Token上限**：本次发给模型的资料容量上限。
- **输入字符上限**：资料包文本字符上限。
- **输出Token上限**：模型本次最多返回的容量。
- **正文有效字数**：真正验收的中文、英文和数字有效字符。
- 预算是上限，不代表每次塞满；实际使用量由任务快照记录。

### 1.3 三类资料严格分开

1. **必须读取**：开书信息、活动设定、活动卷纲、当前事件、当前章纲、作者明确要求等直接依据。
2. **按需检索**：与人物、地点、道具、伏笔、时间和因果相关的正式资料及原文证据。
3. **禁止混入**：其他书、未摘录灵感聊天、过期候选、被替换版本、无关全文、AI猜测和其他审查员报告。

必须资料超预算时应停止并重新整理，不得悄悄删掉硬约束。可选资料按优先级取舍，并记录未纳入项目及原因。

## 2. 一次AI任务怎样运行

```text
作者触发任务
→ 冻结当前书、业务对象和活动版本
→ 确认成员、模型和输出合同
→ ContextCompiler编译必须资料与按需资料
→ 生成可追溯ContextPack
→ 编译岗位提示词、任务提示词和输出规则
→ 调用模型
→ 校验身份、格式、来源、字数和业务边界
→ 保存候选或审查报告
→ 作者选择、融合、修改或确认
→ 只有确认版本才能成为下游正式依据
```

### 2.1 任务冻结内容

- `owner_id`、`book_id`；
- 开书、设定、卷、事件、章纲、正文活动版本；
- 岗位与模型绑定快照；
- 提示词模板版本；
- 资料包、未纳入资料及原因；
- 输入与输出预算；
- 上游工作流指纹。

生成期间上游正式版本变化时，旧结果不能覆盖新版本，只能作为过期候选重新生成或重新确认。

### 2.2 提示词组成

1. **岗位合同**：身份、擅长、职责、边界和工作方法；
2. **全局硬规则**：只处理当前书；不展示思维链；不伪造来源、状态或异模型意见；候选不自动成为正史；保护人物生命力和合理惊喜；
3. **任务说明**：本次节点与目标；
4. **输出合同**：字段、长度和合法值；
5. **本书岗位补充要求**：团队页可为每本书的每位成员保存最多4000字补充要求，版本化保存，不能覆盖系统硬规则；
6. **冻结资料包**：正式资料和按需证据；
7. **技术修复提示**：只修格式，不借机改变创意。

提示词模板按内容生成指纹和不可变快照。模板改变生成新版本，旧版本保留追溯。

> “岗位补充要求保存成功”只表示配置已版本化。验收某次任务还要查看调用快照，确认补充要求确实进入了该次提示词。

### 2.3 压缩与整理

1. **上游定长整理**：开书、设定、上一卷或上一事件结算整理为任务摘要；
2. **正文专用胶囊**：只拿完整本章章纲、最近状态、前章尾部、承诺与风格胶囊；
3. **检索证据块**：按任务检索实体、伏笔、时间、因果和原文；
4. **预算裁剪**：硬资料不静默裁剪；可选资料按优先级、重复度和预算纳入，排除有记录。

Token估算对中文字符按约1 Token、其他字符按约0.25 Token计算，仅用于预算，不等于厂商最终计费。

## 3. 全流程介入图

```text
开书信息（作者填写）
→ 设定小组独立提案 → 主编融合 → 作者逐项确认
→ 编剧A/B独立卷纲 → 主编融合 → 作者确认
→ 编剧A/B独立事件 → 主编融合 → 作者确认
→ 指定编剧拆事件章节序列；作者可选让另一编剧挑战关键节点 → 作者确认
→ 指定编剧逐章细化章纲；作者可选让另一编剧挑战钩子或冲突 → 作者确认
→ 单一主笔写正文；两次明确技术失败后副笔最多接管一次
→ 确定性代码硬检查
→ 事实 + 文学 + 体验三审并行、互不偷看
→ 主编汇总分歧 → 必要时主笔定点修改 → 作者定稿
→ 章节结算 → 事件结算 → 卷结算 → 下一卷
```

开书信息不靠AI猜测。结算只记录正式正文实际发生的内容，不能把未来规划倒灌为正史。

## 5. 十一名成员怎样工作

默认模型可版本化调整。这里写当前代码默认值；真实任务以团队页和任务日志里的模型快照为准。

### 5.1 貂蝉｜主编｜Kimi K2.7 Code

- **介入**：设定、卷纲、事件候选完成后融合；三审后汇总；卷末承接下一卷。
- **接收**：当前任务包、已保存独立候选、作者选择与意见、正式上游约束。三审汇总时只读三份报告，不重审正文。
- **方法**：先找共同硬约束，再比较因果、人物动机、代价、卷目标和下一接口；冲突处择优，不机械平均；保留分歧和未知。
- **输出**：设定/卷纲/事件融合稿；三审优先级与保留分歧。
- **边界**：不伪造共识，不替作者确认，不以多数票压过事实错误，不在汇总时偷改正文。

### 5.2 西施｜副编｜MiniMax M3

- **介入**：副编岗位代表资料准备职责；当前实现主要由确定性`ContextCompiler`在每次任务前完成编译、压缩、去重、来源标注和排除记录。只有确有需要并发生真实模型调用时，西施才显示正在工作。
- **接收**：当前书正式对象、版本、来源、预算、检索重点、排除规则和正式结算。
- **方法**：确定性结构化直达 → 全文/向量/关系/时间因果检索 → 原文回查；去重排序；编译资料包；记录纳入与排除。
- **输出**：ContextPack、来源/排除清单、状态导航、实体和伏笔检索结果。
- **边界**：只准备资料，不判断设定真假，不决定剧情，不把猜测写成事实，不混书，不把规划当正文。事实与逻辑判断由文姬读取已经编译好的资料后完成。
- **真实状态**：确定性服务不能伪装成副编模型调用；团队状态、任务和模型快照必须如实。

### 5.3 婉儿｜编剧A｜DeepSeek V4 Pro

- **介入**：独立卷纲A、独立事件A；被指定时生成事件章节序列或单章章纲。
- **接收**：压缩开书与活动设定、卷任务和软节奏模板、作者意见、事件种子、上一事件真实结算、活动卷纲与完整事件。
- **方法**：明确进入状态和本层责任；建立触发→行动→阻力→选择→代价→结果因果链；服务卷目标但不写死场景；保留合理惊喜；新设定无依据时标未知。
- **输出**：完整卷纲A、事件A或章纲。
- **边界**：不看B未提交方案，不跨卷决定全局，不把模板当公式，不为反转破坏人物动机。

### 5.4 红玉｜编剧B｜GLM 5.2

- **介入**：与A并行生成卷纲B、事件B；被指定时设计章纲。
- **独立性**：与A使用同一任务依据，但有独立模型、任务、资料包快照和输出；不是检查A，也不能偷看A后换词。
- **方法**：从关系、铺垫兑现、信息差和长期后果寻找完整另一条路线；不为不同而猎奇；明确必达与自由区；用下一接口检查结尾。
- **输出**：完整卷纲B、事件B或章纲。

### 5.5 文姬｜设定/事实审查｜GLM 5.2

- **介入**：设定阶段；正文后的事实一致性审查；资料库事实候选提取。
- **设定资料**：全部开书信息、当前设定项、作者意见、已确认相关设定。
- **审查资料**：不可变正文、章纲和上游约束、前文状态、相关正式原文与资料库证据；不读文学和体验报告。
- **方法**：设定时守住开书承诺，补世界逻辑、人物边界和可持续冲突。审查先查人物/能力/物品/地点/时间/数量/状态，再查因果、认知边界和伏笔；问题带位置、双方证据和修复动作；证据不足标未知。
- **输出**：设定候选、事实报告、最多16条待复核事实候选。
- **边界**：使用副编/`ContextCompiler`已经编译的资料做判断，不负责检索编排或资料包压缩；不评价文笔，不把软偏好判违规，不抹掉人物合理变化。

### 5.6 秋香｜主笔｜DeepSeek V4 Pro

- **介入**：章纲确认后写正文；硬检查或三审要求时定点修改；作者要求时整章重写。
- **接收**：完整本章章纲；约1500字工作单、650字开篇胶囊、600字阶段结算、400字前章状态、500字前章尾部、400字承诺与伏笔、风格胶囊和少量正式证据。不接收整书全文或其他书。
- **方法**：先完成必达结尾与禁区；把纲要写成场景、行动、对话和反应；保持人物可辨识；在自由区创造细节和惊喜；结尾准确交接下一章。
- **输出**：目标2700—3200有效字，硬范围2350—3650；每次修改创建新版本。
- **边界**：不擅改卷/事件结果；不输出提示词、JSON、内部说明或占位符；不写成逐字段说明或模板腔。

### 5.7 湘君｜副笔｜Kimi K2.7 Code

- **介入**：主笔首次明确技术失败后，同一模型只重试1次；两次明确失败、超时或不可用后才接管，且整章最多接管1次。供应商结果未知先调和，不盲重试。
- **接收**：与主笔同一冻结任务包、两次失败证据和接管原因。
- **规则**：按同一章纲、目标2700—3200与硬范围2350—3650完成；显示真实模型和原因；接管仍失败就交作者处理。
- **边界**：作者对文风、情节或表达不满意不属于技术失败；不伪装第二位独立主笔，不并行竞写，不因风格偏好抢占主笔，不产生两个正式版本。

### 5.8 妲己｜文学审查｜MiniMax M3

- **介入**：正文通过硬检查后，与另两审并行；修改后按新版本重审。
- **接收**：不可变正文、章纲、写作合同、风格胶囊、必要近章对照和少量证据；不读另两份报告。
- **方法**：查场景、叙述、节奏、情绪、人物声音、重复、空泛和模板腔；保护作者风格；每条问题定位原文并给动作。
- **输出**：通过/需修改/阻断；最多8项问题、分数和文学风险。只描述可观察AI腔，不判断作者身份或AI概率。

### 5.9 昭君｜体验审查｜Doubao Seed 2.1 Turbo

- **介入**：与事实、文学审查并行。
- **接收**：当前正文、前章必要衔接、章纲、目标读者、情绪目标和少量证据；不读其他报告。
- **方法**：按阅读顺序标出跳读、困惑、反感、无感和期待位置；区分个人偏好与广泛风险；检查情绪兑现是否有铺垫和代价；敏感内容给位置和处理动作。
- **输出**：最多8项问题、分数、读者风险和敏感内容风险，前端转成自然语言。

### 5.10 道韫｜研究｜DeepSeek V4 Flash

- **介入**：只有当前任务需要现实知识、专业常识、历史背景或术语核实时按需触发。
- **接收**：明确研究问题、当前书范围、允许来源、所服务对象和必要虚构规则。
- **方法**：区分正式来源、可靠二手来源、推断和未知；给适用范围和不确定性；转成创作可用材料。
- **输出**：研究摘要、来源、限制和事实候选。
- **边界**：不无来源断言，不用现实资料推翻明确虚构规则，不直接改剧情或正史。

### 5.11 弄玉｜来源与版权｜Kimi K2.7 Code

- **介入**：导入正文、外部引用、相似风险和发布前来源审查；硬检查发现来源不清时。
- **接收**：当前书导入来源、引用片段、正式正文和来源记录；不拿其他用户书籍当素材。
- **方法**：判断作者原文/正式引用/公共事实/新生成；检查长度、来源和边界；只报告可观察相似；给改写、缩短、标注或移除动作。
- **输出**：来源记录、风险、相似位置和处理建议。
- **边界**：不混入其他书，不保存密钥隐私或付费全文，不用模糊指控代替证据。

## 6. 各节点怎样设计、融合与确认

### 6.1 开书

作者输入书名、卖点、题材、标签、目标读者、总字数、主角、初始目标、金手指、开篇场景和自定义想法。这是全书源头，不从其他书、聊天或AI猜测补齐；未填的可选项保持未知。

### 6.2 设定

**候选**：设定小组成员读取同一份最小必要资料但独立生成；单个候选通常80—220字；不显示JSON、模型指令或工作流术语。作者可采纳、修改、重写或补充。

**融合**：编辑只读取已保存候选、作者选择和当前设定依据；单项答案通常约300字，并附少量重点、风险和待确认问题。未确认内容不进入正式资料库。

### 6.3 分卷

编剧A/B都要输出：卷名和开始状态；核心目标、冲突和失败代价；人物变化；事件序列及每个事件的进入、触发、行动、结果、下一接口和章节范围；信息揭示；压力升级与恢复；卷末状态、遗留线索、下一卷触发；必达、禁区、自由区和待确认问题。

两案独立保存后，主编比较因果、人物、代价、节奏和长线价值，不机械平均。融合稿仍需作者确认。

### 6.4 规划·事件

编剧A/B都要输出：事件标题及卷责任；开始状态、触发、参与人物与目标；阻力、选择与代价、信息变化；局部推进、必须结果和自由区；结束条件、下一事件影响、人物弧与卷高潮贡献；建议章节范围和未知项。

后端保留结构字段，前端默认转成“上一幕、当前困境、必须选择、可能代价、下一幕钩子”的故事预告；可切换大纲模式，但默认不把内部字段堆成配置表。

### 6.5 事件章节序列

**主方案由指定编剧完成，不是A/B两案再融合。**

编剧先评估事件结束条件需要多少章，再生成连续章节：章节号和标题、事件责任、开始状态、人物目标、冲突、选择与代价、信息变化、故事节拍、结束状态、下一章接口、软建议和自由区。后一章开始必须承接前一章结束，整套章节覆盖事件结束条件。

作者可选“请另一位编剧看看”。挑战者必须是另一位异模型编剧，读取活动卷纲、完整事件、当前章链候选精确版本和作者关注点，输入预算12000 Token/28000字符，输出不超过1800 Token。只给最多3条关键替代思路，每条写明另一种走法、可能收益、代价和对后续章节的影响；不完整重写、不自动融合、不写正式版本。

### 6.6 单章章纲

**主方案由指定编剧细化，不走双方案融合。**

资料包含活动卷纲、完整事件、确认章节序列、最近1—3章章纲和作者意见。输出本章功能、开始和必达结束状态、出场人物、冲突、情绪目标、场景节拍、信息控制、伏笔动作、结尾钩子、必写、禁区、候选和自由区。

作者可选让另一位异模型编剧挑战当前单章候选。挑战资料冻结完整事件、确认序列、目标章纲精确版本和必要近章接口，输入预算14000 Token/32000字符，输出不超过1800 Token。只挑战核心冲突、人物选择、转折或结尾钩子中的关键点，最多3条；作者可忽略，候选换版后旧建议不再作为当前建议。

### 6.7 正文与三审

- 单一活动主笔写正式初稿。主笔首次明确技术失败后只重试1次；供应商结果未知不盲重试；两次明确失败、超时或不可用后副笔才接管，且最多1次。风格不满意走作者修订，不触发接管。
- 硬检查由确定性代码执行，不属于任何AI成员。顺序为占位符/内部指令 → 标题/格式 → 正文长度 → 版本/来源 → 版权风险；优先目标2700—3200有效字，低于2350或高于3650直接打回；最多2次定点修复，仍失败则阻断。
- 事实、文学、体验三个职责读同一不可变正文，用不同模型并行，互不读报告。
- 主编只汇总报告并保留分歧；事实硬错误不能被两份主观“通过”投票覆盖。
- 正常生产最多自动定点修改2轮；新稿若破坏已通过硬门禁，就拒绝新稿并保留上一版本，冲突交作者。

## 7. 输出和前端规则

### 7.1 后端与作者界面分层

- 模型与后端可用严格JSON校验和保存；
- 作者页面必须转为自然语言卡片、故事摘要、报告和明确操作；
- 不显示JSON键、内部枚举、提示词指令、检索分数、数据库字段、Token日志、异常堆栈或思维链；
- 技术进度翻译成“正在核对人物状态”等大白话。

### 7.2 输出门禁

- 身份必须与任务指定成员一致；
- 正文版本、模型快照和业务对象必须与冻结任务一致；
- 格式错误只做技术修复，不改变创意；
- 卷纲与事件最多2次技术尝试；
- 三审报告可做1次格式修复，仍失败则阻断；
- 结果状态未知时不盲重试，避免两个正式版本；
- 正文修改创建新版本，不覆盖旧版。

### 7.3 作者意见优先级

1. **必须遵守**：除非与正式事实冲突，否则是硬要求；
2. **尽量照顾**：强偏好，冲突时说明取舍；
3. **灵感参考**：可吸收、重组或不用；
4. **我想先问问**：只回答，不自动改变正式对象。

独立灵感聊天不自动进资料包。只有作者主动摘录并绑定到设定、卷、事件、章纲或正文后才成为正式输入。

## 8. 上下文与检索

### 8.1 节点资料矩阵

| 节点 | 必须接收 | 明确排除 |
|---|---|---|
| 开书 | 作者填写的全部开书信息 | 其他书、聊天、AI猜测 |
| 设定 | 开书、当前设定项、作者意见、已确认相关设定 | 未确认候选、其他书、无关正文 |
| 分卷 | 压缩开书、活动设定、题材/节奏、卷想法、上一卷真实结算 | 未来候选、无关全文 |
| 事件 | 压缩开书/设定、完整活动卷纲、事件种子、上一事件结算、作者意见 | 其他卷候选、未确认灵感 |
| 章纲 | 压缩开书/设定/卷纲、完整事件、确认章节序列、作者意见 | 无关事件全文、未来正文猜测 |
| 章纲挑战 | 同一冻结上游、精确主方案版本、作者本次关注点 | 其他候选、聊天、审查报告；结果不自动进入后续资料包 |
| 正文 | 压缩卷/事件约束、完整本章章纲、近章状态、前章尾部、正式证据 | 整书全文、其他书、审查报告 |
| 事实审查 | 正文、章纲、上游硬约束、正式事实与前文证据 | 文学和体验报告 |
| 文学/体验 | 正文、章纲、风格/读者、必要近章对照 | 其他审查报告、无关资料库全量 |

### 8.2 混合检索顺序

结构化直达 → 全文精确检索 → 向量语义检索 → 关系检索 → 时间/因果检索 → 正式原文回查。检索不依赖单一相似度阈值；结果带来源、版本、对象和证据；摘要只导航，不能单独裁决事实。

### 8.3 长期防跑偏

卷纲约束事件，事件链约束事件大纲，事件大纲约束章纲，章纲约束正文。规划写未来，结算写真实发生。每章保存进入/结束状态，每事件和每卷用真实结算衔接后续。上游版本变化时，下游旧候选失效或重新确认。

## 9. 怎样调整每个成员的质量

### 9.1 不改代码

- 团队页修改本书某成员的岗位补充要求，最多4000字；
- 在每个业务节点写作者意见并选择优先级；
- 更换岗位模型绑定并产生新版本；
- 选择、混合或放弃方案；
- 指定要保留的段落和重写目标。

推荐写法：

```text
关注什么：人物选择必须付出真实代价。
优先顺序：先人物动机，再反转，再节奏。
不要做什么：不要靠突然出现的新能力解围。
输出习惯：重大转折写清触发、选择、代价和后果。
不确定时：列为待确认，不自行补成设定。
```

### 9.2 需要改规格和代码

- 单成员节点改为双成员独立方案再融合；
- Token/字符预算和检索数量；
- 输出字段、问题数、正文字数；
- 重试、副笔接管和自动修改轮数；
- 审查职责边界；
- 必须读取和必须排除的资料类型。

这类调整必须同步工作流、Agent、上下文、质量、API、验收和测试，不能只改提示词。

### 9.3 调整后验收

1. 显示真实成员和模型；
2. 资料包只含当前用户、书、对象和活动版本；
3. 硬资料未被静默删除；
4. 岗位补充要求进入实际调用快照；
5. 输出符合结构、字数和边界；
6. 页面无技术字段、内部指令、乱码和思维链；
7. 候选不自动成为正式版本；
8. 上游改变后旧候选不污染下游；
9. 多书切换不串任务、资料、提示词和状态；
10. 失败、重试和接管记录真实。

## 10. 当前真实现状和质量关注点

1. 团队固定11名；事实审查由“设定”职责成员承担；小文秘书不是第12名。
2. 卷纲和事件已是双编剧独立方案加主编融合，作者最终确认。
3. 事件章节序列和单章章纲只有一个正式主方案；作者可选让另一位异模型编剧提出最多3条非正式挑战建议，不自动融合。
4. 正文是单一主笔；主笔最多两次明确技术尝试，之后副笔按同一冻结资料包最多接管一次。
5. 三审是三异模型独立审查，主编最后汇总。
6. 压缩、去重、版本冻结和资料包编译很多由确定性代码完成，不能伪装为模型工作。
7. 岗位补充提示词必须用调用快照验收；保存配置不等于所有生产链已注入。
8. 当前正文硬合同是目标2700—3200有效字、硬范围2350—3650，旧通用提示不得覆盖。
9. 后端JSON和作者界面分层；作者看到自然语言和故事化表达。
10. 所有预算是当前代码配置，不是创作公式，可以经测试调整但不能破坏隔离和追溯。
