# 时光机与故事线库完整设计方案

版本：开发规格 v2.0，2026-09-10。完成本地方案与代码证据审计，补齐第22节实施合同；本轮仅文档维护，未实施、未部署。第22节是当前工程与验收细则，前文是产品说明；同项冲突以第22节为准并在实施前原位统一。旧业务只作参考，不拼接。执行状态见[本批记录](../coauthoring-v7/docs/worklists/TIMEMACHINE-192.md)，规格存在不代表功能已实现。

方案范围：故事线资产、推荐、全书方案、分卷容量、上下文、成员执行、事实/结算、树与轨迹、编辑和后台、失败恢复与发布。历史授权与进度不覆盖当前“先核查方案”的任务；后续按明确的实施授权与第22节分批执行。

## 1. 本轮确定的方向

- 作者页面继续使用“分卷”，不新增“大故事单元”导航或替换现有卷、链、章名称。
- 主要故事指有完整目标、过程、结果的一段故事。多个主要故事围绕主线展开，为人物提供连续的能力、认知、资源、关系或处境变化；不要求每次都升级或获胜。
- 故事数量只是篇幅容量参考，不是最低合格线。取消此前“低于34/50/84个必须补足”的提议；更不能靠拆步骤、重复冲突凑数。
- 故事线根据题材、融合题材、人物和作者偏好推荐，不把同一套模板套给所有作品。
- 首次进入自动启动主编推荐流程，作者选择具体故事线后，再设计三套完整全书方案。
- 同时显示可选的故事组织偏好，默认“由主编推荐”；作者可选择集中讲一个核心故事或几个重要故事交织，不必先填写主线数量。群像意愿独立，不与主线结构互斥。
- 开篇尽早建立期待：约300字抓住注意、首章形成明确期待、前三章有推进或小兑现。具体手段服从题材，不强制爆炸、打脸、死亡。
- 主角历程、全书情绪方向、长期期待、分卷故事和完结落点共同构成全书骨架。最后一卷收束，不再显示“接下一卷”。

## 2. 页面目标与边界

作者看完应能回答：这本书讲什么、为什么值得追、谁会经历什么、哪些故事交织、各卷大致发生什么、最后如何完结。

时光机负责全书方向和分卷粗规划，不提前完成所有人物人设、事件链和章纲。采用后给下层提供清楚的任务与边界，也保留后续创作调整空间。尚未发生的规划不成为正文事实。

## 3. 故事线库：按用途组织，按作品推荐

### 3.2 群像与双主角

人物组织与主线结构分开保存：单主角、双主角、群像描述人物组织；单主线、多主线描述核心追求的组织。一位主角可以推动多条主线，多位主角也可以共同推动一条主线，不能根据人数或总字数机械确定。根据已有开书信息推荐，作者可调整；修改已确认主角结构要说明影响，不能默默替换主角。

群像中，每个主要人物或群体有自己的目标、行动及落点，多条线会交汇、相互促成或阻碍。禁止全员只是帮助主角，禁止仅增加视角数量冒充群像。双主角明确双方推动故事的职责，不强制戏份平均。群像不必多视角，单主角也可以有丰满配角；故事组织和叙述视角分别处理。

### 3.2.1 主线、支线与完整故事的区别

| 概念 | 职责与判定 |
|---|---|
| 全书主线 | 承担核心追求，有持续行动、重要转折及终局职责；一条或多条由具体方案决定 |
| 贯穿支线 | 重要关系、秘密或独立追求，跨多个卷发展并影响全书 |
| 阶段支线 | 某阶段展开并收束的独立追求，可与主线汇合 |
| 本卷核心故事 | 本卷重点解决什么、推进哪些主支线，不因此新建一条全书主线 |
| 主要故事 | 有目标、过程、结果的完整故事段落，可直接服务主线，也可服务支线；其数量不等于支线数 |

成长、爱情、经营等是内容类型，不预设主支线身份。恋爱作品的爱情可以是主线；同一类型也可以形成多个人物的不同具体线。主编推荐时提出主支线建议，三套方案各自确定结构与数量；作者可以调整。多主线不等于平分戏份，每卷说明当前重点推进哪些、哪些暂隐及重新承接位置。

### 3.3 题材与融合题材推荐

主编同时读取题材组合、主辅风格、创意尺度、核心卖点、人物与世界。题材用于解释推荐，不作为排他过滤器。

示例：仙侠+经营可以推荐技艺成长、工坊经营、伙伴和势力建设；悬疑+恋爱可以推荐调查与信任变化，但不能因融合恋爱而强制破坏推理；体育+群像可以推荐竞技成长、团队磨合、宿敌与职业选择；日常+奇幻可以围绕非人伙伴与共同生活，不必拯救世界。

推荐必须指出本书具体人物、目标及可能变化。缺少配角时可提出候选身份，明确尚未设定，不能编造为已存在角色。融合题材不能简单拼接各题材固定套餐；主编判断哪些形成同一个故事，哪些独立展开。作者明确不要的内容不得自动加入。

### 3.4 每条资产的后台结构

稳定ID、名称、短简介、适用情形、设计要点、变体、可搭配类型、语义重复或区别说明、题材化示例、可参考方法ID、各层用法、版本与状态。默认展示名称和短简介，展开查看其他字段。

故事线资产回答“写什么关系或追求”；方法资产回答“怎样展开”。关联方法是参考，不是必须引用。初始通用简介建议一两句话，题材化例子按需读取，不整库注入。

## 4. 作者流程与手机交互

### 4.1 首次进入

进入后立即建立或恢复本书推荐任务，显示主编正在准备推荐。系统先检查当前正式版本对应的短卡；没有或过期则由资料成员整理，之后主编推荐。资料成员实际工作时显示其真实身份，不能伪装主编已在设计。

进入即显示“你希望故事怎样展开？”选择区，不等待推荐完成、不设单独必答步骤。三项单选，手机纵向卡片：

| 作者选项 | 页面介绍 | 后台偏好 |
|---|---|---|
| 由主编推荐（默认） | 根据本书人物、题材和想写的故事，推荐合适的安排。 | 自动判断，不预设主线数 |
| 集中讲一个核心故事 | 围绕一个主要追求展开，其他故事共同推动它。 | 单主线 |
| 几个重要故事交织推进 | 几个重要目标分别发展，相互影响，共同走向结局。 | 多主线，数量由主编建议 |

作者明确的既有同项偏好应恢复，不用默认值覆盖。下方独立选项“也希望配角拥有自己的完整故事”，介绍“让重要人物有自己的目标和选择，他们的行动会影响全书走向”。它表达人物展开意愿，不自动把作品改为多主线或增加叙述视角。已有群像、双主角信息直接继承并可见，不要求重新作答。

主编推荐同时返回建议组织方式及一句本书理由。“由主编推荐”仍保持自动偏好，不因收到建议就替作者锁定。作者在推荐中途修改选择，系统保留其最新版本；旧推荐不得覆盖新选择。改组织方式不清空已选故事线，开始设计时按最新版本重新判断主支线。若建议与明确选择冲突，提出具体建议由作者决定，不能暗改。

推荐完成后显示主编大头像及引导语：“老板，我们来设计全书骨架。这是我为本书推荐的故事线，您看看，还想加入哪些？”

每张卡为“具体类型＋本书一句话介绍＋选中状态”。推荐可预选，但作者点击开始设计前可自由调整。没有固定选择数量，不铺满36项；推荐多少由作品需要决定。至少需要表达一个可推进的核心故事追求，不要求一定选中名为“成长”的标签。

### 4.2 添加与选择

作者选择小类型，不选择“个人命运”等整个分类。点整张卡可切换，选中不仅依赖颜色。点“添加其他故事”打开独立面板：搜索、按用途分类浏览、简介、选择；提供“我想加入……”文本输入。新增通用项需转化为本书建议后再进入正式设计，不伪装已有具体剧情。

手机底部显示已选数量和开始设计操作，已选项可展开移除；不得遮住正文、输入法或设备安全区。分类导航可以换行或纵向选择，不把入口藏在不可察觉的横向滚动里。桌面使用同一数据和流程。保留输入、滚动与选择，失败不清空。

### 4.3 合并与主次建议

首次推荐前，主编先处理明显重叠；作者调整后，在开始设计时统一检查，不每次勾选就调用模型。

没有需要决定的问题直接设计；有问题则就地展示具体建议：例如两条都围绕同一工坊经营，建议合成一条并保留两方面意图。操作“接受建议／分别保留”。多条不重叠但篇幅有限时建议哪些贯穿、哪些阶段展开，作者可修改。

不因数量多自动删减，不静默改变作者主次。一次汇总相关建议，避免连续弹窗。作者分别保留后不反复要求合并；后续设计通过不同目标、关系或阶段明确区别。

## 5. 结果页：三套完整方案

三套回应同一作者选择和正式上游，核心行动路线、冲突组织、人物关系或结局实现路径有实质差异，不能擅改既有结局约束。切换卡固定标方案A/B/C并显示成员；结果内部的故事标题体现差异，不仅换文风。

明确选择单主线时三套均采用单主线，明确多主线时三套均采用多主线，具体条数可不同；自动推荐时三套可以结构相同或不同，不强制单线、多线、群像各出一套凑差异。群像及配角偏好独立继承。采用后若改结构，生成新候选并识别关联影响，原采用版本保留。

每套顶部可显示“全书主线1条 · 贯穿支线3条 · 阶段支线暂拟8条”一类概览，数字来自该方案实际记录，不是预设目标。未具体设计的数量明确为预计；同一条线跨卷不重复计数。展开显示名称、人物、目标、展开与收束卷。主要故事数量另作容量参考，不混进支线计数。

切换时整个方案内容一起变化，作者已填意见按方案保存，状态不串。每套页面如下：

| 顺序 | 默认展示 | 展开或编辑 |
|---|---|---|
| 全书概览 | 谁从何处出发、争取什么、如何走向结局 | 主要看点、整体味道、创作边界 |
| 开篇抓人 | 开头抓眼、首章期待、前三章推进 | 各项怎样承接本书卖点 |
| 长期期待 | 开篇惦记什么、想看到的变化、结尾怎样回应 | 推进到哪些卷、阶段兑现 |
| 故事线 | 主支线身份、谁的线、起点、主要变化、最终落点 | 群像归属、交汇关系、展开及收束卷 |
| 分卷 | 卷名、主要故事、转折高潮、结束变化 | 篇幅参考、主要故事清单、关系变化、期待职责和衔接 |
| 完结 | 最终冲突结果、人物落点、期待兑现 | 保留有意开放的问题及理由 |
| 操作 | 调整故事线、修改意见、采用本方案 | 新旧候选比较与版本 |

去掉无关说明、技术字段、方法编号和“设计依据”入口。上下文短卡、版本和调用记录放后台。必要失败提示与候选身份仍须明确，不能为了简洁误导作者。

### 5.1 全书基线

#### v1.6 全书方案页的故事线与交织

本次对象是全书方案页“故事线怎样交织”，不是时光树。首次设计产出主线和支撑全书方向的重要支线，不固定四条，也不把重要支线全部强制贯穿全书；局部支线与链以后按卷细化。用紧凑纵向编号目录显示：编号、主线/重要支线身份、名称、一句从起点到落点的走向。手机不挤成多栏。

目录下展示关键交织：003→001表示有向影响，001＋002表示汇合；每项有一句本书具体作用，不只写“相互推动”。点击编号查看走向及相关关系。多线时按编号定位或聚焦直接关系，不截断目录；细小碰面留给卷链。同线跨卷延续不等于两线交织。

分卷引用当前方案目录编号；切换候选时目录、关系、分卷整体更新。候选编号是方案内标识，采用时由系统映射到稳定书内ID，不能与另一候选或独立时光树演示样例强行等同。

基线是采用方案共同遵循的创作方向，包括主要看点、整体情绪、主角出发点与最终走向、作者保留与排除的内容。前端用“主要看点／整体味道／最终走向”等直白文字，不另外堆术语表。

情绪基线承接已有风格，可有局部低谷、紧张与反差；不是全书保持同一情绪。角色成长可表现为能力、资源、关系、认知或选择，不强制性格改变。全书基线在方案采用时形成版本，三套中允许的差异明确显示，不以一个隐藏基线限制三个方案。

### 5.2 开篇约束

快节奏网文默认要求：开头约300字出现可感知的冲突、异常、欲望或趣味；第一章形成明确继续阅读的期待；前三章有实际推进或小兑现，并引出后续期待。300字是设计定位，不能硬截文字或机械计数判定文学质量。

时光机给简短开篇安排，首卷继承，前三章规划落实，实际正文再检查。惊险、反差、关系、谜团、机会均可抓人，不强制固定打脸或爆炸。作者明确选择其他节奏时采用其偏好并可见记录。剧本未有运行链时不得承诺该功能已支持剧本，按本期网文实施。

### 5.3 长期钩子与阶段看点

长期期待须尽早建立可感知的苗头，贯穿推进并在结尾回应；不必首章公布谜底。不是“下次出现什么装备”等循环新鲜感，也不是后期突然出现的终局设定。

前端用三列表达“开篇让读者惦记什么／读者想看到的变化／结尾如何回应”。同义期待合并，不强制固定三条。允许一条核心期待及必要的辅助期待。阶段钩子归相关卷链，全书中只记录其对长期期待的贡献。

例如无灵根者能否立足，是处境期待；机甲能否作为伙伴被承认，是关系与世界期待。展示必须结合具体方案，不能三套照抄同一兑现路径。这里不向作者展示模型推理过程。

## 6. 主要故事数量与分卷容量

### 6.1 口径与参考

“主要故事”有相对完整的目标、发展过程与结果，围绕主线或有作用的支线展开。报名、抽签、进场不算三个主要故事；一个完整故事也可能跨卷，跨卷只算一次。多视角重复呈现同一故事不重复计数。

按平均约3万—6万字承载一段主要故事，可给出以下初始估算。它不是行业统计，也不是全题材统一标准：

| 目标篇幅 | 主要故事参考数量 |
|---|---|
| 200万字 | 约34—67个 |
| 300万字 | 约50—100个 |
| 500万字 | 约84—167个 |

数量只用于讨论容量，不强制最低数量、不因超出或低于范围阻断生成。主编结合题材、群像交织和故事复杂度解释明显偏差，必要时建议丰富故事或调整篇幅。实际字数是所有故事交织后的总叙述量，不能按故事线各算一遍再相加。

### 6.2 如何放进设计

时光机先规划全书路线与各卷，再按卷分批补齐主要故事的一两句概览；每段简述目标、过程关键变化和结果。不要一轮生成数百个细节事件。系统提供去重后的数量和篇幅估算，主编判断是否重复、平直或容量不足。

人物的稳定成长指长期有累计：经验、能力、资源、关系、地位、认知或目标逐步变化，允许失败、停顿、损失与恢复，不要求每段升一级。不要因为“成长”要求所有日常、群像或感情故事成为实力升级工具。

前端每卷默认展示最重要的故事概括；展开看该卷主要故事清单和预计篇幅。数量作为辅助信息，不做作者必须凑满的进度条。

### 6.3 分卷输出要求

每卷保存：核心故事、承接局面、目标、主要阻碍、关键推进或转折、高潮或重要选择、结果、人物及关系变化、故事线与长期期待贡献、后续衔接、主要故事清单、篇幅估算。

v1.6卷方向卡：默认卷名与一句主要故事；展开显示“这一卷写什么、主要故事推进、本卷关联编号及具体交织、关键转折、高潮与本卷兑现、人物变化与得失、本卷结束与后续”。主要故事概括目标、关键过程及结果，不提前拆对白、场景、章节，不固定每卷四段。转折、高潮和兑现重合时可合并，无关维度省略。最后一卷末项改为全书收束。

本卷须有自己的阶段兑现，不能只引出下一场危机；日常、情感、经营可用关系或生活成果兑现，不强制战斗与灾变。不为每卷凑齐全部编号。卷取方向卡及直接相关线卡，不注入全书所有关系。以上均为规划，不能提前写成正文事实。原型默认展开“给这片大陆搭个脚手架”的详细卡，其余卷可以自行展开。

明确本卷重点推进的全书主线、其他主线的推进或暂隐、支线新增与收束；前端展开显示“推进哪些线／新增哪些线／收束哪些线”。不把每卷核心故事都计算为新增全书主线，也不因一卷暂隐就把该线标记完结。

这是判断维度，不是每卷都必须有爱情、背叛、伤亡或强反转；无关项省略。最后一卷只显示全书收束与人物落点，不统一生成下一卷任务。未兑现期待要么安排回应，要么明确是有意开放，不能遗漏后称开放式结局。

## 7. 向卷、链、章传递

### 7.1 v1.7 职责与结束条件（待本轮作者确认）

全书故事线管长期追求，卷管阶段局面，链管相对完整的具体故事。不能硬性规定一卷/一链等于一条支线；链可推进主线、支线或多线。卷的链数由阶段故事需要决定，不能按全书线数分配固定链数，也不要求每条链结尾都引出新悬念。保持既有稳定ID，不为呈现同一关系重复创建故事。

全书线卡补充四项：追求什么、关键变化、怎样才算核心期待得到回应、预计哪些卷推进与收束。每卷对每条线单独指定职责及一句具体目标：推进、转折、阶段兑现、最终收束。它们是本卷计划动作，不替代该线实际生命周期；同一卷可承担多项职责。未列出的卷不自动承担推进任务。例：003匠人合作、004历史误判在第7卷完成核心回应，第8卷重点完成001工程与002自主选择；已获得的联盟和知识作为成果继承，不因被使用就重开旧线。

卷方向卡必须有阶段目标、阻力、主要故事推进、线职责、阶段结果和结束条件。结束条件描述足够明确的故事结果，而不是“写够字数/完成固定链数”。例如第7卷结束须联合工程完成局部验证、各方合作职责落定、误判原因获得证据解释；完整天劫可留到终卷，不阻塞本卷结束。可按题材合并表达，不强制成功、战斗、牺牲、性格改变。

链在后续卷设计中生成，包含当前局面、本链目标、关键阻力与变化、结束条件、后续保留项及所影响线ID。订单链在验收及责任落定时可以结束，即使旧零件谜团仍未解。目标失败、明确放弃或改变亦可形成完整阶段结果；但须由成员依据正文说明结果，不把任务技术完成当作叙事完成。若原计划要求成功而正文实际失败，标记偏离并定向修订依赖计划，不能悄悄宣布原计划成功。

正式正文接受后，记录成员结合正文证据判断阶段结果及尚欠事项；系统保存不可变来源、版本、权限、幂等和状态，不能只靠关键词/字数决定完结。证据不足保留待核对；章节数量到达计划值但关键结果未发生，不能自动收束。作者已接受正文不因计划不符而自动覆盖。

下一条链上下文为“本卷阶段目标与职责＋当前链卡＋直接相关线卡＋必需前文实际结果”。结果卡记实际事件、资源/关系等变化、未解事项、证据引用、版本和对计划的偏离；不要重复搬运已完成链全文。必要原文通过限定书籍和版本的工具补读，重要事实缺失不静默截断。计划终点与当前事实分栏；前端显示“本卷怎样结束／留给后续什么”，内部来源引用留在详情或后台。

审查重点：全书期待是否有去向、每卷是否有阶段兑现、链是否有可辨认结果、未解伏笔是否有归属、提前收束线是否被终卷机械重开。审查不给所有作品强加相同节奏，不因某卷没有爱情或强反转而失败。资料供给按已有token预算动态编译，不把全书关系图送给每一章。

前端保留故事目录与关键交织，点编号查看线目标和卷安排；分卷把“关联编号”替换为“编号＋本卷职责＋具体结果”，然后显示结束条件及交接。原型首卷提供“链交接示例”帮助核对边界，它不是提前生成的真实链。全部状态标规划候选，不冒充实际正文。正式开发需覆盖未设计、准备中、已形成候选、部分失败与续做、已采用、来源改动待核对；本轮静态原型不伪装真实任务流程。

| 层级 | 继承什么 | 本层补充什么 |
|---|---|---|
| 卷 | 采用的全书方向、相关故事线、当前卷主要故事、关键结果、人物起止变化与期待职责 | 具体矛盾过程、人物安排、转折高潮与链分配 |
| 链 | 本卷目标、当前主要故事及相邻衔接、相关人物事实与规则 | 行动、阻碍、选择、事件结果与章分配 |
| 章 | 当前链进度、章职责、实际已发生事实、相关关系状态和局部规则 | 场景、叙述、对白、节奏与章末期待 |

同一主要故事可包含多条链，也可跨卷；使用稳定ID保持归属，不能强制主要故事等于链。下层可补全实现方式，若改变采用的关键结果、人物落点或世界规则，提出上游修订并标记受影响范围，不静默改写。

规划终点不是当前人物状态。后续生成同时区分“现在实际发生到哪里”和“计划最终走向哪里”，避免角色提前知道真相或提前获得能力。

## 8. 信息短卡与上下文规则

### 8.1 六栏模板

1. 创作要求：题材及融合方式、主辅风格、创意尺度、目标篇幅、明确偏好。
2. 主角与起点：已确认的核心人物、处境、当前关系；未知项不补造。
3. 核心卖点：关键能力、反差、主要吸引力及必要边界。
4. 世界背景：足以理解宏观故事的环境、资源与冲突来源。
5. 影响全书的规则：会改变路线可行性、人物身份、死亡或能力结果的条件。
6. 已有全书意图：前序已采纳的开局、结局、主题方向，明确是规划。

资料成员整理而不创作新事实。原始资料保留，卡附来源及版本；不是整套设定的无损替代品。不重复装入同一事实的正文、规则字段和审查评价。方法资产不是作品事实，单独提供。

### 8.2 注入分工

系统：鉴权、版本选择、源读取、缓存、token预算、工具授权、防重、状态与保存。资料成员：判断相关性、合并重复表达、填卡、发现关键缺项。主编／设计成员：理解创作意图、推荐与设计、按需要申请补读和方法。

推荐阶段注入短卡、当前故事组织与人物偏好及故事线轻目录，需要时查具体资产；方案阶段注入短卡、作者最新选择及意见、当前方案任务、已选方法摘要；分卷细化阶段只注入该方案必要基线、主支线职责、当前卷及相邻衔接，不重复携带另外两套方案全文。作者偏好与主编建议分别保存，不能把建议冒充指令。

成员可以按用途搜索全库，但不要求查询或读完全部方法。工具只返回本次相关结果；方法选材后清理无用工具输出。系统不靠关键词硬判文学相关性。找不到方法可原创设计，方法是参考，不能以“未引用某方法”直接否决作品。

### 8.3 预算与分批

不设一个通用于所有模型的字符安全值。模型路由提供实测可用上下文及输出预算，系统按实际token计量，为输出和工具补读预留空间；后台同时显示字符数方便理解。没有可用预算配置不得盲发超长请求。

开发时为短卡整理、推荐、单套方案、分卷补全分别配置并测试预算。预计超限时先去重复表示、缩小当前工作范围，再让资料成员重整相关卡或拆批；不能截断关键条件、静默删原文、反复用同一超限输入重试。短卡长度以必要信息完整为准，R191的594字符只是一个人工样例，不作为目标上限。

资料过多时分源整理再合并，保留关键事实出处。每轮传入任务所需事实与近期产物，不携带无限历史会话。增加批次不固定为一次只设计一个微小条目，按实际输出大小和速度测试调整。

## 9. 成员执行节点

### v1.8 三名编剧与真实归属

最新显示修订：三个切换卡片固定标为“方案A、方案B、方案C”，同时保留编剧头像、姓名与职责。故事名称保留在对应结果内容，不卡在切换标签中代替方案字母；字母表示当前候选位置，不代替内部稳定ID或真实成员归属。

默认三套由三个不同的已启用策划编剧成员各负责一套，主编负责推荐、发现明显重复与定向复核，不把主编头像当作三套设计者。三位成员读取同版上游短卡和作者要求，各自规划路线并按用途查方法；初稿不互相传阅，完成后由主编比较差异，不预先固定为三种模板。负责一套的成员继续补全该套分卷，除非明确换人。

每个方案标签显示成员头像、姓名、职责与方案名。数据来自该候选任务冻结的成员快照，不按第几个标签硬编码；模型绑定、工具、预算及真实调用来源留在后台，成员身份不同不代表底层模型必定不同。重试保留同一候选身份，换人须记录原成员与接续成员，不伪造原作者。历史配置更新不能倒改旧结果署名。

三名成员不足时明确缺席与原因，可先完成可用成员的方案；不能把同一成员改名凑三人。并发数由供应商限流与预算决定，不要求同时发请求。每套先完成骨架，再按实际token预算分批补卷，分批持久化；任何一套失败只续该套未完成部分。进度由实际完成的结构单元计算，不按计时假装完成；未完整方案可查看但不可采用。完整且核查通过的一套不被其他失败方案阻止采用。

原型使用真实成员目录的红玉、幼薇、苏映棠与头像，明确“席位演示，样例非成员实际生成”，不能将手写候选冒充模型实测。正式UI成员由任务返回，数量状态与头像失败回退（姓名首字）也须覆盖。

岗位职责固定，显示姓名、头像和模型来自统一成员注册表，不在前后端各写一套。主编是本流程负责人，设计成员执行方案，资料成员提供短卡；具体可用成员需实施核查，不假称新岗位已上线。

| 节点 | 执行者 | 输入／产物 | 是否启动AI |
|---|---|---|---|
| 进入与恢复 | 系统 | 会话、书籍、版本／恢复已有状态 | 否 |
| 短卡缺失或过期 | 资料成员 | 正式源／六栏短卡及来源 | 是；有效缓存不重复调用 |

| 组织偏好、勾选、输入、保存 | 系统 | 作者选择／含主线与人物偏好的选择版本 | 否 |
| 开始设计检查 | 主编 | 最新偏好、选择与推荐／通过或具体结构、合并主次建议 | 是；相同输入复用结果 |
| 作者处理建议 | 系统 | 接受或分别保留／确定要求 | 否 |
| 三套路线 | 设计成员 | 同一要求／三套独立候选 | 是，分别保存与恢复 |

| 语义复核 | 主编 | 三套摘要及必要补读／差异、遗漏与修改意见 | 是 |

## 15. 时光树的结果与视觉

### 15.1 大树结构与故事关系分开

粗壮树干代表作品，大枝代表卷、小枝代表链。章节在链详情中展开，不默认再画一层。主线与支线是贯穿这些结构的故事关系，不等于卷或链；一条线可以跨卷推进，一条链可推进多条线。多主线不复制树干，用主线筛选与路径高亮表达，共享链只保留一个结构节点。

时光机只确定全书主线、重要贯穿线和各卷方向，不预先生成全部链与支线。具体故事随卷、链设计逐步展开；未知数量显示尚待展开，不能按字数机械补齐空故事。原型8卷、32链、8条故事线是交互样例，不是生产数量限制或实际全书规划。

全树缩略图保留所有卷的轮廓，链多时折叠成枝形；点击卷展开其链和故事线编号。大量卷使用缩放、定位与局部展开；完整序列表始终可检索全部对象，分页不截断数据。全树内大号数字为卷序号，卷内小圆数字为链序号，三位数字为故事线编号；画布外图例及详情区分语义。卷/链序号随排序更新，故事线稳定编号不变，内部稳定ID不依赖序号。

每条线拥有永久内部ID和书内稳定展示编号，如主线001、支线012；删除或归档不重用号码，标题、卷归属、排序变化不改号码。候选方案中的临时身份与采用后的书内身份分开，合并方案时系统保留映射，不让模型自行重排全书编号。

| 符号 | 语义 | 禁止误判 |
|---|---|---|
| 红色果实＋已收束文字 | 正式正文已完成该故事线的当前目标 | 规划写了结局、任务已完成、主角胜利一次不等于整线收束 |
| 绿色叶片＋伏笔编号 | 正文已埋设但尚未充分兑现的伏笔 | 所有未结束支线不能自动变成伏笔 |
| 枝梢＋推进中 | 线仍在发展 | 没有更新不等于遗忘或停滞 |
| 淡色枝干＋规划中 | 已采用但正文尚未开展 | 不计入正文已发生数量 |
| 灰色标记＋停止/撤销 | 明确弃置或不再采用 | 不显示红果实冒充兑现 |
| 待核对标记 | 证据不足、来源改动或归属未确认 | 不假装确定、也不删除原记录 |

支线收束与伏笔兑现是独立状态，一枝可以同时有果实和绿叶。一个伏笔可涉及多条线，拥有唯一ID并引用多个关联，树上引用同一伏笔，统计只计一次。若一个目标明确结束后开启新目标，优先建立关联的新线；若原收束判断被纠正，则同一线记重开事件并保留原因。

### 15.2 规划与正文

规划与正文使用独立切换视图。有正文时默认正文，没有正文时默认规划并明确尚无正文；原型初始为规划演示。规划只显示预期经过与依赖，不显示红果绿叶冒充已兑现。正文只用有效正式正文事件投影，尚未写到的卷可保留淡色轮廓，不编造链进展。画布内只显示数字与符号，不放标题、简介或长状态文字，名称、来源和状态文字放在列表与详情。

电脑采用“左侧树／右侧支线序列表”，手机采用“上方树／下方可展开列表”。列表显示编号、支线名称、状态与一句话进展。树上点击编号定位并选中列表项，列表点击定位并突出枝干；手机点编号可直接打开底部详情。点按热区至少44px，不能要求精准点叶尖。

一条线的红果与绿叶可以共存，伏笔详情按唯一ID去重。故事线编号可在不同卷链中重复显示，表示同一实体的多个推进位置，不重复计数；红果与叶片正式实现必须挂到对应收束、埋设或推进事件位置，不在每个历史位置复制当前最终状态。原型符号只演示选中范围内的当前状态，尚未实现逐章位置投影。

### 15.3 路径与交织

点击故事线高亮它经过的卷链；“交织关系”按需展示选中线的路径与直接相关连接，默认不铺满全树。结构父子线表示包含；故事推进路径表示同一线的出现顺序，不自动代表因果。承接、影响、汇合分别记录关系类型、具体卷链端点及一句原因；只因同卷出现不能建立因果连接。原型使用树外路径条与关系卡，避免手机画布交叉遮挡，后续可在选中节点之间增加连接。

规划关系由设计成员提出并随规划版本保存；正文关系由记录成员依据正式文本确认，两者不能自动互转。选择视图决定关系的数据来源。序列表可按卷、主线、状态筛选，并保留全局数量与回到全树入口；手机在当前卷展开链列表与底部详情，全树可随时返回。未归属故事有独立列表，不强行挂到任意卷。

支持缩放、拖动、回到全树、搜索编号或名称、未收束与待兑现筛选；筛选后保留必要主干和选中关系。手机默认聚焦当前卷相关枝干。详情展示目标、归属、当前状态、最新变化、关联伏笔、来源章节和历史轨迹。停止、待核对、规划中等也有独立形状与画布外文字图例，不只靠红绿颜色。

不得在官网公开暴露作者树或正文证据。分享、导出若后续增加须沿用书籍权限，本期不顺手开发公开分享。

## 16. 正文轨迹及其他旧内容怎样展示

时光机页内分为“全书方案／时光树／正文轨迹”。首次推荐和设计仍是主流程，未有正文时后两项显示真实空态，不复制规划冒充轨迹。

正文轨迹按正文阅读顺序展示，不按AI任务完成时间排序。可按人物、故事线、卷筛选，记录本次发生什么、关系/资源/认知/目标如何变化、伏笔推进、线的交汇或收束及来源章。默认一章简短摘要，展开看变化与证据，不铺满全部结构化字段。

“交汇”是可重复发生的事件，不应永久替代故事线的生命周期。线可以在交汇后继续推进、完成或暂停。人物轨迹展示正文支持的实际变化，不画凭空数值成长曲线；情绪结果是成员对文本的判断，标注为故事情绪，不声称真实读者情绪。

未解问题与伏笔分别保存：明确埋设的叙事承诺是伏笔；信息暂缺、人物疑问或事实不确定不自动升级为伏笔。正文回答问题才标回答，不能以规划答案结案。长期间隔只作可查看信息，不按“若干章未出现”直接判遗忘。

前端展示“正文已保存至第N章／记录已核对至第M章”，存在中间缺口时显示缺口及待处理数量，不用最大章号冒充连续覆盖。部分更新失败保留最后成功结果并标注不是最新状态。

## 17. 正文更新、成员判断与事务边界

1. 正文正式采用：系统保存不可变版本及正式事件，正文保存成功不依赖后续AI维护成功。未采用草稿不更新正式树。
2. 资料准备：系统取本章正式正文、有效的既有故事线/伏笔目录、相关上一状态与当前规划职责；资料成员在资料超出预算或需要相关性判断时整理补读，不能用摘要替代唯一必要正文证据。
3. 记录成员判断：识别推进、交汇、收束、埋设、强化、部分兑现、完整兑现、停止及未知，引用正文位置；“本章没出现”不等于结束。只产出变化提议，不自行改正文、编号或规划。
4. 系统验证：身份与书籍、源版本、可引用ID、证据出处、状态枚举、幂等和并发版本。结构错误可修复；有效引用不自动证明语义判断正确。
5. 需要复核的变化：与现有状态矛盾、收束缺关键结果、关联有歧义等交给记录复核成员定向核对；普通清晰推进不每次额外叫主编。仍不确定保留待核对，不强行选一个。
6. 成功应用：以一个结算版本写入增量事件和投影，更新树与轨迹；实际内容与未来建议分开。后续生成只在其依赖的必要状态可靠时继续，非相关维护失败不全书阻断。

成员判断依据：目标是否已得到明确结果，结果可以成功、失败、放弃或改变；“失败”不代表故事不完整。“弃置叙事线”与“角色作出放弃选择并完成其故事”不同，前者不是兑现，后者可以是有据的收束。

伏笔完整兑现要求文本足以回应该伏笔的核心承诺，提到一次或揭示一半只标部分兑现。人物的错误解释与真实答案区分，不因人物自信就记为世界事实。悬念故意保留可继续为叶片，不自动认定缺陷。

## 18. 版本、编号、重修与异常恢复

规划采用时系统分配稳定线ID/编号及关系；正文新出现未规划的线，成员提出新建与归属，由系统分配。无法确定归属进入“待归属”，不凭相同姓名或相似标题自动合并。合并保留旧编号别名与历史证据；拆分分配新编号并记录来自哪条旧线，不修改过去事件。

并行或乱序结算以章节顺序和当前正式版本处理。晚到旧结算不能覆盖新状态，重复事件不能增加编号或果实。涉及不同人物的同时变化可保留并行记录，但最终投影必须可重放。

正文重修建立新正式版本，系统找出依赖旧版本的变化，标记相关投影待重核，再按有效正文顺序重算受影响部分；保留旧状态历史，不直接覆盖证据。后续章仍引用旧事实时先提示冲突，不假装单章重算解决了全部下游影响。

撤回采用、改变主线、线合并拆分、角色改名、跨卷迁移等均有版本映射。改名不生成新人物或新线；计划删除不删除已发生正文。作者可以提出纠错，成员核对来源；不能直接点击果实把未发生事件写成事实。若作者明确改正文，走正文版本流程。

暂时网络错误有界重试，模型结果未知先查调用记录避免重复计费；输入超限拆批，缺关键证据补读；无权限、源消失和不可恢复格式问题明确停止相关节点。重试不会重写已经成功的正文或其他线。前端刷新只读取，不触发全书重新结算。

## 19. 时光树输入后续成员的方式

不把树的图片作为权威上下文。成员接收结构化相关线卡：稳定ID与显示号、目标、生命周期、最近进展、未解决事项、相关伏笔、实际证据及计划职责。按编号可查历史和原文，工具始终限定owner/book。

卷设计查本卷推进线及即将需要回应的期待；链设计查当前故事关联线、伏笔与上一结果；章设计查当前事件所需事实。是否需要回应由成员结合计划与正文判断，不能按编号、颜色或固定章数自动下结论。全书未收线目录可以分页搜索，不每次注入全量轨迹。

交织短卡只含“承接什么—本次推进什么—影响或留给谁”，每条关系包含稳定端点ID、计划/正文身份、版本与来源引用。卷取本卷的入边、主要汇合与输出；链取直接依赖和预期影响；章取当前链职责及必需事实，不递归展开全书关系。资料成员选择相关项、合并重复事实，系统按模型实际token预算预留输出与工具空间；超预算定向补查或分批，不能静默截断必要因果。语义待核实关系明确标记，不作为已发生事实注入。不保存思维链，不以树上视觉距离判断相关性。

## 20. 结果验收与责任补充

除第12节外，完整交付须证明：正文采用后树自动变化、支线果实与伏笔叶片可以共存、多主线正确挂接、编号不会因排序刷新而变化、轨迹按章顺序、跨卷伏笔不重复统计、重修后旧结算不覆盖、失败保留正文及可恢复、权限隔离、旧数据不被编造关联。

后台每个节点明确是否启动AI、岗位和实际模型、输入来源、工具、输出、预算、重试与状态；不把主编、资料和记录岗位混为一个“AI处理中”。界面与真实运行同源，并同步本方案、开发路线和验证证据。自动更新机制、真实模型语义效果与长期小说质量分别验收，不承诺零遗漏或永久不崩。

## 21. 全新实现结构与切换边界

工程落地与已核实缺口详见第22节。以下对象与模块仍是设计边界，不是已具备的接口。

### 21.1 新模块划分

新领域核心位于`rebuild/packages/time-machine-core/`，独立定义对象、状态、输入输出、工具权限与验证，不导入coauthoring-v7的规划、结算或页面模块。应用编排、持久化和作者界面分别围绕新核心实现，旧代码作为查证资料而非依赖。

| 新模块 | 职责 | 不承担 |
|---|---|---|
| 创作意图与推荐 | 资料卡、题材融合、作者偏好、主编推荐与建议 | 决定正文已发生什么 |
| 全书方案 | 三套候选、主支线、主要故事、分卷、开篇、期待与采用 | 提前写完章纲或冒充正史 |
| 故事关系 | 稳定编号、线的归属交汇、伏笔与问题关联 | 用树形外观强迫关系只有一个父节点 |
| 正文记录 | 正式正文变化提案、证据校验、语义复核与版本事件 | 改正文、替作者采纳草稿 |
| 状态投影 | 从有效事件构建时光树、轨迹和资料查询 | 模型文学判断、根据颜色推断状态 |
| 工作编排 | 任务状态、预算、批次、续作、重试和配置冻结 | 自行猜测未完成结果 |
| 作者与后台界面 | 同源状态、清晰选择、结果与记录查看 | 自己重新推算收束或把缓存当最新 |

账号、会话、正文保存、模型凭据与现有账本是平台外部能力，不在本次重复实现。新模块通过明确定义的适配接口使用，禁止导入旧时光机业务。模型调用统一计费入口只提供传输和计量，提示词、调用顺序和上下文选择重新设计。

### 21.2 新对象与状态语义

作者意图版本记录题材融合、主辅风格、结构偏好、人物偏好、选择和自定义。推荐版本绑定意图及源资料版本；主编建议与作者指令分别存储。方案有draft/reviewable/adopted/superseded身份，不和模型任务状态混用。

故事线ID与编号由系统分配，包含主线/贯穿支线/阶段支线职责、目标、人物和关系。线的正文生命周期为尚未展开、推进、暂缓、收束、明确停止；交汇是事件，待核对是可信状态而非生命周期。胜败是收束结果，不是生命周期。伏笔为计划、已埋、发展、部分回应、已回应、明确撤销；计划不算已埋，撤销不算回应。

轨迹事件包含事件ID、书籍、相关对象ID、正文版本及位置、前置状态版本、变化类型、结论、执行成员、判断依据及核对状态。事件追加保存，投影可重建；不以最后一次写入的整块JSON作为不可追溯真相。

### 21.3 正文事件入口

新模块接收平台正式采用事件，必须再次查证当前正文版本和内容哈希，不能信任浏览器声明。消费凭据按书籍和正文版本防重。已接管书籍仅一个记录执行所有者，旧维护不得同时写新模块对象；切换不通过修改作者任务制造窗口。

支持正文新采用、替换和撤回的独立事件。重修使直接或间接依赖失效，新投影标记待核对，按正文顺序补核；已经保存的正文不回滚。节点失败只阻断确实依赖该状态的生成。未知结论不写为确定事实，资料供给必须显露未知。

### 21.4 历史与发布

先在独立测试环境完成新流程。已有作者书籍不自动删除、不强制重新设计；旧方案可只读保留，若用户选择迁入新树，由新成员基于正式正文及选定规划重新识别，并保存迁移来源，不能直接把旧状态算作新系统已核对。

发布开关按书籍控制新业务所有者，新旧界面与执行器不共同管理同一新任务。开关变更需检查在途任务并保留回退路径；已产生新版本不能回退成旧代码误读新结构。完整依赖检查确认新模块没有旧业务导入后，才允许接入和上线。

### 21.5 结果优先的验收案例

用全新合同运行至少这些场景：单主线与多主线、群像与单主角、无战力成长的日常、融合题材、三套部分失败、作者中途改选、主要故事跨卷、支线收束但伏笔未回收、伏笔关联多线、交汇后继续推进、来源正文改写、晚到旧结果、重复采用事件、未知归属、历史迁入、跨账号/书隔离。

各项验收关注作者看到的结果及后续成员实际收到的资料，不以旧测试数量或复用比例作为成功标准。没有完成或没有实测的部分在后台和交接里明确保留未完成，不能承诺今晚必然全部完成而省略验证。

## 22. v2.0可实施合同与全面核查结论

### 22.1 核查证据与纠正

本轮核对本文、详细开发规格入口、交接记录、新核心`rebuild/packages/time-machine-core/src/domain.ts`及新API的`rebuild/apps/api/src/create-server.ts`，未访问生产、未读新的作者资料、未运行真实模型。既有原型交互测试与7项核心单测是历史证据，不能冒充本轮端到端测试。

| 问题 | 修订决定 |
|---|---|
| 原型三套与树为手写独立样例 | 正式版所有页面按同一采用版本/书籍查询；候选不得生成“已发生”树 |
| 新核心仅有线、伏笔与事件，缺分卷/链职责和应用层 | 先补协议和存储事务，再接成员；现有核心不是可以直接上线的后端 |
| `parentIds`无环校验容易被当作故事交织规则 | 卷/链包含关系无环；相互影响允许双向，汇合可多端点；有时序的具体依赖事件才检查不可能的时间循环 |
| 原文位置吻合被误当作事实正确 | 位置校验只是结构验证，另做语义支持、否定、传闻、人物认知与世界事实区分 |
| 当前投影依赖单章版本且默认依赖输入完整 | 增加事件所依赖的多章来源、对象状态版本、正式章顺序；持久化维护完整依赖和连续核对水位 |
| 原型职责、终卷安排仍是样例 | 实际输出必须引用本套目录并覆盖每条核心期待，不能把样例数量和阶段当模板 |
| 新API仅见账号/书架/开书路由，且独立PG配置 | 不宣称新时光机已接入。使用新领域包＋当前生产宿主的薄适配层；不要求先切整个数据库和身份系统 |
| 缺修改入口、脱敏细则、任务事件协议 | 以下给出明确入口、对象、状态与错误恢复；实现前补测试，不靠页面推断业务状态 |

### 22.2 上游来源、可信身份与输入清单

每个设计任务冻结`SourceManifest`：owner/book、正式开书版本、已确认设定版本集合、作者偏好版本、采用规划版本（如有）、正文基线水位（如有）、资产/模板版本。版本和摘要hash由系统生成，模型不得自报“最新”。只选已确认条目；草稿、审查意见、示例、工具说明和其他候选分别标身份，不能混成事实。

上游短卡仍用六栏，另附机器可用的引用索引：每个关键断言映射源对象/版本/字段或正文范围。不可遗漏主角身份、明确禁止项、核心能力的故事相关限制、既定开局与结局、创意尺度和作者主辅偏好。与全书方向无关的价格、日常细则不预载；原件可定向补读。短卡不是无损摘要，不能据短卡没写就断言设定不存在。

关键源相互冲突时建立具体待确认问题，展示冲突项与各自出处；不让资料成员私自决定作者意图。已接受正文与设定冲突不静默覆盖任一原件，标出计划修订或正文纠错路径；创意夸张不等于事实错误。未知配角可以设计为候选，新名字绑定候选实体ID，不能冒充已确认人物。

上游修改先使依赖卡标记过期；成员运行中继续使用冻结快照，完成结果标“基于旧资料”。采用前重检manifest，关键变化必须重新核对相应范围；无关改动经影响核对可复用，不能只凭时间戳全书重做。缓存键至少含owner/book、manifest、任务层级、模板版本与脱敏策略版本。

### 22.3 对象、事务和后端接入

在新领域包定义运行时schema与TypeScript类型，入库、工具返回和模型输出均按schema验证，不能只依靠TS编译。下列是逻辑对象，物理表/索引随宿主存储适配落地，但事务边界不可拆掉：

| 对象 | 必需信息与约束 |
|---|---|
| SourceManifest / ContextCard | 来源版本清单、断言引用、有效/过期/待核对；原件不覆盖 |
| IntentRevision / Recommendation | 意图版本、推荐版本、作者选择与主编建议分离 |
| CandidateRevision | 候选ID、不可变修订、来源、成员快照、基线、线目录、期待、卷卡、完整性及核查结果 |
| StoryLine / StoryRelation | 稳定ID、书内编号、角色/范围/目标/回应条件；有类型的关系及端点；编号不当数据库主键 |
| VolumePlan / ChainPlan | 稳定ID、显示顺序、起始/目标/职责/结束条件/交接、规划版本；链在后续生成 |
| Adoption | 当前采用指针、候选修订、编号映射、作者操作；旧采用不可变 |
| Task / Step / Attempt | 任务与批次ID、输入版本、实际成员/模型、租约、预算、状态、已保存产物与错误分类 |
| FormalEvent / Assessment / Projection | 正式来源版本集合、证据、依赖、语义判断、可信状态、结算批次与可重建投影 |
| Outbox / Consumption | 提交后事件、消费键、重试、连续水位；业务写入和outbox同事务 |

必要唯一约束：`(owner,book,displayNumber)`分别约束线与伏笔编号空间；`(owner,book,operation,idempotencyKey)`防重；`(task,step,batch,inputRevision)`防同批重复产物；正式消费键包含事件类型、正文稳定ID与版本。ID和owner/book都从会话及服务端目标绑定，拒绝前端跨书ID拼接。采用事务校验完整性、来源和expectedRevision，分配映射并更新指针、写outbox一次提交。并发冲突返回409和当前版本，不覆盖作者改动。

新应用层只依赖端口：Identity/BookAccess、SourceRead、TaskRepository、PlanRepository、FormalTextRead、ModelGateway/Billing、AssetRead、EventOutbox。凭据仅网关持有。生产适配可以共用当前账号、任务传输与账本，但不可导入旧时光机提示词、上下文编排、生成与结算逻辑。独立API宿主保留适配能力，不能连接另一套PG后假定与生产作者身份相同。一个书籍一个执行所有者，不双写新旧业务对象。

拟定接口均为新增模块合同，尚未实现：
- `GET /api/time-machine/books/:bookId/state`：统一页面快照、revision、可操作能力及来源新鲜度，纯读取不触发AI。
- `POST .../recommendation-runs`：首次入页显式建立或恢复任务；相同输入幂等返回同一run。
- `PUT .../intent`：expectedRevision保存作者选择；不自动按每次勾选调用模型。
- `POST .../design-runs`、`POST .../runs/:id/retry`：开始或只续失败步骤，不能借retry更换输入版本。
- `GET .../candidates/:id/revisions/:revision`、`POST .../candidates/:id/revisions`：读取及保存人工修改/AI修订请求；原候选保留。
- `POST .../adoptions`：原子采用完整修订；前端仅传ID与expectedRevision，不上传“已核查通过”。
- `GET .../events?after=sequence`：鉴权事件流，断线按游标续读；超过保留窗口返回重新取快照指令。
- `GET .../projection`、`GET .../history`、`POST .../correction-requests`：按采用/正文基线读树轨迹及提交纠错。

内部上下文供给不开放给浏览器任意拼接：`compile(scope,level,targetId,planRevision,formalBaseline)`返回卡、引用与预算清单；内部正式正文事件由平台outbox进入，不能以浏览器POST代替正式采用事实。

### 22.4 成员执行与上下文预算

执行顺序：来源检查→必要的资料成员填卡→主编推荐→作者选择→三个独立编剧各自产出骨架→各自分批补卷→逐套必要复核→作者采用。主编比较三套差异是质量建议，不让另外两套未完成成为完整一套采用的硬阻断。骨架先冻结线ID与大致卷职责，分卷批次可提修订但不能自行漂移全书结局。

每个成员接收：岗位任务、来源身份标签、作者明确要求、本层产物合同、预算和可用只读工具。工具允许按用途查方法目录、读方法卡、按实体/来源读作品资料；禁止任意SQL、文件、网络或跨书读取。模型可原创，不需要引用所有方法，不允许借检索结果中的自然语言扩大权限。工具返回是资料而非系统指令；模型产物用文本安全渲染，不执行HTML/脚本。

资料整理、推荐、单套骨架、卷补全分别维护可配置预算。请求前验证 `系统+输入卡+保留工具返回+最大输出+安全余量 ≤ 路由可用窗口`；按模型tokenizer计量，未知tokenizer用保守估算并标识，不能把字符数当精确token。缺少经验证的路由预算时任务等待配置，不能盲发。后台显示每段token、输出上限、补查预算与实际消耗。

首轮工程默认：每步骤最多6次只读工具调用、同一暂时性错误最多2次自动重试、输出格式局部修复最多1次；达到限额保存进度并明确暂停原因。以上是可调初值，真实探针后逐节点定稿，不是文学规则。429/暂时网络按限流退避；输出截断应拆当前批，不能原样反复重试；401/403不重试；模型结果未知先核对网关attempt与账本，不重复收费重发。任务时间、token与费用上限共同控制，并在派发前计入预算。

卷批次大小由输出估算和既有样例决定，不固定一次一卷或一次全书。每批只携本方案基线、当前卷职责、直接前后承接和必要事实；不附其他两套方案、不无限累积检索历史。检索结束把选中的短卡和引用编译为下一步骤输入，丢弃无用工具输出，但保留服务端审计。必要依据容纳不下就缩小工作范围或补读，不能静默截断。

### 22.5 幻觉、事实审查与记录结算

创作允许提出新的候选情节；幻觉控制针对把不存在的来源、人物关系、已发生事件或工具调用说成既成事实。每条关键判断标为源事实/规划候选/人物认知/推测/未知。设计复核重点是姓名身份、作者要求、源事实冲突、故事职责遗漏；不因抽象脑洞违背现实常识就拒绝，也不保证“绝无幻觉”。

正文审查与结算分开：正文接受前可审查事实连续性与文本质量；正文接受后记录成员只识别已接受文本的变化，不能趁结算改正文。来自梦境、传言、谎言、否定、条件句或人物猜测的内容，按其认知主体和可信身份记录，不提升为世界事实。倒叙同时保留阅读顺序和故事内时间；正文后文揭露旧事实不直接抹去当时人物认知。

关键结算（死亡、核心身份揭露、线收束、伏笔完全兑现、逆转既有状态）须有定向语义复核或明确人工核准记录；普通有据的进展不强制重复全章审查。引用切片吻合不是语义通过；多来源冲突或证据不足保留待核对。抽取遗漏亦是风险：对本章当前链目标、已知相关线与明确新承诺做覆盖核对，不要求扫描全书每条线。

结算管线：接受正文并写outbox→读取当前正式版本→抽取候选变化→核验范围/证据/语义→原子写评估事件、依赖与投影revision→写通知outbox→更新连续核对水位。每步可恢复；正文保存不依赖结算成功。读者界面可看到正文已保存，而记录处理中/部分失败，不能把任务结束误标全部核对完成。

水位是按当前正式章节序列连续完成的位置，不是最大章号；删除、重排、番外和倒叙均使用稳定章ID及顺序版本。同一结算对重复事件幂等，乱序到达先等待依赖，独立分支可完成但不跳过缺口。新发现线先分配书内身份再记录事件；未知归属进入待归属，不硬挂到任意卷。

正文重修/撤回使依赖其旧版本的事件失效，再传递至下游依赖；先显示最后有效投影并标待核对，不能把无效果实仍显示为确认。重算产生新评估，旧证据保留。受影响的后续生成等待必要事实可靠，其余阅读、保存和无关设计可继续。引用跨度约定为原始文本UTF-16索引与hash，不做去空白后比对；跨章结论持有多个sourceRef。模块只消费已验证正式版本，不接受外部自报“supported”。

评估修正以`supersedesAssessmentId`连接旧评估，只取当前有效评估构建投影；旧的待核对标记在新评估明确解决后解除，不能因曾经失败永久卡住。对于明确失效但未重算的事实，保留历史展示、从当前供给中排除。安全校验拒绝未知change.kind、非法状态转换和缺失依赖；模型返回枚举正确不等于允许从已收束直接恢复推进，重开必须有原因与来源。

### 22.6 脱敏与最小数据供给

模型只接收当前书创作必需内容。账户密码、会话、API密钥、支付资料、手机、邮箱、IP、内部部署路径和其他书内容不进入提示词；任务身份用内部不透明引用，不能直接把账户整行序列化。作品角色姓名、虚构地址不能一律脱敏破坏故事；发现作者输入中的真实联系方式或外部敏感身份且与创作无关时，以稳定占位符替换，映射只留服务端受控存储。无法判断且会影响内容含义时提示局部处理，不擅改原文。

工具和模型出入口共用脱敏层，检查输入文本、工具参数、错误和日志；新鲜私密键即使混在作品文本也不允许传给模型。原始作品保留在原权限域，脱敏副本可带安全span映射，但不可把模型基于替换文本的索引当原文证据，必须还原核对。后台默认只显示脱敏摘要和长度，查看必要原文需明确权限与审计，不把管理员权限等同可任意浏览所有作品。

普通运行日志不落完整上下文/正文/工具原文，不保存思维链。敏感诊断临时包须有访问控制、过期与审计，实施默认7天自动清理非业务调试包，正式正文和结算历史不受影响。浏览器不缓存其他作者资料；登出清理本地私有缓存。无新增公开分享、第三方遥测或作品外传目标。

### 22.7 状态、实时更新与作者编辑入口

任务状态：queued/running/waiting_input/retryable_failed/failed/succeeded/cancelled；步骤同样有独立状态、lease与attempt。候选状态另为draft/partial/ready/stale/adopted/superseded。正文投影为current/updating/needs_review/partial。不得用一个status同时表达三者。租约过期先核对真实调用状态再接管，旧attempt无权覆盖新产物。

UI只依统一快照与递增sequence更新。推送失败以带版本的定时读取降级；隐藏页降低频率，返回即补读。过期响应不能覆盖新revision；不同方案各自有进度，不伪装共享百分比。总批次变化显示已完成项与当前工作，而不是进度倒退的假百分比。失败保留已完成内容及明确续做入口；首次入页只幂等建立推荐，不因刷新重生成。

| 修改内容 | 作者入口 | 写入及后果 |
|---|---|---|
| 开书与设定源 | 返回资料/设定，保留当前意见 | 原模块新版本，相关候选标旧来源，不清空原结果 |
| 故事选择/主次偏好 | 调整故事线 | 保存意图草稿，点击开始设计才新任务 |
| 候选文字、线目标、卷安排 | 当前卡的“修改”与整体“提出调整” | 人工修改原样留修订；AI修改先展示建议版本，不自动覆盖 |
| 线的增删合并/拆分/排序 | 故事目录编辑 | 临时ID映射、关系引用校验；采用后删除为归档，不删除正文关联 |
| 分卷顺序、职责、结束条件 | 卷卡修改与顺序调整 | 更新计划修订，列出受影响卷链；不重排已接受正文 |
| 改用另一套/重新设计 | 方案级操作 | 有正文时展示未来影响并建新规划版本，不改变历史事实 |
| 记录不准确 | 线/轨迹详情“反馈记录有误” | 提交纠错，核对来源后新评估；不能点红果直接改事实 |

作者修改保存与采用分开；关键结构/引用未通过时可以保存草稿但不能采用。只对影响已采用内容的重要操作展示具体差异，不每次改一句话都弹确认。手机保持输入与滚动、可到达主要操作，三套用ABC＋成员，标题在正文。多线列表可搜索/分页，不能只截取前几条冒充全部。等待、空态、部分成功、过期和恢复必须在真实API联调时验证。

### 22.8 后台必要信息与可调项

后台同源显示：方案版本及实施状态；各步骤真实负责成员/模型；来源manifest及新鲜度；工具实际调用与所选方法；输入/输出token、预算、时延、重试原因；候选完成度/采用版本；结算缺口、待核对项、重放状态。默认展示结论与定位入口，不把模型内部字段倾倒给作者。

可配置：启用成员与模型路由、各节点预算/并发/超时/重试、短卡模板、方法资产名称简介与版本、提示词版本、发布开关。修改需要权限和审计，新配置只影响新任务，历史冻结快照保留。后台不可把“未实测”切成“通过”、不可无证据修改正文事实、不可取消作者任务制造发布窗口。方案/路线/功能介绍按已验证交付同步，不把本规格所有功能一键标完成。
