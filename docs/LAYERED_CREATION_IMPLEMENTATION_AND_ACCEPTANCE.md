## 1. 文档用途与结算规则

本文件把已经确认的产品决定集中转换成可实施、可测试、可验收的开发合同。它不能替代项目章程和生效决定；发生冲突时，按 `AGENTS.md` 规定的权威顺序处理。

从本文件生效后：

1. 不再以“页面出现字段”“接口能够返回”“全量测试通过”单独代表整项功能完成。
2. 每个功能必须同时核对数据对象、领域规则、API、前端、下游继承、运行时检查、自动测试和人工体验证据。
3. `部分完成` 一律不得勾选为完成。
4. 没有真实模型证据的创造性质量项目，只能通过 E0-E2 工程验收，不能通过 E3-E4 质量验收。
5. 本文件所有必须项完成、当前文档无冲突、标准验证通过、管理员真实走查通过、生产环境复验通过后，才能宣布整套分层创作方案完成。

状态定义：

| 状态 | 含义 |
|---|---|
| `未开始` | 尚无有效实现或只有讨论稿 |
| `进行中` | 已开始实现，尚未形成可验收闭环 |
| `部分完成` | 某些层已实现，但至少一个必需层缺失 |
| `已完成` | 全部必需层与对应证据均通过 |
| `阻塞` | 已记录明确外部阻塞、替代方案和恢复条件 |

## 2. 总体目标

系统帮助小白作者一层一层完成小说设计，不要求作者开书时一次填写大量内容，也不把专业理论、内部模型、任务编号或技术错误暴露给作者。

目标工作流：

```text
开书信息
→ 非剧情设定
→ 当前卷方向
→ 当前卷事件链
→ 当前事件大纲
→ 当前事件完整章节链
→ 最近连续 1～3 章详细章纲
→ 单章正文
→ 章节结算与后续章纲回校
→ 事件结算
→ 卷结算
→ 下一卷重新设计
```

上游与下游职责：

```text
开书信息给方向
设定给事实骨架和边界
卷方向决定本卷故事责任
事件链决定责任由哪些事件承载
事件大纲决定当前小故事怎样完成
章节链决定事件怎样拆成连续章节
章纲决定本章场景、情绪和有效变化
正文负责文学表达
结算只记录正文实际发生的内容
```

这是“责任递归”，不是“模板套娃”：上层下发必须完成的故事责任和目标状态，下层自由设计实现过程；任何一层都不能把同一套幕或节拍再次完整套入下一层。

## 3. 不可改变的产品边界

1. 整体布局保持左侧书籍区、上方功能栏切换页面。
2. 移动端优先，重点覆盖 360、390、430 像素宽度；桌面端保持现有风格。
3. 作者可见文案全部使用大白话，专业结构方法只在后台使用。
4. 作者不必一次设计完整本书，只设计当前层和当前需要的对象。
5. AI只能在作者明确启动、请求建议、请求融合、请求质检或工作流需要生成候选时介入；不能建书后擅自开始正式设定设计。
6. 候选内容在作者确认前不是正式约束。
7. 未来规划与正文事实严格分离；正文事实只能来自定稿正文与结算。
8. 软参考不能被提示词、质检或检索提升成硬公式。
9. 同一活动正文只使用一个主笔；事实、文学、体验三职责由三个异模型独立审查，彼此不读取对方报告。
10. 不增加创作团队人数；各职责绑定当前 Agent 注册表中的成员。

## 4. 约束、作用域与真实性模型

### 4.1 约束强度

所有正式资料片段必须具有以下强度之一：

| 后台类型 | 作者看到 | 用途 | 下游行为 |
|---|---|---|---|
| `hard_fact` | 全书不能改 | 已确认事实、明确边界、不可违背条件 | 必须保留；冲突时阻止确认或生成 |
| `current_task` | 这一层必须做到 | 当前卷、事件或章节必须完成的责任 | 当前任务必须落实；任务结束后不自动成为永久事实 |
| `soft_reference` | 尽量体现 | 风格倾向、路线建议、可选方法 | 可以改写、混合、舍弃，不能阻止确认 |
| `open_space` | 暂时不定 | 作者明确留白或暂不确定的区域 | 不得擅自补成事实；允许创作提出候选 |

### 4.2 真实性状态

| 类型 | 含义 |
|---|---|
| `planned` | 尚未写进定稿正文的规划 |
| `confirmed` | 作者确认的正式设计，但仍可能被正文合理调整 |
| `actual` | 已在定稿正文中实际发生并由结算确认 |

### 4.3 作用域

每条正式资料至少具有：

```ts
type ScopeType =
  | 'book'
  | 'volume'
  | 'event'
  | 'chapter'
  | 'scene';
```

资料还必须保存 `scopeId`、来源对象、来源版本、依赖版本和失效状态。卷内约束不能自动污染全书，章内临时安排不能自动成为世界观事实。

### 4.4 作者原话

作者可以在设定、卷、事件、章纲和正文任务上直接补充原话，但必须附着明确业务对象和目标版本：

```ts
interface AuthorInstruction {
  id: string;
  targetType: 'setting' | 'volume' | 'event_chain' | 'event' | 'chapter_chain' | 'chapter' | 'manuscript';
  targetId: string;
  targetVersionId?: string;
  originalText: string;
  strength: 'must' | 'strong_preference' | 'inspiration' | 'question';
  createdAt: string;
}
```

- “必须遵守”完整执行，冲突时阻止确认；
- “强偏好”和“灵感”是软参考，不能冒充事实；
- “问题”只要求AI回答或提出方案，不能自动进入正式约束；
- 独立灵感只有作者主动摘录并绑定对象后，才能成为上述作者原话；
- 所有作者原话原样保存，作者展示门禁不得改写其剧情语义。

## 5. 分层正式对象

### 5.1 开书信息

开书信息只描述创作方向和基本定位，例如：

- 书名或暂定名；
- 类型与题材；
- 目标读者；
- 基本卖点；
- 主角初步形象；
- 作者明确想写或不想写的内容；
- 可选的开局想法；
- 可选的结局方向；
- 可选的故事核心软方向；
- 预计长度与连载偏好。

故事核心可以留空，也可以在第一卷方向确认后由主编根据真实卷方案生成候选，作者确认前不能反向写成正式设定。

开书信息不承担世界观全集、完整剧情、完整人物小传或全书节拍表。

建书成功后只建立空的设定工作区，不自动启动正式AI设定任务。作者点击“请AI一起设计”后才启动协作。

### 5.2 设定

设定只负责不依赖具体剧情也应成立的书籍骨架。默认四项核心设定：

1. 世界舞台；
2. 主角处境；
3. 规则与代价；
4. 边界与留白。

“主角处境”必须拆层：主角身份、能力、缺陷、底线属于设定；本卷开始时主角被什么局面推动、面对谁和必须解决什么属于卷方向。

题材推荐由主要分类和融合题材的确定性规则产生，不由AI擅自替作者决定；默认不勾选，作者可以自由增删。

故事核心、人物扩展、势力、地点、资源、文化等作为可选或题材推荐项。主要对立力量与本卷反派不作为全书核心设定强制项，应在卷方向中按需要设计。

旧六项设定数据完整保留，不改写或删除作者原文；旧“故事内核”和“对立面”按可选/历史项展示，旧“主角处境”保留来源并映射到主角底板或本卷开场状态，映射不确定时必须让作者确认。

设定完成度按必要规则判断，不按条目数量判断。四项核心满足、没有阻断性矛盾即可继续；可选项缺失不阻止作者进入卷设计。

设定最终稿作者侧显示自然语言，后台保存结构化片段：

```ts
interface SettingClause {
  id: string;
  itemKey: string;
  text: string;
  kind: 'fact' | 'direction' | 'blank' | 'boundary';
  constraintStrength: 'hard_fact' | 'soft_reference' | 'open_space';
  scopeType: 'book' | 'volume';
  scopeId: string;
  sourceVersionId: string;
  dependencyVersionIds: string[];
}
```

### 5.3 按需补设定

卷、事件、章纲或正文任务发现缺少必要设定时，不能直接猜成正式事实。系统生成设定缺口对象并让作者选择：

1. 现在补充设计；
2. 本卷暂不使用这项内容；
3. 保持未知，让未知本身成为允许状态。

下层AI新提出的人物、规则、势力或能力默认只属于当前卷、事件或章节；只有作者主动提升并确认后，才能创建新的全书设定版本。

```ts
interface SettingGapDecision {
  id: string;
  discoveredAtScopeType: 'volume' | 'event' | 'chapter';
  discoveredAtScopeId: string;
  question: string;
  whyNeeded: string;
  affectedObjects: string[];
  decision: 'design_now' | 'not_used_this_volume' | 'keep_unknown';
  resolvedSettingVersionId?: string;
}
```

### 5.4 全书故事总线

第一次设计第一卷时，在分卷页面同时建立一份版本化的全书故事总线，不新增顶部页面。它只保存远期软方向：

```ts
interface BookStorySpineVersion {
  id: string;
  bookId: string;
  sourceFirstVolumeDirectionVersionId: string;
  longTermReaderPromises: string[];
  protagonistLongArc: string;
  centralQuestion: string;
  escalationLadder: string[];
  optionalEndingDirections: string[];
  protectedOpenSpaces: string[];
  sourceVersionIds: string[];
}
```

故事总线是全书的软北极星，不是几百万字的完整大纲，不规定每卷使用同一结构。后续卷可以参考并通过新版本调整；已经发生的正文事实仍以结算为准。

### 5.5 卷方向

卷方向只表达本卷的大故事方向，不直接保存事件列表：

```ts
interface VolumeDirectionContent {
  openingSituation: string;
  protagonistDrive: string;
  volumeGoal: string;
  centralOpposition: string;
  escalationPath: string[];
  majorChoices: string[];
  relationshipMovement: string[];
  expressionFocus: string[];
  climaxResponsibility: string;
  costAndConsequence: string;
  closingState: string;
  benefits: string[];
  risks: string[];
  openSpaces: string[];
  firstVolumeLaunch?: FirstVolumeLaunchPlan;
}
```

`eventSequence` 不得继续写入新的卷方向版本。旧版本只保留兼容读取和迁移投影。

### 5.6 事件链

作者确认卷方向后，再建立独立的事件链版本：

```ts
interface EventChainVersion {
  id: string;
  volumeDirectionVersionId: string;
  events: EventChainNode[];
  coverage: VolumeResponsibilityCoverage[];
}
```

事件链节点只说明：

- 本事件承担什么卷责任；
- 从什么状态开始；
- 人物采取什么主要行动；
- 阻力怎样升级；
- 产生什么阶段回报或代价；
- 结束后怎样把状态交给下一个事件；
- 铺垫、兑现和后果关系。

事件链不能因为事件数量足够就确认，必须通过卷责任覆盖和因果衔接检查。

### 5.7 当前事件大纲

事件大纲是一个完整小故事，受卷方向和事件链节点约束，保存：

- 事件目标；
- 进入条件；
- 参与人物与各自欲望；
- 冲突与升级；
- 铺垫与回收；
- 阶段回报；
- 高潮与选择；
- 代价与结果；
- 向下一事件移交的状态；
- 允许主笔自由发挥的空间。

如果事件设计发现必须修改卷方向，系统只能提出“修改卷方向建议”，并展示影响预览；作者确认后才创建新卷方向版本并使受影响下游候选失效。

### 5.8 章节链与详细章纲

当前事件先生成完整章节链，使作者能看到整个事件的章节顺序和责任分配。完整链只保存章节骨架，不把所有章节一次性写成详细章纲。

详细章纲只生成最近连续 1～3 章：

1. 先看到完整章节链；
2. 作者选择最近连续 1～3 章形成详细候选；
3. 只冻结马上要写的章节；
4. 每章定稿并结算后，根据实际结果回校仍未写的后续详细章纲；
5. 不改变事件总体承诺时允许调整场景、动作、信息顺序和情绪路径。

### 5.9 结算

章节、事件和卷结算只记录正文实际发生的内容：

- 事实变化；
- 人物状态；
- 关系变化；
- 资源、能力、身份变化；
- 已提出、推进、兑现或失效的承诺；
- 新增铺垫与已回收铺垫；
- 实际代价；
- 未解决问题；
- 与原规划的偏差及偏差是否被作者接受。

### 5.10 故事线程账本

全书故事总线、卷方向和事件链共同维护版本化故事线程账本，用于串联承诺、伏笔和人物变化：

```ts
interface StoryThreadRecord {
  id: string;
  type: 'promise' | 'foreshadowing' | 'question' | 'relationship'
    | 'inner_change' | 'conflict' | 'identity_resource_emotion';
  title: string;
  scopeType: 'book' | 'volume' | 'event';
  scopeId: string;
  status: 'planned' | 'planted' | 'advanced' | 'due' | 'resolved' | 'abandoned_by_author';
  plannedWindow?: { fromEventId?: string; toVolumeId?: string };
  sourceVersionIds: string[];
  actualEvidenceVersionIds: string[];
}
```

规划只能创建 `planned`；只有定稿正文及章节、事件、卷结算才能把线程更新为已埋、推进或回收。计划时间使用事件或卷软窗口，不把伏笔锁死在精确章号。作者决定放弃时保存原因和影响，不删除历史证据。

结算不能把“计划要发生”误记为“已经发生”。

## 6. 设定页协作体验保留与修复

保留现有K3设定页的优点：

- 核心、推荐、资料库分组；
- 作者主动启动AI；
- 队列与进度；
- 独立提案；
- 片段选择；
- 主编融合；
- 候选确认；
- 重做、手写、留白；
- 质检与恢复；
- 手机端卡片交互。

必须完成以下修复：

1. 自定义分组不重复显示；
2. 每个候选持久化并显示好处、代价、风险和留白；
3. 整份方案与片段可以混合选择；
4. 选择状态只使用稳定 `proposalId` 和 `fragmentId`；
5. 普通作者接口不返回模型、供应商、任务、讨论、方法键或错误代码等内部字段；
6. 所有作者可见错误统一经过作者错误门禁；
7. 设定参与者独立生成候选，不能互看候选；
8. 主编只融合作者实际选中的整份或片段；
9. 质检只检查矛盾、边界和当前任务所需基础，不强迫填满全部可选项。
10. 三名编剧的必要候选未齐时禁用融合，点名缺席席位、显示真实进度并只重试缺席席位；
11. 设定队列每项候选出来后停下等待作者确认，不在作者未裁决时把候选自动写入下一项上下文；
12. 开书向导步骤编号、视觉顺序和语义顺序一致，回归测试覆盖第三步；
13. “重新设计”允许作者填写可选的不满意原因，并绑定当前条目、当前版本和新一轮候选。

## 7. 内部结构方法与卷路线

关联：`DR-20260820-internal-structure-routes-v1`

### 7.1 版本化内部方法库

猫咪写作法、三幕式、五幕式、三幕九线、英雄旅程、八序列、七点式、故事圈、起承转合、网文节奏等方法保存为后台软工具。

完整方法目录按功能分为五类：

| 内部类别 | 收录方法 | 使用边界 |
|---|---|---|
| 宏观故事骨架 | 三幕式、四幕式/起承转合、五幕式、六幕式、拯救猫咪、八序列、七点式、悉德·菲尔德范式、三幕九线 | 每个卷方案只选择一个主骨架，不平铺多套节拍 |
| 人物变化线 | 英雄之旅、故事圈、特鲁比人物变化步骤 | 只映射到主骨架已有节点，不额外制造第二套完整剧情 |
| 因果设计原则 | 麦基式激励—纠葛—危机—高潮—结局 | 用于检查触发、选择、代价和结果，不成为作者表单 |
| 连载节奏策略 | 黄金三章、升级循环、阶段爽感/打脸兑现、悬念钩子、单元剧、多线并进 | 调整回报、追读和组织方式，不规定固定间隔 |
| 叙述表现手法 | 非线性、不可靠叙述、元叙事、寓言/象征 | 只影响信息呈现，不推翻已确认因果 |

组合规则：

1. 同一方案只能有一个主要骨架；
2. 可以叠加一条人物变化线，但只标注人物在既有故事节点上的变化；
3. 可以加入少量连载策略，但不得新建第二套完整节拍；
4. 叙述手法只控制信息如何呈现；
5. 相同功能节点合并，冲突节点必须取舍，禁止把多个节拍表首尾拼接；
6. 当前事件可以选用适合自己的小结构，但只接收本事件责任，不能重复套用整卷模板；
7. “拯救猫咪”不能被等同于固定打脸，“章节钩子”也可以是决定、情绪、信息或下一步期待，不强制突然遇险。

```ts
interface InternalStructureMethodVersion {
  methodKey: string;
  version: string;
  contentFingerprint: string;
  solves: string[];
  organizationGuidance: string[];
  category: 'macro' | 'character_arc' | 'causal_principle' | 'serial_rhythm' | 'narration';
  publicGoalMapping: string[];
  suitableGenres: string[];
  suitableLengths: string[];
  risks: string[];
  movableParts: string[];
  removableParts: string[];
  mergeableParts: string[];
}
```

作者页面、普通作者API、事件链、章纲和正文上下文均不得出现内部方法名称、方法键、幕、节拍编号等专业术语。

### 7.2 双路线生成

每次卷设计：

1. 读取开书信息、活动设定、上一卷真实结算、当前人物状态、未解决问题和作者本卷想法；
2. 诊断本卷主要任务；
3. 选择两条实质不同的内部结构路线；
4. 两名独立编剧分别只收到自己路线的精简软参考；
5. 输出统一的大白话 `VolumeDirectionContent`；
6. 保存内部方法版本、内容指纹、选择原因和调用证据；
7. 普通作者响应只返回具体故事路线。

两条路线至少在以下四项形成实质区别，并且因果路径、主要代价、高潮触发三项不得全部相同：

- 主角主动或被迫；
- 主要对立力量；
- 解决路径；
- 关键选择；
- 关系变化；
- 主要代价；
- 高潮触发；
- 卷末状态；
- 主要阅读情绪。

差异不足时只重做相似度过高的一条，不把同义改写展示给作者。

### 7.3 作者选择与主编融合

作者可以：

- 整份采用方案一；
- 整份采用方案二；
- 跨方案选择片段；
- 请求主编只融合所选内容；
- 编辑融合稿；
- 放弃两份并重新设计；
- 改为手写；
- 对非必要项保持留白。

主编不得在作者选择前自动读取两份完整方案并生成第三份折中稿。每个融合片段保存来源候选、来源字段和来源版本。

### 7.4 向事件链传递

卷确认后生成不含内部方法信息的责任投影：

```ts
interface ConfirmedVolumeResponsibilities {
  openingSituation: string;
  protagonistPush: string;
  firstStageGoal: string;
  escalationResponsibilities: string[];
  majorChoice: string;
  climaxPath: string;
  climaxResolution: string;
  costAndConsequence: string;
  closingState: string;
}
```

事件链只读取该责任投影、必要设定和上卷真实结算，不读取内部结构方法。

后续卷重新诊断并重新选择方法，不能沿用第一卷的方法成为全书固定骨架。

## 8. 首卷强启动合同

关联：`DR-20260820-first-volume-launch-v1`

首卷强启动属于第一卷任务约束，不属于设定。硬要求是达到阅读效果，具体写法属于软工具和主笔自由空间。

```ts
interface FirstVolumeLaunchPlan {
  primaryDrivers: string[];
  immersionAnchor: string;
  first500Interest: {
    readerQuestion: string;
    immediateSituation: string;
    emotionalGrip: string;
    promisedMovement: string;
  };
  goldenThree: Array<{
    chapterNumber: 1 | 2 | 3;
    responsibility: string;
    protagonistAction: string;
    pressureOrPull: string;
    deliveredPayoff: string;
    nextExpectation: string;
  }>;
  earlyMomentum: string[];
  majorClimax: {
    promiseToFulfill: string;
    centralChoice: string;
    cost: string;
    centralConflictChange: string;
    irreversibleChange: string;
    nextStageTrigger: string;
    noLaterThanEffectiveChars: 100000;
  };
  variationAndRecovery: string[];
  forbiddenShortcuts: string[];
}
```

只有第一卷必须存在此字段。后续卷使用普通卷方向和本卷重点表达。

`primaryDrivers` 允许爽感兑现、强冲突、情绪拉扯、悬念与秘密、新奇设定、人物魅力、关系变化或混合驱动；不能把“爆款”翻译成固定战斗或打脸。`first500Interest` 只说明读者为何继续看，可以来自问题、损失风险、异常处境、人物关系、强情绪或迫近选择。

`variationAndRecovery` 必须安排冲突换型、爽感与压迫交替、情绪回报、人物关系或生活细节以及高潮前蓄力。“密集”是有效变化密集，不是全程高声尖叫。

### 8.1 事件链覆盖

首卷事件链必须标注：

- 开篇启动承载事件；
- 黄金三章承载事件；
- 早期阶段回报；
- 冲突升级与情绪拉扯；
- 10万字前高潮承载事件；
- 高潮铺垫事件；
- 高潮后果事件或状态。

没有高潮承载事件、没有铺垫责任或高潮不产生代价与不可逆变化时，事件链不得确认。

### 8.2 黄金三章

第一事件进入章纲阶段时一次设计前三章总体启动包：

1. 第一章进入处境、产生抓力、启动故事；
2. 第二章人物主动行动、阻力升级、展示独特看点；
3. 第三章兑现第一次明确回报并打开更大期待。

先形成三章总体承诺，只冻结第一章。第一章定稿结算后，保留总体承诺并重新校准第二、三章的具体场景。

### 8.3 第一章专属合同

```ts
interface FirstChapterLaunchContract {
  first500InterestAnchor: string;
  immediateSituation: string;
  firstDesireDangerOrEmotion: string;
  requiredEffectiveChange: string;
  firstRevealOfUniqueAppeal: string;
  firstPayoff: string;
  nextExpectation: string;
  writerFreedom: string[];
}
```

正文主笔只接收自然语言任务，不接收整份爆款检查表或内部方法名。

### 8.4 首章三审与定点重写

- 班昭（事实审查）：核对事实、设定和时间关系；
- 妲己（文学审查）：核对是否以场景和人物启动、是否存在大段说明、人物是否鲜活；
- 昭君（体验审查）：核对前500有效正文字符是否产生问题、期待或情绪，并引用正文位置给出证据。

系统只能准确切出前500有效正文字符，不能用关键词或评分公式代替读者体验判断。明显没有兴趣锚点时，创建定点重写候选，不继续生成第二章。

### 8.5 10万字高潮追踪

有效正文字符：不计标题、空行、系统说明，只统计活动定稿正文。

如果第一卷不足100000有效正文字符，大高潮必须在卷末前完成；如果第一卷超过100000字符，大高潮不得晚于累计100000字符。

每章结算后更新：

- 首卷累计有效正文字符；
- 高潮承载事件状态；
- 铺垫责任完成情况；
- 按剩余章节链预测的高潮位置；
- 是否存在超过100000字符风险；
- 是否需要调整事件链或章节链。

高潮完成后必须由结算记录实际兑现、选择、代价、不可逆变化和下一阶段触发。规划中写有高潮不能视为已经完成。

## 9. ContextCompiler与资料包

### 9.1 原则

1. 正式对象完整保存，不通过截断破坏权威源。
2. 每次任务按对象、作用域、依赖、强度、真实性和相关性编译资料包。
3. 硬事实和当前任务约束不能静默删除；超出预算时阻止调用并报告可操作原因。
4. 软参考按任务相关性选择；其余只提供目录，不堆叠全文。
5. 留白明确告诉模型“可以保持未知”，不能被补成事实。
6. 摘要只导航，争议事实回查正式源。
7. 不使用固定“前N条设定”“字符串头尾截断”替代结构化编译。

### 9.2 分层资料包

| 任务 | 必需资料 | 按需资料 | 排除资料 |
|---|---|---|---|
| 设定设计 | 开书信息、当前设定项、作者输入 | 相关已确认设定 | 剧情候选、未摘录灵感 |
| 卷方向 | 开书、活动设定、上卷实际结算、作者本卷想法 | 相关角色与未解决问题 | 事件候选、内部无关方法 |
| 事件链 | 确认卷责任、必要设定、上卷实际状态 | 铺垫关系和作者备注 | 内部方法名、未选卷候选 |
| 事件大纲 | 当前事件节点、卷责任、进入状态 | 相关人物与历史事实 | 其他事件全文 |
| 章节链 | 当前事件大纲、进入状态、必须覆盖责任 | 必要铺垫 | 全书全文、远期候选 |
| 章纲 | 当前章节骨架、前章实际结算、当前事件责任 | 最近相关原文、人物状态 | 远期详细章纲 |
| 正文 | 当前详细章纲、必要硬事实、最近正文、文风证据 | 定点相关原文 | 内部方法库、完整检查表 |
| 审查 | 活动正文版本、职责专属事实 | 必要权威源 | 其他审查报告 |

### 9.3 稳定组合包

资料包使用稳定、可版本化的组合对象，不靠散落提示词临时拼接：

- `BookCorePack`：完整覆盖活动开书字段；
- `SettingConstraintPack`：全部活动硬设定紧凑账本＋当前相关设定原文；
- `BookStorySpinePack`：全书故事总线软方向和受保护留白；
- `VolumeResponsibilityPack`：确认卷责任和本卷重点表达；
- `EventResponsibilityPack`：当前事件责任、前后接口和卷责任覆盖；
- `ChapterTaskPack`：当前章骨架、详细章纲、必须实现、禁止违反和自由区；
- `RecentActualStatePack`：最近正文结算后的真实人物、关系、资源和局面；
- `StoryThreadPack`：当前任务相关的承诺、伏笔、问题和回收窗口。

每个组合包保存编译版本、来源版本、纳入/排除理由和预算；当前目标对象必须完整，远期对象只能以职责和软方向进入。

### 9.4 依赖与失效

上游版本变化时：

1. 计算依赖影响；
2. 展示受影响卷、事件、章纲和候选；
3. 已定稿正文不失效、不覆盖；
4. 未确认候选自动失效；
5. 已确认但未执行的下游对象进入重新确认；
6. 作者确认后才重建正式下游版本。

## 10. 前端交互方案

### 10.1 大布局

```text
┌──────────────┬──────────────────────────────────┐
│ 左侧书籍列表  │ 上方：开书｜设定｜卷｜事件｜章纲｜正文 │
│              ├──────────────────────────────────┤
│ 当前书籍状态  │ 当前页面主工作区                    │
│ 当前卷/事件   │ 桌面双栏或多栏，手机单列逐步展开      │
└──────────────┴──────────────────────────────────┘
```

不改变左侧书籍、上方功能栏的整体布局和现有视觉语言。

### 10.2 手机端

1. 360像素下无横向滚动；
2. 主要按钮进入底部安全区，点击区域不小于44像素；
3. 候选卡片单列展示，差异摘要优先，长内容折叠；
4. 选择状态固定显示，不因折叠丢失；
5. 融合操作使用底部操作条或抽屉；
6. 进度、失败恢复和重新设计不遮挡正文；
7. 左侧书籍区在手机端使用现有抽屉模式，不移除书籍入口；
8. 输入法弹出时保存、生成、确认按钮仍可达。

### 10.3 卷路线页面

作者首先只看到两条实质不同的具体路线。每张卡片展示：

- 路线标题；
- 开始局面；
- 推动力；
- 解决路径；
- 升级；
- 重大选择；
- 高潮；
- 代价；
- 卷末局面；
- 好看之处；
- 风险与留白。

作者选择后才出现“请主编融合”。不得预先显示自动融合的第三条路线。

### 10.4 事件与章纲页面

事件链继续放在现有规划页面内部，不新增顶部页面。默认卡片只显示：

- 本事件承担什么卷责任；
- 从哪个实际状态接上；
- 本事件会改变什么；
- 结果怎样自然触发下一事件；
- 涉及哪些承诺、伏笔或人物变化。

线程责任和前后衔接放在可展开区域。当前事件可以选择“不指定、一个大白话阅读感受或作者自定义”，不能要求作者选择专业方法，也不能把多个感受变成硬评分表。

章纲页面默认显示完整章链，每章一行故事责任；只有最近连续1～3章可以展开详细场景、情绪、信息变化和章末接口。

### 10.5 作者确认粒度

- 设定逐项确认，因为它是长期资料；
- 卷方向整份确认一次，内部允许跨方案选片段；
- 事件链整条确认一次；
- 当前事件大纲确认一次；
- 完整章节链确认一次；
- 最近详细章纲按马上要写的章节逐章确认；
- 正文和结算继续逐章确认。

不能把设定页的逐项确认机械复制到每层，让作者陷入几十个确认按钮。

### 10.6 AI介入时机

| 页面 | AI介入时机 |
|---|---|
| 开书 | 作者请求补全、比较或确认，不自动创建正式提案 |
| 设定 | 作者选择条目并点击协作后 |
| 卷方向 | 作者进入新卷并填写可选想法后 |
| 事件链 | 卷方向确认后由作者启动 |
| 事件大纲 | 作者选择当前事件后 |
| 章节链 | 当前事件大纲确认后 |
| 详细章纲 | 作者选择最近连续1～3章后 |
| 正文 | 当前章纲确认后 |
| 审查 | 正文候选完成后自动进入三个独立职责 |
| 结算 | 正文定稿后生成候选，作者确认后入正式状态 |

## 11. 作者API与错误门禁

### 11.1 普通作者API禁止字段

普通响应不得返回：

- `provider`、`modelId`、内部Agent实例ID；
- `taskId`、`discussionId`、内部队列ID；
- 内部结构方法键、方法版本和指纹；
- SQL、表名、文件路径、堆栈、错误代码和Worker内部状态；
- 其他owner、其他书籍的任何标识或内容。

作者只看到业务对象ID、可理解状态、进度和恢复操作。内部审计接口仅管理员可访问，并与作者投影分离。

### 11.2 错误门禁

所有页面、弹窗、Toast、空状态和恢复提示统一调用作者错误门禁。组件不得直接渲染 `Error.message`。错误文案必须说明：

1. 哪个业务动作没有完成；
2. 作者数据是否已保存；
3. 可以重试、恢复还是返回修改；
4. 必要时提供不泄漏内部信息的恢复编号。

## 14. 停止条件与回滚合同

出现任一情况时停止扩大上线范围，保留失败证据并回到对应批次修正：

1. 三份设定候选或两条卷路线只换措辞，没有方向、人物选择、因果路径、代价或高潮方式的实质差异；
2. 分层后作者必须执行的操作明显增加，或手机端完成同一任务需要反复跨页；
3. 软参考、方法节拍或推荐设定被提示词、质检或接口提升为硬要求；
4. 规划被误写成正文实际，或线程账本没有定稿正文证据却进入 `planted`、`advanced`、`resolved`；
5. AI输出出现内部方法名、技术ID、模型、任务、数据库或错误堆栈；
6. ContextCompiler依赖硬截断、全文堆叠或固定前N条，导致必要事实丢失；
7. 360像素手机端出现横向滚动、遮挡、选择丢失或主操作不可达；
8. 新后端让缓存中的旧前端无法读取、恢复或继续已有对象；
9. 新机制使人物辨识度、原创性、合理惊喜、情绪力度或整体阅读质量明显下降；
10. 出现跨用户/跨书污染、作者原话或定稿正文被覆盖、重复正式写入。

回滚必须满足：

1. 数据迁移只增不删；不修改已合并迁移，不永久删除作者资料；
2. 新旧卷方向、事件链、故事总线和线程账本保持兼容读取；
3. 通过功能开关或编译策略停用新写入，不删除作者输入、候选、版本、正文、结算和模型调用证据；
4. ContextCompiler可以恢复上一活动配置和包版本，且恢复后仍从权威正式源读取；
5. 已定稿正文永不因回滚失效；未确认候选可以标记失效但保留追溯；
6. 回滚后重新执行迁移、恢复、owner/book隔离、旧前端兼容和管理员核心链路验证。
