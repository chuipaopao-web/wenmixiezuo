## 0. 本轮决定与现状核查

### 0.1 不再设置“有故事线/无故事线”两套工作流

系统只保留一套可以逐步生长的故事线模型：

- 作者可以开书时一条故事线也没有，直接准备第一卷。
- 作者可以随时录入已经想到的一小段、某个阶段终点或完整故事线。
- “第十卷结束宗门复仇”是一个已知阶段节点，不等于全书结局。
- 全书结局、最终反派、故事线数量都允许长期未知。
- 每卷结算后，系统根据实际正文更新已存在故事线的真实进度，并提出可能萌芽的新线路。
- 主编只推荐下一卷至未来两卷的可见走向，不负责替作者强行补完全书。
- AI 产出的提炼、潜在线路和后续推荐全部是候选；未经作者确认，不得写入正式规划。

这套模型同时容纳“完整规划型”和“边写边想型”作者，不要求作者先选择永久模式，也不形成两套难以维护的分支产品。

### 0.2 老板本轮纠正

以下决定高于本方案上一版表述：

- 设定页是在现有设定工作台上重新调整，不恢复旧“信息页”，也不重建独立开书资料页面。
- 截图中的“开书资料 → 设定库 → 逐项设计 → 主编审查 → 完成”属于流程栏，必须删除。
- 全站所有页面，包括作者端、辅助页和独立后台，都不得再显示横向步骤圆点、连线、阶段柱或同类流程栏目。
- 顶部主功能导航仍负责页面切换；手机继续保留现有顶部两排导航。导航不是流程栏，不能跟着误删。
- 字体以 V6 重构前的生产界面质感为基准，只调整字体系统和排版层级，不照搬旧页面布局。
- 团队准确口径是 7 类岗位、初始 25 名 AI 成员，不是 25 种岗位。
- 初始人数为主编 3、副编 3、编剧 5、主笔 5、事实审查席 3、文学审查席 3、体验审查席 3；25 名只是初始后台配置，不写死，可以继续增加。
- 每个 AI 节点默认自动分配一名符合岗位要求的成员，作者只选择 AI 成员，可以更换默认成员或追加多人独立出方案，不直接选择模型。
- 闲置或未选成员不调用模型、不产生模型消耗；同岗位同批次成员收到完全相同的资料包。

## 1. 新核心创作流程

### 1.1 统一流程

```text
开书信息
  ↓
主角与开局 + 首卷必需设定
  ↓
第一卷方向（允许零故事线）
  ↓
事件 → 章纲 → 正文 → 章/事件/卷结算
  ↓
根据结算更新“已经发生”
  ↓
提炼已有线路进度 + 发现潜在线路（候选）
  ↓
主编推荐下一段 2–3 个方向，或建议继续观察
  ↓
作者确认看得见的部分 / 修改 / 暂不决定
  ↓
下一卷
```

### 1.2 放行规则

- 第一卷开放条件：开书信息确认、主角与首卷必要设定达到最低可写状态；故事线数量可以为零。
- 下一卷开放条件：上一卷完成结算，并明确上一卷实际结果、当前状态和未解决压力；不要求全书故事线完整。
- 作者已知很远的节点可以提前登记，但不会强制补齐从现在到该节点的所有中间卷。
- 故事线拓扑由当前已确认线路动态推导，仅作为视图，不再是开书前必须确认的业务对象。
- 作者可以一直选择“继续边写边看”；系统仍保存实际进展和开放问题，但不得制造虚假规划。

### 1.3 卷与故事线的自然衔接

每个下一卷方向必须能回答以下因果桥，缺一不可：

1. 上一卷实际改变了什么；
2. 角色或世界现在处于什么新状态；
3. 哪个压力、承诺或矛盾仍未解决；
4. 主角为什么会主动或被迫作出下一步选择；
5. 下一卷要解决的最近核心问题是什么；
6. 它推进、暂停、汇合或新生了哪些故事线；
7. 哪些内容只是候选，还没有发生。

主编推荐无法建立完整因果桥时，只能给出“证据不足，建议下一卷继续观察”的诚实结果，不得靠补造终局填空。

### 1.4 逐项验收

- [ ] 1.4.1 新书零故事线时可以创建并进入第一卷。
- [ ] 1.4.2 旧书已有完整故事线时仍可直接使用，不强迫降级或重录。
- [ ] 1.4.3 作者只填写第十卷阶段终点时，可以正常规划当前卷，不出现“全书不完整”警告。
- [ ] 1.4.4 第一卷、第二卷结束仍无正式故事线时，可以继续创作。
- [ ] 1.4.5 卷结算后，已关联线路的真实进度自动投影；未关联内容只产生候选。
- [ ] 1.4.6 作者拒绝或暂存 AI 候选后，候选不会污染正式规划和 ContextPack 硬事实。
- [ ] 1.4.7 下一卷方向能追溯到上一卷结算和具体正文证据。

## 2. 故事线“生长地图”产品设计

### 2.1 页面目的

用户现在需要的不是填写一份全书大纲，而是看清“写到哪里、哪些线正在长、我目前想到哪里、下一段可以怎么走”。当前最大障碍是页面先要求全书拓扑并用固定四阶段制造完成压力。改版后唯一主操作是：`请主编根据目前正文推荐下一段`；没有足够结算时，主操作切换为 `先完成本卷结算`。

### 2.2 桌面结构

```text
┌ 当前写作位置 / 本卷结算状态 / 唯一主操作 ┐
├ 已经发生 ────────────────────────────┤
│ 按卷与实际证据展示，只读，可回到来源                 │
├ 正在推进 ────────────────────────────┤
│ 每条线：当前问题、真实进度、最近一次推进、活跃/观察状态 │
├ 我目前想到这里 ───────────────────────┤
│ 作者确认的阶段节点、最远视野、允许空白                 │
├ 主编推荐的下一段 ─────────────────────┤
│ 2–3 个真正不同的方向；选择、修改、暂存、继续边写边看    │
├ 还没决定 ────────────────────────────┤
│ 开放问题、待观察矛盾、可能萌芽但未确认的线路             │
└────────────────────────────────────┘
```

### 2.3 故事线状态

正式故事线状态：`萌芽`、`推进中`、`暂缓`、`阶段完成`、`完成`、`放弃`。

潜在线路不是正式故事线，单独使用：`观察中`、`待作者确认`、`已采纳`、`已忽略`。以下条件至少满足两项，且必须有证据，才允许进入潜在线路候选：

- 同一矛盾跨越多个事件或连续出现；
- 它影响主角的重要选择或代价；
- 它对未来形成可识别的承诺；
- 它和既有线路不能简单归为同一阶段动作。

一次性章末钩子、普通悬念、尚未兑现的 AI 猜测不得自动升格为故事线。

### 2.4 已知视野

每条故事线允许仅保存作者当前知道的部分：

- 当前问题：现在这条线在追问什么；
- 已知节点：作者已经确认的阶段锚点，可以只有一个；
- 最远视野：例如“约第十卷完成宗门复仇”；
- 下一小段：目前看得见的一至两卷；
- 开放问题：尚未决定、需要保留的空间；
- 结局方向：可空，不能作为完整度门禁。

原固定“起点/发展/转折/收束”板块停止作为强制结构；如某本书确实使用该结构，只作为可选模板映射。

### 2.5 全站取消流程栏

截图中的圆点、连线和阶段名称不是导航，而是重复展示流程的装饰性步骤栏。本批次按共享 UI 基础设施处理：

- 删除设定、故事线、分卷、事件和章节页全部 `.v6-phase-line` JSX。
- 删除未使用的 `StageTrack`、`V6_STAGES` 及 `.v6-stage-track` 样式；若仍有有效引用，先迁移其导航职责再删除。
- 搜索并删除作者端、辅助页和独立后台同类“步骤一 → 步骤二 → 完成”的横向圆点、时间轴式页头和手机缩小版本。
- 不用另一种面包屑、进度柱或阶段卡替换流程栏。
- 页面只在标题附近用一句当前状态说明“现在正在处理什么”，真正的 AI 任务进度留在对应任务卡内部。
- 顶部主功能导航继续承担设定、故事线、分卷、事件、章节和辅助工具切换；手机仍为现有两排，不增加第三排。
- 删除流程栏后回收首屏高度，当前内容和唯一主操作上移，桌面与手机都不得留下空白占位。

### 2.6 全站字体与排版

字体修改以 V6 重构前的生产页面和浏览器计算样式为取证基准，只恢复字体质感，不恢复旧信息页或旧布局：

- 正文、说明、按钮、标签、导航和表单统一使用原无衬线中文字体栈：`SF Pro Text / Segoe UI Variable Text / PingFang SC / Microsoft YaHei UI / system-ui`。
- 衬线字体只允许用于品牌字和少量大标题，不再用于功能导航、按钮、流程状态、小标签和密集正文。
- 拆分 `--font-ui`、`--font-reading`、`--font-title` 三个共享令牌，删除 V6 对 `--font-display` 的泛化使用。
- 桌面正文与控件主字号保持 14–16px，辅助信息不低于 12px；手机输入保持至少 16px。
- 中文正文和导航默认不拉大字距；普通文本字距控制在 0–0.02em，大标题按实际字体单独登记。
- 正文行高 1.65–1.8，按钮和标签使用稳定行高；避免宋体伪粗、700 以上假粗和 8–11px 密集小字。
- 在 Windows、macOS/iOS 和 Android 字体回退环境分别检查，不得只在开发机有目标字体时好看。
- 设定、故事线、分卷、事件、章节、团队、资料库和后台共享同一套排版令牌，不允许页面各自追加一次性字体覆盖。

### 2.7 手机端

- 保留现有顶部两排导航，不增加第三排全局导航，也不保留任何页内流程栏。
- 五个区域改为单列折叠段；默认展开“正在推进”和当前唯一主操作。
- 360px、390px、430px 下不得横向滚动，线路节点改为纵向时间轴。
- AI 推荐抽屉全屏打开，作者可在不丢失原路线的情况下比较 2–3 个方向。
- 证据详情二级展开，首屏不堆技术字段、版本号或内部 AI 岗位名。

- [ ] 2.8.2 页面不再出现必须选择全书拓扑、必须填写结局或完整度不足的硬阻塞。

## 3. 数据模型、版本与 API

### 3.1 权威分层

| 层级 | 权威内容 | 可否由 AI 直接写入 |
| --- | --- | --- |
| 正文事实 | 不可变正文版本、正式结算 | 否 |
| 实际线路进展 | 从正式结算投影，保存来源 ID | 仅可提出归属建议，不能伪造事实 |
| 作者规划 | 作者确认的线路、节点、下一段、开放问题 | 否，必须经作者确认 |
| AI 候选 | 潜在线路、后续方向、证据解释 | 可以生成候选，不能自动升级 |

### 3.2 合同升级

新增故事线内容版本，保留旧版本只读解析：

- `currentQuestion?`
- `knownMilestones[]`
- `knownHorizon?`
- `nextSegment?`
- `openQuestions[]`
- `endingDirection?`
- `protectedOpenSpaces[]`
- `status`

所有远期字段可空。旧 `stageGoal/expectedStages` 可迁移为已知节点，但不再要求三段或四段齐全。

### 3.3 新增记录

- `storyline_growth_rounds`：一次卷结算后的故事线整理批次，关联结算版本、AI 批次、作者决定和状态。
- `storyline_emergence_candidates`：潜在线路候选、证据、观察次数、作者处理结果。
- `storyline_route_decisions`：作者对主编方向的选择、修改、暂存或继续观察决定。
- AI 团队复用现有 7 类 `agent_role_pools_v6`，初始目标人数为 3/3/5/5/3/3/3，并允许管理员以后继续增加成员。
- 扩展现有成员配置，使每名成员拥有独立头像、姓名、岗位、供应公司公开名、消耗等级、工作状态，以及仅管理员可见的供应商和模型绑定。
- 复用或扩展 `ai_node_batches_v6` 与成员明细，记录节点默认分配、作者更换、作者追加和最终冻结的成员集合。
- 同岗位同批次成员共用一个冻结 ContextPack ID 与哈希；成员变化不得重新编译出不同资料包。
- 实际进展继续进入创作台账的 `storyline/actual` 分层，不复制第二套“故事记忆”。

新表和新字段必须携带适用的 `owner_id`、`book_id`；确认、驳回和读取全部验证业务会话，跨书引用为零。7 类岗位和成员基础配置可以是系统级数据，书籍任务与批次快照必须按书隔离。

### 3.4 主要接口

- 获取故事线生长地图：返回事实、活跃线、作者视野、候选和开放问题的分区视图。
- 开始卷后提炼：只接受已完成的正式卷结算版本，幂等创建生长轮次。
- 获取/确认潜在线路：确认时新建正式线路版本，不覆写候选原文。
- 请求主编推荐：冻结 ContextPack、Skill、模板、模型和来源清单后创建异步任务。
- 处理推荐：支持选择、编辑后采纳、暂存、全部拒绝、继续边写边看。
- 获取证据：仅返回本书可见的正文/结算导航信息，不暴露模型思维链。
- 获取 7 类岗位与成员名册：作者投影只返回头像、姓名、岗位、供应公司、消耗等级和工作状态，不返回模型名、擅长领域、速度或成功率。
- 获取节点默认成员与可替换成员：节点先确定需要的岗位，再自动分配一名可用成员；作者只提交成员选择，不提交模型或供应商参数。
- 更换或追加节点成员：支持同岗位多人独立出方案，开始前冻结成员集合、相同 ContextPack、相同作者输入和费用预估。
- 管理员成员配置：独立维护每名成员的供应商、模型、启用状态、公开资料和消耗等级；历史任务绑定不可变。

### 3.5 兼容与清理

- 旧故事线和台账可读，按需升级为新内容版本，不原地改写历史记录。
- 旧 `BookStorySpine`/`storySpine` 停止主动生成和作为放行条件；历史任务、历史上下文和审计记录仍可读取。
- 新闭环通过后删除旧前置故事线入口、固定四阶段组件、旧放行判断、旧主动生成器、对应无效测试和旧说明。
- 历史迁移和作者正式数据不删除；“删除旧代码”不等于删除作者旧数据。

## 4. AI 介入、7 类岗位与初始 25 名成员、Skill、模板、提示词与资料包

### 4.1 AI 介入边界

卷结算后先执行不收费的确定性步骤：校验结算、更新已明确关联线路的实际进展、编译证据索引。只有以下动作创建模型任务：

- 作者主动请求“主编推荐下一段”；
- 系统在卷结算后检测到需要语义判断的潜在线路，并得到当前产品策略允许的触发条件；
- 作者主动要求整理、改写或比较方向。

不得为了让页面看起来完整而后台静默生成全书规划。

### 4.2 7 类岗位与初始 25 名成员

团队定稿如下，人数是初始后台配置，不写死，管理员以后可以继续增加成员：

| 岗位 | 初始人数 |
| --- | ---: |
| 主编 | 3 |
| 副编 | 3 |
| 编剧 | 5 |
| 主笔 | 5 |
| 事实审查席 | 3 |
| 文学审查席 | 3 |
| 体验审查席 | 3 |
| 合计 | **25** |

现有具名成员继续保留并归入以上 7 类，缺少的成员补齐到初始 25 名。所有用户可见成员都必须有真实后台配置，不能用占位卡或前端假数据凑人数。

成员和选择规则：

- 初始 25 名及后续新增成员分别在后台绑定各自的供应商和模型；绑定可以单独调整，不能按岗位共用一个隐式模型。
- 用户不直接选择岗位、模型或供应商。AI 节点先确定所需岗位，再默认自动分配一名可用成员。
- 用户可以更换默认成员，也可以追加同岗位多人独立出方案。
- 作者端只显示头像、姓名、岗位、供应公司、消耗等级和工作状态。
- 作者端不显示模型名、“擅长领域”、速度、成功率、内部成员 ID 或模型路由细节。
- 同岗位、同批次的全部成员必须收到完全相同的 ContextPack ID、内容哈希、作者输入、岗位 Skill、节点 Skill 和模板版本，保证比较公平。
- 成员方案彼此隔离，不能先读其他成员的结果再伪装成独立方案。
- 闲置、未选、被更换或未实际启动的成员不调用模型，不产生模型消耗。
- 开始任务后冻结成员集合和后台模型绑定快照；管理员之后改绑定只影响新任务。
- 成员不可用或调用失败时保留其他成功结果，作者可以只换掉或重试失败成员。

副编是用户可见的 AI 成员，负责局部内容整理、融合和执行性检查。资料包选择、裁剪、来源分层和哈希编译由不可见的系统服务 `ContextCompiler` 承担；它没有头像、姓名、成员状态或发言入口，也不能伪装成副编。

节点选人界面上，用户此刻要完成的是确认本次由谁参与；当前最大障碍是成员被折叠成 7 类汇总且缺少更换/追加入口；改版后唯一主操作为“按当前成员开始”，更换和追加为就近次要操作。

### 4.3 Skill 更新

已有三层 Skill 机制继续使用：核心规则 Skill、岗位 Skill、节点协议 Skill。新增内容如下：

- 深化 7 份岗位 Skill；同岗位成员共享相同岗位责任和公平比较规则，成员差异来自冻结的成员配置、供应商和模型绑定。
- 副编 Skill 只负责局部内容整理、融合和执行性检查；ContextCompiler 是系统组件，不创建成员 Skill，也不进入成员选择。
- `storyline_progress_extract`：只从正式事实提炼进展并附来源。
- `storyline_emergence_detect`：判断是否持续成线，允许输出“继续观察”。
- `storyline_next_segment_recommend`：只规划下一卷至未来两卷。
- `storyline_route_review`：检查方向差异、因果桥、代价和开放空间。
- `storyline_author_merge`：把作者选择或修改写成候选正式版本，等待确认。

Skill 只新增版本，不修改已经被任务冻结的旧版本内容或哈希。

### 4.4 AI 协作顺序

1. 事实审查席从冻结资料包独立生成事实证据表；
2. 作者确认的两名或多名编剧从完全相同的资料包独立提出真正不同的下一段方向，彼此不可见；
3. 副编对局部方案做整理、融合和执行性检查，不承担资料包编译；
4. 体验审查席指出每个方向最可能崩坏的位置；
5. 主编整理为 2–3 个并列方案，不替作者拍板，不掩盖分歧；
6. 作者选择、修改、暂存或继续观察；
7. 只有作者确认后才生成新的规划版本和下游候选。

若所谓独立意见实际由同一模型、同一上下文串行模仿，不得在 UI 中伪装成独立复核。

### 4.5 新输出结构

每个主编方向至少包含：

- 从哪些正文/结算事实自然延伸；
- 主角为什么继续卷入；
- 下一段核心问题和可见终点；
- 推动、暂停或汇合哪些已有线路；
- 是否可能长出新线路；
- 预计代价、节奏风险和设定冲突；
- 哪些是推测、哪些仍开放；
- 推荐视野，默认下一卷，最多未来两卷。

### 4.6 提示词硬规则

- 不要求全书故事线或最终结局。
- 不凭空创造最终反派、世界终极秘密或“宿命主线”。
- 不把旧规划、AI 候选和未发生事件写成实际事实。
- 不把每个伏笔、章末钩子和配角登场都升级成故事线。
- “不知道”“证据不足”“继续观察”是合法且高质量的答案。
- 所有关键判断必须带可导航的来源 ID；不得输出思维链。
- 推荐必须形成不同选择，不能只换词复述同一方向。

### 4.7 创作模板更新

新增软性模板，不作为强制结构：

- 因果延伸：结果 → 新状态 → 新压力 → 主角选择；
- 代价升级：成功带来更大的个人/关系/资源代价；
- 关系转向：同盟、对手或亲密关系改变下一段问题；
- 线路汇合/分叉：已有线路产生交叉或暂时分离；
- 阶段终点反推：作者已知第十卷终点，仅规划当前可见的最近桥段；
- 继续观察：证据不足时保护空白，不制造路线。

旧全书脊柱模板退出新书主动流程；历史模板 ID 只为旧任务审计保留。

### 4.8 ContextPack 更新

ContextCompiler 仍是唯一上下文权威编译器，不另建“故事线记忆”。新编译策略按以下优先级：

1. 硬约束：业务身份、本书、作者明确要求、确认设定；
2. 正文事实：不可变正文版本、章/事件/卷正式结算；
3. 当前实际状态：已发生线路进展和角色/世界变化；
4. 作者规划：有效的线路版本、已知节点、最远视野、开放问题；
5. 软资料：相关旧证据、待观察矛盾、近期作者备注、可选创作模板。

未经确认的潜在线路、失败候选、作废下游、他书内容和模型隐藏推理不得进入硬事实。为避免重建旧表，内部 `BookStorySpinePack` 类型暂保留兼容，编译策略升级后在后台显示为“当前故事线地图与已知视野”；来源清单必须标明实际、规划和候选。ContextCompiler 是不可见系统服务：同岗位同批次只编译一次并向所有已选成员分发完全相同的资料包，不出现在作者团队、成员状态、发言流或可选名单中。

### 4.9 后台 Skill 与调用治理

独立后台新增 `AI 治理` 分组：

- 团队：7 类岗位、初始 25 名及后续新增成员、头像/姓名/公开公司/消耗等级、管理员可见供应商与模型绑定、健康、负载、费用和失败；
- Skills：核心/岗位/节点三层清单、版本、状态、哈希、正文、使用触发器、调用次数和最后使用时间；
- 模板：创作模板版本、适用节点、启用状态和引用次数；
- 提示词：基础提示、覆盖、输出模式、版本和差异；
- ContextPack/调用：友好分层视图、来源清单、哈希、冻结 Skill 三元组、模板版本、模型和输出校验结果。

后台允许比较版本和停用未来使用，但不得修改历史任务的冻结快照。

## 5. 设定页重新设计

### 5.1 问题判断

新设定页需要在现有页面内部调整，不恢复旧信息页。当前问题有三层：

1. 顶部流程栏抢占首屏，却没有提供额外导航价值；
2. V6 把衬线字体、小字号和较大字距用在大量功能文字上，阅读观感明显变差；
3. 旧开书数据中的主角性格仍然存在，但当前设定页摘要只展示姓名、背景和特殊机制，人物信息被隐藏。

宏观世界设定继续排除人物条目是正确的。修复方式是在设定页内提供轻量“主角基础”摘要和编辑入口，不把人物塞进宏观设定库，也不重新建立独立信息页。

### 5.2 页面目的

用户此刻要完成的是选择、设计并确认当前真正需要的设定。当前最大障碍是流程栏和字体抢走注意力，同时主角基础缺失、当前设定任务不够突出。改版后首屏唯一主操作跟随真实状态变化：未开始时为 `开始设计当前设定`，有候选时为 `确认当前设定`，全部完成时为 `请主编审查`。

### 5.3 新结构

```text
┌ 设定 / 本书名称 / 当前真实状态 / 唯一主操作 ─────────┐
│ 无圆点、无连线、无“开书资料→完成”流程栏                 │
└────────────────────────────────────────────┘
┌ 主角基础（轻量摘要，不是信息页）─────────────────┐
│ 姓名、身份、当前处境、性格标签、欲望/缺陷；就地编辑入口   │
└────────────────────────────────────────────┘
┌ 当前设定任务（页面主体）────────────────────────┐
│ 当前条目、作者输入、成员选择、候选、编辑稿、确认和失败恢复 │
└────────────────────────────────────────────┘
┌ 完整设定库 / 已确认设定（按需展开）────────────────┐
│ 选择范围、版本、来源、冲突、历史和重新审查状态             │
└────────────────────────────────────────────┘
```

开书资料继续通过现有修改弹窗维护，不新增旧信息页路由。主角基础只承担当前创作需要的可见摘要；展开或编辑后写入版本化角色卡。设定页主体始终是当前设定任务，不能让主角摘要、资料库或团队面板重新变成卡片墙。

### 5.4 数据权威与迁移

- 开书蓝图保留为“初始主角来源”，不被普通编辑覆写。
- `CharacterCard` 升级版本，补充 `personalityTraits`、`strengths`、`flaws`、`fear`、`voiceHabits`、`background`、`publicFace`、`privateNeed` 等可选字段。
- 新书确认开书时创建主角角色卡；以后角色卡版本是当前人物权威。
- 旧书没有主角角色卡时，从开书蓝图幂等生成一次，恢复性格标签；已有角色卡绝不被迁移覆盖。
- 宏观世界设定继续不接收人物条目，避免双权威。

### 5.5 响应式和视觉验收

- 保留手机顶部两排功能导航；设定页内部不显示任何流程栏。
- 主角性格标签、欲望、缺陷和当前处境在 360px 首屏可见，不藏到三级弹窗。
- 桌面依据新的强制设计图做稳定区域像素相似度验收，目标不低于 95%。
- 字体严格使用第 2.6 节新共享令牌；正文和控件恢复旧版无衬线质感，衬线只留给少量大标题。颜色、间距、边框和状态反馈同时统一，不能只补信息。

### 5.6 逐项验收

## 6. 独立管理后台更新计划

独立后台继续使用独立域名和管理员权限，不与作者工作台混成同一导航。本节为独立实施流，但和作者端共用业务事实与审计数据，不能复制第二套统计口径。

### 6.1 后台信息架构

```text
总览
用户与书籍
任务与问题
会员与收入
AI 治理
  ├ 团队
  ├ Skills
  ├ 创作模板
  ├ 提示词
  └ ContextPack / 调用审计
模型与成本
```

### 6.2 经营看板

新增或统一以下指标：

- 注册用户数：排除管理员账号；
- 付费用户数：至少存在一笔成功、正金额的会员交易；青铜/免费会员不计付费；
- 累计付费率：累计付费用户数 ÷ 累计注册普通用户数；
- 30 日付费率：30 日内首次付费用户数 ÷ 同期新注册普通用户数；
- 已记录会员收入：正金额会员开通/续费交易之和，退款出现后按净额计算；
- 今日失败用户数、今日失败任务数、失败率；
- 总书籍、活跃书籍、今日有创作行为书籍；
- API 成本、会员收入和净贡献只在统计口径一致时并列，不能伪造利润。

当前系统没有支付渠道回调，因此第一阶段必须使用“已记录会员收入”，不能标成“支付平台实收”。若以后接入微信、支付宝或其他支付渠道，需要另建支付订单、回调幂等、退款、对账与密钥管理批次；该批次涉及新密钥和真实资金，必须另行确认。

### 6.3 用户与书籍详情

用户列表增加：书籍总数、有效书籍数、会员状态、累计已记录收入、最后活跃时间、今日失败任务数和红色定位入口。

用户详情页或抽屉展示：

- 账号状态、会员、额度、成本、累计收入、最后登录/创作；
- 创建书籍总数、活跃/归档数量；
- 每本书的书名、创建时间、当前创作阶段、当前卷/事件/章节、已结算章节、最近活动；
- 7 类岗位人数、初始 25 名成员补齐状态、当前节点已选成员和成员健康；
- 当前运行任务、最近完成任务、今日失败任务；
- 今日失败具体发生在书籍、阶段、节点、成员、API/Worker/前端页面的哪里；
- 安全错误摘要、时间、恢复键和跳转至任务/问题审计的入口。

后台仍只显示业务必要的错误和审计数据，不展示 API Key、完整凭证、模型思维链或其他用户书籍内容。

### 6.4 任务失败统一定位

把现有问题页扩展为统一故障视图：

- API/Worker 任务失败；
- 7 类岗位内本次已选成员的局部失败、超时、降级和重试；
- 故事线提炼、潜在线路识别、主编推荐、作者确认失败；
- 前端已上报且可恢复的关键交互失败；
- 失败所属用户、书籍、对象版本、节点、页面、成员和恢复状态。

同一底层失败应有稳定关联键，避免同一事故在总览、用户页和问题页被重复计数。

### 6.5 AI 治理后台

按照 4.9 实现团队、Skill、模板、提示词和 ContextPack 五类治理页。管理员可以查看未来任务使用配置、停用问题版本和检查书籍收敛，但不能修改历史调用快照或作者事实。

### 6.6 后台页面的 UI 目标

后台用户现在需要从“一个用户今天失败了”直接定位到“哪本书、哪个节点、哪名成员、如何恢复”。当前最大障碍是指标分散、用户列表没有书籍与故障上下文。改版后每个页面只有一个主动作：总览查看异常、用户页打开用户详情、故障页执行恢复或标记处理、AI 治理页查看当前生效版本。

### 6.7 后台逐项验收

- [ ] 6.7.1 付费率分子分母可展开核对，免费会员和管理员不计入付费用户。

## 9. 部署与回滚计划

### 9.1 发布顺序

1. 备份和迁移预演；
2. 发布向后兼容的数据/API/Worker，旧 Web 仍可使用；
3. 发布独立后台，先核对新数据和 AI 治理；
4. 发布作者端 Web；
5. 运行新旧书核心冒烟、登录、首卷、结算、推荐、设定和后台定位；

### 9.2 回滚边界

- 数据变更以新增表/新增版本为主，旧读路径保留到新闭环稳定；
- 回滚应用版本不回写或删除作者新数据；
- 已生成的新版本和作者决定保留，回滚后只暂停新功能入口；
- 生产异常优先切回上一应用版本，不在线猜测修改作者数据。
