# 火山方舟 Coding Plan GLM-5.2 / GLM-5.3 可配置能力恢复清单

## 变更合同

- 任务类型：模型适配器恢复与后台配置能力修复。
- 当前问题：上次把“暂时停用 GLM”错误实现为模型目录、后台保存和运行时适配三处整体下架；未绑定岗位的模型也无法保持可配置状态。
- 复现步骤：读取管理后台平台模型方案时 GLM-5.2/5.3 不在 `allowedModels`；直接解析两个 Coding Plan 模型时返回“模型已下架”；保存含 GLM 的未来岗位方案被拒绝。
- 期望结果：GLM-5.2、GLM-5.3 均可由同一 Coding Plan 凭证连接，可在独立后台作为可选模型使用；当前岗位方案不绑定 GLM。
- 允许修改：模型运行配置目录、方舟适配器准入、平台模型方案服务与其接口装配、直接相关测试、模型配置说明和部署环境变量示例。
- 明确不改：25 名成员名单及岗位默认模型、作者端成员选择规则、创作工作流、提示词、资料包、ContextCompiler、数据库结构、作者正式内容、前端布局与视觉。
- 必须保留：现有 Coding/Agent Plan 端点隔离、严格零现金回退、密钥仅来自环境变量、作者端不显示模型名、现有岗位绑定与模型异源校验。
- 新功能验收：两个 GLM 出现在后台可选模型目录；二者均可由 Coding Plan 适配器解析并完成真实最小连通探针；后台未来保存方案时接受合法 GLM 分配。
- 原功能回归：现有模型仍可解析；当前 25 名成员模型方案不含 GLM；非法供应商/模型仍被拒绝；普通用户仍看不到模型目录。
- 测试范围：模型运行配置单测、方舟适配器单测、管理后台平台方案集成测试、API 类型检查与构建、两个模型的零现金最小真实探针。
- 部署要求：无数据库迁移；发布前检查生产当前平台方案不含 GLM，等待在途任务连续 30 秒为零后仅重启 API/Worker，并验证健康、后台目录和线上最小探针。
- 全量触发判断：本次不改数据库、权限、恢复系统或核心创作工作流，不触发 `npm run verify:full`；若实现被迫扩大到这些范围，暂停并更新工单。
