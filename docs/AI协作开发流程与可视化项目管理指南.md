# AI协作开发流程与可视化项目管理指南

**给不写代码的项目负责人，也给接手开发的AI。**

版本：1.0 · 2026年9月15日

用途：将本文件交给任何开发AI，用于建立新项目的方案、执行、验收、交接与后台管理流程。适用于网站、应用、管理系统和含AI能力的产品。文中的编号、文件名与技术结构是推荐起点，可按项目规模调整。

本指南从“文秘写作”的协作实践中提炼，也吸收了重复返工、测试与真实运行不符、报告误判等教训。它是一份独立复用资料，不改变文秘写作现有规则，不携带该项目的服务器、账号、删除或发布授权。

**这套方法的核心是：先把用户要得到的结果说清楚，把已确认方案保存在项目中，按小批次实施，用证据验收，再把真实进度展示给负责人。** 文档能显著改善交接，但不能保证任意AI都一次做对或产品没有BUG。

## 一、人员分工与决定权

| 角色 | 负责什么 | 不应做什么 |
|---|---|---|
| 项目负责人，也就是老板 | 说明目标、用户、偏好、预算及重要取舍；确认产品方向 | 不需要决定数据库字段、代码文件或逐条解释报错 |
| 方案负责人 | 核对现状，提出方案，明确技术路线、任务范围、验收条件；安排开发与审查 | 不把模糊愿景当作详细任务，让执行者自行猜测 |
| 执行者 | 按本批方案实现、测试、记录实际差异和结果 | 不擅自新增功能，不为通过测试降低标准 |
| 验收者 | 对照方案、实际差异和运行证据，判断是否达标 | 不只看执行者总结，也不每次把已关闭问题重新检查一遍 |

一个AI可以兼任多个角色；高风险改动优先安排独立审查。若仍是同一个模型或同一会话，应如实说明，不能把更换角色名称当成独立验证。没有必要每个小修改都使用多模型。

### 哪些事需要老板决定

- 产品要服务谁、主要解决什么问题，重要功能要不要改变。
- 新增实际付费、预算变化、第三方敏感数据传输。
- 永久删除用户数据、生产数据恢复、不可逆且影响权益的操作。
- 缺少凭据、登录或确实只能由本人完成的事项。

普通、可逆且在已授权范围内的工程选择，由方案负责人和执行者处理。不要反复询问已确认的决定，也不要要求老板理解技术细节才能继续。

**“我们讨论一下”是讨论；“这个方案可以”是方案认可，是否同时开工结合上下文判断；“按这个实现”是开发指令。** 部署授权单独记录，可约定已验证的小修持续发布，也可逐版批准，不能默认继承其他项目的授权。

## 二、新项目先准备什么

AI先根据已有信息填表，只向老板询问真正缺失的关键内容，不发一份几十题的问卷。

| 要明确的事情 | 用普通话怎么说 | AI应给出的结果 |
|---|---|---|
| 服务对象 | 谁每天会用它 | 用户类型与权限边界 |
| 核心任务 | 用户来这里最想完成什么 | 一条完整主流程 |
| 第一版范围 | 先做到哪一步就有价值 | 首版必须做、可以后做 |
| 使用环境 | 手机、电脑、浏览器还是客户端 | 设备与交互约束 |
| 数据 | 要保存什么，哪些不能丢 | 数据归属、正式来源与保存规则 |
| 外部能力 | 是否用支付、邮件、AI、地图等 | 依赖、成本、密钥与故障处理 |
| 视觉偏好 | 喜欢什么风格，有无参考 | 原型与基础样式约定 |
| 交付条件 | 本地试用还是给真实用户上线 | 验收与发布范围 |

### 新项目与已有项目分开接管

**新项目：** 可以先提出架构和预计目录，但必须注明“计划新增”，不能写成已存在。先确认主流程和最小可用范围。

**已有项目：** 先核对当前分支、未提交修改、运行入口、已有功能和部署版本。只读必要代码与文档，明确保留、修复、替换和未知部分，不先全量重写。

两种情况都应尽早交付一条真实可运行的主流程。例如预约产品先做到“创建预约→保存→查看”，不用先建完庞大的管理平台才开始做产品。

## 三、完整开发流程

| 步骤 | 具体做什么 | 本步留下什么 | 什么时候能继续 |
|---|---|---|---|
| 1. 讨论 | 理解用户任务，提出推荐，说明代价与必要替代方案 | 候选方案、待决定问题 | 关键产品方向清楚 |
| 2. 确认 | 明确本轮采用哪种方案、范围和偏好 | 已确认决定及版本 | 没有影响本批的关键歧义 |
| 3. 保存 | 将决定写入项目内正式方案，关联功能编号 | 当前方案原件 | 后续AI可以脱离聊天理解它 |
| 4. 定位与拆批 | 核对入口、数据、依赖；按可验证结果拆分 | 本批执行任务 | 关键技术路线明确，可直接实施 |
| 5. 实现 | 根据依赖顺序编码，及时验证 | 代码、必要数据变更和测试 | 本批目标实际实现 |
| 6. 自查与审查 | 检查差异、失败路径、真实运行；集中反馈缺口 | 证据与待修项 | 相关验收达标，无已知阻断 |
| 7. 发布 | 构建、备份或回退准备、切换、线上检查 | 发布版本与线上验证 | 已获发布授权且满足安全条件 |
| 8. 收尾 | 更新功能状态、方案偏差、日志和下一步 | 可接手的当前状态 | 不把尚未验证的事记为完成 |

### 确认之后还能改方案吗

可以。方案不是禁止思考的命令书。执行者发现现实与方案不符时，先给出证据和影响。

- 仍属于本批目标的普通工程调整：更新原方案的相关段落，说明原因后继续。
- 改变用户行为、重要范围、费用或数据权益：先提出具体变更，取得必要决定。
- 不相关的新需求：进入后续清单，不顺手混进当前批次。

每次变更都记录“为什么变、影响什么、当前采用哪版”，不再另开一份名字相似的正式方案。

### 批次怎么拆才合理

按用户可理解的结果拆，而非随意按文件数拆。例如：

- 第一批：用户能提交预约并在刷新后查到。
- 第二批：用户能取消预约，重复点击只取消一次。
- 第三批：管理员能查预约及处理异常。

必要的基础设施可以单独成批，但要说明它服务哪个用户结果、后续如何接上。不要连续做很多批工具维护，却一直没有用户能试用的功能。

## 四、文档如何保存而不越堆越多

**一项事实只有一个维护原件，其他地方引用或展示它。** 老板拿本指南启动新项目即可，不用先复制文秘写作所有文档。

推荐最小结构：

```text
项目根目录/
├─ AGENTS.md                  AI接管入口、分工和授权规则
├─ docs/PROJECT_PLAN.md        项目目标、功能方案、技术路线、验收与发布约定
├─ tasks/CURRENT.md            当前执行批次、具体步骤和最新结果
├─ project/features.json       后台所需的功能记录；建管理页时再增加
└─ evidence/                   测试、截图和发布证据，不存密钥
```

- 小项目可以把验收、发布、接管信息放在上述文件中，不强制另建多份文档。
- 项目变大后按独立职责拆分，例如部署操作手册；入口链接回原件，避免全文复制。
- 当前任务完成后可归档，下一任务有新编号。旧任务只用于追溯，不自动成为新任务规格。
- 聊天记录是背景资料；有效决定必须落到项目原件。
- `Skill`是可选的工具接入方式。若创建，只做简短入口，引用这些原件，不再复制一整套流程。
- 本指南是跨项目方法说明；项目正式规则由接手AI结合目标建立，不必把本指南全部塞进每次开发上下文。

### 编号约定

建议采用简短稳定编号加中文短语：

- 功能：`F-001 用户注册`、`F-002 预约创建`。
- 任务：`T-001 打通预约创建`。
- 缺陷：`BUG-001 重复提交产生两条预约`。
- 发布：`R-001 首次试用版`。

显示顺序、目录分类与稳定编号分开。移动位置、改名称不能改变对象身份，删除的编号不重复分配。Git提交号用于定位代码，不能代替负责人看得懂的功能名称。

## 五、功能方案模板

以下内容直接保存在正式方案内，每个功能一节；简单功能合并字段，不必填满不相关内容。

```text
功能编号与名称：
方案状态及版本：候选 / 已确认；版本与确认日期
解决的问题：谁在什么场景下遇到什么困难
用户结果：做完后能得到什么
进入位置：从哪里打开，是否需要登录或权限
功能流程：输入 → 处理 → 输出 → 下一步
页面与交互：主要操作、默认值、保存时机、设备要求
重要状态：加载、成功、空结果、失败、恢复等实际需要的状态
业务规则：可做什么、限制什么、谁能修改
数据规则：保存对象、归属、版本、重复操作与删除方式
技术路线：复用/新增模块、接口与必要依赖；说明选择理由
异常处理：超时、重复点击、刷新、权限失效、外部服务失败
保留项：不能丢失的能力、数据和已确认偏好
暂不包含：本版明确不实现的功能
验收标准：可实际执行的操作和预期结果
发布与兼容：是否改变现有接口/数据，需要怎样切换或回退
变更记录：哪些决定修改过及原因
```

### 一个足够具体的例子

`F-002 预约创建`：登录用户选择日期和服务后提交，系统保存预约并显示详情。刷新仍能看到；同一次提交因网络重试不应生成两条；未登录不能查看别人的预约。失败时保留已填内容，说明能否重试。用户只点一次确认，不再跳到第二个重复确认页。

验收包括：正常创建、连续点击、请求已保存但响应丢失、重新登录后恢复、跨账号访问被拒。技术方案再落实到接口、存储和具体文件。

这比“做好预约功能，完善所有异常”更容易被准确执行。

### 含AI能力时再补充

明确AI任务的可信输入、工具权限、输出结构、来源版本、预算、时限、失败与恢复。程序负责身份、存储、数值、格式、防重；AI负责需要理解和判断的内容。

检索只引入当前任务需要的资料。保留简短结论、采用理由与证据，不保存或展示模型内部思维链。若要求独立审查，应核对实际模型身份，不能只换头像或岗位名。

## 六、单批执行与交付模板

**方案负责人先定位，再派工。** 技术路线尚未确定时，下达有边界的“定位任务”，不要标为“可直接开发”。新文件可以计划新增，现有路径、函数和验证命令必须实际核对。

```text
任务：T-xxx 中文结果名称
状态：定位中 / 可实施 / 实施中 / 待验收 / 已关闭 / 受阻

1. 本批结果
用户操作前后有什么变化；本批明确不做什么。

2. 依据与基准
功能编号、正式方案章节和版本；工作区、分支、基准提交。
必须先读的文件与符号；已核实事实和剩余未知。

3. 具体实现
按实际调用链说明改哪一层、输入输出、数据写入及失败处理。
关键决定已定；普通实现细节由执行者选择。
保护其他人未提交修改；写清允许修改范围及必要依赖。

4. 执行顺序
按依赖列出步骤，每步有可检查结果。
已经通过且未受影响的部分无需重做。

5. 验证
实际可运行的命令、操作和预期结果。
修BUG先复现或建立相关反例；不以测试数量代替覆盖目标。
验证受阻时记录原因，不假装通过。

6. 交付和授权
提交、集成、外部调用、部署的范围。
唯一结果与证据位置；结束条件；允许接续的下一批。
```

执行完成后，在同一任务记录中补充：

```text
用户现在可以做什么：
具体改了什么、为什么：
与确认方案一致吗；偏差是否已获认可：
验证结果及证据：
未完成、未验证和已知问题：
代码版本；是否上线；线上核验结果：
开发者、审查者与实际模型/工具（可取得时）：
下一步与负责人：
```

不要把几十次命令失败的操作流水当作交付摘要。原始日志可以留存，老板首先看到结果和影响。

## 七、负责人看得懂的后台

建议为需要持续迭代的产品设置“产品与开发管理”页面。它帮助老板了解产品和进度，不要求老板操作数据库或理解代码。

### 1. 页面布局

顶部展示：当前线上版本、已验证功能数量、已知阻断数量、待验收数量、最近更新时间及信息来源。

左侧用较窄的功能目录，按用户业务分类，例如“账号与权限、核心业务、内容与资料、运营管理”。支持搜索编号和中文名称。开发阶段、负责人、状态另做筛选，避免同一功能在多个目录重复出现。

右侧作为主要阅读区，提供以下内容：

| 页面分区 | 负责人能看懂的内容 |
|---|---|
| 功能概览 | 这个功能做什么、谁使用、当前能做什么 |
| 使用流程 | 从哪里进入、每步做什么、失败怎么继续 |
| 设计方案 | 已确认方案、版本、确认时间及原型 |
| 实现对照 | 每项承诺已实现、部分实现、未实现或待核实 |
| 开发记录 | 谁改了什么、为什么改、关联任务和代码版本 |
| 检查与缺陷 | 检查范围、结果、未验证项、已知BUG和处理进度 |
| 发布记录 | 哪次上线包含它、线上版本、检查及回退情况 |
| 当前运行 | 最近一次真实检查是否正常、何时检查、依据是什么 |

允许合理折叠长说明、调整列宽或在窄屏切换列表与详情。主要内容不能被过宽目录挤走；不要为了状态丰富把每条记录展示成一堵技术文字。

### 2. 不能只用一个“已完成”

至少区分以下事实：

| 维度 | 示例状态 |
|---|---|
| 方案 | 待讨论、已确认、已变更待核对 |
| 实现 | 未开始、开发中、部分实现、已实现 |
| 验收 | 未验证、部分通过、通过、未通过 |
| 发布 | 未发布、部分发布、已发布、已回退 |
| 运行 | 未检查、最近检查正常、异常、证据已过期 |

例如：**“已实现｜本地通过｜未上线｜线上未检查”**，比“完成90%”更准确。健康状态必须带检查时间和环境；昨天正常不能冒充现在正常。

若显示进度百分比，要注明分母，例如“10项验收条件中7项通过”。没有可解释口径就显示数量和缺口，不由AI凭感觉填写百分比。

### 3. 方案与实际逐项对照

| 编号 | 确认的承诺 | 实际结果 | 证据 | 缺口 |
|---|---|---|---|---|
| F-002.1 | 预约保存后刷新不丢 | 本地通过，线上未验 | 对应测试与截图 | 发布后核验 |
| F-002.2 | 重复点击只创建一次 | 未通过 | 失败反例 | 等待修复 |

编号用于关联，不必给每句文案造新编号。只为可独立判断的重要承诺建立条目。

### 4. BUG自检和业务状态

“自检”应展示检查了什么，而非给出一个没有依据的“无BUG”。

- 测试检查：相关测试是否通过。
- 页面检查：真实点击、布局与保存恢复是否核验。
- 业务检查：主流程是否走通。
- AI质量检查：真实模型是否成功，结果是否满足要求。
- 运行检查：接口、任务执行器和外部依赖最近是否正常。

管理页按钮若会发起昂贵AI调用、修改数据或执行发布，应明确标注作用、权限和预计费用。普通查看不产生外部调用；不能给不懂代码的负责人一个默认执行破坏性脚本的“全部修复”按钮。

### 5. 老板可以调整什么

老板可以添加需求、评论、优先级建议和反馈。修改已确认的功能逻辑时形成“变更提案”，明确确认后更新正式方案。

后台编辑说明不等于代码自动实现；改优先级不等于已部署。技术状态必须来自相应证据，不能让人工点一次“完成”就盖过失败测试。

## 八、后台数据与技术路线

### 推荐从轻量实现开始

第一阶段，正式方案用Markdown，功能索引用结构化文件，后台提供只读展示。项目确实需要多人编辑、操作审计和运行监测后，再增加数据库/API；不因为做管理页就先引入复杂微服务、向量数据库或消息平台。

建议实现顺序：

1. 建立目标、功能编号和首批方案。
2. 完成一条可运行主流程。
3. 建轻量后台，展示功能目录、方案链接、状态和证据。
4. 随迭代加入缺陷、发布记录和实际运行检查。
5. 有多人并发维护需求时，才增加受权限保护的编辑接口和数据库。

### 单一来源与同步规则

- **产品决定**以正式方案为准；**代码事实**以对应提交为准；**部署事实**以发布记录为准；**运行事实**以带时间的检查结果为准。它们互相关联，但不能互相代替。
- 功能编号、当前状态和证据引用保存在唯一结构化记录中，后台直接读取或构建投影。
- 长篇功能说明继续保留在方案章节，后台通过稳定功能ID引用，不维护第二份正文。
- 任务报告保存本批交付事实，完成后更新功能记录；不要在交接文件、方案和后台各维护一份互不一致的状态。
- 若数据库后来成为管理记录的权威来源，明确停用旧文件写入口，并提供导出。不要文件和数据库双向随意修改。
- 后台显示记录版本、生成时间、来源提交和运行检查时间；发现过期或版本不符要提示，不悄悄展示缓存为最新。
- 不用脆弱的Markdown标题或行号推断完成状态。文档格式变化不应让整个后台无法读取；结构化数据做字段校验，坏记录明确标错，不静默显示成空库。

### 功能记录示例

以下仅为结构示例，里面的编号和证据不是已完成项目的事实：

```json
{
  "schemaVersion": 1,
  "featureId": "F-002",
  "name": "预约创建",
  "category": "预约服务",
  "spec": { "path": "docs/PROJECT_PLAN.md", "sectionId": "F-002", "revision": "1" },
  "dependsOn": ["F-001"],
  "designStatus": "confirmed",
  "implementationStatus": "partial",
  "verificationStatus": "failed",
  "releaseStatus": "not_released",
  "health": { "status": "not_checked", "checkedAt": null, "environment": null },
  "acceptance": [
    { "id": "F-002.1", "promise": "保存后刷新不丢", "status": "passed", "evidenceIds": ["E-001"] },
    { "id": "F-002.2", "promise": "重复提交只创建一次", "status": "failed", "evidenceIds": ["E-002"] }
  ],
  "currentTaskId": "T-001",
  "issueIds": ["BUG-001"],
  "implementationCommit": null,
  "productionReleaseId": null,
  "updatedAt": null
}
```

配套的证据记录应有：证据ID、关联功能/任务、类型、结果、执行者、环境、代码版本、执行时间与文件位置。缺陷记录应有：用户影响、复现方法、期望与实际、严重程度、处理状态、修复和复验依据。发布记录应列出实际包含的提交、功能与验证结果。

没有现成信息的字段填“未知/未检查”，不要编造。后台不公开密钥、会话、用户私密内容或模型思维链；访问权限由服务端控制。

## 九、测试和验收

### 分清几种“通过”

- 文档写好了，只能说方案已准备。
- 编译和类型检查通过，说明部分技术检查通过。
- 模拟数据测试通过，说明被覆盖的工程行为通过。
- 真实浏览器操作通过，才支持相应交互结论。
- 真实外部服务或模型调用通过，才支持该集成路径的结论。
- 已部署且线上检查通过，才支持“这一版已上线可用”。

截图存在不等于截图已检查；视觉模型摘要也可能看错，应查看原图。脚本直接触发按钮回调不能代替真实用户点击。测试模型不能代替真实生成质量。

### 按风险选择验证

| 改动 | 通常需要 | 不默认需要 |
|---|---|---|
| 文档与普通文案 | 结构、引用、差异或相关页面检查 | 全站测试与真实模型调用 |
| 页面样式/局部交互 | 相关测试、构建、关键设备真实走查 | 无关后端全量测试 |
| 局部接口或任务逻辑 | 相关合同、权限、异常恢复及构建 | 无关业务全站重测 |
| 身份、受保护数据、核心流程变化 | 项目约定的完整验证及针对性隔离/恢复测试 | 无关文学或市场效果测试 |
| 生产发布 | 对应发布检查、回退准备和线上核验 | 与本次发布无关的功能扩建 |

项目自己的验收方案应给出真实命令和环境，不照搬另一个项目的脚本名称。

### 失败如何处理

先区分产品缺陷、测试夹具问题、工具问题、外部服务失败和证据不足。都有可能存在，不能默认“测试失败就是旧债”或“模拟通过就是供应商的错”。

第一次修正后仍失败，先核查新证据和根因，再调整方案；不机械重试。已通过且未受改动影响的部分保留，不反复重审。已存在的全量失败要列明影响，不能只比较失败数量；不得删断言、放宽权限或降低输出质量制造通过。

非阻断优化可以进入后续列表。主流程不可用、数据泄漏、数据丢失、未经授权操作等问题不能为了结项跳过。

## 十、跨AI交接与节约用量

### 交给另一位AI时只提供必要入口

1. 本批任务文件和对应方案章节。
2. 正确工作区、分支、基准提交，已有未提交修改的归属。
3. 必要代码入口、已确定的技术决定和验收命令。
4. 已通过成果、已知失败及证据位置。
5. 当前应执行的第一步、结束条件和发布范围。

接手AI先核实上述基准与实际状态一致，存在差异则定位，不盲目覆盖。不要求每次重读全部聊天或扫描全仓库。

**任务文件夹只是传递渠道，不是自动调度器。** 若使用桌面会话，可能仍需要老板说一句“执行当前任务”。自动执行需要工具支持和明确授权，不能把写好任务文件描述成另一个AI已经开始工作。

### 节约来自减少无效工作

- 派工前把关键路线确定，避免执行者做二十小时探索才发现方向不对。
- 按需读文件、日志只回传必要摘要，已确认信息引用原件。
- 快速离线验证格式、参数与预算，之后才做真实外部调用。
- 连续失败保留检查点；不要从头重做已成功部分。
- 审查者集中反馈已发现的问题，不逐轮挤出一个新要求。
- 同一批任务有结束条件，不随意追加“顺便全部优化”。

用量统计区分：成功调用、失败已知用量、未知用量、输入/输出、缓存口径与实际现金。未知不算零；订阅内零新增现金不等于没有消耗额度。耗时依据时间戳，区分生成等待、测试、工具故障和返工，不凭印象估计。

## 十一、发布、重构和清理

发布前明确版本、环境、权限、数据变化、备份/回退及关键检查。网页资源、后端服务、数据迁移的风险不同，采用相应流程，不把所有发布都做成同样庞大的仪式。

接口合同变化要协调前后端版本；避免前端已发新请求而后端仍只接受旧请求。不得取消真实用户任务来制造上线窗口。生产数据恢复、永久删除等操作遵守本项目已记录的具体授权。

重构时把每项旧能力标成“保留、替换、合并、废弃”，记录新实现的实际接管入口、数据来源和退出条件。新代码存在不等于旧运行入口已被替换。

旧代码确认无运行引用且替代验收通过后再清理。用户数据、历史备份、已应用迁移、密钥和当前回退版本不能作为普通“死代码”清除。授权、影响范围与恢复能力需分别核实，不直接复制其他项目的清理命令。

发布结束后同步后台的实际发布版本和核验时间。源码改了而线上没变，要明确显示“本地已完成，未发布”。

## 十二、直接交给AI的启动指令

把本文件和以下文字一起交给新项目AI即可。只需补充项目想法；不知道技术选项可以留空，由AI推荐。

```text
请以附件《AI协作开发流程与可视化项目管理指南》建立这个项目的协作方式。

我的项目想法：[用普通话说明你想做什么]
现有情况：[全新项目 / 已有项目及位置]
用户与主要用途：[知道多少写多少]
必须保留的要求：[风格、功能、数据等]
预算或发布限制：[有则写；没有明确授权的实际付费不得自行发生]

我不写代码。请你承担方案负责人的职责，用中文说明用户结果与建议，
普通工程选择由你核实并负责，不把数据库、字段和代码文件问题推给我。

第一步先做必要的只读了解和方案讨论，不直接批量写产品代码：
1. 总结目标、主流程、首版范围、必要未知和推荐路线。
2. 已有项目先核对实际入口与功能，不按旧文档猜测完成情况。
3. 只问影响产品方向、费用、权限或数据安全的关键问题。
4. 列出需要建立的最少文档和项目管理记录，避免重复文件。
5. 提出老板能看懂的后台方案：功能介绍、流程、确认方案、实现对照、
   开发日志、测试与BUG、发布版本、业务是否可用；各状态都要有依据。
6. 把候选方案与已确认决定分开。我确认的方案保存到项目原件，
   明确实施后再按可验证批次开发；不要反复询问已经授权的事项。

实施时：先核对基准与入口，再给出可执行任务、测试和结束条件。
允许交其他AI执行，但交接必须包括具体范围、技术路线和证据要求。
发现当前方案不符现实，提出证据并调整，不能悄悄另做一个产品。
先交付一条真实可运行的主流程，管理后台逐步完善。
已通过且未受影响的工作不重复做；失败不机械重试、不删测试造绿。

每次交付先告诉我：现在能做什么、还有什么不能做、是否真的上线、
下一步由谁做。测试数字、提交数量和“代码写好了”不能代替功能结果。
不要保证零BUG或100%准确；对未验证内容明确说明。

请现在给出第一轮理解、推荐方案及最少需要我补充的信息。
```

### 已有方案，直接委派开发时

```text
请读取本项目AGENTS.md及当前任务文件[填路径]，按其中已确认方案执行。
先核对工作区与代码基准；只读指定方案章节和必要实现。
保留已通过成果，不擅自扩展产品范围，不覆盖其他人的修改。
按任务中的验证、交付和发布边界完成；存在真实阻碍时说明证据，
继续不受阻的部分。结果更新原任务与关联功能记录，不另建重复报告。
```

### 老板日常只需要问这些

- 这批完成后，我能实际使用什么？
- 后台显示的是计划、本地测试结果，还是线上真实状态？
- 与我确认的方案相比，还缺哪几项？
- 现在最大的阻碍是什么，有什么证据，谁来解决？
- 换一个AI后，从哪个文件、哪一步继续？

这些问题能帮助负责人掌握项目，而无需亲自阅读代码。流程的价值在于让决定、实现、证据和责任对应起来，并持续交付可用结果。
