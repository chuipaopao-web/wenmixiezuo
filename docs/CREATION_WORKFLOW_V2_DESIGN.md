## 1. 结论摘要

新版采用“卷驱动、事件展开、逐章落地”的创作流程：

```text
书架与开书
→ 填写开书信息
→ 与AI讨论并确认设定大纲
→ 设计当前卷纲与卷内节奏
→ 设计当前卷的事件大纲与事件节奏
→ 为第一个事件设计章纲
→ 按章纲创作并逐章结算正文
→ 当前事件结算，继续下一个事件
→ 当前卷结算
→ 根据前卷结果自然设计下一卷
```

当前卷纲是这一卷的大方向约束。事件设计必须结合开书信息、活动设定和当前卷纲；章纲必须继续结合当前事件；正文必须再结合当前章纲和上一章结算。系统阻止无提示的剧情漂移，但允许作者确认有价值的偏离并创建新规划版本。

内部可以参考三幕式、五幕式、救猫咪、起承转合等方法设计节奏模板，作者前端不显示这些术语。作者只看到大白话说明：这一种方案怎么推进、接下来要设计什么、适合什么故事、可能有什么套路风险，以及如何自己修改。

## 2. 已明确的产品方向

1. 开书后先填写作品信息，再进入设定讨论，不直接跳到正文。
2. 设定确认后先设计第一卷；不提前把所有卷和所有章节一次写死。
3. 卷纲是正式、版本化、作者可编辑的规划对象，不再只是物理目录。
4. 卷内先设计事件链，再为当前事件设计章纲，最后创作正文。
5. 卷纲和事件都可以选择节奏方案，作者可以随时加入自定义想法供AI参考。
6. 作者想法保留原话、目标层级和意图强度；AI说明采用到哪里，不能只留下摘要。
7. 编剧工作必须引用活动卷纲、事件大纲和章纲，禁止在小层级静默偏离大方向。
8. 一卷结束后以正式正文的实际结果结算，再自然引出下一卷，不清空人物和剧情状态。
9. 前端模板名称与引导全部使用大白话；正式方法名只作为内部维护元数据。
10. 图谱、资料库和取名进入创作台；书内左栏只负责显示和切换书籍。

## 3. 目标与非目标

### 3.1 目标

- 让作者始终知道正在设计哪一卷、哪个事件、哪一章和下一步是什么。
- 让AI辅助作者有规划地构建大纲，同时保留作者随时输入、修改和否决的权利。
- 让卷内高潮逐层递进，前一个事件的后果成为下一个事件的压力来源。
- 让编剧所用规划版本、作者想法和资料来源可以追溯，避免上下文错版。
- 保留不可变正文、正史、任务恢复、混合检索、来源保护和旧书兼容。
- 减少页面跳转、重复入口、重复岗位和巨型前端装配文件。

### 3.2 非目标

- 不固定每卷必须50—100章，也不固定事件必须6—10章。
- 不一次生成全书全部卷纲、事件和正式正文。
- 不把内部叙事方法名称直接显示成作者必须理解的选项。
- 不把模板变成每章反转、固定爽点、固定节拍或固定字数的硬规则。
- 不把“卷纲约束”实现成禁止任何有价值的创作偏离。
- 不让一个拟人角色垄断数据库、检索和上下文准备。
- 不让两个写手默认逐章串行整稿，不开放批量正文绕过逐章确认。
- 不删除已合并迁移、历史数据、正式正文、正史、任务/调用和恢复证据。

## 4. 作者完整工作流

### 4.1 开书信息

作者创建书籍时填写最小但足够的起点：

- 书名、频道、分类、题材、预计篇幅和目标读者；
- 一句话故事、核心看点、主角与主要矛盾；
- 作者已知的结局方向或“暂不确定”；
- 必须保留、明确避免、强偏好和自由灵感；
- 可选参考资料与来源说明。

这些信息属于作品主脉和创作输入，不自动成为已经发生的正史。作者可以先少填，后续在对应对象旁补充；系统明确哪些字段会影响设定和卷纲候选。

### 4.2 设定大纲

AI围绕开书信息与作者讨论当前真正需要的设定：

- 世界规则、时代与空间；
- 主角、主要人物、关系和初始状态；
- 能力、资源、组织和冲突边界；
- 叙事视角、基调、内容边界与读者承诺；
- 刻意留白、待确认问题和不可提前揭示的信息。

需要创意时，两条编剧能力先独立给出差异明显的候选；事实整理和小修改不强制多人讨论。作者可以选择、混合、直接编辑、暂存或拒绝。只有作者确认的设定进入活动设定版本，讨论和候选不进入正史。

### 4.3 当前卷纲设计

第一卷的输入是开书信息、活动设定和作者本卷想法；后续卷额外读取上一卷结算。作者先选择一个白话节奏方案，也可以选择“由我自己安排”。

卷纲至少包含：

- 卷名或临时名称；
- 卷首人物、关系和局势状态；
- 本卷核心目标、核心矛盾和失败代价；
- 主角及关键人物在本卷的变化；
- 本卷事件链及前后因果；
- 信息揭示、伏笔、承诺和回收计划；
- 蓄势、升级、重大受挫、核心高潮和卷末余波；
- 卷末状态、保留线索和下一卷自然触发点；
- 必须实现、不得违反、自由创作区和待确认事项；
- 作者想法引用及采用、调整、暂存或未采用状态。

两条编剧能力在互不可见条件下形成不同卷纲候选，统筹能力说明差异、代价、风险和推荐，但不自动折中。作者可以选择、合并、编辑、锁定单个节点或要求重做。确认后生成不可变活动卷纲版本。

卷纲只细化当前一卷。远期只保留作品主脉和少量跨卷承诺，不提前生成下一卷详细事件。

### 4.4 当前卷事件设计

事件是卷内可结算的跨章因果单元。设计第一个事件时读取活动卷纲；设计后续事件时还读取前一事件的实际结算。

事件至少包含：

- 事件目标及其在本卷中的职责；
- 起始状态、触发条件和参与人物；
- 人物目标、阻力、关键选择与代价；
- 需要揭示、隐藏、误导或回收的信息；
- 事件节奏方案及作者自定义想法；
- 局部蓄势、升级、转折、高潮和余波；
- 必须发生的结果、允许变化的实现方式和结束条件；
- 对下一事件、人物弧、卷级高潮和卷末目标的影响；
- 预计章节范围与不确定性。

事件可以选择白话节奏卡、混合多个卡片、完全自定义或不用模板。事件节拍不是章节；作者可以跳过、合并、拆分和重排。AI必须解释调整是否仍满足卷纲目标。

如果事件设计与活动卷纲冲突，不能直接生成。系统显示冲突位置和影响，让作者选择修改事件、局部修订卷纲或创建新卷纲版本。

### 4.5 当前事件章纲设计

事件大纲确认后，先设计这个事件的完整章节序列，再开始正文：

- 为预计涉及的每章建立章纲卡，说明该章在事件中的作用；
- 全事件章纲先达到因果连续、人物状态可接和事件结束条件可兑现；
- 即将写作的1—3章细化并冻结为写作任务，后续章保留可调整的较粗章纲；
- 每章说明开场状态、人物目标、冲突、选择/代价、信息变化、结束状态和下一章接口；
- 每章引用活动卷纲版本、事件版本、相关节拍和作者想法；
- 正文结算后根据实际状态滚动细化后续章，但不得静默改变事件结局或卷末目标。

这样既满足“先把当前事件章纲设计好再写正文”，又避免几十章远期细节在实际正文反馈前被全部锁死。

### 4.6 正文创作

正文写作输入使用最小充分上下文，不把全部卷纲、全部资料和全部协作记录原样塞给写手。上下文包包括：

- 开书信息中的作品核心与必须遵守；
- 活动设定中与本章相关的硬事实；
- 当前卷纲中与本事件、本章相关的目标和边界；
- 当前事件大纲、节拍与结束条件；
- 当前章纲、上一章正式结算和人物最新状态；
- 作者针对本章的必须、强偏好、灵感和问题；
- 少量人物声音与灵感材料；
- 明确的自由创作区。

一章只有一个活动写手生成当前正式候选。作者可以直接写、粘贴和编辑，每次保存创建不可变完整版本。完整草稿形成后再进行事实、文学和体验三个独立维度的审校；软问题优先定点修改，根因在章纲、事件或卷纲时返回上游。

作者确认后才结算正式正文和正史，并更新后续章纲、事件进度和卷内状态。

### 4.7 事件结算、卷结算与下一卷

事件结束时根据正式正文结算：

- 事件目标是否兑现；
- 人物、关系、资源、知情和局势的实际变化；
- 已揭示、已回收、仍开放和新产生的线索；
- 原事件大纲与实际结果的偏离；
- 下一事件必须承接的后果。

一卷结束时再生成不可变卷结算：

- 卷首到卷末的实际状态变化；
- 人物弧和核心矛盾的兑现情况；
- 重大高潮造成的后果与卷末余波；
- 已完成、延后、改变和新增的长期承诺；
- 下一卷可自然启动的冲突、机会、威胁或人物选择；
- 需要回查的正式章节与正史来源。

下一卷设计读取开书信息、活动设定、作品主脉和上一卷结算，不复制上一卷原计划当事实。作者确认下一卷方向后再选择白话节奏方案、补充想法并形成新卷纲。

## 5. 白话节奏模板

### 5.1 前端呈现原则

前端不显示“救猫咪”“五幕式”等方法名作为选择标题。每张卡使用：

1. 一句大白话标题；
2. “这种安排会怎样推进故事”；
3. 适合的故事情况；
4. 作者接下来需要回答的3—6个问题；
5. 预计会形成的节奏预览；
6. 常见套路风险；
7. “使用并修改”“查看另一种”“由我自己安排”。

示例卷纲卡：

- **先把局面立稳，再不断加压，最后集中爆发**：适合主线明确、冲突逐步升级的故事。
- **先取得进展，再跌入最低谷，最后完成反击**：适合逆袭、成长和强转折故事。
- **先让读者在意人物，再让每次选择付出更大代价**：适合人物驱动、情感与商业节奏并重的故事。
- **先铺垫和推进，再改变方向，最后留下回响**：适合悬念、情感和意味更重的故事。
- **由我自己安排这一卷**：作者直接建立节点，AI只检查因果、遗漏和影响。

示例事件卡：

- **发现问题—尝试解决—付出代价**；
- **目标受阻—办法升级—局势改变**；
- **误解加深—真相揭开—关系变化**；
- **寻找线索—排除假象—逼近答案**；
- **先获得希望—再失去依靠—被迫选择**；
- **由我自己安排这个事件**。

### 5.2 内部模板合同

正式方法可以作为内部 `source_method`，但不进入作者标题：

```text
template_key / template_version
source_method（内部）
scope: volume | event
public_title / public_explanation
fit_conditions / known_risks
author_questions[]
beats[]: id, public_function, expected_change,
         optional, order, author_idea_refs
```

模板定义不包含作品事实。作者选择后产生作品专属模板实例，保存在卷纲或事件不可变版本中。卷纲模板不会自动复制给每个事件；AI应根据事件目标另行推荐，也允许完全不用模板。

### 5.3 高潮不是恒定高压

“持续高潮感”通过后果递进实现：

```text
章节选择或局部转折
→ 事件级代价和状态改变
→ 后果进入下一事件并提高压力
→ 卷级不可逆重构与核心高潮
→ 卷末余波成为下一卷触发
```

安静、恢复、关系深化和后果消化可以是必要章节。系统检查的是前一高潮是否改变了人物和局势、下一层是否在这个结果上继续发展，不用每章反转、固定爽点密度或单调递增数值判断质量。

## 6. 作者想法卡

作者可以在开书、设定、卷纲、事件、章纲和正文旁输入想法。统一字段为：

```text
owner_id / book_id
author_input_id
surface: book_profile | setting | volume_plan | event | chapter_outline | manuscript
subject_type / subject_id
intent_strength: must | preference | inspiration | question
original_text / attachment_refs
scope_notes
status: new | adopted | adapted | parked | rejected | superseded
applied_to_refs[]
handling_reason
created_at / decided_at
```

处理规则：

- 永久保留作者原话，不用AI摘要替代；
- “必须遵守”进入对应规划或写作任务的硬目标，但与正式事实冲突时先提示；
- “强偏好”尽量满足，允许有理由偏离；
- “灵感”可以变形或不用；
- “问题”触发讨论，不自动变成决定；
- AI候选必须标明引用了哪些作者想法；
- 未采用必须给简短理由，作者可重新启用；
- 作者确认的规划进入活动版本，想法本身不自动进入正史。

## 7. 分层上下文与防偏移

### 7.1 编剧上下文矩阵

| 任务 | 必须引用 | 按需引用 | 不应默认注入 |
|---|---|---|---|
| 设计第一卷 | 开书信息、活动设定、作者本卷想法 | 作品资料、题材参考 | 全部协作历史、全库资料 |
| 设计后续卷 | 开书信息、活动设定、上一卷正式结算、跨卷承诺、作者想法 | 关键旧章原文 | 旧卷原计划全文 |
| 设计事件 | 活动卷纲、相关设定、前一事件结算、作者事件想法 | 相关人物原文、资料证据 | 无关卷与全部Wiki |
| 设计章纲 | 活动卷纲、当前事件大纲、上一章结算、人物状态、作者章想法 | 当前事件前文 | 后续事件的全部细节 |
| 创作正文 | 相关开书核心、相关设定、卷纲约束、事件目标、当前章纲、上一章结算 | 少量声音证据和灵感 | 全卷所有规划原文、全部评论 |

每个上下文包记录：

```text
context_package_id
owner_id / book_id
task_type / target_id
book_profile_version
setting_version
volume_plan_version
event_version
chapter_outline_version
previous_settlement_refs
author_input_refs
included_sources / excluded_sources / reasons
model_binding / token_budget / hash
```

编剧只能根据冻结的上下文包执行任务，不直接从前端临时状态猜测版本。上下文服务负责检索、去重、权限、故事时间和来源回查，拟人成员不垄断数据库访问。

### 7.2 防偏移规则

- 硬偏移：与活动正史、人物状态或作者“必须遵守”冲突，停止并请求处理。
- 规划偏移：事件、章纲或正文改变卷目标、重大人物命运、事件结局或卷末接口，先做影响分析。
- 合理偏离：具体场景、对白、局部动作、意象和更自然的因果实现，可在自由创作区内进行。
- 有价值的重大偏离：保留候选，说明收益与代价，由作者选择修订上层规划或回到原计划。
- 任何上层修订创建新版本，使依赖的未写章纲/事件候选失效；已结算正文不被改写。

## 8. 信息架构

### 8.1 书架与左栏

- 根页面继续是书架，显示活动书、归档书、全局任务、团队模板和设置。
- 打开书籍后，左栏只显示紧凑书籍列表/切换器和返回书架入口。
- 左栏不再承担对话、版权、图谱、资料库和取名导航。
- 切换书籍只改变当前作用域，不暂停或取消后台任务。

### 8.2 创作台

主流程使用六个白话入口：

1. 开书信息
2. 设定大纲
3. 卷纲设计
4. 事件设计
5. 章纲设计
6. 正文创作

辅助工具：

7. 图谱
8. 资料库
9. 取名

创作台顶部显示当前位置和进度，例如“第一卷 → 事件二 → 第8章”，以及“下一步：完善事件二的章纲”。作者无需理解内部Artifact、阶段或模板术语。

### 8.3 对象旁协作

每个主流程页面都可以：

- 输入作者想法并选择意图强度；
- 上传资料或图片；
- 点名当前成员；
- 请求两个独立方案、核对、修改或重做；
- 查看真实任务状态、候选差异、影响和待确认项；
- 查看当前对象历史与来源。

独立对话页退役后，历史消息按对象显示；无法定位的旧消息进入只读工作记录。作者原话只保存一次，页面只保存对象引用。

## 9. 团队运行候选

团队是否精简为九名仍是单独待确认项。无论人数如何，新流程必须具备：

- 方向统筹与作者协作；
- 两条真实独立的卷纲/事件创意路径；
- 设定、事实与连续性核对；
- 一个活动写手和可接管的候任写手；
- 事实、文学、体验三个真实独立审校维度；
- 按需研究与来源风险保护；
- 确定性上下文编译、状态机、恢复和权限。

卷纲、事件和章纲由创意能力设计，确定性服务准备各自上下文并验证版本引用。状态只由真实任务、Worker、模型和工具事件驱动。

## 10. 技术结构

### 10.1 前端边界

```text
app/shell
features/bookshelf
features/creation-desk
features/book-profile
features/settings
features/volume-plans
features/story-events
features/chapter-outlines
features/manuscripts
features/author-inputs
features/plain-language-templates
features/graph
features/library
features/naming
features/team-status
```

先无行为拆分巨型装配文件，再改导航和流程；不引入新的UI框架。

### 10.2 后端边界

- `CollaborationService`：作者原话、对象定位、附件、点名和任务引用。
- `PlanningTemplateRegistry`：内部模板版本与作者可见白话卡，不保存作品事实。
- `VolumePlanningService`：卷纲候选、版本、事件链、影响分析、活动版本和卷结算。
- `StoryEventService`：事件候选、版本、节奏实例、顺序、因果接口和结算。
- `ChapterPlanningService`：当前事件章纲序列、近期冻结、后续滚动调整和版本引用。
- `ContextCompiler`：按任务编译分层、最小、冻结、可追溯的上下文包。
- `ProductionPipeline`：单章生成、三维审校、作者确认和正文结算。
- `SourceSafetyService`：资料来源、授权、隔离和原创性风险预检。

业务层继续只通过Repository访问数据；Worker不得直接修改核心业务表或正式正文。

### 10.3 数据增量候选

老板正式确认本草案后，使用下一条向前迁移新增，不修改旧迁移：

- `volume_plans`：卷身份、卷序、状态、活动版本和前后卷接口。
- `volume_plan_versions`：不可变完整卷纲版本、事件链、白话模板实例、作者想法引用、影响与哈希。
- `story_events`：事件身份、所属卷、顺序、状态和活动版本。
- `story_event_versions`：不可变完整事件版本、节拍、作者想法引用、因果接口、影响与哈希。
- `author_planning_inputs`：作者原话、附件、目标对象、意图强度、处理状态和理由。
- `volume_settlements`：由正式正文派生的不可变卷结算与下一卷接口。
- `collaboration_context_links`：旧/新消息、附件、任务与创作对象的定位关系。

所有核心记录携带 `owner_id`、`book_id`。模板定义使用带版本和哈希的只读配置；作品对模板的改写保存在卷纲/事件版本中。正文、正史和作者确认仍使用现有不可变与事务边界。

旧卷纲/阶段Artifact、对话、消息、讨论、附件、来源和旧角色数据保留兼容读取。旧规划不能无校验直接转换成新活动卷纲；先生成迁移候选和差异，由作者确认。

### 10.4 API候选

- `GET /books/:bookId/planning-templates?scope=volume|event`：返回白话卡，不返回内部方法名作为标题。
- `POST /books/:bookId/author-planning-inputs`：保存作者想法卡。
- `GET /books/:bookId/volume-plans/:id/generation`：读取最近一轮真实任务与候选检查点，不触发模型。
- `POST /books/:bookId/volume-plans/:id/generate`：创建持久任务，生成两份独立卷纲候选和主编融合候选。
- `POST /books/:bookId/volume-plans/:id/confirm`：确认活动卷纲版本。
- `POST /books/:bookId/volume-plans/:id/impact-preview`：预览修订影响。
- `POST /books/:bookId/story-events/candidates`：在活动卷纲下设计事件。
- `POST /books/:bookId/story-events/:id/chapter-outlines`：设计当前事件章纲序列。
- `POST /books/:bookId/volume-plans/:id/settle`：从正式正文结算当前卷。
- `POST /books/:bookId/volume-plans/:id/start-next`：以上一卷结算为输入启动下一卷候选。

所有生成型接口返回持久任务并保存真实状态；携带幂等键、活动版本前置条件和结果不明处理。当前卷P7以读取端点和有界轮询恢复，P13统一接入SSE游标。具体路径以API规格为准。

## 11. 来源、历史与项目精简

- 独立对话页和独立版权页可以退役，但消息、讨论、附件、来源原件、授权状态、隔离和正式生产预检继续保留。
- 页面先停用和重定向，运行观察后才能删除不可达装配；不按目录名整包删除对话或版权服务。
- 旧书、旧URL、旧任务、旧角色和旧Artifact兼容读取。
- 已合并迁移、不可变正文、正史、任务/调用、删除墓碑和恢复证据不得为了精简删除。
- 前端先拆分 `App.tsx` 和样式边界，再实施卷驱动导航，避免在巨型文件中一次完成所有变化。

## 12. 验收标准

### 12.1 作者流程

- 作者可以完成“开书→设定→第一卷卷纲→第一事件→事件章纲→正文→卷结算→下一卷”的完整路径。
- 前端模板选项全部是大白话，作者不需要理解三幕、五幕或救猫咪等术语。
- 卷纲和事件均支持推荐方案、自定义想法、混合、直接编辑和不用模板。
- 当前事件的完整章纲序列在正文开始前可见；近期1—3章可冻结，后续可受控调整。
- 每条作者想法都能找到原话、目标对象、采用位置和处理理由。
- 一卷结束后，下一卷候选明确引用前卷正式结算和卷末后果。

### 12.2 防偏移与恢复

- 事件候选引用正确的活动卷纲版本；章纲引用正确的事件版本；正文任务引用正确的章纲版本。
- 上层版本变化会使未执行的依赖候选失效或要求重算，不影响已结算正文。
- 重大规划偏移有影响预览和作者确认，不静默放行或静默改纲。
- 刷新、切页、取消、超时、结果不明和重启后，不重复调用、不丢作者想法和候选。
- 旧书、旧规划、历史消息、附件、任务和来源可追溯，跨书污染为0。

### 12.3 长篇质量

- 卷内事件因果相接，前一事件的后果实际进入下一事件。
- 高潮阶梯具有蓄势、升级、核心高潮、余波和下一卷触发，不退化为恒定高压。
- 白话模板没有造成全卷与每个事件的同构套娃。
- 卷纲约束提升方向一致性时，原创性、合理惊喜、人物可辨识度、情绪力度和整体阅读质量相对基线非劣效。
- E0文档、E1实现、E2构造测试、E3对抗回放和E4真实连续创作分别表述，不提前宣称解决长篇质量。

## 13. 待确认与生效边界

本次老板已经明确卷驱动流程、白话模板和作者想法参与方式。仍需单独确认的主要产品决定是：可见创作团队是否采用九名候选方案。

本草案确认后，先写入新的生效决定，并同步产品、架构、数据、Agent、记忆、API、路线图和验收规格；之后才开始业务代码、迁移和旧页面退役。任何删除都遵守“保留、合并、停用、兼容、删除”分类和完整回滚证据。

## 16. 完整前端UI与交互

### 16.1 应用外壳

打开软件先到书架。书架保留新建、继续、归档、导入、全局任务和设置。进入书籍后：

- 左侧只显示返回书架、书籍搜索、活动书和归档书切换；
- 中间顶部显示书名、当前卷、当前事件、当前章和保存状态；
- 中间主体是创作台；
- 右侧是可收起的成员状态和当前对象任务；
- 窄屏将书籍与成员放入抽屉，只突出当前步骤和下一步；
- 切书不取消后台任务，但未保存文本或附件必须先保存、放弃或留在当前书。

创作台一级入口固定为“开书信息、设定大纲、卷纲设计、事件设计、章纲设计、正文创作”。图谱、资料库、取名放在“辅助工具”，不再占左栏。

### 16.2 开书信息

从零创作使用四步表单：

1. 作品起点：书名、一句话看点、预计篇幅；
2. 主角与矛盾：复用现有一至八位主角资料，增加每位主角当前目标；
3. 开篇情况：故事从哪里开始、首批重要人物和可选资料；
4. 题材与写法：现有频道、分类、标签，加白话节奏偏好。

世界背景、完整故事方向、地图、必须遵守、避免内容和风格意图等现有字段进入“补充更多”。预计篇幅只影响建议。每一步自动保存并可恢复。

已有正文续写仍是同级入口：先导入、确认章节、逐章分析和逆向章纲，再进入缺口设定与当前卷规划，不能被从零创作流程覆盖。

### 16.3 设定大纲

页面一次突出一个当前设定项：显示当前问题、候选差异、理由、代价和未知；作者可选择、融合、直接编辑、暂存、跳过可选项或重做。底部固定有“补充我的想法”，支持附件和意图强度。完整目录与建议项默认收起。确认后显示版本、来源和后续影响，不再出现跳转对话。

### 16.4 卷纲设计

顶部是卷切换、活动版本、预计范围和状态。主体分为：

- 本卷目标：核心矛盾、失败代价、人物变化和卷末结果；
- 节奏轨道：蓄势、升级、受挫、核心高潮和余波等可编辑阶段；
- 事件链：每个事件的进入状态、行动、结果和下一触发。

白话节奏卡必须说明“适合什么、怎么推进、可能的套路风险、代入本书的短预览”，并提供“不用模板”和“我自己安排”。生成时展示两份独立方案及差异；作者选择或指定保留部分后，主编才整理单一连贯候选。确认前展示版本差异与影响。

### 16.5 事件设计

桌面提供时间轴和列表切换，窄屏使用纵向卡。每张事件卡显示标题、预计章节、发生原因、人物目标、阻力、失败代价、结果、对卷目标的贡献、上一事件带来的状态、下一触发和作者想法。

允许插入、重排、拆分、合并和调整范围，但先预览章号、章纲、任务、伏笔和已写正文影响。已结算事件不能直接重排。

进入单个事件后可选事件推进卡和读者收益/压力意图卡。两位编剧各给一份完整方案；作者选择部分后，由主编重新校验动机、因果、节奏和下一接口。

### 16.6 章纲设计

先展示当前事件的完整章节序列，再细化并冻结近期一至三章。作者可见字段为：

- 这一章为什么必须写；
- 开始时人物处境；
- 谁想做什么、知道什么；
- 冲突和失败代价；
- 三至五个连续剧情节点；
- 结束后的状态变化；
- 给下一章留下什么；
- 必须做到、不能违反；
- 情绪、读者期待、信息控制和伏笔动作；
- 主笔自由发挥区；
- 作者本章想法。

批量按钮只生成或刷新候选序列。上层变化时逐章显示仍有效、需要复核或已失效及原因。

### 16.7 正文创作

保留现有卷章目录、导入、作者编辑、不可变版本和离线阅读。新增：

- 显示所用卷纲、事件和章纲版本；
- 写作前显示一页内可读完的任务摘要；
- 作者可指定修改意见和必须保留段落；
- 三份报告命名为“事实与前文、文字与人物、读起来怎么样”；
- 每条问题定位段落，说明依据、严重度和建议动作；
- 硬事实问题必须处理，文学和体验意见由作者裁决；
- 重写只针对确认问题，不默认整章重写；
- 定稿后完成章结算再解锁下一章。

正式正文不提供连续写多章入口。允许提前准备下一章资料，但上一章未结算时不启动正式生成。

### 16.8 事件和卷收尾

事件完成后显示实际结果与原计划差异：人物、关系、资源、线索、承诺、卷目标进度和下一触发。作者确认后才解锁下一事件。

卷完成后显示实际章数/字数、主要变化、高潮结果、承诺状态、人物/关系/势力状态、开放线索、卷末余波和二至三个下一卷起点。下一卷以正式正文和卷结算为事实，以旧计划作比较参考。

### 16.9 通用体验

- 输入自动保存，错误不清空文本；
- 生成按钮只创建一个持久任务，重复点击和刷新复用；
- 长任务显示排队、准备资料、生成、格式检查、等待作者、失败或取消；
- 取消后晚到结果不能提交；
- 删除、重排、换活动版本先显示影响，普通编辑支持撤销；
- 对象历史、来源、版本和任务随处可达，但默认不显示内部ID；
- 保留键盘、对比度、减少动画、字号和主题；
- 主区不放大段教学，只在首次、空状态和错误时给最短行动提示。

## 17. AI成员介入时机

团队人数不随本设计自动变化。合同按能力定义：

| 触发点 | 参与能力 | 产出与边界 | 作者门禁 |
|---|---|---|---|
| 新书创建 | 活动主编 | 校准理解并问一至三个高价值问题，不直接写总纲/正文 | 作者决定下一步 |
| 设定首次发散 | 主编、两条异模型编剧；设定能力按需核对 | 独立候选、理由、代价和未知 | 选、融、改或暂存后确认 |
| 设定小修改 | 主编或设定能力 | 单一可撤销候选 | 重大设定仍需确认 |
| 当前卷开始 | 两条异模型编剧、主编统筹 | 两份结构不同卷纲；主编先比较不折中 | 作者选择后才整理激活 |
| 事件链 | 主编、两条编剧 | 事件序列、因果接口和高潮阶梯 | 确认序列后才设计事件 |
| 单事件 | 两条编剧、主编；设定能力预检 | 两份完整事件方案和风险 | 选择后形成单一连贯候选 |
| 章纲序列 | 两条编剧、主编；设定能力硬检查 | 完整序列与近期详细章纲 | 确认后冻结写作工单 |
| 正文初稿 | 一个活动写手 | 单一完整暂存稿 | 不自动成为正式正文 |
| 正文审查 | 事实、文学、体验三席，均与写手异模型 | 同一稿件三份独立报告 | 硬问题修复，软意见作者裁决 |
| 定点重写 | 原活动写手；候任写手仅接管或明确A/B | 新不可变候选，保留指定范围 | 作者再次确认 |
| 章结算 | 确定性服务、设定能力核对 | 章末状态与候选事实 | 确认后进入正史 |
| 事件/卷结算 | 确定性服务、设定能力、主编 | 实际结果、偏差、开放线索和下一接口 | 确认后解锁下一级 |
| 外部事实或材料 | 研究与来源保护按需 | 有出处证据和使用边界 | 未通过门禁不得进入正式写作 |
| 导航、附件、故障 | 本地工具受理能力 | 真实状态与行动回执 | 不代替创作成员给剧情结论 |

## 18. 上下文合同

### 18.1 所有任务共用包头

每个生成或审查任务保存owner_id、book_id、task_id、幂等键、任务类型；开书/设定/卷纲/事件/章纲版本；正史修订和正文水位；作者想法ID与原话哈希；检索、模板、模型绑定和预算策略版本；采用/排除来源及哈希；完整包哈希和结果版本。

硬来源或版本缺失即失败，不能让模型补猜。任务开始后包被冻结；重试复用同一包，除非作者明确创建新任务。

### 18.2 任务资料矩阵

| 任务 | 必须内容 | 软内容 | 默认排除 |
|---|---|---|---|
| 第一卷卷纲 | 开书原话、活动设定、本卷想法、作品承诺 | 少量题材参考和模板实例 | 全部聊天、全资料库 |
| 后续卷卷纲 | 第一卷内容、上一卷正式结算、跨卷承诺、当前状态 | 命中旧章原文 | 上一卷未实现计划作为事实 |
| 事件序列 | 活动卷纲、卷首状态、必须/不得、作者想法 | 相关设定和开放线索 | 无关卷和完整Wiki |
| 单事件 | 卷纲相关部分、相邻事件接口、人物状态、相关事实 | 推进卡和少量历史证据 | 全书所有事件 |
| 章纲 | 压缩卷级约束、活动事件、上一章结算、知识边界 | 当前事件已写片段 | 后续卷细节 |
| 正文 | 开书身份胶囊、相关设定、卷约束、事件目标、当前章纲、上一章结算/尾段、作者要求、自由区 | 少量声音证据和灵感 | 全卷规划全文、全部评论 |
| 事实审查 | 同一完整稿、权威事实、相邻正文、相关原文/时间线 | 候选冲突 | 文学偏好 |
| 文学审查 | 同一完整稿、章纲软目标、人物声音边界 | 少量相邻正文 | 全书硬资料清单 |
| 体验审查 | 同一完整稿、读者承诺、本章意图、前章接口 | 相关情绪轨迹 | 其他审查结论 |
| 事件/卷结算 | 正式正文、章结算、正史修订、活动计划 | 偏差说明 | 未确认草稿 |

摘要只导航，不裁决事实。重要实体、规则、承诺、知情、时间或冲突命中时回查原文。混合检索不设全局0.8阈值；查不到返回未知。软风格证据允许不用，不要求仿写原句。

## 19. 状态、版本和恢复

书籍主流程由服务端状态驱动：开书草稿→开书确认→设定进行中→设定确认→卷纲进行中→卷纲确认→事件设计→事件确认→章纲设计→可写下一章→正文处理→等待作者→章结算→事件结算→卷结算。续写另有导入、分析、缺口设定和可规划当前卷支线。

卷纲/事件状态为草稿、生成中、候选、待确认、活动、已替代、已完成、已归档。活动版本切换使用预期版本比较。作者想法状态为未处理、已采用、调整后采用、暂存、未采用、已撤回；撤回不删除历史。

作者状态映射现有任务：排队中=pending/queued；准备资料=context/preflight；正在生成=working且真实调用存在；等你决定=waiting_confirmation；需要处理=blocked/failed/result_unknown；完成=succeeded且产出已保存。成员任务结束后回到空闲/待命。

每个下层版本保存上层ID和哈希。上层变化后，未写候选标记复核/失效，未定稿正文暂停并展示影响，已结算正文不变。局部无关变化可由确定性影响分析保留；无法确定时等待作者。
