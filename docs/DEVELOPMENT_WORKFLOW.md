# 开发与验收流程

授权与安全以 [AGENTS.md](../AGENTS.md) 为准；测试矩阵与证据标准只在 [ACCEPTANCE.md](ACCEPTANCE.md) 维护。Skill负责按需路由，不复制本文件的合同或另设审批。

## 1. 识别请求和授权

| 请求 | 执行方式 |
| --- | --- |
| 分析、比较、建议、整体规划 | 可以完整研究和提出方案；不自动修改产品代码或定稿 |
| 修改规则、Skill或正式文档 | 只修改对应来源和直接依赖，进行文档验证 |
| 实现、修复、调整 | 按已明确目标建立合同并执行，无需固定“开始开发”口令 |
| 整体重构的实施 | 建立总体范围与分批替换计划，再交付可验证部分 |
| 部署已完成改动 | 按获准版本和发布要求执行，不扩大产品范围 |

确认建议与授权实现不同；结合上下文判断，不能把单纯讨论当开工，也不能忽视已明确的行动请求。已授权的普通、可逆、无新增现金的产品细化和工程选择由Codex决定，给出必要说明。真正影响产品目标、作者权益、费用或安全的缺失决定才询问。

### 事实核查与专业判断

Codex承担项目总开发责任，交付标准是用户目标在实际约束下得到正确实现。产品讨论和开发统一遵循以下四条原则；讨论只按本节判断，不因此启动实施合同、编码或测试：

1. **先核对事实，不顺着用户的话下结论。** 区分用户目标、偏好、明确约束、可验证事实和待核实假设。影响方案的关键前提以代码、数据、运行结果或可靠来源核实；文档、用户判断和先前回复都可能有误。证据支持才认可，错误直接指出并解释影响；缺少证据就给暂定判断，不能装确定，也不为反对而反对。视觉喜好等合理偏好不当作技术错误。
2. **给出明确建议和理由，不把技术选择推回用户。** 从作者要完成的事情、操作负担、创作价值和商业交付条件出发，说明推荐方案、依据、代价与限制。方向清楚时直接推荐，不为凑数罗列选项；授权内普通、可逆、无新增现金的工程决定由开发者承担。只有影响目标、作者控制权、费用或安全的决定/授权确实缺失时，才提出最少必要问题，其余独立工作继续。用户知情选择合法取舍应受尊重，不强制每轮结束提问或重新确认已定事项。
3. **区分讨论建议、已确认方案和开发授权。** 未确认方案保持候选，已确认结论写入对应源文档；确认方案不自动等于授权实施，明确要求“按此实现”也不需要额外开工口令。可以一次讨论整体关系和多个决定，不受固定句数或方案数量限制；用户明确要求的逐页讨论节奏仍须遵守。规则清理不使历史架构、页面或Agent分工建议自动定稿。实施范围与证据进入当前唯一合同，HANDOFF只记录接管位置，不另建重复决定板。
4. **不让旧页面、旧流程限制新设计。** 当前代码与运行数据用于查证现状、成本、迁移和回滚，旧规格、历史工单、对象层级、岗位和候选数量不能否决新目标。复用或替换以当前目标和证据决定，不能为了符合旧结构扭曲方案。用户未改变的明确偏好和要求保留的能力继续有效；替换仍需按授权处理兼容、数据保护和验证，设计自由不等于可以擅自删除已有资产或越过安全边界。

选择方案时检查相称的反例和失败路径，包括是否只掩盖症状、重复操作和旧数据影响；普通小改不为凑格式建立大型审计。先明确预期结果，再以不迁就实现的证据验收；不能删有效失败测试、放宽标准或把构建通过当功能正确。用户已明确替代的旧行为可更新测试，但要说明语义变化。自己判断或实现有误时说明实际影响、修正根因并复验，如实报告剩余问题；道歉不能代替解决问题，规则或架构也不能保证零BUG。

## 2. 开工说明与相称合同

修改前用简短说明交代：理解的目标、准备修改的范围、明确保留和不改的内容、如何验证、是否部署。这是工作说明，不是默认等待批准。

- 小型文案、规则或机械修复可以使用一张短清单；不要求重复填写不适用的页面、AI、数据库或回滚字段。
- 多轮任务、业务改动及整体重构必须有唯一任务编号和可恢复的清单路径，开工时告知。
- 同一任务只维护一份当前状态；整体重构总计划记录批次关系，各批清单只记录该批实现证据，不重复维护同一状态。
- 范围或关键假设变化时先更新合同并告知。仍在已授权目标内的必要技术调整可以继续；新增独立用户目标或需要新授权的操作不能静默加入。

合同最低记录如下，格式可以合并为段落或表格：

```text
任务编号与唯一清单（长任务必填）：
目标与当前问题：
允许修改、明确不改：
必须保留的功能/数据/用户偏好：
实现验收与回归范围：
验证范围及风险理由：
部署要求：
```

只补充与本任务有关的内容：
- UI：用户主任务、需要支持的真实状态、目标设备、输入保存与失败恢复。
- AI：可信输入与版本、职责/工具/权限、模型参数和总预算、输出合同、问题反馈、恢复与审计。
- 数据与任务：身份/书籍范围、权威版本、幂等与事务、兼容、失效与补偿。
- 正式内容后的维护：触发事件、必要资料、最大可接受延迟、重复事件、冲突与追赶方式。
- 高风险变化：权限、不可变内容、数据库语义、跨服务恢复、模型计费、上下文权威或不可逆操作的影响、备选方案、恢复与验证证据。无需单独固定审计编号、报告章节或轮数；安全授权仍按根规则执行。

用简短编号或表格对应目标、实现、验收与证据，不强制每条拆成四组编号。任务恢复或对话压缩后，按已知清单路径核对当前状态、最新用户要求和Git差异；不重做已完成事项。

## 3. 小修与重构采用不同尺度

### 局部修复

先确认问题与直接依赖，优先最小差异。能在现有实现内准确修好就不整文件重写，不顺手改无关页面、抽象、接口或数据语义。

### 新功能与整体重构

根据用户目标设计边界，可以重新划分模块、替换不合适的实现和调整技术方案。合理性依据是正确性、可维护性、用户体验、成本与风险，不是新旧代码行数。

整体重构先列出现有能力的保留、调整、合并、删除或新增决定；不以重写为由悄悄丢功能。未明确替代的有效用户能力与受保护数据仍应纳入兼容和回归；旧内部实现、已淘汰交互不成为新设计门禁。

分批应有明确结果、可验证边界和回滚或隔离办法。先尽早形成能运行的代表性纵向路径；必要的数据层、任务底座或迁移准备可以单独验收，不强迫每个内部批次都有页面。同一授权内的后续批次验证通过后继续，定期展示结果；只有真正未解决的重大产品决定或新权限才等待用户。

本次全产品重构的最新授权、顺序和单元合同统一在 [重构执行文档](REBUILD_EXECUTION_PLAN.md)。第110批用户已将方案与实施安排交由Codex，GPT-5.5按路线开发，替代此前逐页等待讨论的节奏；保留已明确的内容页UI与数据安全，逐批合同、实现和验收。需要用户授权/亲自测试/外部凭据的部分登记跳过并继续独立工作，不能将跳过项计为完成或静默绕过依赖。用户后续明确要求讨论或暂停时服从最新安排；普通小修流程不变。

渐进替换允许新旧实现短期共存，但明确数据权威、入口与任务所有权、兼容期限及退出条件，防止重复执行和双写冲突。不能把新系统一次性覆盖生产作为默认重构策略。

## 4. 定位与复用审查

- 检查当前实现、相关测试和真实状态；有需要再查Git历史、远程或外部方案。纯规则任务只查规则及引用，不读取无关产品代码。
- 优先考虑已验证的项目能力、标准库或成熟依赖；记录复用、适配或重写的关键理由。不要求穷尽旧版本、逐层搜索后才允许写代码。
- 复用不能保留已确认要替代的缺陷；重写也不能丢掉已有正确行为与兼容证据。
- 不恢复已删除旧产品为运行依赖。过渡层与历史记录的保留、退出按当前合同处理。
- 新引入公开源码或依赖时核对来源、版本、许可证及商业兼容、安全与维护状态，保留必要声明；不因方便而复制来源不明的代码。

## 5. 系统与Agent的责任

只在相关节点做一次职责判断，不为每个读写函数重复建立审计表：
- 确定性事务由系统负责：身份、权限、版本、格式、数值计算、精确匹配、持久化、防重与队列。
- 语义判断由有明确任务合同的Agent负责：作者意图、相关性、归纳、文学冲突、创作与自然语言更新。
- 混合任务由系统提供有来源的资料，Agent判断，系统核验结构、权限和版本后保存。

候选召回、关键词、正则和阈值可以辅助定位与硬检查，不能冒充语义理解。也不为增加AI参与而把可确定执行的事务交给模型。作者明确选择的精确选项可由系统原样保存。

任务只接收最小充分资料，正文、规划、候选、推断和审查意见保持身份与版本。总时限、尝试次数和消耗有边界；格式失败可有限补交，结果未知先核对，不盲目重发。保留已成功检查点，重复操作不产生重复业务提交或内部重复扣量。

正文安全保存与后续整理分开；正式内容形成后可靠触发必要维护。维护失败保留证据与恢复动作；下一步依赖的关键事实尚不可靠时暂停该依赖，不把未核实的状态写成事实。

## 6. 实施与范围检查

1. 检查其他任务的未提交改动，保护现有工作；无法隔离的冲突暂停相关部分。
2. 按合同实现并及时验证，不堆积大量无法运行的代码。反复失败时重新诊断，不机械重复同一路径。
3. 用户可见状态来自真实执行，错误用自然语言说明结果与恢复方式；技术审计留在受权限保护的位置，不保存或泄漏思维链。
4. 使用多成员时保留各自结果；需要独立评审时隔离输入与先前意见，准确记录模型身份。不默认要求固定成员数量或厂商数量。
5. 发现合同外问题记录为后续项；阻碍当前目标的必要依赖更新合同并说明，涉及新权限仍先取得授权。
6. 每批核对目标、保留项、实现与证据。验收不通过就修正或如实报告，不为结项降低标准。

## 7. 差异、兼容与清理

完工前检查最终文件列表、`git diff --stat`、完整差异及暂存差异，确认没有合同外代码或其他任务改动混入。共享组件变化要回归实际受影响路径，不能只检查最初报告问题的页面。

删除旧实现前检查启动、路由、动态注册、任务、数据读写、恢复和测试引用。满足替代、兼容和回滚条件后，清理旧代码、只验证废弃行为的测试及冲突文档；不清理作者数据、不可变正文或已合并迁移。过渡期有明确用途的兼容层不等于替换失败。

规则工具废弃时同步检查调用者、专属测试和样本；删除固定模板约束不能删除内容安全与真实质量的检查目标。

## 8. 验证、交付与发布

按 [验收标准](ACCEPTANCE.md) 选择风险相称的测试；高风险事实触发全量验证，普通小修不自动全量。UI无真实浏览器证据就不声称视觉通过，真实模型与长篇质量也不得用夹具替代。

清单使用“待处理、进行中、通过、未通过、未验证、不适用”标明状态；只对已经取得证据的部分声明通过。最终回复简洁说明改动、为何这样改、验证结果、未验证项与必要风险；有提交/部署则列实际版本和回滚信息，不要求把所有空字段照抄给老板。

发布遵循合同及根规则第7节；没有发布记录与线上验证不称已上线。文档维护默认不部署；小型BUG按已有发布授权执行；整体重构需要明确的分批发布范围。

逻辑完整后提交，当前规则和状态写回源文档。未达成的关键目标或验证不能因预算、时间或报告格式被标记为完成。
