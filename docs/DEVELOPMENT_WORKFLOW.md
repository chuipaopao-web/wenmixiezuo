# 功能开发与验收流程

> Codex 调用入口：.agents/skills/wenmi-development-workflow/SKILL.md。本文件是开发规则的唯一源文档；Skill 负责触发和执行本闭环，不复制另一套规则。

## 0. 先识别工作模式

不同任务不能强行套用同一流程：

- **产品讨论/设计探索**：用户要求讨论、评估、比较或先出方案时，只澄清目标、查证必要现状、记录假设与待决定项；不建立开发清单、不修改产品代码、不把旧规格当约束，也不把讨论稿自动升级为定稿。
- **规则与文档维护**：用户明确要求修改规则、Skill或正式文档时，本流程只约束这些文件；不因此获得产品功能开发、数据迁移或部署权限。
- **功能开发**：用户明确要求实现、修复、调整或重构时，执行完整变更合同、开发、验证与报备。
- **部署**：只发布已经完成且合同允许发布的改动；单纯部署不反向扩大开发范围。

V7 讨论期由 `HANDOFF.md` 标识。此时老板最新决定与当前讨论目标是产品输入；V6 页面、流程、对象层级、岗位、UI、旧验收和历史实现只用于查证生产现状、复用资产与兼容风险，不得自动进入 V7 的必须保留项。只有老板明确说“开始开发”才激活 V7 功能开发。

## 1. 功能开发顺序

每个已获授权的功能开发、BUG 修复、局部调整或重构任务都按同一闭环推进：

```text
用户的大白话需求
→ 开工回复：确认消息＋工单信息
→ 判断任务规模并拆成可独立验收批次
→ 真实页面和代码
→ 信息节点职责审计：确定性系统 / 大模型 Agent / 混合闭环
→ 当前实现、V6/历史代码、现有依赖与合适公开源码复用审计
→ 确认根因
→ 必要时更新工单并冻结唯一变更合同与验收清单
→ 最小真实纵向实现
→ 本批测试、回归、差异审计与阶段结算
→ 确认后再进入下一批
→ 按合同部署及线上验证（不部署则记不适用）
```

没有唯一清单不开始修改；没有逐项证据不勾选完成；不能用“字段已存在”代替真实交互成功，也不能把多个未验收批次积累到最后一次性结算。

### 默认自主执行边界

老板已授权开发者按商业产品标准直接处理普通、可逆、任务范围内的工程选择。现有凭据已经配置、不会购买新服务或突破既定用量边界时，开发者可以直接调用内部/外部 API、执行相称模型探针、选择实现方案、修复问题并完成验证，不得把老板不懂的模型参数、接口、数据库和代码选择反问给老板。

只有出现新密钥或新登录、额外现金采购、不可控批量消耗、向第三方发送敏感数据、永久删除作者数据、生产恢复、不可逆迁移或其他重大安全风险时，才暂停并说明需要老板决定的具体事项。调用已配置 API 不等于获得扩大产品范围、对外写入或绕过数据门禁的授权。

## 2. 新功能、任务拆分与复用优先

- 老板当前需求是功能和交互的唯一产品起点。先把新需求整理为本次实现合同，不从旧产品文档反推需求。
- 开始修改前检查同一工作区是否有其他未完成任务或未提交改动；不得覆盖、回退、整理或混合提交其他任务的文件，无法安全隔离时停止并等待。
- 老板提出明确修改意见时，只处理明确问题及其不可分割的直接依赖；清单必须写明“不改范围”，未经要求不得顺手调整、重构、美化或重排无关模块。旧功能只有在本次合同明确要求保留时才成为回归门禁；已明确替代或删除的行为不能反过来否决新设计。确实必须扩大范围时，先停止并说明原因。
- 动手前先想最小实现：能少写就少写，能删冲突规则就不重写，能改现有值就不新增抽象，能复用就不复制；局部修改不得借机引入额外层级、状态、依赖或大段样板。
- 修改已有功能前，依次检查当前代码、本地 Git 历史和已配置远程仓库。旧版本已有且符合老板当前要求的成熟实现时，优先最小复原或复用相关片段，不重新发明；复原后用范围差异和受影响测试证明没有影响其他功能。旧实现只提供代码来源，不能否决老板最新需求或安全硬门禁。
- 旧代码、旧页面、旧测试和旧文档只用于找到替换范围，不具有否决新设计的权力。
- 新功能与旧实现冲突时，以新功能为准；完成替代和数据兼容检查后，删除旧实现，不保留两套并行流程。
- 不为了兼容已经废弃的界面或临时状态继续增加分支。确有旧数据需要读取时，只保留最小数据兼容层，并写清退出条件。
- 已合并数据库迁移、作者正式数据和不可变正文属于历史事实，不能按“旧功能”删除或改写。

### 先判断系统和 Agent 各自做什么

每个涉及信息读取、整理、推荐、翻译、更新或审查的节点，在写代码前都必须完成一次“信息职责审计”，并在唯一清单写明结论：

| 信息性质 | 负责者 | 允许做什么 |
| --- | --- | --- |
| 确定性事务 | 系统 | 身份与权限、`owner_id/book_id`隔离、版本、哈希、幂等、任务队列、存取、排序、格式与目录合法性、硬性安全门禁 |
| 语义工作 | 大模型 Agent | 理解作者意图、资料翻译、相关性判断、归纳取舍、冲突判断、创作推荐、文学审查、自然语言状态更新 |
| 混合节点 | 系统＋Agent | 系统装配带来源和版本的最小充分资料包，Agent完成语义判断，系统校验合同、保存结果和恢复状态 |
| 正式内容后的持续更新 | 可靠事件＋指定 Agent | 正式版本提交后立即排队，小批量提取人物、关系、事实、蓝图、故事线、伏笔和开放问题；系统保证幂等、来源、版本与失败恢复 |

审计时必须主动搜索关键词匹配、正则、固定标签映射、分数阈值、硬编码路由和前端本地推断。它们可以用于候选召回、精确匹配、格式校验和安全阻断，但不能直接得出“作者是什么意思”“哪些内容适合本书”“是否存在文学冲突”等结论。需要语义却没有 Agent 的节点，不能用确定性兜底伪装成功；模型不可用时显示真实失败或待恢复状态。

反过来，系统能够零歧义完成的身份、版本、数学计算、格式和权限工作不交给模型，避免不稳定、浪费和不可审计。作者明确点击的精确选项可以由系统原样保存；只有需要解释、扩展或判断选项含义时才调用 Agent。

### 先拆成可验收批次

一个开发批次必须同时满足：只有一个主要用户结果、可以独立验证、可以独立回滚。跨前端、API 和数据层的纵向闭环可以作为一批，但多个互不依赖的页面、用户目标或修复不能因为属于同一个大需求就塞进一张清单连续开发。

出现以下任一情况时，修改前先拆批并在开工回复中说明：

- 同时包含两个以上可以独立交付的主要用户结果；
- 产品语义、工作流或 UI 方向仍需要老板选择；
- 必须同时铺开大量页面或服务，第一条真实用户链路无法提前运行和验收；
- 当前批次无法在不依赖后续批次的情况下测试或回滚；
- 预计需要连续完成多个产品可见批次，才能第一次看到真实结果。

产品可见的工作流或 UI 必须先完成一条最小真实纵向闭环，取得运行或浏览器证据并完成阶段差异审计。结果涉及审美、交互或产品判断时，先向老板展示并确认，再复制到相邻页面或继续下一批。纯内部且产品语义已经冻结的机械批次，可以在每批证据通过后按合同继续，不需要制造无意义的等待。

### 写代码前先做复用审计

每个功能在写新代码前，必须在唯一清单记录检查对象、证据、复用决定和理由。检查顺序是：

1. 当前目标代码库中是否已有可直接修改的实现；
2. 当前生产、V6、本地 Git 历史或已配置远程中是否有语义相符且经过验证的实现；
3. 项目现有依赖、语言标准库或官方 SDK 是否已经解决；
4. 确有必要时，是否存在维护良好、商业许可兼容的公开源码或依赖；
5. 前四项都不适合时，才编写满足当前合同的最少新代码。

复用方式优先选择“直接使用或最小修改”，其次是“复制已验证片段并微调”，再其次才是新增实现。不能为了架构整齐重写成熟代码，也不能复制整套旧项目、无关抽象或大段样板。使用搜索和定向读取定位相关文件，不为找一个功能通读整个仓库；减少 Token 不能成为跳过语义理解、测试、权限和数据安全核查的理由。

V7 在自己的代码库中实现新产品，不把 V6 产品层模块作为运行时依赖直接导入或调用。开发某项能力前仍必须检查 V6 真实代码和测试：语义一致且质量合格的代码可以复制或抽取必要片段到 V7 后最小微调；不一致的放弃。登录、数据库、部署等受保护的共享平台能力按 V7 明确合同或适配边界复用，不复制第二套系统，也不让 V6 页面和工作流反向决定 V7。

采用公开 GitHub 仓库、代码片段或第三方依赖前，至少核对许可证和商业使用兼容性、来源仓库与版本/提交、维护状态、已知安全风险、依赖体积以及需要保留的版权或声明。优先使用官方发布且可锁定版本的依赖；来源不明、许可证不清、维护停滞或引入风险大于节省量的实现不得采用。

## 3. 变更合同与开发清单

### 开工回复

用户不需要使用产品、技术或测试术语，也不需要自己填写模板。开发者必须把用户原话自动翻译成明确、可执行、可验收的工单；每个开发任务的第一条用户可见回复必须同时包含：

1. **确认消息**：用一至两句话复述理解的目标和本次明确工作内容。
2. **工单信息**：列出任务类型、用户目标、允许修改的文件或模块、明确不改范围、老板明确要求保留的现有行为、新功能验收、合同内回归、测试范围和部署要求。

发出开工回复前不得编辑文件；只读检查可以继续用于确认根因。只读检查发现原工单有误或必须扩大范围时，先向用户发送更新后的工单和原因，再继续修改；不得静默改变工作内容。

### 变更合同

每次开发在修改前建立变更合同。每个任务必须有唯一任务编号和唯一清单路径，并在开工回复中告知；同一任务不得同时维护两张“当前清单”。完整模板只保存在本节，AGENTS 和各 Skill 只引用，不复制：

```text
任务编号：
本次唯一清单：
任务类型：
当前问题：
复现步骤：
期望结果：
允许修改：
明确不改：
必须保留：
新功能验收：
原功能回归：
测试范围：
部署要求：
```

清单把老板原话按固定编号映射为 `REQ`（需求）→ `IMP`（实现）→ `ACC`（验收）→ `EVD`（证据），每项只使用“待处理、进行中、通过、未通过、未验证、不适用”。任务恢复、对话压缩、工具中断或长时间执行后，先按已知路径重读唯一清单并核对当前编号，不通过文件名猜测、语义搜索或聊天记忆选择旧清单。

除上述合同外，开发与验收清单还必须覆盖：

1. 用户可见目标：作者最终能完成什么。
2. 页面与交互：只覆盖本次功能实际存在的初始、选择、工作中、失败、完成、修改和恢复状态；不得为了满足清单凭空增加状态或步骤。
3. AI介入：仅在本次功能包含 AI 时，说明谁由作者或系统选择、何时调用、接收什么资料、输出什么、不可用时怎样显示；清单不预设岗位、成员数或介入节点。
4. 数据与接口：新增或替换的对象、版本、权限、兼容和幂等要求。
5. 失败兜底：按本次功能实际涉及的模型/成员失败、任务中断、刷新恢复和审计记录设计，不预设必须采用多成员或独立问题中心。
6. 响应式：按本次合同确认的目标设备和视口检查主操作、输入、长文本和错误状态；未约定时采用当前产品支持范围，不把某组宽度写成产品架构。
7. 清理项：被替代的组件、路由、服务、字段读取、文案、测试和当前文档。
8. 验收证据：每一项对应的测试、构建、浏览器走查或运行记录。
9. 范围守恒：明确列出本次允许修改和禁止改动的模块，并记录复用的当前/本地历史/远程实现来源与最终差异检查。

AI功能还必须补充“成员能力合同”：岗位目标、可信输入和版本、允许使用的工具与权限、模型与套餐、温度/上下文/时限等任务参数、输出结构、作者可见反馈、失败报告、幂等恢复和后台审计。温度和性能按任务类型选择并以真实结果验证，不使用全岗位统一值；缺少完成任务所需工具或反馈能力时不得验收为可用。

涉及正式内容后持续更新时，清单必须写明触发事件、指定成员、更新对象、推荐的小批量窗口、最大允许延迟、来源证据、版本冲突、重复事件、失败补偿和追赶策略。正常链路不能等几十章后才集中理解；“两三章”是鼓励及时处理的产品尺度，不写成所有题材的固定章数。Token预算服务于去重和防失控，不能成为延迟必要连续性更新的理由。

前端功能还必须写一份最小交互合同：当前页面唯一主任务、唯一主按钮、可合并操作、必须保留的次要入口、弹窗必要性、重复标题/介绍清理、技术词作者投影和手机端首要视口。能在当前页面展开、折叠或原位完成的操作不另开弹窗；多个同级按钮能合成一个主操作或渐进展开时必须简化。危险确认、权限授权和确需隔离注意力的跨对象选择可以使用弹窗，但要验证手机端尺寸、返回和未完成状态不丢失。

## 4. 逐项开发与核查

- 一次只把一个清单项推进到“实现＋测试通过”，再勾选完成；相关项可以同批编码，但验收必须逐条对应。
- 一个纵向批次完成后立即更新 `REQ/IMP/ACC/EVD` 状态，执行本批受影响测试、合同内回归和阶段差异审计；不能先堆积多个未验收批次再统一找问题。
- 产品可见结果与已确认方向不符、最小闭环无法运行、相同实现路径连续失败两次，或复用审计发现原合同判断错误时，停止重复写代码，重新核对根因和范围。需要改变产品语义、扩大范围或增加外部权限时先向老板说明。
- 本次功能采用 AI 时，成员状态必须来自真实能力检查、任务和模型调用；只实现当前合同存在的业务状态和恢复动作，不由开发规则增加状态。
- 每个 Agent 节点实现后检查：资料包是否最小充分且带来源版本，成员是否拿到必要工具和权限，模型/温度/上下文是否适合任务，输出合同是否可校验，能否独立反馈缺失资料或冲突，失败/超时/结果未知是否可追踪和恢复。只验证“接口返回200”不能证明成员能力完整。
- Agent 在作者端的工作中、完成、等待决定和失败反馈使用一句简短口语化大白话，并配合真实头像/成员身份和真实任务状态。失败反馈必须先真诚道歉，明确说“对不起/抱歉，这次没有完成”，随后说明保留下来的结果和作者可执行的恢复动作；道歉不能替代真实失败状态，也不能继续声称正在加急、即将完成或已经交接。完整创作成果按任务需要展示，不强行压缩成一句话。
- 作者投影不得出现模型名、供应商协议、内部字段、键名、哈希、提示词、思维链、堆栈、乱码或无效过程文本；这些信息只进入受权限保护的审计。发现技术泄漏时先修投影和错误映射，不把内部原文直接显示给作者。
- 正式版本提交触发的持续更新必须先可靠记录事件，再由指定 Agent 异步执行；任务要绑定书籍、来源版本和幂等键。Agent 只能基于作者接受的内容证据更新衍生记录或实际状态，不能用计划、猜测或旧摘要覆盖正文。失败不得阻止正文保存，也不得静默丢失，必须进入可恢复状态。
- 本次功能采用多成员并行时，单成员失败不能抹掉其他成功结果；是否补发、替换或继续由当前产品合同决定。
- 运行失败必须保留必要的用户、书、任务、调用与错误摘要关联，供授权人员追溯；采用独立问题中心、日志、审计账本或其他承载方式由当前架构决定。
- 修改确认内容必须创建新版本；不覆盖作者原内容，不跨用户或跨书读取。

## 5. 差异审计与旧实现清理

完工前必须执行并记录差异审计：

- 检查 `git diff --stat`、完整 `git diff` 和最终修改文件列表；合同外文件必须恢复为未修改状态或暂停说明，不能混入提交。
- 检查是否意外删除、隐藏或改变合同明确保护的按钮、入口、状态、数据读取、失败恢复和设备行为；老板要求替代的旧交互不属于保护对象。
- 修改共享组件、全局 CSS、全局 token 或共享外壳时，列出所有受影响页面并逐页执行对应回归；不能只测试报告问题的页面。
- 删除旧代码前，证明新闭环可用且旧实现零有效引用；证据不足时不删除、不宣称完成替代。

功能替代完成后执行引用检查：启动入口、路由、组件、服务、动态注册、任务类型、测试、迁移和恢复逻辑。确认新路径覆盖并且没有有效引用后：

- 删除旧组件、旧接口分支、旧服务和重复样式；
- 删除只验证旧行为的测试，改为验证新清单；
- 删除或改写当前文档中的旧流程，避免新旧说法并存；
- 不修改已合并迁移，不删除作者数据，不用清库代替兼容；
- Git历史负责追溯，当前目录不保留废弃规格或生成副本。

## 6. 验收结算

验收表每项只能标记为：

- `通过`：实现存在，相关测试和交互证据通过；
- `未通过`：行为不符合或测试失败；
- `未验证`：尚无足够证据，不能称完成；
- `不适用`：说明为什么与本次功能无关。

最终结算默认只运行受影响测试、对应包类型检查和构建。单页 UI、文案、局部接口、模型适配器或明确 BUG 修复，不得为了“更保险”擅自扩大成全量测试；模型调用策略变化应优先验证对应适配器、受影响业务集成测试和一次必要的真实探针。

局部 BUG 的默认测试范围是受影响测试、对应类型检查/构建和相关浏览器或运行场景。测试必须同时对应变更合同的新功能验收与原功能回归；即使测试全绿，只要验收目标错误或合同中的必须保留项未验证，也不能算完成。没有浏览器或运行证据时，交互只能标记“未验证”；没有真实发布记录和线上核查时，部署只能写“未部署”或“未验证”，不得写“已上线”。

只有以下任一条件成立时才运行全量 `npm run verify:full`：迁移改变既有受保护数据的语义或形状、迁移需要回填历史数据、权限或账号隔离、跨服务恢复、不可逆迁移、核心创作工作流的结构性变化，或者老板明确要求全量测试。仅为独立新功能新增表或索引、且不改变既有表语义和数据解释的加法迁移，默认只验证迁移清单、空库安装、重复执行安全性、受影响仓储/接口测试和对应类型检查/构建。运行全量前必须在本次验收清单写明具体触发事实；“有数据库迁移”本身不是充分理由，写不出触发事实就不得运行。测试范围既要覆盖风险，也要控制执行时间、算力消耗和会话上下文开销。

前端重构还要按受影响范围检查合同要求支持的设备与真实状态。测试失败、合同要求删除的旧入口仍可进入、后台漏记失败或作者数据版本被覆盖时，不得宣布完成。

### 商业产品结果验收

自动测试通过后，再以作者视角执行一次结果审查；这一步不是随意扩大修改范围，而是决定本批是否真的达标。至少回答并留下证据：

1. 功能是否准确解决作者问题，输出是否完整、易懂且没有技术泄漏；
2. AI是否承担了需要理解和创作判断的工作，系统是否越权用死规则处理语义；
3. Agent是否具备完成任务、使用工具、报告问题、保存状态和恢复任务的完整能力；
4. 主流程是否还能减少点击、输入、等待、弹窗、同级按钮或重复介绍；
5. 手机端是否比桌面端更早验收，是否存在横向溢出、过大留白、长文堆叠、操作遮挡或状态丢失；
6. 失败、超时、刷新、返回和重复操作是否真实、稳定、可恢复且不重复扣量；
7. 对需要持续维护的资料，正式内容形成后是否及时触发小批量增量更新，而不是长期积压。

结论只能以结果为准。问题在当前合同内则修正后重验；问题属于合同外相邻能力则明确列为发现项和后续工单，不得静默顺手开发。只要准确性、完整性、核心交互、Agent能力或数据可信任一项不达标，就标记“未通过”；缺少真实页面、模型或设备证据时标记“未验证”，不能用测试全绿弱化结论。

先服从变更合同的部署要求；合同明确不部署时不得部署。合同未禁止部署的小型 BUG 修复通过相称门禁后，默认直接部署生产，不再逐次等待上线指令。部署仍须遵守在途任务、原子切换、健康检查和回滚要求；若涉及实际付费、新密钥/新登录、永久删除作者数据、生产恢复、不可逆迁移，或无法保证在途任务安全，则暂停并说明原因。

完工报告使用以下唯一模板；无法取得的证据必须明确写“未验证”：

## 7. 长期保留的硬底线

日常功能调整不受旧产品框架和旧UI文档限制，只长期保留下列底线：

- 登录身份、`owner_id`、`book_id`隔离；
- 作者正式数据和正文不可变版本；
- API Key、密码、会话和模型思维链不泄漏；
- 已合并迁移不改写，生产部署可回滚且不破坏在途任务；
- 永久删除作者数据必须预览影响并二次确认。

其他产品、工作流、AI岗位介入、页面、导航、文案和测试实现只有在老板最新需求纳入本次变更合同时才可以重做，并在同一次任务中同步清理旧实现。
