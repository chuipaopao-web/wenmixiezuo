# 功能开发与验收流程

> Codex 调用入口：.agents/skills/wenmi-development-workflow/SKILL.md。本文件是开发规则的唯一源文档；Skill 负责触发和执行本闭环，不复制另一套规则。

## 1. 唯一开发顺序

每个新功能或重构任务都按同一闭环推进：

```text
老板最新需求
→ 新建本次开发清单与验收清单
→ 逐项实现
→ 每完成一项立即核对代码、页面、接口和状态
→ 逐项自动测试与必要的真实交互测试
→ 删除已被替代的旧代码、旧入口、旧测试和旧说明
→ 全量检查受影响主流程
→ 记录已通过、未通过和证据
```

没有清单不开始大改；没有逐项证据不勾选完成；不能用“字段已存在”代替真实交互成功。

## 2. 新功能优先

- 老板当前需求是功能和交互的唯一产品起点。先把新需求整理为本次实现合同，不从旧产品文档反推需求。
- 旧代码、旧页面、旧测试和旧文档只用于找到替换范围，不具有否决新设计的权力。
- 新功能与旧实现冲突时，以新功能为准；完成替代和数据兼容检查后，删除旧实现，不保留两套并行流程。
- 不为了兼容已经废弃的界面或临时状态继续增加分支。确有旧数据需要读取时，只保留最小数据兼容层，并写清退出条件。
- 已合并数据库迁移、作者正式数据和不可变正文属于历史事实，不能按“旧功能”删除或改写。

## 3. 每次开发清单必须包含

1. 用户可见目标：作者最终能完成什么。
2. 页面与交互：初始、选择、工作中、部分失败、全部失败、完成、修改和恢复。
3. AI介入：谁由作者选择、何时调用、接收什么资料、输出什么、不可用时怎样显示。
4. 数据与接口：新增或替换的对象、版本、权限、兼容和幂等要求。
5. 失败兜底：单成员失败、模型不可用、任务中断、刷新恢复和后台问题记录。
6. 手机端：360、390、430px的主操作、输入、长文本和错误状态。
7. 清理项：被替代的组件、路由、服务、字段读取、文案、测试和当前文档。
8. 验收证据：每一项对应的测试、构建、浏览器走查或运行记录。

## 4. 逐项开发与核查

- 一次只把一个清单项推进到“实现＋测试通过”，再勾选完成；相关项可以同批编码，但验收必须逐条对应。
- AI成员状态必须来自真实能力检查、任务和模型调用。可用、不可用、等待、工作中、完成、部分失败、失败都要有明确文案和恢复动作。
- 多成员任务按席位隔离：单席不可用或失败不能抹掉其他成功结果；能继续时保留成功结果，只重试失败席；无法继续时告诉作者原因和下一步。
- 前端失败、API失败、Worker失败和成员局部失败都要进入独立管理后台问题中心，并保留用户、书、任务、成员和错误摘要的可追溯关系。
- 修改确认内容必须创建新版本；不覆盖作者原内容，不跨用户或跨书读取。

## 5. 清理旧实现

功能替代完成后执行引用检查：启动入口、路由、组件、服务、动态注册、任务类型、测试、迁移和恢复逻辑。确认新路径覆盖并且没有有效引用后：

- 删除旧组件、旧接口分支、旧服务和重复样式；
- 删除只验证旧行为的测试，改为验证新清单；
- 删除或改写当前文档中的旧流程，避免新旧说法并存；
- 不修改已合并迁移，不删除作者数据，不用清库代替兼容；
- Git历史负责追溯，当前目录不保留废弃规格或生成副本。

## 6. 验收结算

验收表每项只能标记为：

- `通过`：实现存在，相关测试和交互证据通过；
- `未通过`：行为不符合或测试失败；
- `未验证`：尚无足够证据，不能称完成；
- `不适用`：说明为什么与本次功能无关。

最终结算至少运行受影响测试、类型检查和构建；涉及核心工作流、任务恢复、数据库或权限时运行全量 `npm run verify:full`。前端重构还要检查手机端和桌面端的初始、工作中、失败、恢复、完成状态。测试失败、旧入口仍可进入、后台漏记失败或作者数据版本被覆盖时，不得宣布完成。

## 7. 长期保留的硬底线

日常功能调整不受旧产品框架和旧UI文档限制，只长期保留下列底线：

- 登录身份、`owner_id`、`book_id`隔离；
- 作者正式数据和正文不可变版本；
- API Key、密码、会话和模型思维链不泄漏；
- 已合并迁移不改写，生产部署可回滚且不破坏在途任务；
- 永久删除作者数据必须预览影响并二次确认。

其他产品、工作流、AI岗位介入、页面、导航、文案和测试实现都可以随老板最新需求重做，并在同一次任务中同步清理旧实现。
