# 项目总章程

## 产品使命

帮助作者有规划地完成长篇小说，同时保留作者决定权、人物生命力和合理惊喜。系统负责准备资料、提出方案、执行正文、核对事实和结算状态，不能把创作压成固定公式。

## 唯一主流程

开书信息 → 设定 → 分卷 → 事件链 → 当前事件大纲 → 当前事件章纲 → 单章正文 → 章节/事件/卷结算 → 下一卷。

已有正文导入与反向拆解是兼容入口，最终仍进入同一主流程。

## 产品边界

- 创作台承载开书、设定、卷纲、事件、章纲和正文。
- 图谱与资料库合并为资料库，取名是创作台辅助工具。
- 应用启动先进入统一登录页；登录成功后直接进入创作台。左栏只显示当前账号的可滚动书籍列表、新建和归档操作，不设书架首页，也不混入对象功能导航。
- 顶部功能栏统一提供信息、设定、分卷、规划、章纲、正文、资料库、取名、团队、任务、灵感与设置；点击左侧切换书，点击顶部切换功能页面。
- 默认界面采用iOS式浅色玻璃视觉，不设置独立版权页面。
- 灵感与生产工作流隔离，不保存为生产记忆，不自动生成或修改任何正式对象；只有作者主动摘录到具体对象后才能作为作者输入。
- 作者原话附着具体对象；AI 通过方案、差异、融合和修改反馈协作。
- 创作团队保持14名成员；小文秘书是工具角色，不计入创作成员。

## 权威与版本

- 作者确认的开书资料、设定、规划版本和不可变正文是正式来源。
- 规划描述未来，结算记录已经发生的事实。
- 分卷约束事件，事件链约束事件大纲，事件大纲约束章纲，章纲约束正文。
- 上游版本改变时，下游候选必须失效、重编译或重新确认。
- 摘要、向量、全文索引、图谱和 Wiki 只作导航或投影，争议事实回查正式源。

## 不可突破的门禁

- 所有核心记录和查询携带 `owner_id`、`book_id`，禁止跨书污染。
- 正文采用不可变完整版本，修改产生新版本。
- API Key 只来自环境变量，不进入数据库、日志、上下文、备份、导出或 Git。
- 作者数据普通删除为归档；永久删除需影响预览、输入 `YES` 和二次确认。
- AI 状态由真实任务、心跳、调用和工具事件驱动。
- 同模型不得冒充异模型独立意见。
- 灵感分身不得冒充生产成员状态，也不得写入正式对象、正史或结算。
- 不保存或展示模型思维链，只保存任务、来源、结论和调用证据。

## 成功定义

作者可以从新建书籍连续推进到卷、事件、章纲和正文；每一步知道 AI 成员为什么介入、读取了什么、输出保存在哪里。系统可恢复、可追溯、跨书隔离，并在提升一致性的同时不降低原创性、人物可辨识度、情绪力度和整体阅读质量。

## 统一身份边界

- 本机和公网部署使用同一套注册、登录、退出和权限规则，不存在免登录的单用户产品分支。
- 当前首发身份为邮箱加密码；首位注册者为管理员并接管账号体系启用前的本机老板数据，其余账号为普通用户并获得全新独立数据空间。管理员可以查看用户列表并暂停或恢复账号。
- 每个业务请求必须从已验证的服务端会话取得 `owner_id`；客户端提交、默认配置或书籍参数都不能替代登录身份。
- 账号会话、密码摘要和审计记录不得进入模型上下文、作者导出、正文、日志明文或产品检索。

## 分层故事设计合同

- 开书给方向，四项核心设定给书籍骨架；卷负责大故事方向，事件链负责因果结构，事件大纲负责小故事，章纲负责场景与情绪执行，正文只在当前层自由表达。
- 第一卷必须把前500字、黄金三章和约10万字内或卷末重大高潮设计成针对本书的具体职责，但不得承诺商业结果或固化爽点频率。
- 专业叙事方法只在系统内部组合，作者面对两条具体路线；事件阅读感受最多单选一个。上层硬约束向下传递，软参考可以不用，创作空白必须保留。
- ContextCompiler按硬事实、当前任务、软参考和创作空白分层编译，核心信息无损，其他信息按相关性全文纳入或延后回查。
