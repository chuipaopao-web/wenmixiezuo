# 文秘写作前端故事化界面优化方案

本文档针对当前合订版存在的“系统指令与故事创作界面混淆”问题，提出一套**不改变底层架构、只升级表现层**的优化方案。目标是让作者在创作台看到的不是数据配置单，而是有悬念、有情绪、有选择困境的**活故事蓝图**。

---

## 一、问题诊断与优化原则

### 1.1 核心矛盾
-   **底层（后端/数据库）** 已经清晰定义了事件、触发、代价、结束条件等字段，逻辑严谨。
-   **表现层（前端卡片/大纲展示）** 却直接把这些内部字段名和结构暴露给作者，导致界面像“AI工作流转单”，不像“故事设计工具”。

### 1.2 三大病灶
1.  **事件蓝图**：卡片直接显示“目标”“阻力”“选择与代价”等字段，像任务配置，无故事张力。
2.  **爽点模块**：分类选择器强化了“爽点配方”心理暗示，可能诱导机械拼凑。
3.  **大白话门禁**：只完成了术语过滤，但没有为故事摘要注入“悬念与情绪”。

### 1.3 优化原则
-   **表现层与逻辑层分离**：底层数据模型不变，前端展示完全重构为“故事叙述体”。
-   **用悬念代替陈述**：每个事件摘要以“困境”或“意外”开头，而非平铺直叙。
-   **保留作者控制权**：所有展示信息仍可编辑，但默认视图更直觉化。
-   **渐进增强**：先从事件卡片和事件链入手，再逐步优化大纲与章纲。

---

## 二、核心改造方案

### 2.1 事件卡片：从“配置表”升级为“故事预告片”
**现状**：卡片展示类似：
```
目标：取得内门资格
触发：主角被师兄羞辱
阻力：实力不足、无人信任
选择与代价：放弃自尊求人 or 冒死突破
```
**问题**：这更像任务简报，缺乏情绪的驱动。

**优化后设计**：
每张事件卡片改为**故事预告卡**，包含以下元素（自然语言，无字段名）：

| 元素 | 示例 | 说明 |
|------|------|------|
| **诱人标题** | `第3事件·带血的入场券` | 用悬念短语作标题，可由AI生成、作者修改 |
| **上一幕** | 主角刚刚突破炼气期，却被师兄当众羞辱，还被剥夺了外门资源。 | 简短总结上一事件结果，建立上下文 |
| **核心困境** | 他手里有反击的证据，但远远不够。要拉拢唯一的盟友，对方却要他证明自己的价值。 | 突出主角面临的两难或危机 |
| **要命的抉择** | 是想保住仅剩的自尊，还是赌上一切去换取一次翻身的机会？他身边的人也会因此承担风险。 | 强调选择与代价，制造悬念 |
| **这一幕的终点** | 主角用一个谁也想不到的方式暂时过关，但他和盟友的关系却因此变质，新的麻烦悄然找上门。 | 暗示结果，但留有神秘感，自然引出下一事件 |

**交互**：
-   作者可以一键切换“故事模式”与“大纲模式”（大纲模式保留原来的结构化字段，供有经验作者速览）。
-   所有文字都可点击编辑，AI仅提供初稿。

### 2.2 爽点模块：弱化标签，强化“叙事目标”
**现状**：一堆“身份揭晓、打脸、越级挑战”的勾选框。

**优化后**：改为**情绪节奏引导器**，不直接提“爽点”。

**交互设计**：
-   **主问题**：用醒目的提示语：“**这段剧情最想让读者感受到什么？**（可选）”
-   **轻量选项**（仅提供氛围方向，不强制）：
    -   😤 **扬眉吐气**（压抑后爆发）
    -   😱 **细思极恐**（揭开可怕真相）
    -   💔 **心碎时刻**（重要关系破裂）
    -   🤯 **惊天反转**（意料之外，情理之中）
    -   🧠 **智斗博弈**（逻辑与计谋取胜）
    -   ✨ **自定义一句话**（自由输入，如“让读者为主角捏一把汗”）
-   **底层映射**：每个氛围选项对应后端的多种爽点组合，但不在前端暴露具体标签。作者的自定义描述直接作为提示词传给AI编剧。

**优势**：
-   降低机械拼凑感，引导作者从情感体验出发。
-   依然可以用作AI生成的软约束，但不限制其创造性。

### 2.3 事件链：从“逻辑链表”升级为“故事心电图”
**现状**：横向卡片序列，箭头连接，显示简要目标和章数。

**优化后**：改为**故事动脉线**——一条带情绪起伏的时间轴。

**视觉元素**：
-   **横轴**：时间/章节推进，但用虚线箭头连接。
-   **纵轴**：**故事张力**（手动或AI辅助估算），以波形曲线呈现，让作者直观看到剧情节奏。
-   **节点卡片**（hover/点击展开）：
    -   默认显示标题 + 一句话钩子。
    -   展开后显示完整的预告片内容（上一幕、核心困境、抉择、终点）。
    -   节点之间用一个小箭头和“因为…所以…”样的微文案连接（如“因为这次的事得罪了长老，所以引来追杀”）。

**技术实现**：
-   底层仍为事件链数据，前端通过渲染器将每个事件对象转化为“动脉节点”。
-   情绪张力曲线初期可由AI基于事件大纲自动生成，作者可拖拽调整。

### 2.4 “大白话”门禁升级：注入叙事润色层
**现状**：过滤技术词，但摘要可能平淡。

**优化方案**：
在展示层与AI生成层之间，加入**叙事润色策略**：
1.  **摘要类文本**（事件大纲摘要、章纲梗概）要求AI使用**现在时、主动语态、设置悬念**。
    -   系统提示词示例：“用现在时描述，仿佛正在发生；结尾留一个‘但是…’或‘没想到…’。”
2.  **章纲详情**：在保留指导功能的同时，以“如果…那么…”或“当…时，却…”的句式增加情绪提示。
3.  **作者原话** 永远不受影响。

## 三、实施路径与兼容性

### 3.1 第一阶段：事件卡片重构
-   **前端**：新建 `StoryEventCard` 组件，实现故事/大纲双模式，默认故事模式。
-   **API**：无变化，继续用现有 `story_events` 表字段，由前端映射。
-   **数据**：新增一个 `event_blurb` 字段（AI生成的预告片文本）存储在事件版本中，供快速展示。

### 3.2 第二阶段：爽点模块软化
-   替换爽点选择器为情绪氛围引导器，后台映射表保留。
-   自定义描述字段存入 `author_planning_inputs`，作为事件级作者想法。

### 3.3 第三阶段：事件链可视升级
-   在“规划”页面增加 `StoryArtery` 视图（与现有时间轴并存，通过切换按钮）。
-   情绪张力曲线数据可存为事件扩展属性，初始由模型估算。

### 3.4 兼容性保障
-   所有优化都是**纯前端表现层改动**，不修改数据库 schema、迁移或后端领域逻辑。
-   现有“规划”页面的结构化字段仍可通过“大纲模式”完整访问，不丢失任何功能。
-   已经完成的测试和验收标准不受影响，新增交互需额外添加组件测试。

## 四、完整示例：事件3的前后对比

**现代表述（当前）**：
```
事件3：初露锋芒
范围：16-22章
目标：解决第一个小冲突，引起宗门关注
触发：获得能力后有了反击的底气
阻力：师兄的打压、同门的怀疑
结果：赢得小比，引起内门注意
下一事件：进入内门后结识新朋友，引来新对手
```
**故事化表述（优化后）**：
> **第3事件·第一次被人看见**
>
> *上一幕*：主角意外获得签到系统，第一次体会到了力量的味道。但这也引来了师兄变本加厉的打压。
>
> *核心困境*：所有人都等着看他出丑，他手里有了一副好牌，却不敢轻易亮出来。是继续藏着，还是抓住一次偶然的宗门小比，让所有人闭嘴？
>
> *他必须选择*：站出来就可能暴露自己的秘密，引来更大的觊觎；继续隐忍则永远只能任人宰割。这次，他决定不再跪着。
>
> *这一章的终点*：他以最不起眼的方式赢了，但那双注视他的眼睛，来自内门的一位长老。师兄的靠山，也开始注意到他。麻烦，才刚刚开始。

## 五、与其他优化建议的关联

本次优化同时解决了合订版审计中的下列问题：
-   **S01（事件卡片缺乏故事感）** → 由2.1节完整解决。
-   **S02（爽点模块硬配置）** → 由2.2节解决。
-   **S06（事件时间线过于技术化）** → 由2.3节解决。
-   **S07（大白话门禁需增强故事感）** → 由2.4节解决。

其他BUG（如B01登录流程描述不一致）属于文档修正，不在此界面方案范围内。

---

## 六、总结

本方案的核心思想是：**让作者感觉到自己是在设计故事，而不是在操作数据库**。通过故事化的事件预告片、情绪化叙事目标和故事动脉线，我们将底层严谨的数据结构转化为有温度、有张力的创作界面，彻底解决“感觉不好”的问题。开发上可平滑推进，风险低，收益高。
