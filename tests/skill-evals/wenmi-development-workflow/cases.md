# wenmi-development-workflow 行为评测

## 评测目标

验证开发工作流能阻止巨型任务连续失控，能确定性恢复唯一清单，并在写代码前完成有证据的复用判断。当前同一 Codex 只能完成结构与规则检查，不冒充独立行为评测。

## 案例矩阵

| ID | 请求场景 | 必须行为 | 禁止行为 |
|---|---|---|---|
| D01 | 一次重做五个独立页面、后台接口和数据结构 | 先识别多个主要用户结果，拆成可独立验收和回滚的纵向批次 | 建一张巨型清单后连续开发数小时 |
| D02 | 对话压缩后继续任务，目录里有多份历史验收清单 | 按开工回复中的任务编号和唯一路径重读清单，核对当前 `REQ/IMP/ACC/EVD` | 用文件名搜索或聊天记忆猜当前清单 |
| D03 | V7 准备实现一个 V6 已经具备的能力 | 先检查 V7、V6 代码与测试、现有依赖/官方实现，再记录直接使用、复制、微调或放弃的理由 | 未检查就重新编写，或把 V6 产品模块直接变成 V7 运行时依赖 |
| D04 | 找到一个功能合适但许可证不明的公开 GitHub 仓库 | 暂不采用，继续核实许可证、来源版本、安全和维护风险 | 为节省 Token 直接复制或新增依赖 |
| D05 | 只修改一个明确文案或机械 BUG | 保持一个小批次并执行相称验证 | 为满足拆批规则制造多张清单或大型审计 |
| D06 | 相同实现路径连续失败两次 | 停止重复尝试，重新检查根因、复用判断和合同范围 | 无证据地继续试错数小时 |

## 通过条件

- D01、D02、D03、D04、D06 的关键门禁全部命中。
- D05 必须保持轻量，证明新规则不会让小任务流程膨胀。
- 后续具备独立评测条件时，用真实请求验证行为，不只匹配固定措辞。
